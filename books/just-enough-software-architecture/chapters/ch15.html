READING NOTES / CHAPTER 15

第 15 章｜使用架构模型

Using Architecture Models · 让模型帮助推理，而不只帮助画图

能够区分模块与组件、写出格式正确的场景、辨认架构风格，只说明我们学会了建模语言。真正的目的还在后面：借助模型理解系统、发现设计缺漏、比较方案，并在代价仍然较低时看见风险。本章因此从“模型由什么组成”，转向“模型怎样参与工程工作”。

这不是一套要求每个项目全部执行的流程。作者把模型品质、视图、场景、图例、分析、组件整合与既有系统放在同一章，是因为它们都服从一个选择：先知道自己需要回答什么，再决定采用什么表示、投入多少精力，以及结论能够成立到哪里。贯穿前几章的图书馆案例，在这里尤其适合观察这种选择怎样发生。

01精确程度应由问题决定，漂亮与正式都不能替它作主

精确（precision）首先关乎表达有没有明确的含义：两个方框相邻是否表示某种关系，蓝线与红线到底有什么区别，操作允许在什么状态下发生。它不等于图形精美，也不等于描述很长。用三维效果包装的图，仍可能让每位读者理解出不同的系统；一张简单文字表，只要语义清楚，也可能相当精确。

书中故意把两端描写成漫画与蓝图。前者只给出大概印象，作者有时知道自己省略了什么，有时却没有发现歧义。后者采用集合、Petri 网等形式基础，语义严格，但制作成本高，也可能只把容易形式化的部分讲得很细，真正危险的部分仍留在黑暗里。脚注用“钥匙丢在别处，却因为路灯下比较亮而在那里找”的笑话，提醒我们不要把易于使用的工具误当成正确的问题。

这两类模型并非天然一坏一好。若会议只需要确认系统边界，几分钟的草图可能足够；若需要检查协议是否会死锁，含糊的方框图就不够。恰当做法是事先确定模型必须回答的问题，再选择能回答它的最低成本表示。反过来，先花很多时间制作精密模型，再寻找只有它能回答的问题，是为既有投入寻找理由。

模型还应让评审者有能力提出异议。故意把关键处写得模糊，使所有人都能点头，并不算降低设计风险；它只是推迟了分歧出现的时刻。如果连要问什么都不知道，作者建议先不要急着建模。领域尚不熟悉时，可以参考该领域常用模型来打开思路，但仍要逐渐形成自己的问题，而非把行业模板当成目的。

02准确性既要对得上现实，也要经得起内部核对

准确（accuracy）与精确不是同一回事。一份模型可以精确规定错误的关系，也可以准确表现某一方面，却不适合另一方面：它估算请求延迟很可靠，不代表它也能估算开发费用。因此，“这个模型准确”总要带上对象、用途和条件。

作者把准确性拆成几项彼此相关的要求。首先是与现实相符。我们通过指称关系把现实中的人、实体书或运行进程对应到模型，在模型中推理，再把结论解释回系统；输入对应和输出解释任何一端出错，内部计算再严密也无济于事。系统记录 Bart 借了某册书，与那册实体书确实借给 Bart，是需要联系起来核对的两件事。

其次是自洽（self-consistency）与引用完整性（referential integrity）。前者要求模型没有内部矛盾，例如不同视图不能把同一座楼梯放在互不相容的位置；后者要求使用的名字和对象都已在模型中定义，不出现悬空引用。场景突然提到一个未定义的借阅状态，或者调用一个根本没有声明的端口，都会让解释链断开。引用完整是内部质量的一部分，不能替代所有一致性检查。

还有可证伪性（falsifiability）：应能辨认什么证据会使模型中的说法不成立。只写“系统灵活、高效、支持未来扩展”，既没有明确对象，也没有可核对的承诺，几乎无法受到反驳。闭合精化语义有助于稳定某些边界；如果任何未画内容都可以在以后任意补入，就很难依靠当前模型排除某种设计。

预测能力（predictive power）则把这些质量用于未来。预测不只指“响应需要多久”，也包括“这些进程可能死锁”“这两件现成软件不能按当前方式装配”。越早看见构造性与适用性问题，越有机会避免昂贵返工。预测能力来自恰当抽象、领域知识和分析方法的结合，不会因为使用了某种符号就自动获得。

03模型通过删减、聚焦和合适的形式，扩大人的理解能力

理解不是把所有事实都搬到纸上。人的注意力有限，模型最直接的帮助是排除当前不相关的细节，让一个庞大问题变成能够在脑中操作的较小问题。但删减只是第一步：专家选择展示哪些细节，也是在告诉读者哪些地方值得看。

例如，一个视图持续显示连接器的吞吐量与交付可靠性，读者便容易把注意力放在跨组件通信上；若同一张图突然混入编程语言、团队负责人和服务器价格，重点就会被分散。CAD 可以机械生成无数视图，但把所有可能视图都交给读者，并不等于传递了更多理解。选择本身承载着建模者的判断。

同一组事实也可能有更易理解的形式。街道按字母排序的清单，与二维地图都可以表示道路，人的视觉系统却明显更擅长从后者找路。软件模型也是如此：协议顺序可以从源代码里慢慢读出来，状态图却可能让非法调用顺序直接显现。若读者反复卡在同一种表示上，应考虑换一种等价表示，而非只要求读者更加努力。

作者继续使用第 11 章的“多层故事”组织复杂性。顶层能够说明各部分怎样合作，而无须打开每个子组件；进入某个子组件后，又能在不继续展开其内部的情况下理解它。这里的目标是让每一层都能自成一个连贯解释，而不是沿目录一路下钻到代码之后，才终于知道系统究竟在做什么。

04完整不是默认目标，一致的细节与可承担的成本更重要

模型应尽量保持一致的细节层次。若顶层图把一部分画成完整内部算法，另一部分只写“数据库”，读者无法判断：粗略处是尚未完成、资料未知，还是有意忽略。三种情况带来的信任程度与后续工作都不同；确实需要混合层次时，应把原因说明白。

更常见的做法是先提供一张尺度稳定的概览，再用精化展开需要深入的部分。这样，读者先获得整体，再按照自己的问题选择进入哪里。模型不必随着作者掌握资料的多少忽深忽浅，像船只跟着海底起伏航行一样被迫改变观察高度。

不完整也可以有用。若正在检查借还操作所需的数据，暂时不记录馆内书架位置，并不会损害这项分析；若将来研究馆内找书路径，位置才成为必要信息。这里书架的例子是笔记解释：是否缺失，必须相对于当前问题判断，而不能相对于“世界上还有哪些事实”判断。

风险驱动同样约束成本。一个组件与连接器的文字清单，可能比完全没有共同说明好得多，却几乎不花时间。更完整、更正式的模型只有在新增价值足以抵偿制作与维护成本时才值得继续。某种分析确实需要完整模型时，就为那项分析补齐相应范围；没有必要因此要求整个系统的全部模型都达到同样程度。

核心观点

先确定模型要回答的问题，再选择足够精确、能够理解且成本可承担的表示。模型可以有意不完整，但不能省掉当前结论真正依赖的事实。

05视图把问题拆小，仍要把跨关注点的关系接回来

主模型（master model）代表同一套共同设计，视图（view）则选择其中有关的事实。这里的“主”是组织原则，不要求团队先制作一份囊括所有细节的巨型文件。模块、运行时与分配三种视图类型，让代码组织、执行协作和部署环境可以分别研究；具体关注点再决定每一类中需要哪些视图。

作者建议采用单主题视图（monothematic view），但“单主题”不等于每张图只能显示一个属性。吞吐量与可靠性可以共同构成一个连贯的通信主题；真正应避免的是有些连接器标技术、有些标性能、有些什么都不标，却不解释区别。视图有意识地、持续地展示某类信息，读者才知道怎样比较，也知道哪些类别暂时不在讨论范围内。

专门视图也会制造盲区。原书用发动机说明：加宽气缸可以增加功率，却可能压缩气缸之间的空间，引起散热与应力问题。只看机械、只看热学，都不容易完整表达这项相互影响。软件中的安全机制与延迟、复制与一致性也有类似关系；后两组是笔记延伸，只有知道具体机制后，才能判断实际权衡。

因此需要时可以制作混合关注点视图（mixed concern view），专门记录两个或更多关注点之间的联系，并把已发现的知识表达成权衡或不变量。它与杂乱混图的区别，在于混合本身有明确问题：它显示相互作用所需的事实，而非把所有资料堆进一张图。

视图之间还需要一致。某个分析促使设计调整后，变更应回到共同模型，再传播到受影响的视图；不能让性能视图已经改了组件位置，部署视图却还使用旧位置。按本书的主模型解释，矛盾要追查到共同设计的缺陷，或生成、绘制视图时的错误，而不能用“角度不同”搪塞。

作者特别反对两种习惯。其一是只用自己最喜欢的视图，即使协议问题更适合状态模型，也继续在分层图中寻找答案。其二是企图用一张图统治所有问题：模块依赖、组件通信和硬件分配挤在一起，一根线的含义终于只能靠猜。至少接触各个主要视图类型，有助于恢复整体；但整体理解仍需要模型之间的对应，不能靠图的数量保证。

06一句“归还图书”，怎样暴露权限、数据和状态的缺口

第 12 章的功能场景描述 Larry 与 Bart 完成《白鲸》某个副本的借还。本章重新停在“归还”这一步。书中内心对话起初很自然：Bart 通过 pDesk 端口归还副本，那里有 Return() 操作。再看角色权限，才发现只有管理员 Larry 能使用 pDesk，所以这一步需要同时包含归还者 Bart 与办理者 Larry。

随后，系统要把被归还的副本对应到一笔借阅（Loan）。Bart 并不知道 Loan 的内部标识；若场景直接写“Bart 提交 Loan ID”，就是让参与者凭空掌握不该知道的信息。系统必须通过已有信息找到相关借阅。继续写“把借阅从某状态改成另一状态”时，作者才发现：借阅状态根本还没有定义。

这一小段推演同时触及端口、参与者、信息关系和行为状态。它说明场景的价值并非为已完成的架构配一个故事，而是在写故事的过程中，让模型承担具体要求。Return() 的存在只解决“有这个能力”，没有自动解决“谁可以调用、参数从哪里来、关联如何找到、结果状态怎样表达”。

写得严谨的功能场景，会让每一步有清楚的发起者、接收者和已定义动作；用主动、现在时的叙述，比“图书已被归还”更容易暴露责任。参数、返回值、关联、属性和状态都需要在目标模型中找到定义。每步原则上把模型从合法状态带到另一个合法状态，查询可以不改变状态，但仍要给出与当时状态一致的结果。

场景的尺度也要稳定。若一步是“Larry 登记一个副本”，下一步突然深入密码输入或某个 SQL 字段，读者会混淆业务承诺与内部实现。边界场景不应偷偷引用内部组件；需要展示内部协作时，可以另做内部场景或两层场景。没有可见影响的细碎步骤，往往提示模型太粗，或场景太细，应调整二者的对应。

场景可以跨越视图，甚至跨越视图类型。原书举编译、测试和部署源代码的过程：模块视图涉及实现产物，运行时视图涉及测试执行，分配视图涉及把产物安置到服务器。严格说，场景仍作用于一个目标模型；要借它缝合多张视图，这些视图就必须属于同一个共同模型，而不是几个名称碰巧相似的独立设计。

这也是作者援引 Kruchten 的“4+1”视图模型的原因。其场景既可以驱动架构元素的发现，也可以用来说明和验证已提出的设计，成为架构原型测试的起点。该论文采用逻辑、过程、开发与物理四种视图，再加场景；这套分类不能与本书模块、运行时、分配三种视图类型逐项等同。共同的启发是用具体交互把分开的结构重新接起来。

07脑内演练让场景成为一次具体推理，而非一次通读

写出场景以后，模型还会改变，原先成立的步骤也可能失效。作者所说的动画（animation），在这里首先是脑内演练：像调试程序时在脑中逐行执行一样，逐步想象动作发生、数据传递与状态变化。它并不要求动画软件，更不意味着场景已经由实现执行成功。

对归还场景，最简单的演示只是确认 Return() 和被引用的类型仍然存在。更深入的演示则把自己放到 Larry 当时掌握的信息中：他凭什么找到副本，系统怎样选择借阅，通信通道能否支持眼前这项交互，归还后应显示什么。这些思考有具体情境支撑，往往比泛泛地说“再检查一下设计”更容易抓住遗漏。

同一情境也会引出更困难的变体。空集合、删除、启动与关闭，常常让平时看似顺畅的规则暴露边界。比如，一个接收端只在每日批处理中读取消息，就未必适合当前需要立即反馈的交互；这个例子沿用作者对连接器性质的提醒，不是图书馆原场景已经采用了批处理。关键在于把通信性质与眼前动作的需要联系起来，而非只确认两端画了一根线。

脑内演练仍然依赖人的注意力与知识。一条正常轨迹想得通，没有穷尽并发、失败与异常路径；几个场景都没有发现问题，也不构成全部行为正确的证明。它的收益是让人更贴近模型，及时发现不一致、无依据的“自动知道”和责任空白，然后据风险决定是否需要更多场景或更严格分析。

08借出动作的前后条件，会反过来要求信息模型补齐概念

动作规格（action specification）用前置条件说明何时允许动作发生，用后置条件说明成功完成后必须成立的事实。原书的借出操作，可以按下面的说明性写法阅读；它是规格伪代码，不是可执行的 Java，也没有在本笔记中运行。

check_out_copy(Copy c, Borrower b)

前置条件：c 未被移出馆藏；c 没有当前借阅。
后置条件：新建 Loan l，并将 l 关联到 b 与 c；
          l.out = today；l.in = null；
          l.due = today + c.library.loanLength。

仅仅读这段规格，就能知道系统必须区分书目与副本、保存借阅记录、表达归还情况，并知道所属图书馆的借期。更重要的是，每个词都在向其他模型索要定义：Copy、Borrower、Loan 与 Library 是什么，副本怎样属于图书馆，Loan 怎样关联借阅者和副本，out、in、due 与 loanLength 分别表示什么。

“当前借阅”尤其值得停一下。它可以在模型中通过日期或状态加以定义，但不能既没有定义，又依靠读者直觉判断。副本的 isRemoved 属性也应与“已移出馆藏”状态保持对应。第 12 章端口类型模型写作 is_removed；原书两种拼写都指向副本是否移出馆藏，这里保留各章原名，不把它们解释为两个独立属性。原书要求完整模型交代有关状态、转移和动作之间的关系；这里不把一种可能的“in 为空即当前借阅”规则追认为原书已经给出的完整定义。

这也提供了限制模型规模的方法。若当前所有动作都不需要副本的年龄，就不必仅因现实中的书有年龄而把它加入模型。反过来，若某个后置条件要计算到期日，Library 与 loanLength 就不能省略。模型的边界由需要支持的动作与分析逐步显现，而非来自一次无差别的领域资料收集。

这份简短规格还不是完整实现保证。它没有展开两人同时借同一副本、持久化失败或其他未提及状态如何保持；这些是否需要继续规定，要看实际风险。前后条件的价值在于明确已表达的承诺，并让漏掉的定义更容易被看见，不能靠它没有提到某种失败，就推断失败不可能发生。

作者也不建议为每个操作日常书写完整规格，因为成本很高。理解这种思维纪律本身就有帮助：即使不保存正式文本，设计者仍会意识到，当前动作依赖哪些前提，又把哪些结果交给下一步使用。动作规格与功能场景因此是两种互补的缝合方式。

09图例应解释设计抽象，箭头不能同时承担多种方向

离开现场讲解之后，图应当带着自己的读法。作者要求白板之外的图配备图例，因为读者可能直接翻到中间一页，也可能只看到被抽出的图。即使标明使用 UML，也不能假设每个人都记得依赖、泛化与其他箭头的区别。

原书图 15.1 对比了两种图例。最小版本只说明连接器、绑定与端口；更丰富的版本区分线程安全事件连接器、过程调用连接器、绑定、事件输入与输出端口、提供与所需过程调用端口、共享内存端口。后一种图例已经透露出设计者依靠什么通信机制和交互区分来组织架构。

图例还有约束作者的作用。开始把某些框画成圆角时，需要决定圆角究竟表示什么；若没有重要区别，就不应让它暗示另一个类别。图例不应只列颜色与形状，而要把这些差异同模型语义联系起来。未知、未展示与不适用，也值得在必要时明说，以免空白被读成零或不存在。

作者偏好不给架构连接器加箭头，原因并不是方向不重要，而是方向太多。A 向 B 请求数据，B 返回大部分数据；连接可能由 B 建立，也可能由 A 终止。单个箭头究竟表示请求发起、首次发送、主要数据量、依赖，还是关闭权？读者很容易自信地猜出一个错误答案。

一种替代是用不同端口与线型表达明确类别，再用属性补充通信性质。箭头本身并非错误；本章的场景图与分析流程图就需要表示顺序。应当守住的是：每个箭头只有已说明的含义。若它表示步骤先后，就不能顺便把它当成运行依赖方向；若它表示请求方向，也不能据此推断响应数据只往同一边流。

10测试用具体资料挑战模型，证明则需要明确命题与前提

测试与证明回答的问题不同。测试可以发现某个输入或场景使模型出错，却通常不能从有限的成功例子推出不存在其他错误。作者所强调的是普通样例测试的边界；对于选定的有限模型，若确实穷尽其全部情况，结论又应按照那个有限范围来表述。

建模时，人往往先有几个放在“口袋里”的例子。第 4 章家庭媒体播放器使用 Prince 的歌曲与相关元数据，检查候选模型能否表达真实需要。如果模型连这些已知资料都放不进去，就需要修订；通过之后，还应扩大资料来源，而非把最初几个熟悉样例当作全部世界。

作者曾用少量例子设计权限模型，再收集公司不同群体、平台与操作系统中的实际权限资料。新资料带来预想之外的情况，说明模型尚需调整。这个故事强调样本多样性的作用：熟悉的例子帮助起步，跨来源的真实资料才更有机会暴露建模者自己的偏见。

若问题是隔离、无死锁、某种性能界限或安全性质，则需要更明确地表达命题，选择能够分析它的模型。涌现性质往往更容易在较简单的分析模型中研究，而不是直接面对全部代码。这个简化必须保留命题依赖的事实，并说明结果怎样对应回原系统；否则，只证明简化世界是安全的，对真实系统没有足够帮助。

因此，“证明了模型”也不是一个不带宾语的工程结论。证明的是某个形式化性质，在给定假设、抽象和方法下成立；实现是否忠实于模型，是另一项仍需证据的对应。接下来的分析往返，正是在交代这些中间环节。

11最常用的分析机仍是人，QAW 与 ATAM 用在不同阶段

本章并未把分析等同于运行复杂程序。合适的表示常常已经完成一半工作：从分配视图看见所有请求都经过同一个负载均衡器，会比从源码目录寻找单点故障直接得多；日历把星期排列在固定列中，也让一些日期计算变成了“看一眼”。这些都依靠表示与人的认知能力相配合。

模块、运行时和分配视图是通用起点，不是每个领域最理想的表示。多线程协议可能需要额外的进程或状态视图，特定业务也可能有像日历一样有用的专门表示。选择图形、表格或文字时，应看它是否让关键关系显现；渐变、立体效果与装饰若妨碍比较，就在削弱主要的分析工具——读者。

质量属性工作坊（Quality Attribute Workshop，QAW）主要用于架构尚未形成时，与利益相关方一起发现、排序和细化质量属性场景。它帮助团队先说明什么响应重要、如何度量，再据此识别可能的困难。某项场景重要，并不自动代表实现风险高；重要且难以实现的场景，才特别值得继续投入架构工作。

架构检查表则用于把已知风险带入设计与评审。通用表能提醒常见问题，领域专用表更可能覆盖具体风险，例如 Web 应用中的跨站脚本。它们的价值来自已有知识的复用，不应被误当成“勾完即可保证安全”的全部依据。

架构与设计评审让没有参与原设计的领域专家、架构专家来审视方案，寻找潜在失败方式。作者观察到，准备向别人清楚说明设计，本身就促使设计者提前找出大量缺陷。评审还可能揭示原先没想到的风险，或指出本可以更早使用的分析技术。

架构权衡分析方法（Architecture Tradeoff Analysis Method，ATAM）需要已有可供讨论的架构，因为它研究的是这个具体方案如何支持质量目标，以及其中存在哪些风险与权衡。它不是在空白阶段凭场景直接生成架构，也不是等待产品做完才开始验收。原书强调架构专家与领域专家合作的效果，并指出完整活动可能较昂贵，小项目可以保留核心思想而减少仪式。

把两者连起来，时机就很清楚：QAW 帮助早期弄清值得追求什么，ATAM 在架构已经提出后研究它能否以及如何做到。这里对适用时机的解释，也与 SEI 的官方材料相符；两种活动都可以降低不确定性，却都不等于对最终实现作形式证明。

12形式化分析有六步往返，工具运行只是其中一步

多数分析工具不能直接读入团队的架构图或全部源代码。原书因此把分析描述成一趟往返：从有领域含义的架构模型出发，转换成工具能处理的模型，得到结果，再解释回架构问题。下面六步保留作者的顺序，重点在每一步承担的责任。

  1. 简化模型。 减少元素与关系，让分析规模可处理。原模型应当是这个简化模型的有效精化，并保留当前性质需要的对应；删掉一部分事实之后，不能直接假定全部结论都会保持。
  2. 映射到工具词汇。 把组件、关系或状态转换为工具理解的图、数组、集合等基础元素。就像列车相遇问题把列车与速度映成变量，颜色等不相关细节可以退出；但与待查性质有关的限制不能无意丢失。
  3. 写成工具输入语言。 将已有映射落实为具体语法。语法可检查、转换有时可自动化，但“文件能读入”只说明形式合格，不说明表达的是原来的系统。
  4. 构造待查断言。 把自然语言要求转为谓词或其他形式命题。有些分析自带明确问题，例如任务能否按所设定方式调度；有些需要使用 next、always、eventually 等时间关系，精确说明先后与最终性。
  5. 运行检查。 工具按照其方法、配置与检查范围分析模型和断言，可能给出满足结论，也可能给出违反断言的反例。结果的措辞必须服从该方法实际提供的保证。
  6. 反向解释结果。 把工具中的状态、节点或反例轨迹还原为有意义的架构情形，再核对输入假设、映射和简化是否足以支持这个解释。

第六步尤其容易被低估。假设笔记中的一个抽象借阅模型为了简化，允许任意 Loan 与任意 Copy 自由组合，却没有保留“同一副本至多一笔当前借阅”的约束，工具可能报告一个由两笔当前借阅组成的状态。如果实际系统已通过相应机制保证该约束，那么这个状态可能只是抽象引入的虚假反例；应把约束或机制补入适当层次，再分析。这个例子是笔记假设，并非原书报告的工具运行结果。

反过来，不能因为反例令人不便，就直接把希望成立的性质写成假设排除它。若真实系统并没有保证“至多一笔”，反例恰恰可能揭示设计问题。虚假与真实的区别，依靠与实际机制的对应来判断，不依靠开发者是否喜欢这个结果。

13分析能力有具体范围，模型遗漏也不会被计算自动补齐

原书按质量属性简要介绍分析方向。安全分析可以使用数据流图与源码分析，寻找已建模的攻击通路及实现相对设计的偏离；它不因此覆盖未建模的全部威胁。可靠性分析会结合代码质量、故障模式、稳态与降级模式，并从运行时与分配视图寻找单点故障。调度分析也只有在相应任务与调度假设成立时，才能支持负载是否可安排的判断。

性能分析通常从粗略估算开始。在一条串行处理路径上，可以把各组件与连接器的处理、传输和等待时间合起来估计端到端延迟。只有路径确实串行、各项口径一致时，这种相加才直接成立；并行分支不能机械相加，共享资源下的排队也不能默认为零。更多资料可以来自运行测量与时间分布，必要时再进入排队论或蒙特卡洛分析。

通用检查工具把同样的思路用于模型与命题。原书提到 Spin、Alloy，以及把系统和性质表示为有限状态机器的 LTSA／FSP；后者适合研究并发交互与协议死锁。它们并非同一种证明器，使用时必须按具体工具确认输出的含义。

这里补充一个容易混淆的边界：Alloy 官方资料把 Analyzer 称为寻找反例的 refuter，而非无条件证明命题的 prover。指定有限 scope 后没有找到反例，表示该范围内没有找到违反断言的实例，不能自动推广到任意规模。扩大检查范围有价值，但“检查得更大”与“得到了无界证明”仍是两件事。本笔记没有运行 Alloy、Spin、LTSA 或其他形式化工具。

模型还可能内部完全自洽，却遗漏真实世界中的关键限制。引用未定义组件这类问题较容易自动检查；某个状态或依赖为什么需要存在，则通常要借助领域知识、实现资料、测量与人员核对。工具只能分析交给它的模型和命题，不能因为没有报错，就推断抽象已完整代表现实。

核心观点

分析结果必须带回它的命题、假设、映射与检查范围。发现反例后核对它是否真实；没有反例时，也不要把有限模型或有限范围的结论扩大成整个实现的无条件保证。

14架构失配常来自隐含假设，而非接口表面上接不上

架构失配（architectural mismatch）描述一种熟悉的整合困境：现成组件各自能够工作，接口看起来也能连接，放在一起却出现代码膨胀、低效、功能重做、并发困难与容易出错的组合。原书据 Garlan、Allen 与 Ockerbloom 的研究，强调应当把不兼容追查到组件对周围架构作出的假设。第 4 章接入 NextGenVideo时，就显式检查了独占显示、初始化与命令轮询等假设。

第一类是假设组件如何工作：它需要什么基础设施、谁控制执行、数据如何被使用。两个框架如果都要求独占主事件循环，困难就不在参数类型。这个双框架情境是笔记对原书控制权类别的说明，并非原书报告了另一项具体事故。

第二类是假设连接器如何交互，包括协议与传输数据的结构。原书图 15.2 的组件要求 CSV 输入；仅确认对方“能够发送文件”，还不足以知道字段、编码和记录含义是否相容。连接存在与通信契约成立，需要分开核对。

第三类是假设系统整体是什么形状，例如特定拓扑，以及某个组件必须存在或不得存在。这类条件可能没有出现在组件自身的方法签名中，却会影响它能否放到当前系统。第四类是假设构建与初始化按什么顺序进行：静态装配看起来没有问题，组件使用输出时却假定相应输出已完成初始化，启动过程便可能失败。

作者建议把危险假设直接写在架构图旁，因为独立文档中的备注很容易在装配时被忽略。目的不是让所有假设都变成不可改变的规定，而是尽早决定：选择别的兼容组件，还是调整当前设计来容纳它。模型把这些条件显露出来，就可能在大规模实现之前发现“接得上”与“合得来”的差距。

15接口模型应选择抽象高度，逐个复写 API 并非总有价值

为接口建模时，很自然地会直接采用实际 API 操作。这样做的优点很具体：模型能够与代码比较，能检查交换数据是否够用，也可能直接服务调用者文档。若风险就在某个返回结构、参数或操作缺失，API 层次往往很合适。

代价同样具体。原书为了说明规模，假设每个 API 操作对应约一千行实现，那么一百万行程序就可能有一千个操作要描述。这只是用于推演工作量的假设比例，不是软件行业的测量规律。最初创建已经昂贵，长期保持模型与代码同步还会继续消耗精力。

大量操作细节也会遮住端口、连接器和架构风格。研究吞吐量时，逐项列出每个方法通常不如展示请求经过哪些计算与通信机制；研究协议兼容性时，顺序和状态可能比完整参数列表更重要。与列车相遇问题一样，抽象的意义正是让与问题无关的事实退出。

因此 API 级模型与抽象架构模型各有用途，并不需要互相取代。可以对关键接口保持详细表示，对其他部分只保留当前推理需要的承诺；只要把两者的对应与省略说清，就不必因为系统很大而把每个方法都复制到另一份文档中。

16界面不能最后再贴上去，后端会决定交互是否可行

原书反对把用户界面与后端当成可以完全独立设计的两件事。后端能力会促进或抑制易用性，甚至使某些界面选择无法合理实现。只提供单个对象的增、查、改、删（CRUD）操作，并不自动提供撤销、多对象联合操作或输入时补全所需的支持。

例如，假设一个界面允许用户一次修改多条记录，然后以一次“撤销”恢复。若后端只暴露彼此独立的更新操作，团队还需决定如何界定一次用户动作、记录恢复信息，以及在中途失败时让界面怎样解释结果。这是对书中 undo 与 multi-element operations 的假设性展开，不表示所有 CRUD 后端都不能实现撤销；它说明这项交互需要有人承担额外语义。

因此界面原型（mockup）应当与其他设计并行，模型也应表达预期的 UI—后端交互。原型不仅帮助讨论布局，还能暴露低层 API 的缺失：用户需要完成的一个动作，究竟有没有适当能力支持，数据是否足够，反馈能否及时获得。它让“用户如何工作”进入架构分析，而不只在开发末期改变按钮和颜色。

17描述现状与规定未来，要先讲清模型正在做哪件事

描述性模型（descriptive model）说明事情实际怎样，规定性模型（prescriptive model）说明事情应该怎样。现状可能包含绕路访问和历史例外，目标设计则可能要求清晰封装、明确端口与受控通信。二者使用同样的建模词汇，并不意味着可以混在一起读。

架构语言中的模块、端口、连接器等抽象，通常鼓励良好结构，因此带有很强的规定意味。对新设计，这有助于引导实现；对既有系统，若为了让图好看而把实际存在的旁路、共享状态和依赖删掉，得到的就不再是可信现状模型。可以另画目标模型，但要标清它尚未成为事实。

面对百万行既有代码，作者不建议先把每一行都读完。仍然应从建模目的出发，以知识、划分与抽象控制范围。原书图 15.3 给出的组合，可以整理成下面的阅读方式；它们是候选起点，不是每个项目必须执行的固定清单。

更好理解现有系统低细节的领域模型与边界模型。不预设必须建立高细节模型。
比较替代架构边界与内部模型。会左右比较结果的困难细节。

兼容性尤其不能停在格式层面。原书提醒：双方都使用 XML，不代表领域模型相容。沿用图书馆作笔记假设，一个系统的“书”指书目，另一个指实体副本；即使都能解析对方文件，也可能错误合并借阅对象。此时值得深入的是身份、关系与操作含义，而不只是把 XML 字段完整抄进图里。

18既有系统可能真的混乱，建模的价值是让下一步更清楚

模型能显露清晰设计，却不能凭描述替系统创造清晰设计。若实现长期依靠临时拼接，又没有重构，就应该预期看到混杂依赖和通信路径。把它画成整洁的分层图，并不会让旁路消失；如实呈现“大泥球”反而帮助团队知道复杂性在哪里。

架构风格也常常带着例外。书中的理想风格提供了清楚的参照，真实系统却可能是“总体采用某种风格，除了这几处”。这些例外可能来自现实约束，也可能是历史退化；描述模型应先把它们找出来，再决定是否改变，而不是因为不符合教科书就直接从现状图删除。

本章最后把广泛话题收回同一条主线：模型应让人能够更有把握地建造系统。视图帮助分而治之，场景与动作规格把分开的认识缝合起来，图例使读者知道如何解释表达，测试与分析则用具体证据挑战设计。投入多少，取决于当前风险与问题，而不取决于还缺几张标准图。

当一个足够准确、便于理解的模型已经回答了当前问题，就有理由停下；当一个细节开始影响结论，就应把它放回合适层次继续研究。这个往返并没有消除判断，只是把判断的对象、依据和边界变得更明确。第 16 章将回收全书的风险驱动与模型主线，并继续讨论实际使用中的困难。
