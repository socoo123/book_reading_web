READING NOTES / CHAPTER 04

第 4 章｜案例：家庭媒体播放器

Example: Home Media Player · 让风险真正改变设计工作的顺序

“重视风险”很容易成为一句正确却不影响行动的话：团队仍然照惯例画同样的图、写同样的文档，最后再补上一页风险清单。本章把上一章的三个动作放进一个连续案例：识别并排序风险—选择并应用技术—评估风险降低。每一轮都要能解释，为什么此时需要这项工作，以及做完之后，究竟多知道了什么。

家庭媒体播放器（Home Media Player）已经有了可运行的原型。团队接下来不是从头设计一套完美系统，而是依次应对远程新成员加入、第三方播放组件接入，以及音乐元数据模型过于简单这三件事。相同的风险驱动方法，在三处选出了不同的技术，也给出了不同强度的证据。

01从一个能播放的原型开始

书中的家庭媒体播放器是一台连接电视、可选连接音响的普通计算机，只有一组音视频输出。它能够播放本地硬盘或互联网上的多种媒体格式，也支持一边播放音乐、一边放映照片，或一边看视频、一边浏览相关信息。第三方可以编写扩展，增加媒体来源，或取得歌词、演员传记等元数据。它不是今天某个流媒体产品的实现说明。

这个例子受作者对真实系统的代码检查启发，但章节采用的是经过组织的团队情境：我们已经一起做出了原型，现在逐步接到新的任务。播放流畅、低延迟和故障隔离，让它带有系统软件问题的特点；歌曲、艺人和专辑之间的复杂关系，又让它带有信息系统问题的特点。因此，作者能够用同一个系统展示不同风险需要不同分析办法。

最初，开发者在同一地点密切合作，设计决定保存在共同记忆中。原型成功后，公司准备在当年推出产品，并加入一批异地开发者。第一项担心是：新同事不了解领域和设计，迟迟不能独立贡献，甚至无意中破坏原有架构。后来，团队被要求支持多个平台，并接入两个现成组件；第二项担心转为组件能否匹配、能否在故障时保住整个系统。第三项担心则来自插件：即使已经提供 API，内部的歌曲模型会不会简单到无法表达网站上的知识？

这里的顺序很重要。第一轮主要把已有设计说明白；第二轮改变设计并运行原型；第三轮则比较概念模型。没有哪一种技术因为“上一轮有效”，就自动成为下一轮的答案。

为了集中展示设计，原书假定需求已经理解清楚，团队与项目资助者对质量属性的优先级也一致，不讨论需求获取、角色分工或组织争议。这些是案例的简化条件，不是实际项目可以省略这些工作的依据。

02新同事需要的，是能够组织细节的骨架

第一轮最便宜的选择，是让新同事直接阅读已有代码。原型还不大，代码又现成存在，老成员似乎不必额外花时间。但代码的存在，只说明有人能够开始读，并没有说明每个人都能高效重建相同的系统认识。

原书图 4.1 给出目录树：application、gui、media_player、util，以及 external_libraries 下的音频和视频编解码器、播放器、遥控器库。这些名字能够提供线索，却不能证明一个目录就是一个模块，更不能表达模块依赖。原书随后画出的图 4.2，才明确列出 Remote Control、User Interface、Application Logic、Video Player、Audio Player 与平台 API 模块之间的关系。两张图并不一一对应。

读模块图时，应先把箭头理解为依赖：被依赖部分的变化，可能影响依赖它的部分。遥控器模块依赖用户界面，用户界面依赖应用逻辑，应用逻辑依赖音频和视频播放器；播放器与用户界面还依赖 VDPAU／ALSA 这一组平台 API。VDPAU 与视频解码、呈现有关，ALSA 与音频有关；编解码器（codec）则负责媒体编码与解码。它们在此主要说明原型已经与特定平台技术发生关系。

模块名称让人能够猜出一次播放的大致经过：遥控器命令进入界面，由应用逻辑选择歌曲，再让播放器解码并输出。但依赖箭头本身没有声明这段运行顺序，也没有说明消息、线程或进程怎样工作。把模块图上的一条依赖线直接读成“一次运行时调用”，就会把结构提供的线索误当成已说明的行为。

代码还遗漏了另一类更难恢复的信息：为什么选择这个方案、讨论过什么替代方案，以及哪些约束是有意保留的。作者用“模型—代码间隙”说明这种损失。即使设计从未写下来，只存在于原团队头脑中，最终代码也未必能完整表达它。让许多新成员各自花几天猜测，未必比老成员集中说明一次更省团队总成本。

团队于是把领域、设计与代码三个模型当作检查理解缺口的方向：新同事是否懂媒体领域，是否懂我们打算如何组织系统，是否找得到实现？再用模块、运行时与分配三个视图类型检查不同结构。其中，分配视图关心软件部署到哪里，本例只有一台机器，可以简单说明；领域知识又已有公开资料，可以整理参考链接，不必重写一本音视频教材。真正缺少的是设计理由与运行协作。

这不是要求三个模型乘以三个视图，各补一份文档。它是一种逐步评估的办法：每增加一项说明，就看剩余误解集中在哪里。领域参考、代码和模块图已经能够提供一部分骨架，接下来才值得把精力花在质量取舍与运行时模型上。

03质量取舍，怎样变成组件的职责和边界

原团队认为，许多播放器虽然能播，却会因为操作迟钝、声音或画面不平稳而让人不满意。因此，本例的质量属性优先级为：界面响应速度 ＞ 音视频播放平稳性 ＞ 可靠性 ＞ 可修改性 ＞ 播放效率（帧率）＞ 可移植性。这里“平稳”强调帧能否持续、按时呈现，不只是尽量提高帧率。

这个排序解释了原型的两项取舍。系统最初计划随硬件一起提供，可移植性不重要；为优先保证播放体验，团队直接调用平台 API，接受以后迁移更困难的代价。原书把额外平台抽象层可能增加的延迟、音频保真度影响作为当时的担忧，并没有给出所有抽象层都会变慢的性能定律。另一方面，既然选定硬件上的多数视频已经播得足够好，团队便更看重增加编解码器和媒体来源的便利，而没有追求每个来源的极致专门优化。

两条既重要、又难实现的要求成为架构驱动因素。第一，用户发出暂停等命令后，系统应在 50 ms 内完成；遇到无法在这个时间内完成的操作，例如开始播放网络视频，应提供进度条等等待反馈。第二，指定的本地 H.264／MPEG-4 AVC 参考视频，在指定参考硬件上应播放平稳。前者不是“所有网络操作都必须在 50 ms 内结束”，后者也没有承诺所有视频、所有机器都同样流畅。

这些目标又落成了具体决定：顶层运行组件各自放在独立进程中，以隔离故障；媒体缓冲与渲染／播放之间使用共享内存，减少高频数据搬运的延迟；磁盘和网络数据先缓存在 RAM 中，以吸收输入的不稳定。所有媒体元数据集中保存在元数据仓库，即使它们也存在于媒体文件的 ID3 标签里；只有播放器核心可以写入仓库。

集中保存与限制写入口，给开发者提供了明确约定。例如，新功能发现了一段歌词或一项艺人信息，不能因为“离插件最近”就顺手让任意组件写库。但这一约定本身没有解决后文的模型兼容问题：写入路径统一，仍然可能无处表达“某个人是某个乐队的成员”。

原书首先用图 4.3 的职责表说明运行元素。表格同样是模型，不必所有信息都先画成图。它回答的是各部分承担什么责任，从而避免新成员把行为塞进眼前最方便的位置。

运行元素 在本例中的职责
命令输入（Command Input） 接收遥控器、键盘等原始动作，翻译成统一的事件词汇。
播放器核心（Media Player Core） 保存应用状态，组织界面逻辑，协调各组件的活动。
媒体渲染／播放（Media Rendering / Playback） 输出音视频，也绘制菜单等界面元素。核心决定显示什么，渲染组件负责把它画出来。
媒体缓冲（Media Buffer） 将媒体缓存在内存中以降低数据流抖动，通过共享内存提供数据。
元数据仓库（Metadata Repository） 保存歌名、导演等描述媒体的数据。
媒体文件（Media Files） 普通文件系统中的文件，可位于本地或已经挂载的远程磁盘。

这组运行元素与前一节的源代码模块不是同一种划分。一个模块的代码可能参与某个运行组件的实现，组件又可以进一步包含子组件。只有先说明讨论的是代码组织还是运行实体，后面的“独立”“依赖”“通信”才不会混在一起。

04把暂停走一遍，才知道线怎样连接行为

职责表还不能说明组件怎样合作。原书图 4.4 因而进一步给出稳定运行时的组件装配：命令输入把事件交给核心，核心协调渲染／播放与缓冲，缓冲读取文件或互联网，渲染／播放从缓冲取媒体，最终送往电视与音响。本例没有值得单独分析的复杂启动、关闭配置，所以没有继续把所有配置都画出来。

读这张装配图，图例与方框同样重要。方框表示运行实例，小方块是交互端口，圈中的 P 表示独立进程；不同线型表示不同连接器。这里的端口（port）是组件与外界交互的位置，不是 Web 服务使用的操作系统端口号。用户、电视和音响被放进原图，是为了说明系统边界，作者也明确指出它们不是软件组件。

连接器（connector）不只是“能连通”的一条线，它还规定双方怎样交互。本例的消息连接器是异步、双向的；管道连接器是异步、单向并保持消息顺序的。共享内存连接器在书中被建模为同步连接器，配合锁防止数据破坏，并要求两端部署在同一台机器。数据库、互联网与文件系统连接器则分别表达同步 SQL 访问、HTTP 等协议访问，以及采用内存映射 I/O 的文件读取。它们是本例选定的交互语义，不是所有同名技术必然具有的唯一语义。

图 4-1 把原书装配拆成两条容易读的路径。控制路径搬运的是命令和状态，媒体路径搬运的是持续的数据流。两条路径有关联，但不应因为它们最终都服务于播放，就把媒体数据也塞进命令队列。反过来，使用共享内存也没有自动替开发者解决锁的范围、等待与进程故障后的资源处理。

原书图 4.5 选择“暂停正在播放的视频”这个代表性场景，让新同事不必继续猜测：

  1. 用户按下遥控器暂停键，命令输入识别这个物理动作，发送“暂停键被按下”的事件。
  2. 播放器核心知道当前状态是 PLAYING，将这个事件解释为暂停当前视频，再发送“暂停视频播放”的命令。
  3. 渲染／播放冻结当前视频帧、暂停音频，并停止从媒体缓冲中拉取数据。
  4. 渲染／播放通知核心，视频已经暂停。
  5. 核心收到通知，将自身播放状态更新为 PAUSED。

这里特意保留了“按钮事件”和“播放命令”的区别。命令输入认识设备动作，核心根据应用状态解释意图，渲染组件执行实际操作。若新成员让输入组件直接切换视频状态，表面上少走了一步，却跨过了原有职责边界；若核心一发命令就把状态当成已经暂停，则又把请求与完成混为一谈。这两个反例是对原场景的解释，不是原书报告发生过的故障。

这条场景描述了一个合理的执行轨迹，没有穷尽全部行为，也没有证明 50 ms 已经达标。但在当前沟通风险下，它足以帮助新成员把结构与行为连起来。可运行的原型又能补充对其他操作的直观认识，因此团队没有再写完整动作目录。

核心观点

沟通架构，需要同时交代职责、交互方式与选择理由。代码、模块图、职责表和一条代表性场景可以互补；它们的价值，是让新成员少作关键猜测，而不是把文档补成一个规定厚度的册子。

团队在这一轮的停止判断仍带有主观性：主要模型和视图已经有了足够覆盖，可以作为进一步学习的骨架。书中没有用新成员的交付数据证明沟通风险归零。这里得到的是有依据的“可以继续开发”，而不是一项自动成立的培训成功保证。

05接入现成组件，先找各自隐藏的假设

第二轮，团队被要求跨平台运行，并接入伙伴提供的 NextGenVideo。Cross Platform AV 提供跨平台音视频能力；NextGenVideo 支持更多视频格式、性能也更高，却有遇到不完整视频文件就容易崩溃的名声。原书把这类外来现成组件统称为 COTS（Commercial Off-The-Shelf）组件，即使提供方是开源或非商业组织。这里沿用案例名称，不把它们当作需要查找安装的现代产品。

可移植性原先排在最后，现在却成为明确的新任务。这不是先前排序在逻辑上自相矛盾，而是项目条件变了。风险驱动要求重新审视代价，不能拿“当时不重要”否定现在的要求，也不必因此把原先为固定硬件作出的选择追认成错误。

团队识别出四项相互关联的风险：新组件能否集成；NextGenVideo 崩溃会不会拖垮整体；它只负责视频播放、又可能独占显示资源，旧组件负责的屏幕叠加显示由谁接手；新的播放和控制路径是否增加延迟。团队先查集成，因为连基本装配都不成立时，后面的可靠性与延迟分析缺少对象。这是根据依赖关系排序，不是在宣称集成永远比可靠性重要。

架构失配（architectural mismatch）常藏在组件各自认为理所当然的条件里。两个接口的数据类型能够对接，仍可能一个要求被回调、另一个要求主动轮询，一个认为自己拥有主循环、另一个认为它只是普通被调用者，或两个组件都假定独占同一资源。本例先研究边界，而不是立刻为新组件画内部类图。

研究确认，NextGenVideo 本来就能与 Cross Platform AV 配合；它对外有四个端口：媒体输入 Media In、媒体输出 Media Out、命令 Commands、状态 Status。输入端又提供文件和流的示例实现，这使团队对接入已有媒体缓冲更有信心。真正值得在原书图 4.6 的边界模型上标出的，是另外三个假设：显示必须预先初始化，NextGenVideo 假定独占显示，并且主动轮询命令。

这三个假设分别牵动生命周期、资源所有权和控制协议。初始化问题可以在外层组件创建时处理；轮询要求把异步到达的消息转换成可以被查询的命令；显示独占暂时不妨碍单独播视频，却还没有回答菜单叠加能否工作。把它们写在边界上，可以防止“端口已经连完”掩盖尚未解决的问题。

06适配的不只是接口，还有控制权和故障边界

团队希望保留顶层架构，把 NextGenVideo 与 Cross Platform AV 放进原来的媒体渲染／播放组件内部。图 4.7 是对这个顶层组件的精化（refinement），不是再新增一套与旧架构并列的播放器。命令适配器从事件队列读取命令，状态适配器把状态写回队列，媒体缓冲适配器则把已有缓冲接到 NextGenVideo 的媒体输入端；媒体输出交给 Cross Platform AV，再到硬件。

NextGenVideo 和这些适配器同属渲染／播放这一顶层进程。 原书的独立进程标记画在外层组件上，没有给每个内部子组件分配一个进程，也没有为每个适配器声明独立线程。外层通过异步消息与核心通信，内部连接却可以是同步过程调用；消息队列的存在不会自动让内部调用并发执行。

图 4-2 只放大命令与状态的匹配，暂时不画媒体数据和显示资源。主循环在 NextGenVideo 手中：它适时询问命令适配器，适配器才读取队列、翻译命令并返回。对于媒体输出，外层先初始化显示，再把可用的显示交给 NextGenVideo。这样，团队逐项说明了边界假设怎样被容纳，而不是只在每个端口上画一根线。

这个设计可以沿原书图 4.8 的场景检查。核心先发出带有 INPUT 和 POSITION 的播放命令；NextGenVideo 轮询时，命令适配器取出消息、提取媒体来源与起播位置，完成必要转换。随后创建并连接媒体缓冲适配器、打开输入，再从指定位置开始播放。运行中，NextGenVideo 交替读取输入帧、输出帧、报告状态与检查命令。

这个轨迹也暴露了一个关键匹配条件。假设命令适配器在队列为空时无限阻塞，NextGenVideo 的主循环就可能停在“查命令”这一步，无法继续播放或报告状态。外部连接器虽然是异步的，内部读取仍可能阻塞调用者。因此，需要在实现中确认轮询、等待和返回行为确实匹配。这个反例是本笔记沿控制流作出的推演；原书没有报告原型出现过这项故障，也没有规定具体线程或队列实现。

原图的 Event Queue 端口还有一个值得留意的三方绑定：外层端口同时绑定命令适配器的读端与状态适配器的写端。它表达内部端口如何接到外层通信能力，并不意味着一次同步函数调用连接了三个人。书中也没有因此说明所有方向的消息都混进同一个无区分 FIFO。读图应保留“命令向内、状态向外”的语义，具体路由仍需实现承接。

故障处理利用了已有进程边界。核心观察 NextGenVideo 经适配器送出的状态更新；状态停止到达时，将它视作可能崩溃或挂起。在启动新实例之前，先结束旧进程，避免疑似挂起的旧实例仍占着资源，再清理并重启。这里的状态更新起到心跳作用，但“没收到状态”只是故障嫌疑，不足以从逻辑上区分崩溃、挂起或状态路径异常。原书没有展开心跳间隔、判定超时等参数。

模型与场景此时只说明设计看起来可行，实现仍可能推翻它。因此团队制作原型，实际接通播放，主动终止相关进程来模拟崩溃，观察能否检测、清理和重启，而不影响整个家庭媒体播放器。书中叙述的结果是：原型能够在一秒以内完成故障检测并从原位置恢复播放。

“一秒以内”是这个案例原型的结果，不是进程隔离的一般恢复保证，也不是暂停响应时间。它所支持的结论是，已尝试的集成与故障恢复路径足够可行；它没有证明所有损坏视频、资源故障或平台差异都已处理。顶层组件隔离让这一恢复策略更容易实现，但进程边界的价值仍要由实际检测、资源清理和恢复行为兑现。

07叠加显示改变设计，延迟改变验证办法

最初装配成功时，NextGenVideo 独占显示的问题还没有真正被解决，只是尚未触发。旧渲染组件同时负责视频与菜单，新组件却只播视频；要在视频上叠加菜单、进度等屏幕显示（OSD，On-Screen Display），就必须重新研究显示能力。

团队发现 Cross Platform AV 支持虚拟图层与透明度，于是增加 Overlay Renderer：让视频处在下层，在上方建立部分透明的图层，由新组件绘制叠加界面。原书图 4.9 比图 4.7 多出的，正是这个渲染器及其与命令适配器、跨平台音视频组件的连接。它仍位于同一个媒体渲染／播放顶层进程内。

增加一个方框还不够，命令流也必须改变。NextGenVideo 仍然拥有主循环，会来询问自己的播放命令；命令适配器现在却还要识别面向 Overlay Renderer 的命令，并将它们分流过去。作者明确承认，这在“播放器来取自己的命令”这一原本协议里夹带了别的工作，有一点扭曲既定架构，属于可能逐渐积累的技术债务。

这项取舍的可读之处在于，作者没有把“能通过适配器做出来”当作没有代价。新的叠加功能借用了 NextGenVideo 的轮询节奏，其行为必须在走查与原型中一起检查。若只验证视频能播，仍然看不出菜单命令能否及时被处理。团队口头走过修改后的协作过程，再做原型验证，没有因为装配图已经修改就直接宣布风险消失。

此时剩下的是延迟。可以给组件与连接器分别标注耗时，再分析路径；但团队并不知道队列分发、视频帧解码等关键数据。用猜测填满模型再计算，结果仍然主要取决于猜测。既然已经有相当完整的原型，此刻增加计时记录、直接测量，比另造一个缺少参数依据的延迟模型更有效，也更便宜。

这里至少要区分两类观测：用户命令到可见响应的时间，以及播放过程中帧能否按预期节奏呈现。恢复故障的一秒以内，不能替这两项作答；平均帧率看似足够，也不能独自说明不存在间歇停顿。测量对象必须对应原先的架构驱动因素。

原书说明了改用原型计时的选择，却没有给出完整测量结果、分布或各平台数据，因此不能据本章补出“所有命令均低于 50 ms”等结论。本轮最重要的方法变化，是从文档研究到边界建模、装配走查、故障原型，再到直接测量：技术随着剩余风险改变，没有被固定成每次必走的流程。

08元数据风险，先在具体事实中寻找表达缺口

第三轮的元数据一致性（metadata consistency），重点不是数据库事务是否原子、多个副本是否同步，而是内部模型与外部模型能否表达并交换相同的领域事实。插件已经有 API，却可能拿不到表达艺人关系所需的概念；也可能从网站找到了关系，回到播放器时没有地方保存。

最直接的办法，是实际写几个插件。但本次目标只是判断首个版本是否具备插件可行性，而网页查找、抓取、去除标记等实现细节会消耗不少时间。原书在这个情境下估计，几个抓取原型需要数天，领域建模只需数小时。这是案例里的投入判断，不是所有插件项目的工期比例。领域建模能帮助比较概念，却不能调试 API，也不能产出供第三方模仿的示例插件。

“担心音乐模型可能太简单”又很容易诱发没有边界的领域研究。团队于是选定三个代表性用途：显示当前歌曲的歌词；显示歌手或词曲作者的传记；寻找与当前歌曲有关的音乐。它们不覆盖所有未来插件，却让这轮研究有了明确范围。

播放器最初采用一个受 ID3 标签启发的模型。图 4.10 只有 Artist、SongTitle、Album 三种类型，SongTitle 带年份与流派属性；关联两端的 1 与 * 表示，在这个简化模型里，每条歌曲记录关联一个艺人、一个专辑，艺人和专辑则可以关联多条记录。它没有声称真实音乐世界只有这种关系，也不意味着 ID3 标准只能表达这些信息。

只看“艺人—歌曲—专辑”，似乎没什么不妥。团队因此把类型模型变成具体的快照（snapshot，实例图）：按模型规则放入一些实例与连接，检查真实情境中的信息能否放进去。原书图 4.11 使用 Prince 的作品：《Let's Go Crazy》与 Prince and the Revolution、专辑《Purple Rain》关联；《Little Red Corvette》与 Prince、专辑《1999》关联；《Life O' the Party》与 Prince、专辑《Musicology》关联。专辑名《1999》是名称，不应读成年份属性。

这个快照在原模型中合法，却漏掉了关键事实：Prince 是 Prince and the Revolution 的成员。人看到名字可能猜到关系，程序不能把字符串相似当作领域知识。缺口并不是某个字段拼错了，而是模型没有任何一种关联可以表示它。

回看三个用途，歌词插件大致可以利用歌名与艺人发起查找；传记插件却需要分清现在指向个人还是乐队，并找到彼此关系；相关音乐插件即使在网上发现成员关系，也无法把它记回旧模型。一个模型能装下某张列表，不等于它能支持列表之外需要的推理。这个反例把模糊担心变成了可说明的表达能力不足。

团队随后比较其他音乐模型。书中区分以单曲文件标签为中心的模型，以及面向音乐集合的数据库模型，并选择 MusicBrainz 深入查看。按作者当时的研究，MusicBrainz 会区分个人与团体艺人，并用 ArtistRelationship 表达艺人间关系。图 4.12 因而能够增加一条类型为 memberOf 的关系，把原来分离的实例连起来。团队还发现 Prince 的艺名、别名变化，进一步暴露旧模型不能表达名字关系的问题。

09只补足所需表达能力，也承认模型的局限

发现更丰富的外部模型后，有三种明显选择：不改旧模型，接受插件受限；完整采用 MusicBrainz 一类模型；或只吸收当前需要的部分。完整复制虽然获得更多表达能力，也可能让第三方理解、使用 API 的成本过高。团队最终选择第三种：增加个人与团体的区分，并支持成员与艺名关系。

图 4.13 的修订在 Artist 上增加 isGroup 布尔属性，再增加 memberOf 与 pseudonym 两条自关联，也就是同一种 Artist 类型的实例之间可以发生不同关系。这与图 4.12 用独立 ArtistRelationship 类型表示关系的方式不同。二者可以服务于相近事实，但不能因此认为内部模型已经完整复制了 MusicBrainz。

原图 4.13 的关系基数需要谨慎阅读

原图两条自关联的端点标了 1 与 1..*。按 UML 通常的多重性语义，1..* 表示至少一个，不是零个或多个；机械地把这张图当成适用于所有 Artist 的完整约束，会强制没有别名的艺人也参与别名关系，没有团体关系的独立艺人也参与成员关系。关系两端的角色与适用对象也没有被充分细化。这是教学简图的建模局限，不是可以直接落库的通用音乐规范。

本笔记保留其核心修正——区分个人与团体、能够表达成员与名字关系——但图 4-3 只画实例，不照搬这组基数。若要实现一般化模型，至少需要允许相关关系缺省，并明确谁是成员、谁是团体；具体上下限、身份判断与时间范围则应根据实际用途继续确定。没有必要为了本章三个插件，顺手设计一套完整音乐本体。

名字相同不等于身份相同，名字不同也不必然是两个无关艺人。反过来，艺名、别名与独立表演身份也不应无条件合并。原书在此只是展示缺少名字关系的风险；本轮核查的 MusicBrainz 现行文档同样区分别名与某些应独立建档的表演身份。这项补充用于说明适用边界，不把今天的数据规范追写成作者 2010 年的完整设计。

团队此时能说的是：修改后的模型能够表示选定快照，更有希望支持歌词、传记与相关音乐这三类插件。团队没有实际制作这些插件，因而没有验证 API 的全部可用性，更没有证明任何未来插件都能成功。若剩余风险仍不可接受，下一步可以继续做示例插件；若当前目标只要求尽早排除明显表达缺口，这一轮轻量建模就已经提供了值得的收益。

10把不同强度的证据，带回同一条风险主线

贯穿本章的不是“先画哪些图”，而是每做完一项工作，都重新判断剩余风险。对照起来，可以看见不同技术究竟提供了什么：

当前风险 使用的技术与证据 证据没有覆盖的部分
新成员误解设计 代码、领域参考、模块图、质量取舍、职责表与暂停场景，覆盖主要理解缺口。 没有给出新成员实际产出或架构漂移率的测量。
COTS 集成与故障影响 研究边界假设、精化装配、走查场景，再以原型验证播放与模拟崩溃后的恢复。 单次或有限的原型成功不是全部故障、全部平台的可靠性保证。
叠加显示 根据虚拟图层与透明度修改装配，走查命令分流并制作原型。 借用播放器轮询节奏的技术债务及其时序影响仍需关注。
延迟 已有原型上记录计时，比缺少参数依据的模型更合适。 本章没有报告完整测量结果，不能补出达标数字。
元数据模型不兼容 三类代表性插件、具体快照与外部模型比较，找到并补充表达关系。 没有实际插件、API 调试结果或覆盖全部音乐领域的证明。

这也解释了为什么风险驱动允许工程师意见不同。有人可能认为插件原型更值得做，另一些人认为领域比较更省钱；只要双方说明针对什么风险、希望取得什么证据、投入多少，分歧就能成为具体工程讨论，而不必退化成“建模派”和“编码派”的方法论争论。

沟通轮次大量使用文字与代表性模型，集成轮次需要装配和原型，延迟轮次跳过额外模型直接测量，元数据轮次又回到概念与快照。模型可以在白板上画，场景也可以指着装配图口头走过。原书为了让读者看清推理而正式排版，不意味着真实项目必须制作同样整齐、同样数量的产物。

核心观点

足够的架构工作，是取得了与当前失败风险相称的证据，而不是掌握的技术全都用过。证据只支持有限结论；在这个边界内足够可靠，就回到实现，出现新风险再继续分析。

本章因此延续第 3 章的风险驱动模型，也为第 5 章的建模建议提供上下文：省略细节不是目的，穷尽模型也不是目的。模型与原型都要帮助交付系统；真正需要保留的是那些能够改变判断、解释取舍，并指导下一步行动的信息。
