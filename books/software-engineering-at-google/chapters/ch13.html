READING NOTES / CHAPTER 13

第 13 章｜测试替身

Test Doubles · 架构提升读书笔记

一个函数先请求远端服务，再把结果写进数据库，业务逻辑可能只有几行，测试却需要准备网络、账号、数据和清理工作。这样的测试写五个尚可，积累到几百个以后，等待时间、偶发失败和数据干扰都会进入日常开发。测试替身（test double）让我们能在测试里换掉某些实现，保留正在验证的业务，把难以控制的依赖留在边界之外。

本章关注的不只是怎样替换依赖，更是替换以后还剩多少可信的证据。Google 的经验是：模拟框架曾让隔离每个类变得很容易，却也留下大量经常随实现变化而失败、很少发现实际缺陷的测试。作者因此把重点放在真实实现、可复用的伪实现，以及克制地使用打桩和交互验证上。一个容易写出的测试，只有在以后仍能帮助判断行为是否正确，才真正节省工程时间。

01把可替换的位置留在依赖边界

测试替身是能在测试中代替真实对象或函数的实现。它可以是一份内存数据库，也可以是固定返回失败的支付网关函数，还可以记录调用发生了几次。它们承担的工作不同，不能仅凭“这里用了 mock”就判断测试验证了什么。

书中的入门案例是一段信用卡支付逻辑：先判断卡是否过期，未过期才调用信用卡服务。测试直接接触真实服务，会带来实际扣款、手续费和外部系统的运行条件。若当前只想确认过期卡返回失败，一个始终返回成功的简单替身已经够用，因为这个测试走的分支根本不依赖网关的真实行为。

要把替身放进去，代码里需要有接缝（seam），也就是允许测试改变依赖装配的位置。依赖注入（dependency injection）是常用做法：支付处理器接收一个信用卡服务对象，而不是在内部直接创建某个连接真实服务器的具体实现。生产入口传真实服务，测试传替身，支付规则本身继续运行。

这项设计的投入通常很小，收益却会随代码增长而放大。若数据库连接、网络客户端和系统时间都散落在业务方法内部，后来补测试时就得一边分离依赖一边确认原行为。提前把这些依赖作为构造参数、函数参数或统一工厂的可替换部分，更容易在不改变业务的情况下准备测试环境。大型对象图可以由依赖注入框架装配；理解这项原则不需要先引入框架。Python、JavaScript 可以动态替换对象方法，原章因此说依赖注入在这些语言里没那么必要，但清楚的依赖边界仍能让测试读起来更直接。

本章区分三种主要用法。伪实现（fake）用较轻量的方式实现接口行为，例如把授权用户保存在内存集合里：添加用户之前查询无权限，添加之后查询有权限。前后两次操作访问同一份状态，测试不需要告诉查询函数这两次分别返回什么。

打桩（stubbing）则在测试里指定某个函数如何返回。例如，把查询用户的结果设为“未找到”，观察业务是否拒绝访问；再用另一个测试返回有效用户，观察是否允许访问。它便于制造当前测试需要的条件，接口契约是否真实则取决于这些设置是否有依据。

交互验证（interaction testing）检查函数怎样被调用，包括是否调用、参数、次数或顺序。例如，检查授权管理器是否调用了查询用户的接口。这证明调用发生过，得到的信息与直接检查最终权限状态不同。模拟框架（mocking framework）可以同时支持打桩和交互验证；框架是一种工具，两者是使用工具的不同方式。原章刻意不用含义混杂的 mocking 统称所有这些做法，本文也沿用这一区分。

测试大小与测试范围在这里需要分开。把跨进程访问换成内存调用，可以让测试满足小型测试的运行约束；测试仍可能覆盖几个协作类的共同业务行为。参与的类多一些，不会自动把它变成“大型测试”；同样，一个只测单个方法、却访问远端服务的测试，也不会因为断言很少就变成小型测试。

02先保留真实实现，再处理真正困难的依赖

原章的首选顺序从真实实现开始。金额、日期、地址、列表等值对象通常构造简单、执行快，也没有需要避开的副作用。使用真实对象，比较、格式化和边界处理都会真实发生；换成一组预设返回值，反而会把本来已有的行为再描述一遍。

这种偏好背后，是对测试边界的理解。假设一个折扣服务把计算抽到辅助类里，业务接口和输出都没有变化。若测试只因计算被移出当前类，就把辅助类整体替换掉，测试覆盖的内容便随文件组织变化而缩小。原章主张围绕被测 API 的行为组织测试，尽量保留真实协作，不把类边界自动当成隔离边界。

真实依赖里的缺陷会让使用它的测试失败，有时还会让多个调用方的测试一起失败。作者认为这是好事：它说明代码到了生产环境同样无法正常工作。结合持续集成和变更定位工具，团队可以追溯共同原因。全量隔离虽然可能把失败限制在一个类里，却也可能使所有调用方继续通过，直到更晚才发现它们无法一起工作。作者把偏好真实实现的方式称为经典测试风格（classical testing），并将其与更偏好框架替身的 mockist 风格对照；他们发现后者在 Google 难以规模化。

决定能否保留真实依赖，原章主要看三件事。第一是执行与构建成本。每项测试增加一秒，五个测试和五百个测试的影响很不一样；没有脱离测试数量和开发反馈周期的统一“过慢”阈值。情况尚可时，先使用真实实现，再在出现实际瓶颈后引入替身，往往比提前维护一套模拟行为更划算。并行运行、缓存未变化的构建产物也能改善等待，但不消除资源成本。

第二是确定性：在给定的被测版本和受控条件下，测试应当稳定地通过或失败。任意访问公开网页，会受到页面更新和服务负载影响；直接读取系统时钟，会让同一条规则在不同日期走不同分支。受测试控制的服务器实例、固定时间的时钟替身，都能把这些条件稳定下来。若正在验证的恰好是并发时序等真实风险，也需要保留能暴露该风险的测试。

第三是构造依赖的成本。真实对象可能牵出整棵依赖树，手工创建既费力，又容易随着构造函数变化而反复修改。原章建议尽量复用生产中的工厂或对象装配代码，同时允许在困难边界传入替身。这样，测试不必为省几行初始化就放弃整段真实行为。

书中的 @DoNotMock 案例把这项选择提升到了 API 维护层面。API 所有者可以配合 Error Prone 静态检查，声明某个类型不适合由模拟框架构造，并指向真实工厂或已有伪实现。背景是某个类型可能在成千上万处被打桩，每一处都暗中复制了部分契约，甚至返回接口根本不允许出现的空值。API 变化后，维护者面对的就不只是一份实现，而是大量分散且不可靠的行为副本。这项约束最有价值的配套，是提供容易使用的正确替代方式。

核心观点

隔离是控制困难依赖的手段，真实的业务证据才是目标。先保留快速、稳定、容易构造的真实实现，把替换集中到真正妨碍测试的边界。

03伪实现保留接口行为，省掉昂贵的运行方式

伪实现的价值在于，它自己知道一组操作如何共同工作。书中用文件系统说明这一点：写入把文件名和内容放进内存映射，读取从同一映射取出内容；读取不存在的文件时，也应给出与真实接口对应的错误。测试因此可以“先写后读”，不必分别安排写入成功和读取结果。

保真度（fidelity）描述替身的行为与它所代替的真实实现有多接近。对伪实现来说，关键是 API 契约中调用方能依赖的部分：相同输入应产生相应的返回、错误与状态变化。例如，真实数据库规定重复 ID 保存失败，内存伪实现就不能悄悄覆盖旧值；否则一项错误的业务实现会在测试中成功，在真实系统中失败。

保留契约不要求复制整个运行机制。内存文件系统不需要使用磁盘，也不需要花同样的时间完成操作；省掉这些成本正是引入它的原因。它需要保留的是当前接口承诺的可观察行为。假设文本文件接口只接受普通文件名，承诺覆盖写入、原样读回和缺失文件错误，那么测试就可以围绕这三项行为建立依据；目录权限、跨进程锁和断电持久性并未因此获得验证。

这也解释了为什么“对测试足够像”仍需要明确契约。不能仅因为眼前断言没有查看错误，就随意省掉接口必需的错误；否则后续测试很容易把这份替身当成更完整的实现。对于暂不支持的功能，原章建议让伪实现立即报错，告诉使用者这里不适合用它。

性能、延迟和资源消耗通常也不需要伪实现保真。若这些属性本身就是测试目标，例如验证一次调用的延迟，伪实现就派不上用场，要改用真实实现或适合该目标的测试环境。

核心观点

好的伪实现缩减运行机制，保留调用方依赖的契约。真实接口的返回、错误和状态关系需要有依据；磁盘、网络与性能等被省略的部分，留给相应的真实环境测试。

04用同一份契约测试约束两种实现

伪实现也是代码，也会出现错误和随时间漂移。最初它可能与真实接口一致，几个月后真实接口改变了重复写入或错误处理规则，使用旧伪实现的业务测试仍然通过。原章提出的办法是契约测试（contract tests）：面向公共接口编写一组行为测试，再分别对真实实现和伪实现运行。

下面是本笔记原创的完整 Python 示例，仅使用标准库。它把范围限定为一个目录下的普通 UTF-8 文本文件：写入可覆盖，空内容合法，读取缺失文件抛出 FileNotFoundError。真实版本使用临时目录中的磁盘文件，伪实现只使用字典；两者运行同一个检查函数。

from pathlib import Path
from tempfile import TemporaryDirectory


class DiskTextFiles:
    def __init__(self, root):
        self.root = Path(root)

    def write(self, name, text):
        (self.root / name).write_bytes(text.encode("utf-8"))

    def read(self, name):
        return (self.root / name).read_bytes().decode("utf-8")


class FakeTextFiles:
    def __init__(self):
        self.files = {}

    def write(self, name, text):
        self.files[name] = text

    def read(self, name):
        if name not in self.files:
            raise FileNotFoundError(name)
        return self.files[name]


def check_contract(make_files):
    files = make_files()
    files.write("note.txt", "第一版")
    assert files.read("note.txt") == "第一版"
    files.write("note.txt", "修订版")
    assert files.read("note.txt") == "修订版"
    files.write("empty.txt", "")
    assert files.read("empty.txt") == ""
    try:
        files.read("missing.txt")
    except FileNotFoundError:
        pass
    else:
        raise AssertionError("读取缺失文件必须失败")


check_contract(FakeTextFiles)
with TemporaryDirectory() as root:
    check_contract(lambda: DiskTextFiles(root))
print("两种实现均通过文本文件契约检查")

检查空文件很重要：空字符串是有效内容，不能像缺失键那样处理。检查覆盖写入则把两次调用联系起来，验证它们访问的是同一份状态。磁盘版本的契约检查要读写真实文件，运行较慢；业务测试使用内存版本，就不会因为这项依赖超出小型测试的约束。

原章建议由真实实现的所有者编写和维护伪实现，因为他们最了解契约，也最早知道接口变化。业务团队大量复用一份伪实现，接口所有者在更少的地方运行相对昂贵的真实契约测试，就能把“是否仍然一致”的维护成本集中起来。契约测试覆盖到的行为一旦出现偏差，就能被及时发现。

伪实现应放在不适合测试的依赖边界上。例如，问题在数据库，就为数据库 API 提供伪实现，再让调用它的业务类继续真实协作。若每个上层业务类都另写一份伪实现，同一套规则会被复制很多遍，维护负担也随之扩散。多个语言客户端还可能共用一个伪服务，避免每种语言都重写服务语义；代价是跨进程通信，测试大小也要按实际运行方式重新判断。

维护伪实现需要领域知识和长期投入。一个只有少数调用方、真实测试已经够快的 API，未必值得专门再造一套实现。没有现成伪实现时，可以先与 API 所有者协商；只用到外部 API 的一小部分时，也可以在自己的边界包装这部分操作，再为这个较小接口实现替身。是否值得做，取决于反复节省的开发时间能否覆盖维护成本。

05打桩让当前需要的条件稳定出现

打桩最适合帮助测试进入某个具体分支。原章举了统计信用卡交易数的例子：让服务器查询返回三笔交易，然后检查统计结果为三。这个返回值与断言直接对应，读者不需要追踪一长串内部调用才能理解测试。

错误分支也很适合这种用法。有些错误在真实服务上难以稳定制造，伪实现也未必提供触发方式。下面的原创完整 Python 示例把范围限定为支付网关的响应处理：网关拒绝返回 declined，调用超时返回 unknown。超时只说明没有及时得到结果，交易是否完成并不确定，所以例子把它记为未知。

from unittest.mock import create_autospec


class CardService:
    def charge(self, card_token, amount_cents):
        raise NotImplementedError


class PaymentProcessor:
    def __init__(self, card_service):
        self.card_service = card_service

    def pay(self, card_token, amount_cents):
        try:
            accepted = self.card_service.charge(card_token, amount_cents)
        except TimeoutError:
            return "unknown"
        return "paid" if accepted else "declined"


declining_service = create_autospec(CardService, instance=True)
declining_service.charge.return_value = False
assert PaymentProcessor(declining_service).pay("card-1", 500) == "declined"

timed_out_service = create_autospec(CardService, instance=True)
timed_out_service.charge.side_effect = TimeoutError("测试制造的超时")
assert PaymentProcessor(timed_out_service).pay("card-1", 500) == "unknown"
print("拒付与超时两个响应分支均通过")

这里的 return_value 指定返回值，side_effect 指定调用时抛出异常。create_autospec 根据 CardService 约束接口与方法签名，能发现不存在的方法或错误的参数数量；真实网关是否按这种方式返回和报错，仍要由接口文档、真实实现和测试确认。

这两个测试里，每项设置都直接解释了结果为什么应该是拒付或未知。读者只需要理解一个边界条件和相应规则。相反，如果准备测试时先后指定服务可用、开始事务、初始化、支付、提交等许多返回值，阅读者就必须在脑中运行被测实现，才能知道哪些设置真正影响断言。测试的意图会被准备代码盖住。

原章将过度打桩的后果归为三类。首先是难读，因为测试包含大量只有看过实现才懂的安排；其次是脆弱，内部调用稍一调整，这些安排就要跟着修改；最后是证据变弱，因为每个返回值都由测试作者填写，却没有自动保证它符合真实契约。一个被打桩为“写入成功”的方法，并不会自然为另一个被打桩的“读取”方法建立正确的数据。

核心观点

一项打桩设置最好能直接解释一项业务断言。需要大量打桩才能让测试运行时，应重新看依赖边界和可复用的伪实现，减少在单个测试里重建内部流程。

06支付案例：从复刻调用步骤到观察交易结果

原章最有代表性的一组对照，是一次“信用卡已被扣款”的测试。第一版同时替换信用卡服务器和事务处理器，先安排服务器可用，再安排开始事务返回事务对象，随后安排初始化、支付和结束事务的返回值。执行支付以后，测试只能检查 pay 方法是否带着指定的事务、卡和金额被调用。

准备工作描述得很细，最终证据却停在调用层面。网关替身没有真实交易状态，所以测试既无法从账本读回金额，也无法确认这次调用产生了相应交易。原示例甚至把支付返回值设为 false，最后仍只验证调用发生，这恰好凸显了测试名称与它实际证明的内容之间的距离。

第二版保留交易处理所需的真实协作，并使用知道如何维护交易状态的信用卡服务替身。测试执行支付，然后通过服务的公开查询接口读取最近一笔扣款，检查金额是否正确。服务器可用性检查、事务怎样传递，不再需要逐项写进这个测试；它们由真实组件或集中维护的伪实现处理。

这次改写有两项收益。阅读者可以直接把“处理这张卡的付款”和“账本里的这笔金额”连起来，不必先理解事务处理器如何工作；维护者以后重构内部事务步骤时，只要公开行为保持不变，这项测试就有机会不改。测试更接近用户关心的结果，也更少复制内部实现。

这个测试显然不该连接外部的真实收费系统，所以原章认为信用卡服务最好用伪实现。如果没有伪实现，也可以让真实客户端连接由测试控制生命周期的隔离服务器实例，代价是更多运行成本。无论选哪一种，真实客户端、协议和服务能否一起工作，都要留给更大范围的测试确认。

07交互验证提供调用证据，状态验证提供结果证据

状态验证（原章称 state testing）调用被测系统，再检查返回值或可观察状态的变化。“状态”不只指对象字段，还包括返回的有序列表、保存后能否查询到记录等。原章用排序说明这种方式：输入 [3, 1, 2]，检查返回 [1, 2, 3]，至于内部选择快速排序还是冒泡排序，通常与这个行为无关。

若把排序器都替换成不会真正排序的框架对象，再验证快速排序函数被调用，测试便只能确认“尝试走了这条路”。结果是否有序、是否丢失元素，都没有得到检验。以后把实现改成另一种正确算法，这项测试可能失败；把算法结果丢弃，它也可能继续通过。原章把这类过度依附实现的测试称为变更探测器：它们对代码变化敏感，却未必对业务错误敏感。

交互验证仍有适当的位置。一种情况是真实实现过慢、也没有可用伪实现，暂时只能确认调用方按约定发出了请求。另一种情况是调用本身具有要求，例如次数或顺序变化会造成不希望的结果。此时，调用约定就是当前行为的一部分，不能只看返回值。

缓存就是原章给出的例子。读两次得到相同数据，还不足以说明缓存减少了数据库访问，因为程序可能每次都查询。下面的原创完整 Python 示例同时检查数据和调用次数；假设缓存不设过期时间，测试范围只覆盖同一键在同一实例里的重复读取。

from unittest.mock import create_autospec


class DatabaseReader:
    def read(self, key):
        raise NotImplementedError


class CachedReader:
    def __init__(self, database):
        self.database = database
        self.cache = {}

    def read(self, key):
        if key not in self.cache:
            self.cache[key] = self.database.read(key)
        return self.cache[key]


database = create_autospec(DatabaseReader, instance=True)
database.read.return_value = "记录内容"
reader = CachedReader(database)
assert reader.read("item-1") == "记录内容"
assert reader.read("item-1") == "记录内容"
database.read.assert_called_once_with("item-1")
print("结果正确，重复读取只访问数据库一次")

前两项断言确认调用者拿到正确数据，最后一项确认重复读取没有重复访问依赖。只验证“不超过一次”可能连完全不读取数据库的实现都放过；结果断言与调用约束放在一起，才完整表达了这个小场景。这里检查的是只读方法，但它属于有明确理由的例外，因为减少读取次数正是缓存的目标。

若单元测试只保留了调用证据，测试组合中应有真正检查结果的补充。比如，保存记录的单元测试只能验证 save 的参数，那么还应有使用真实数据库、写入后能读回的集成测试。增加的测试范围，用来验证此前被假定成立的协作关系。

08只约束当前行为真正需要的交互

原章对交互验证的第一项建议，是优先把它用于改变外部状态的操作，例如发送邮件、保存记录、写访问日志。这些调用代表被测系统对外产生的效果；当状态难以直接观察时，验证调用至少能确认这一层按约定发出了相应操作。

对读取用户名、查询权限、读取文件等不改变状态的操作，通常可以通过使用返回值以后的行为来判断。例如，读到无权限信息后应拒绝访问，那么检查拒绝结果就比再要求“恰好调用某个查询方法”更贴近目标。后者容易固定查询方式，使添加缓存、合并查询等内部改动牵动大量测试。上一节的缓存是例外，因为读取次数本身就是被测行为。

第二项建议是避免过度规定（overspecification）。书中问候界面的例子要检查用户名显示正确，却同时固定了问候语、版本号和图标。只要版本从 2.1 更新，或图标换了，这个“用户名”测试就失败。修测试的人还要重新判断用户名行为到底有没有问题，失败信号因此变得嘈杂。

原章的改写将行为拆开：检查用户名的测试只约束用户名参数，其他无关参数使用适当的匹配器；检查早晨显示效果的测试，才固定时间、问候语和太阳图标。每项测试验证自己负责的行为，其他行为仍在各自的测试中受到约束。

顺序和次数也应以同样方式处理。若顺序只是当前实现的安排，就不要把它永久写进断言；若“写入成功后才能发送通知”是明确业务要求，顺序才值得被验证。测试越少替实现作不必要的决定，重构时就越能依靠它检查结果。

核心观点

能观察结果，就优先观察结果；需要验证调用时，只固定当前行为所依赖的操作、参数、次数或顺序。把无关变化留给其他测试，才能让一次失败清楚地指向一项业务约定。

本章的选择顺序可以连成一条主线：可用时保留真实实现；需要省去昂贵或不可控的运行方式时，优先采用符合契约的伪实现；为了稳定触发少量特殊条件，再使用打桩；只有调用约定本身重要或缺少更好观察方式时，才引入交互验证。图 13-3 把这条主线画成从上往下的几次判断。

替身帮助测试快速、稳定地发生，契约测试和真实依赖测试则负责让这种便利一直有现实依据。下一章将进一步讨论这些依赖放回系统后，怎样验证更大范围的协作。
