READING NOTES / CHAPTER 21

第 21 章｜依赖管理

Dependency Management · 架构提升读书笔记

把一个外部库接进项目，往往只需要几行声明。几年以后，修复它的安全漏洞却可能牵动一串从未直接使用过的库：某个组件需要新版运行时，另一个组件还停在旧接口上，最上层应用同时需要它们。这时，问题已经从“怎样下载一个包”变成“怎样让一张持续变化、又没有统一指挥的依赖网继续工作”。

本章把第十六章的版本控制与第十八章的构建问题向组织边界外推进。重点是版本选择背后的兼容承诺、维护责任和验证证据。作者坦承，Google 对内部协同有丰富经验，对跨组织、大规模依赖网络却没有已经验证成功的完整答案。

01真正需要维护的，是一张会变化的依赖网

直接依赖是自己的代码明确使用的组件，传递依赖是这些组件继续依赖的东西。即使应用只声明了两个库，它最终需要的运行时、基础库和构建工具，也可能来自许多互不认识的维护者。每一方都在解决自己的问题，发布时间和升级动力自然不同。

原书用 libuser → liba／libb → libbase 说明菱形依赖冲突。应用同时需要 A 和 B，两者又使用同一个基础库。基础库作出不兼容变更后，A 已经升级，B 还没有跟进；若同一运行环境只能接受该库的一个版本，就可能再也找不到让两条路径同时成立的选择。菱形这个形状本身很普通，冲突来自两条路径对共同基础提出了互斥要求。

用一组假设的版本范围把它写清楚：A 要求 2.0.0 ≤ base < 3.0.0，B 要求 1.5.0 ≤ base < 2.0.0。两个范围没有交集。在“不改 A、B，且 base 只能选一版”的前提下，再聪明的解析器也选不出答案。调整上层版本、为旧调用方做迁移，或者建立真正的多版本隔离，才可能改变这个局面。如果新版是为了修复必须处理的安全漏洞，退回旧版也未必是可接受的出路。

相同结构还会藏在版本号以外。A 只能使用新编译器，B 的某项扩展只支持旧编译器；两个组件分别需要不同的操作系统、语言版本或编译选项，也会形成冲突。把这些条件看作依赖图中尚未画出的节点，就能理解为何“每个库自己都测试通过”，仍不足以保证整个应用可以组装。

语言机制能够缓解一部分冲突。例如 Java 的 shading 可以重定位类和包，把一份依赖封装成私有副本；独立进程也可以隔离运行环境。难点在共享边界：两个版本定义的同名类型未必具有相同身份和语义，一边返回的对象不能仅靠改包名就成为另一边所需的对象。能够完全隐藏的内部依赖，通常比穿过公共接口的依赖更容易隔离。第十六章的单一版本与公共词汇类型已经展开了这种区别。

作者由此用“能否共同控制变更”划分版本控制与依赖管理。若组件的维护者和使用者都能被同一组织协调，可以查看调用方、修改它们、运行测试，许多困难便能化成一次共同的源码变更。反过来，同一家公司里的团队如果各自发布、彼此不可见，也会遭遇类似外部依赖的问题。仓库数量是实现细节，协作权限与信息边界更接近问题本身。

核心观点

在条件相近时，尽量把需要共同演进的代码放进可以共同观察、修改和验证的协作范围。减少独立版本选择，能少承担许多“每个组件都合理，组合起来却不成立”的工作。

02引入依赖，也接下一份长期契约

复用软件的收益十分真实：团队不用重新实现解析器、压缩算法或正则引擎，可以把精力放在自己的产品上。作者并不主张凡事自研。他要求补上的，是时间这一维度：省下首次开发的成本之后，未来谁来理解升级、修复不兼容、跟进上游停止支持的平台？

一份依赖因此可以看作长期契约。提供者说明哪些用法受支持、准备维护多久、允许哪些变化；使用者依照这些约定使用接口，并承担必要的测试和迁移。许可证中的免责条款与工程上的支持预期是两回事。一个库即使完全合法、当前功能也正确，仍可能与十年期系统的维护需求不匹配。

这里首先要区分 API 兼容和 ABI 兼容。API 是源码使用的接口；API 兼容通常关心已有的受支持源码能否继续使用新版。ABI 是应用二进制接口，涉及符号、对象布局和调用约定等；ABI 兼容关心已经编译出的产物能否继续与另一版本配合。源码重新编译后能工作，说明的是 API 兼容；旧目标文件能否直接混入新程序，要看 ABI。

原书用 C++ 标准库和 Java 展示基础设施对长期兼容的重视，用 Go 展示另一种取舍：Go 1 承诺受支持的源码在后续版本继续编译运行，但不保证跨版本编译包的二进制兼容。C++ 的长期兼容也有条件：ABI 是否稳定，实际取决于标准库实现、工具链和编译选项，SD-8 还保留了增加名字、重载等演进空间。兼容总要对应具体承诺和具体用法。

Abseil 的例子强调“可迁移”可以成为契约的一部分。到本书写作时，它不承诺 ABI 稳定，并提出在必须破坏 API 时提供自动化重构工具，尽量把使用者的升级成本降为运行工具、评审补丁。这表达了一种责任分配：提供者最了解为什么改接口，应尽量把这份知识做成迁移能力。现行 Abseil 兼容指南仍不保证 ABI 稳定；破坏性变更改为在提交说明和 LTS 发布说明中公告，并按所遵循的政策处理，不再统一承诺附带自动化工具。

作为对比，原章引用 Boost 的说明：各库持续改进，跨版本兼容不能一概保证。作者借此讨论项目目标与使用方寿命是否匹配，并特意说明这与技术水平无关，只关乎项目承诺什么、优先考虑什么。探索性组件、长期兼容基础设施和提供迁移工具的库，都可能非常优秀；它们把演进成本放在不同位置。

具体到引入决策，原书关心的证据包括能否取得并运行测试、测试是否通过、维护者的可靠性、支持范围、破坏性变更频率，以及组织内是否有人承担升级。这些信息需要连成一个判断。一个流行但无人负责更新的依赖，可能比一个较小、边界清楚且团队熟悉的库更难长期维护；一个实现复杂、维护良好的成熟库，也可能远比临时自研更经济。

假设报表服务要引入日期解析库。团队今天只验证了几个示例日期，未来却要处理新地区、运行时升级和安全修复。如果有人能持续关注上游、保留业务日期样本并在小步升级中运行它们，复用收益便有了延续条件。如果库依赖了团队无法维护的特殊运行环境，这份成本应在深度接入之前进入取舍。功能是否匹配与能否持续维护，需要放在一起判断。

03third_party 的故事里，责任怎样逐渐落空

Google 大量内部依赖由同一组织开发，能够共同搜索、测试和迁移。对于外部项目，原章介绍的做法是把它们放进单仓库的 third_party 目录。这样可以保存并统一构建选定代码，却不会自动获得上游的知识，也不会自动建立持续维护的动力。

原书用 Alice、Bob 和 Charlie 的情境展示这个缺口。Alice 为了在休假前完成演示，找到一个刚好解决问题的开源库。引入流程要求它能够用内部构建系统构建、没有重复版本，并由至少两位工程师登记为 OWNERS。她请同事 Bob 帮忙签上名字。两人接触了接口，却未必研究过实现，也没有练习过升级。眼前任务顺利完成，长期责任已经悄悄成立。

库入库后，其他团队也能使用。Charlie 从重要的搜索基础设施中引入它，随后更多组件通过传递依赖间接使用。Alice 和 Bob 可能根本不知道影响面已经扩大；后来使用它的人，也未必看得到最初维护安排其实只够支撑一次演示。文件位置与所有者名单都没有变化，业务重要性却已完全不同。

稳定还会制造一种误导。几年没有更新，所有调用方都逐渐适应了这一版的具体行为，包括未承诺的排序、错误格式或边界处理。原章把这与 Hyrum 定律联系起来：使用者越多，越容易有人依赖这些细节。与此同时，上游已经积累许多小版本，内部对原始实现的知识却可能越来越少。

等到安全问题迫使升级，Bob 已转向管理工作，Alice 也换了团队，OWNERS 仍是旧名字。大量项目间接依赖该库，不能简单删除；负责应急的人还要跨过多年变化，分辨哪些失败来自上游变更，哪些来自调用方依赖了未承诺行为。升级此时既紧迫，又缺少熟悉路径的人。作者由此指出，这套流程会让“重要”和“无人实际维护”同时发生。

作者提出的改进方向，是提高所有权的实质要求，让定期更新更容易、也更值得做，并减少关键依赖成为孤儿的机会。把这个方向落到前面的报表情境，可靠的维护关系应能回答：谁仍然在使用和理解这个库，升级结果在哪里验证，依赖进入更关键链路后谁会知道。登记姓名只是入口，职责必须在人员变动和使用范围增长后继续成立。

这里的成本不是凭空多出来的。更新工作原本就存在，只是可以分散在常规维护中，也可以一直推迟到安全事件里集中偿还。例行升级还会保留团队的操作记忆：怎样取得新版、怎样判断失败、怎样回退。每次升级未必都简单，但第一次真正尝试升级，就不太会恰好落在最紧急的时刻。

核心观点

把依赖放进仓库，并列出负责人，只完成了引入。持续维护还需要真实的职责、可运行的验证，以及随人员和使用范围变化而更新的安排。

04冻结、求解与打包：版本选择交给谁

介绍完引入成本，原书转向依赖网络的四种治理模型。它们的重要差别，是谁承担寻找兼容组合的工作，以及允许怎样变化。

最简单的是静态依赖模型：选定一份代码以后，假定它不再变化。若初始组合兼容，而且软件真的不需要升级，就没有后续版本选择。对于短期实验和刚起步的项目，这种简化可能十分合理，作者也承认没有必要一开始就建设几十年寿命的维护体系。困难在于，安全问题、平台退出支持或更上层依赖升级，可能结束这段静态时期；事先很难准确知道它会持续多久。

接着是语义化版本（Semantic Versioning，SemVer）。对于已经进入稳定阶段的 X.Y.Z 版本，主版本表示不兼容的公共 API 变化，次版本表示向后兼容的功能增加，补丁版本表示向后兼容的缺陷修复。SemVer 规范要求先声明公共 API，0.y.z 和预发布版本有不同预期。三个数字帮助双方交流变更性质；范围表达式与解析算法则由各包管理生态另外定义。

例如，把“使用 1.5 系列之后、但不跨入下一主版本”明确写成 ≥ 1.5.0 且 < 2.0.0，便能避免把裸写的 ≥ 1.5 误读成自动排除 2.x。应用的依赖图会汇集许多这样的要求；某个库升级后，还可能改用另一组下层依赖。解析器要选出一组满足全部声明约束的版本，若无解就报告冲突。它能处理选择过程，不能保证任何一组要求必然存在共同答案。

一般版本选择确实可能具有很高的最坏情况复杂度。原书脚注引用 Russ Cox 的证明：当包可以声明依赖及具体版本、不同版本可以有不同依赖、依赖必须满足，而且某些版本不能共存时，“是否存在有效安装组合”是 NP 完全问题，在这类一般问题上尚无已知能保证所有输入都高效求解的算法。有些解析器会把版本要求转成布尔条件，交给可满足性（SAT）求解器寻找取值；也有设计通过限制约束形式改变问题本身，后文介绍的 MVS 就是一例。

第三种是捆绑发行模型。像 Linux 发行版那样，由发行维护者挑选一组版本，完成必要补丁、集成和测试，再把整组作为一个发布单位。原来每个应用都要面对的版本组合工作，被汇集到发行者那里；使用者可以说“采用这一版发行集合”，而不必逐项重新协调。各组件不必来自同一时刻，关键是这一组合有人验证和维护。

这种简化依赖一个边界：使用者主要依赖同一发行集合。如果再从另一个来源取入相互冲突的组件，就重新越过了已经验证的组合。发行模型也没有让维护消失，只是让专业角色承担它。本章的第四种模型是 Live at Head：进一步把验证放到变更进入上游之前。

图 21-1 把四种模型并排对照，每一行看寻找兼容组合的工作落在哪一步、由谁承担。从上往下，这份工作发生得越来越早，也越来越集中到专门的角色：静态模型把它推迟到被迫升级，SemVer 交给每个使用方的解析器，捆绑发行交给发行者，Live at Head 交给发起变更的提供者。

理解第四种模型之前，需要先看版本号究竟丢掉了什么信息。

05SemVer 压缩了信息，也留下两种误差

SemVer 有正式的规则与明确的沟通价值。作者称它为有损摘要，指的是人们把复杂变更压成版本类别以后，仍然无法从数字还原所有具体使用方式。解析器能够严格执行声明，却不能仅凭这些声明证明程序实际兼容。

第一种误差是约束过度。书中设想基础库只有 Foo 和 Bar 两个接口，A、B 都只用 Foo。维护者不兼容地修改了 Bar，按规范提高主版本；A、B 的依赖范围仍停在 1.x，于是解析器拒绝 2.x。就这些调用方而言，真正使用的接口没有变化，组合本来可以工作。对整个库只给一个主版本，使没有使用变更接口的人也被拦住。

第二种误差是保护不足。一个补丁修复了实现，公共接口约定没有变化，但日志输出、结果顺序或耗时发生变化。某个使用者恰好解析了日志，或者测试默认无序结果总以某种顺序出现，升级后就会失败。调用方可能超出了受支持用法，提供者也可能漏判了影响；对应用维护者来说，实际失败仍然需要解决。第一章的 Hyrum 定律解释了这些隐含依赖为何会随使用规模增长。

图 21-2 按上下两行阅读。每行从一次变更走到版本声明，再走到调用方的实际情况，箭头表示判断的先后。上行展示“声明不允许，但当前用法可以工作”，下行展示“声明允许，但当前用法会失败”。

把兼容性落实到“哪一批用户、怎样使用”以后，这两种误差就容易理解。删除无人使用的接口，会改变公共 API，却未必破坏当前生态；新增一个函数，看起来只是增加功能，也可能与某个调用方自己补写的同名功能冲突。局部判断很有用，但没有包含整个使用网络。

原章还指出一种激励错位。上游决定破坏接口，通常只承担迁移成本的一小部分；多数间接使用者甚至不知道自己受它影响。若一次主版本提升就可以把后果完全交给下游，维护者未必有足够动力设计平滑迁移。作者因此希望依赖提供者公开长期兼容目标，让“这种改变是否值得”有共同依据，并讨论了不兼容大版本应当拥有新身份的做法。

原书举 Go 与 Clojure 为例：在它们的标准包管理生态里，主版本提升相当于发布一个全新的包。Go Modules 的做法是，在规范要求带主版本后缀的情形中，v2 及后续主版本使用不同模块路径，如 example.com/lib/v2，与旧路径被视为不同模块。这有助于让不兼容版本并存，也把迁移显式化；两边的类型如何互通，仍需另外处理。

作者认为，依赖较少、维护认真、边界细、使用方式受约束时，SemVer 可以很好地服务项目。网络变大以后，每一条边都可能有版本标注错误、过粗粒度或隐含行为依赖，误差会累积。合理的落点是让版本规则处理声明，让测试和维护工作继续处理实际行为。

核心观点

解析成功，说明声明的版本约束得到满足；测试通过，则为特定组合和用法增加行为证据。版本号适合交流与筛选，不能代替后者。

06最小版本选择，只向前走到需要的位置

Russ Cox 在 2018 年提出的 Minimal Version Selection（MVS，最小版本选择），为版本选择换了一个默认方向。若 A 要求基础库至少为 1.7.0，仓库中已经有 1.8.0，普通构建不因“有更新版”就自行取用 1.8.0；它先使用满足当前需求的较低版本，把额外升级留给明确的更新动作。

“最小”容易被误解为在冲突要求中取最旧的那个。实际上，以同一个模块路径为单位，MVS 遍历需求图，汇集遇到的最低版本要求，然后选其中的最高者：这个最高下限，才是同时满足所有下限的最低选择。不同被访问模块版本又可能引出新的要求，因此要继续沿图处理，不能只看应用直接声明的那一层。

下面是一组假设的简化情境；所有版本都属于同一模块路径及兼容主版本，只考虑下限要求，没有替换和排除规则：

依赖图中的要求已知可用更新版为 base 选择的版本
A 要求 ≥ 1.7.0，B 要求 ≥ 1.6.01.8.01.7.0
A 要求 ≥ 1.7.0，B 改为要求 ≥ 1.8.01.9.01.8.0
前一组要求，再显式要求安全修复版 ≥ 1.9.01.10.01.9.0

第一行避免无需要地前进；第二行表明任何一条更高需求都能推动共同版本；第三行表明安全修复应成为明确更新要求，而非等待算法自动发现。若选中的版本继续要求另一个组件升级，那个要求也会参与后续遍历。

作者看重的，是这种选择可能更接近组件作者实际开发和测试时采用的组合。A 写下“至少 1.7.0”，在它确实用该版本开发、进行过测试的前提下，便存在一份弱但有意义的互操作经验。任意跳到今天最新的兼容版本，可能离这份经验更远。更高的共同下限仍会产生新组合，所以 MVS 只是让选择更接近已知组合，整张网仍未必共同测试过。

MVS 的简化还有重要的政策前提：同一模块路径的新版本应遵循向后兼容规则，依赖主要表达最低要求，而不是任意上限与互斥列表。它靠限制问题本身，换来可预测的图遍历。Go 官方参考至今仍按“遍历并记录每个模块的最高要求版本”解释其构建列表。

因此，MVS 与“永远使用旧版”没有关系。团队仍要主动升级、处理漏洞、运行测试并提交新的需求记录。书中把它视为改善版本选择保真度的方向，同时承认当时没有充分的实证证明，它能修复 SemVer 在巨大网络中的全部问题。

07Live at Head，让变更带着下游证据进入

本章最积极的设想，是把主干开发的协作方式扩展到依赖网络：Live at Head，持续跟随共同的当前稳定状态。它试图减少“每个调用方分别选择过去某一版”的组合空间，并让提供者在提交之前了解变更会怎样影响下游。

这个模型有一组很强的条件：依赖提供者能找到足够多的使用者，取得可运行且有信号的测试，把候选变更真正放进下游构建，并愿意因这些失败而调整自己的工作。遇到必须推进的接口或安全变更时，提供者先协助修改调用方，或提供自动迁移工具。对无法直接观察的闭源使用者，迁移工具尤其关键，它承担了向他们传递迁移知识的责任。

原书用不同类型的变更解释这个过程。只改内部实现或提高效率，可能使受影响测试全部通过，便获得一份可以推进的证据；改变可观察接口，可能使许多调用方失败。作者需要评估收益是否值得处理这些影响，并与下游合作完成迁移。把成本尽量放回发起变化的一侧，有助于鼓励容易采用的接口设计，而不是只提高主版本、把碎片留给旁观者。

图 21-3 从左到右读：候选改动进入替换了该依赖的测试环境，持续集成（CI）系统运行下游测试，结果再影响是否提交。虚线表示失败后修复调用方或提供迁移工具，再重新验证；箭头表示验证流程的先后。

这与 Google 的单一版本政策相关，但关注点不同。第十六章的 One-Version要求已有依赖有明确的共同选择，第十八章的外部输入管理要求构建使用可追踪的确定内容；Live at Head 则讨论这个共同选择怎样不断向前。一次构建仍然可以记录精确快照，升级仍然可以受审查、有回退。

受控升级也可以短暂保留新旧版本。通过禁止新增旧版使用、迁移现有调用方并最终删除旧版，组织维持“朝共同版本收敛”的方向。这沿用第十六章的升级过渡约定，并要求实际处理共存期间的命名、类型或运行隔离。一个版本政策减少选择，迁移机制让这项政策在真实变化中可执行。

原书随后用“算力无限”的思想实验追问：比版本数字更好的兼容证据来自哪里？如果能运行受影响下游的测试，就能观察变更与真实用法的相互作用。只要测试仍然通过，就比单凭提供者的估计多了一层经验。若试图测试所有历史版本的全部组合，资源消耗仍然惊人，于是持续测试当前稳定版本，成为简化这一空间的自然方向。

现实还缺少的不只是算力。生态需要反向依赖信息，才能从库找到使用者；需要可自动构建的项目、有意义的测试及可信的失败信号。一个总因无关原因失败的测试，会降低提供者持续响应它的意愿。固定版本的项目也必须允许在专门测试环境中替换成候选依赖，否则测试只会再次验证旧版。

资源有限时，原书建议按下游重要性、测试质量、历史信号和变更风险选择测试。例如内部重构先运行自身和部分重要调用方测试，删除接口或改变行为则扩大范围。这样的抽样能降低风险，但没被运行的用法仍是证据缺口，公开项目样本也代表不了闭源客户。

作者在 2020 年把 Live at Head 视为值得探索的方向：在 Google 这样拥有共同工具、测试与协调权限的边界内，成本高但有效；扩展到整个开源生态，需要新的责任分配和基础设施。可以先采用的部分，是让每次升级携带更具体的验证结果，并由提供者和使用者共同承担迁移。

核心观点

Live at Head 的核心条件是可见性、持续测试和迁移责任。减少版本选择只是结果；没有这些支撑，直接追随最新版本会失去作者设想的安全基础。

08发布 gflags，为什么又约束了自己

依赖关系有两端。自己引入别人的库会承担维护成本，把自己的库发布出去，也会让未来变化遇到另一组利益和使用方式。原章用 gflags 的经历说明，“代码已经公开”与“组织有能力持续支持它”之间的距离。

书中记述，Google 大约在 2006 年开放了 C++ 命令行参数库。当时内部还不擅长大规模重构，不能轻松把广泛使用的库搬到新的位置；内部代码管理又区分自有代码与具有不同许可、法律处理要求的外部代码。开放项目接受外部贡献后，贡献者的权利并不会自动变成 Google 的完整所有权。在当时这套内部安排下，外部补丁难以直接回到原始内部版本，两个版本于是逐渐分叉。

最初，维持同步或许还能依靠贡献者的热情。后来组织的工作重点逐渐集中于内部工具链和生产环境，面向外部多个平台的可移植性支持越来越难维持。原作者和支持者换了岗位，也没有一支团队把维护外部版本列为明确职责。外部版本因此长期缺少内部投入，后来由外部开发者分叉并认真维护。

声誉成本之外，还出现了技术上的回传。某些需要同时在 Google 内外构建的项目，找到了两份参数库都支持的公共子集，长期在不同环境切换不同版本。大约 2008—2017 年间，这种共同子集相对稳定，逐渐成了事实上的跨环境接口，尽管没有人明确承诺两份分叉会一直等价。

随后，内部 C++ 库团队为优化而调整一些可观察、但未正式承诺的实现细节。依赖两份库等价的项目突然无法照常构建和发布，优化也因这些项目而延迟。原章用这个结果说明：即使内部绝大多数调用方都能统一修改，少数跨组织、跨分叉的用户也可能形成另一条约束。主仓库里的可见调用关系，没有完整表达外部世界的依赖。

对外发布因而需要持续支持的计划和组织授权。落到实处，可以归纳为几个问题：谁接收贡献，怎样同步内外版本，在哪些平台验证，以及何时结束支持。真正重要的是，组织愿意为自己邀请他人形成的依赖关系持续投入。代码本身很好，仍可能因为没人维护社区和升级路径而损害双方。

09AppEngine：外部承诺怎样传回内部

AppEngine 的历史案例把这种约束推到付费服务。原章介绍，早期 Python 运行环境使用较旧解释器和 32 位构建，底层服务仍由 Google 内部的 Python、C++ 和共同构建工具支撑。内部源码处于单仓库，并没有使客户应用也处于同一个可共同修改的边界内。

2014 年，Google 开始一次较大的 Python 运行时升级，同时更新 C++ 编译器和标准库。这两项升级在技术上被绑定在一起：升级到当前 C++ 工具链，也意味着采用更新的 Python 运行环境。对于大多数内部项目，平台专家处理少量问题后就能向前推进；对 AppEngine 客户，变化却涉及他们自己的应用、升级安排和成本。

部分客户不愿或无法更新 Python，部分客户无法接受从 32 位迁到 64 位 Python 所带来的资源消耗变化。客户中有重要付费用户，AppEngine 因而有足够强的业务理由延迟强制迁移。

这个决定沿依赖关系传回内部：AppEngine 所需的整片传递 C++ 依赖都必须继续兼容旧编译器与标准库。底层团队即使已经准备好采用新版工具链能力，也要保留旧环境可用性。原章记述，这种状态持续了接近三年。受约束的是实现该服务所依赖的整个基础设施范围，而不只是面向客户的接口文件。

约束是这样产生的：客户首先依赖一个能够满足其应用和成本的运行环境；运行环境与内部工具链耦合；业务上又无法强制客户同时升级。三件事连接起来，便让外部承诺影响到原本属于内部实现的选择。若只查看公开 API 的参数和返回值，会漏掉这条路径。

作者并不因此反对对外提供服务或开源。他提醒组织，在对外提供能力时，把兼容期限、使用范围、升级方式与维护投入一起考虑。依赖使用者不能随意要求世界永不变化，提供者也不能假定内部修改方便，就能让未知外部用户同步迁移。双方不同的时间表，需要由真实的支持安排承接。

核心观点

对外提供依赖，会把别人的业务和时间表带进自己的演进空间。明确承诺，并使实现与升级路径能够承担这些承诺，是发布软件的一部分。

贯穿本章的线索是，把隐藏的成本和证据带回决策。引入时看清长期契约，使用中让维护责任持续成立，升级时区分声明满足与行为兼容，发布时理解外部承诺怎样约束内部。SemVer、发行集合、MVS 和 Live at Head 以不同方式分配这些工作；真正可靠的依赖关系，仍要靠清楚的支持边界、可执行的迁移和不断积累的验证来维持。

补充核查与表述澄清：

  • SemVer 的范围表达：原章用 ≥ 1.5 同时表达不跨主版本的预期 → 裸下限本身不含这个上界，而 SemVer 2.0.0 只规定版本号的含义，不定义范围表达与选版算法（原章脚注 6 也有说明）→ 本文显式写出 < 2.0.0，并把版本语义、生态的范围约束和求解器分开讲；补丁号按规范表示向后兼容的缺陷修复。
  • NP 完全结论的前提：原章概括许多包管理生态由 SemVer SAT 求解器支撑，并引用 NP 完全结论 → Cox 的 Version SAT 证明的是特定一般约束模型（可声明具体版本依赖、不同版本依赖不同、某些版本不能共存）下的判定问题，Minimal Version Selection 则刻意限制约束、改用图遍历 → 本文只在该模型前提下使用 NP 完全结论，也不把所有包管理器描述为通用 SAT 求解器。
  • C++ 与 Go 的二进制兼容：原章对 C++ 标准库长期 ABI 兼容的概括较强 → SD-8 保留了具体接口的演进权利，GCC libstdc++ ABI Policy 说明兼容取决于编译器、库版本及编译选项 → 正文写明 C++ 的 ABI 稳定有条件。Go 的源码兼容承诺、例外以及不保证跨版本编译包 ABI，依据 Go 1 compatibility。
  • Abseil 的兼容承诺：原章称 Abseil 破坏 API 时会同时提供自动化重构工具 → 现行 Abseil Compatibility Guidelines 区分 API 与 ABI，声明 ABI 可随时变化，破坏性 API 变更在提交说明和 LTS 发布说明中公告，并遵循其链接的 OSS Library Breaking Change Policy 等政策，没有统一的“必附工具”承诺 → 正文把附带工具保留为原书写作时的说法；该外部政策只适用于明确加入的项目。
  • 多版本隔离：原章对类型问题措辞较强 → Maven Shade Plugin 的 Relocating Classes 明确支持移动类并改写字节码 → 本文把难点放在跨边界的类型身份和语义上，类本身可以重定位。
  • Go 的 MVS 与模块身份：依据 Go Modules Reference 的 MVS 及主版本后缀，MVS 取遍历中遇到的最高的最低要求版本，不自动取最新版，也不自动识别或修复安全漏洞。
