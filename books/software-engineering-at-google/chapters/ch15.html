READING NOTES / CHAPTER 15

第 15 章｜弃用

Deprecation · 架构提升读书笔记

软件并不会像机械零件一样磨损，但它所处的环境一直在变化：依赖库更新，语言和运行平台演进，原先合适的实现也可能逐渐变成维护负担。发布替代系统，只完成了变化的一半；旧系统仍有人使用时，组织还要同时承担两套代码、运行环境和知识体系。

本章把弃用（deprecation）理解为一个完整过程：有序地把使用者迁走，最终移除已经过时的系统。它可以小到一个函数，也可以大到一整套软件栈。Hyrum Wright 主要讨论维护者能够了解使用情况的内部技术系统，并坦承 Google 当时也仍在摸索。值得学习的是，怎样把“以后要删掉”变成有依据、有人负责、能够逐步完成的工程工作。

01保留有用的能力，减少持续付出的代价

原书提出“代码是负担，而非资产”，随后专门解释了这句话：真正为用户创造价值的是功能，代码是实现功能的手段。代码需要被阅读、测试、升级和运行；相同功能若能由更简单、易懂的实现提供，组织便可以少承担一些长期成本。作者因此主张，与其关注写了多少代码，不如关注每单位代码能交付多少功能。

这些成本有些很容易看见，例如服务器资源、值班安排和安全更新；有些则散落在日常工作中，例如新人需要判断应该调用哪个接口，工程师排查问题时需要同时理解新旧两套行为。即使系统暂时没有故障，这些支出也一直在发生。

旧系统与新系统长期并存，还会产生它们各自之外的成本。原书描述了一种逐渐变复杂的局面：业务代码开始使用新系统，某个底层依赖却仍使用旧系统，于是两者之间需要转换逻辑。以后任一系统变化，转换逻辑也要维护；如果双方又开始互相依赖，拆除工作会更加困难。新系统还可能为了兼容旧行为，迟迟无法简化自己的设计。

用一个假设情境来理解：报表平台已经有了按日结算快照生成文件的新服务，但旧导出库仍接受实时查询。一部分报表调用新服务，一部分公共组件继续调用旧库。平台团队因此既要维护两条数据路径，也要向使用者解释“同一天的结果为什么不同”。只上线新服务，这些结果分歧和排查成本并不会消失；把确有需要的报表迁到合适的新路径，才可能真正收回这部分支出。

不过，系统年龄本身不是弃用理由。原书以经过几十年改进的 LaTeX 排版系统说明：成熟而稳定的系统可能仍然很好地满足需要。弃用更适合有证据表明已经过时、又存在可承担相应功能的替代方案的系统。判断时应比较继续维护与迁移移除两条路径的整体代价，而不能仅凭技术新旧作决定。

组织同时承受变化的能力也有限。原书把这比作道路翻修：所有道路一起封闭，即使每条路最终都会变好，当下的交通也无法继续。维护团队和使用团队都有自己的工作，选择少数值得做的弃用项目、投入资源并把它们完成，往往比同时宣布大量迁移更有效。

核心观点

弃用的收益，是在保留所需能力的同时，减少维护、兼容和理解系统的持续成本。评估时既要看到旧系统的支出，也要把迁移和移除本身的支出算进去。

02最难迁走的，往往是没有写出的约定

第一章的 Hyrum 定律在这里尤其重要：使用者足够多时，可观察到的行为就可能被某个人依赖。旧接口的返回顺序、错误文本、延迟特征，甚至本来只供内部使用的符号，都可能已经进入其他系统的实际工作方式。移除是最彻底的一种行为变化，它会把这些依赖集中暴露出来。

替代系统通常提供相同用途，却未必提供逐项相同的行为。新系统可能通过不同的错误处理、更严格的输入约束或新的数据模型获得改进。正因为两者有差异，迁移就需要理解调用者原来依赖什么，而不只是找到名字相似的新函数。

继续看假设的报表平台。旧库把“尚未结算”和“确实没有记录”都表示为空列表，有个调用方据此生成空文件，并把任务标记为成功。新服务区分了这两种状态：前者要求等待，后者才允许生成空报表。机械地把旧调用替换成新调用，无法决定业务遇到等待状态时应怎样继续。迁移者需要和报表负责人一起确认：什么时间点算完成，等待后怎样重试，以及测试如何表达这项约定。

这个差异也可能改变原来的弃用判断。如果调查发现新服务尚不能满足一项重要业务需求，就需要补齐能力、调整迁移范围，或重新考虑替代路径。原章把发现使用情况视为贯穿过程的工作，正因为新信息有时会改变决定，而不仅仅增加待修改文件的数量。

技术之外，工程师还可能对自己多年建设的系统产生感情。书中记录过清理旧代码时遇到“我喜欢这段代码”的阻力。Google 的一个应对办法，是让代码搜索支持历史版本：退出当前代码库，不会抹去过去的设计和贡献；需要参考时，仍能找回历史实现。这让保留知识与继续运行旧系统可以分开处理。

资金和优先级也会放大困难。安排迁移团队要立刻占用人力，继续保留旧系统的成本却分散在各处，容易被当成现状。第七章关于生产力测量的思路在此仍然适用：先说清哪项决定会被证据改变，再收集运行支出、重复排查或兼容负担等相关信息，让是否迁移成为可以讨论的取舍。

这也解释了原书为什么倾向于在可能时原地演进。一次完整替换，会把接口差异、调用方修改和最终关停集中到同一个项目里，其成本常被低估。逐步重构现有系统，则可以先替换一个内部组件，交付一部分收益，再处理下一部分。弃用工作仍然存在，只是被拆成更容易理解、验证和完成的变化。

03系统刚开始建设，就已经有了生命周期责任

原书用核电站设计作对照：这类工程会在建设阶段考虑最终退役，连相关资金安排也纳入视野。借到软件工程中的，是把退出当成生命周期一部分的思路。语言、架构、依赖组织、团队安排和公司政策，都会影响一个系统将来能否被替换。

作者建议设计者考虑两件事：使用者迁往潜在替代方案是否容易，以及系统内部能否逐块替换。它们共同指向依赖边界。调用者直接依赖大量实现细节时，未来即使功能没有变化，也可能需要跨许多团队修改；依赖集中在清楚的接口上时，内部更换组件通常更容易控制。

在假设的报表系统中，可以让调用者表达“为某个统计日生成报表”，由服务内部决定怎样读取快照和生成文件，而不是要求各业务团队直接拼接旧存储路径、识别内部文件名。未来更换存储或生成引擎时，许多调用者便可以保持原有意图，只由少数边界承担变化。做到这一点靠的是清楚的接口，不必为尚未出现的后端预先搭建复杂框架。

设计中的另一项责任是明确长期安排。一旦系统已经存在，组织大致只能选择继续支持、有序弃用，或让它在某次外部变化后失效。最后一条路径也会发生真实后果：依赖平台停止维护、原维护者离开，都可能使先前未作出的退出决定，以故障的形式出现。不同组织会有不同取舍，但建设时便应承认，系统发布以后还有一段需要承担的工作。

原章还描述了一个困扰使用者的局面：旧方案已经被宣布弃用，新方案却仍然差一点才能使用。清晰文档、迁移指引和能够答疑的专家，可以降低这种不确定性；更根本的前提，是对替代方案的可用性和支持责任作出真实承诺。让使用者知道今天应当选什么，比只描绘新架构的最终形态更有帮助。

04从建议迁移，到承担完成迁移的责任

原书把弃用看成连续谱，并区分出两类典型方式。建议性弃用（advisory deprecation）没有明确的移除期限，组织也尚未投入专门资源推动全面迁移；它主要告诉使用者，已有更值得选择的替代方案。强制性弃用（compulsory deprecation）通常有最终移除日期，届时仍然依赖旧系统的调用方可能停止工作。

建议性弃用适合介绍新方案、吸引愿意先行迁移的团队。即使采用这种较温和的方式，原书也要求新系统已经能够承担生产用途和负载，并准备长期支持新使用者。旧系统一旦以任何方式被宣布弃用，新系统就会成为组织的关键基础设施，不能再按测试版对待。

当新方案为使用者带来显著收益时，通知加自助迁移工具可以产生较强吸引力。例如在假设的报表平台里，新服务若能解决业务一直受困的超大报表导出问题，相关团队就有自己的迁移动机。反过来，如果改善主要是平台团队维护更轻松，调用方原来的流程又运行正常，那么对方主动改变的收益很小。仅靠一则通知，很难让这项工作排到业务功能之前。

原书还指出，旧系统的既有用法会形成一种引力。工程师搜索示例、复制邻近实现或沿用熟悉工具时，仍然容易选择旧方案。增加一条弃用说明，可以减少部分新增使用，却很少使已有调用自然消失。建议性弃用有它的用途，但全面移除通常需要更主动的安排。

强制性弃用因而需要同时具备权限与资源。负责推进的团队应获得执行最终移除的授权；时间表可以根据事实调整，但不能让每个调用方都通过无限推迟来否决整个项目。与此同时，迁移团队要实际帮助使用者完成工作。只有期限、没有执行人力，会让客户团队感到自己被要求额外投入，只为维持原先就能完成的事情，合作也容易变成相互推诿。

集中迁移专长，是原书认为可扩展的做法。让负责移除旧系统的团队反复处理同一类迁移，可以积累语义差异、修改工具和验证经验。相同问题不必由每个业务团队从头研究，专家也更有动力消除最终剩余的障碍。调用方仍需参与业务判断和评审，但迁移的共性成本由专门团队承担。

图 15-1 把本节的三种安排放在一起：只发弃用通知、只下期限，以及期限配齐授权和迁移团队。前两种安排下旧系统都留在原处，只有第三种能让迁移持续到旧系统可以移除。

最后一个使用者如果恰好是全组织依赖的关键基础设施，期限的可信度就会受到考验。原书用这个情境说明：政策上的“强制”并不能自动消除组织约束。要让最后一段工作可完成，就要及早发现这类关键依赖，并与有权安排其工作的负责人共同制定计划。

核心观点

强制性弃用要配套能够执行的期限、明确授权和持续到完成的迁移投入。把迁移专长集中起来，再与调用方协作，比让所有团队各自摸索更容易形成可重复的进展。

05把警告送到能够采取行动的地方

弃用警告是一种沟通渠道，价值取决于它促成了什么行动。原书举出依赖链 A → B → C：A 的构建过程中出现了 C 的警告，而 A 的维护者可能只直接使用 B。警告随着间接依赖不断上浮，用户反复看见相同消息，却未必有条件修改真正的调用点，最终容易把整片警告都当成背景噪声。医疗领域把这种现象称为“告警疲劳”（alert fatigue）。

作者为有用的警告提出两个条件：可行动性（actionability）与相关性（relevance）。可行动，意味着在通常可以期待的知识水平下，收到消息的人确实能执行下一步。只说“此接口已弃用”，没有说明使用位置、替代方案和迁移方式，仍然把调查工作留给了对方。

以假设的报表迁移说明，一条更有帮助的信息可以指出：“此处调用旧实时导出接口；按统计日导出请使用快照服务。新服务会区分未结算与空结果，迁移说明给出了相应处理方式。”这条消息让作者知道要改哪里、改到哪里，以及哪些行为需要另作处理。若可以自动完成等价替换，工具还可以给出可评审的修复；需要业务选择的部分则保留明确说明。

相关性进一步关心信息出现的时间和工作上下文。工程师刚写下旧接口调用、正在提交评审时，修改最自然；几周后再收到一批历史警告，往往需要重新理解代码。数据迁移邮件最好在旧系统移除前几个月发出，等到关停前的周末才补发就太晚了。可行动性回答“我能做什么”，相关性让这个行动能进入当前的工作。

书中描述的 Google 做法，是广泛标记旧接口，再通过 Error Prone、clang-tidy 等工具有针对性地展示信息，例如只对新修改的行提示旧符号用法。这样可以阻止新增引用，而不要求每个路过旧代码的工程师同时清理全部历史问题。更有干扰性的依赖目标警告，只在强制性弃用、且团队正主动迁移使用者时才添加。

图 15-2 对照了警告的两种去向：随依赖链上浮的警告，落在无从下手的人面前；定向提示则出现在作者正在修改的那一行。

这与第八章的自动执行形成同一条思路：把反馈放到正在工作的入口，降低正确操作的成本。警告负责引导或拦住新增使用；已有调用的调查与迁移，仍然要进入有人负责的项目。

06沿着静态关系与真实运行，找到剩余依赖

原章把弃用工具分成发现、迁移和防止回退三类。发现工具要回答的，除了旧系统还有多少调用，还有谁在使用、怎样使用，以及哪些行为无法直接替换。这份认识在开工时用于估算范围，在推进中用于衡量剩余工作，也可能带来重新评估弃用决定的新证据。

静态分析从代码和构建关系入手。书中提到 Code Search 与 Kythe：前者帮助查找实际使用，后者提供代码语义与交叉引用等信息，使维护者能够沿符号关系了解调用方。对远程服务而言，调用通常也要经过客户端库或一层薄封装，因此静态关系仍然能提供不少线索。抽样阅读实际调用，则有助于分辨表面相同的 API 使用背后，有没有不同的业务约定。

运行关系还需要日志和生产采样补充。配置产生的服务地址、动态加载的组件以及不同时间才会运行的任务，可能无法仅凭显眼的函数调用看清。回到假设的报表平台：网页已经迁到新服务，但月末结算任务仍通过一份配置访问旧导出服务。只搜索网页仓库，或者只观察普通工作日的流量，都可能误以为旧系统已经无人使用。

Google 的单仓库和依赖图提供了很强的可见性，原书仍然强调未知依赖的存在。一种主动发现方式，是在最终关停前安排已通知使用者的临时停用，逐渐增加持续时间和频率，观察哪些系统受到影响。这与灾难恢复测试 DiRT 的思路相近：把“有一天依赖会不可用”提前变成一次能够处理的观察。

这类停用通常安排在关停前的数月和数周。临时停用暴露出依赖后，相关团队就有机会准备迁移，也可以依据实际困难与弃用团队协商时间表。Google 有时还会改变仅供实现使用的符号名称，观察哪些使用者意外依赖了它。这里的收益是获取真实依赖的信息；信息若表明影响比预期更大，就应反馈到迁移安排中。

对于假设的月末任务，短时停用若没有覆盖它的执行窗口，就不会带来证据。这个例子提醒我们，把观测时间与实际业务周期对齐，才能解释“没有发现失败”的含义。实际运用这类停用时，团队还需事先约定可接受的影响范围、监测和恢复方式。

全局测试套件提供另一层反馈。原书把它作为移除旧符号和防止意外行为变化的重要判断依据，并要求调用方用足够的测试表达自身需要。静态关系、测试结果和运行观测各自提供证据：测试能够揭示已表达的需求，真实调用还能帮助发现测试没有表达的依赖。它们配合起来，才使最终移除不必完全依赖维护者的记忆。

07迁走存量的同时，让新增使用无法悄悄回来

发现使用者以后，迁移工具把认识转化为代码变更。原书提到代码生成、代码评审与大规模变更工具，可以成批地把调用更新到新库或新服务。迁移团队由此把已经理解的改动方式重复应用，再通过评审和测试确认它们适合具体调用方。

在假设的报表平台里，可以先把调用按行为分类：已经按统计日工作的报表，可能适合直接改用快照接口；依赖实时查询的报表，则需要先确认产品语义；确实无人使用的导出路径，可以评审后删除。这样分类，是为了让机械修改覆盖真正等价的部分，让需要判断的少数情况尽早显露出来。

但只清理存量还不够。工程师仍可能从旧示例复制调用，或因为熟悉旧库而重新添加依赖。假设一轮迁走三个调用方，同时又新增三个，团队虽然完成了不少变更，距离关停却没有更近。原书把这种反复比作打地鼠：持续消耗人力，也削弱迁移团队的士气。

在细粒度上，Google 利用 Tricorder 静态分析框架，在评审时提示新增的弃用符号调用，并给出替代方向，部分情况还支持一键修复。接口维护者通过弃用标记控制消息，工具负责把消息送到变更作者。在 Java 里，这个标记是 @Deprecated 注解；小写的 @deprecated 是 Javadoc 标签，用来说明弃用原因和推荐替代（原章把注解写成了小写，纠正见文末）。

在更大的依赖边界上，原书使用构建系统的可见性允许列表（visibility whitelist）：只有已经列入的调用方，才能继续依赖待移除目标。迁移一个调用方，就从列表中移除它。新项目无法加入旧依赖，已经迁走的项目也不能不经察觉地重新接回去。

这形成一种只向退出方向收紧的机制。允许列表最初为现有使用保留过渡空间，之后随迁移持续缩小；最终清零，才具备删除目标的一项重要条件。它约束的是构建依赖，运行中的间接访问仍需前一节的观测。把边界规则与调用点提示放在一起，才既照顾具体代码作者，也控制整个系统继续扩散的方向。

核心观点

稳定推进弃用，需要同时减少已有依赖并限制新增依赖。调用点的及时反馈，加上会随迁移收缩的接入许可，可以把一次次修改积累成不容易倒退的进展。

08让退出成为有人负责、能够看见进展的项目

原书强调，弃用需要明确的流程负责人。系统维护者熟悉旧实现，但盘点使用者、安排迁移、协调阻塞和执行最终移除，需要有人明确负责。没有这项责任，发出更多警告也很难使剩余工作自然消失。

这种问题在被遗弃的项目中尤其突出。原来的团队已经转去建设下一代系统，旧系统仍在运行，并且还是某个关键项目的依赖。它看起来只剩一点维护，实际上已经失去持续作决定的人。此时仍需安排掌握迁移和清理能力的负责人，把安全退出作为明确目标，而不是默认交给一个随时会被新功能挤走的顺带任务。

在假设的报表平台里，退出负责人可以维护一份随调查更新的调用方记录，把每个阻塞接到具体团队和下一步行动。迁移专家处理共性改写与验证，报表负责人确认数据口径，平台负责人安排旧服务的停用。这样，一项“某报表暂时还不能迁”的说明，就能进一步落到等待状态处理尚未实现、哪个团队负责补齐，以及何时重新验证，而不只是留下一个永远存在的例外。

里程碑也应有自己的设计。新系统不断增加可见功能，旧系统的退出却容易被简化成一个终点：彻底关停。原书提醒，若迁移做得足够好，真正关停时已经没有用户，它反而可能是最少被外界注意的一刻。仅以这个终点评价团队，会使漫长的过程看起来毫无成果；有些项目还可能因新情况暂时无法到达终点。

原书建议设置可测量、能交付增量价值的里程碑，例如删除一个关键子组件。沿着假设平台的工作，可以把不再需要旧文件转换器、收回一部分运行资源、迁走一个具有独特语义的报表类别视为阶段成果。相比“已经改了很多文件”，这些变化说明维护负担减少在了哪里，也更容易判断剩余工作是什么。

最终收尾仍需要把技术与责任接起来。把前文串起来，收尾大致包括：确认替代路径已经承担所需工作，清理剩余调用与接入许可，再按约定移除旧代码和运行资源，并更新使用说明。代码历史负责留下过去的知识，当前系统只保留仍有必要支持的部分。退出负责人也由此有一个可以被共同确认的完成状态。

核心观点

弃用项目的进展，应体现为真实依赖和维护负担逐步减少。明确负责人、承认增量成果，并把最后的代码、运行资源与说明一起收尾，才能让“准备退休”变成已经完成的工作。

把本章连起来看，长期维护并不止于建设和运行系统，也包括在合适的时候移除系统。判断哪些能力值得保留，理解使用者真正依赖的行为，投入迁移资源，再用工具防止旧依赖重新扩散，才能使软件生态在增长之外，也具备有序变简单的能力。
