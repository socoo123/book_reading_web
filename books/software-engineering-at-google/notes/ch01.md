# 第 1 章｜什么是软件工程？

**What Is Software Engineering? · 架构提升读书笔记**

一段代码写完以后，往往还要经历需求变化、依赖升级和人员交接。软件工程关注的，就是让它在需要的时间里持续有用，并让团队能够共同维护。第一章从时间、规模和权衡三个角度展开：时间带来变化，规模放大变化的成本，权衡则决定我们怎样投入有限的资源。

Google 用一个简洁的说法来概括这种区别：把编程放到时间中去考虑。编程产生一个能工作的版本，软件工程还要让后面的版本有机会继续工作。为此，测试、文档、评审、工具和组织政策会成为软件的一部分：它们决定后来的人能否理解现状、发现影响，并安全地完成改变。

这些安排应当与任务相称。一个下午就会完成使命的脚本，与计划运行十年的服务，面对的约束很不一样。本章讨论的价值，在于帮助我们看清这些约束怎样形成，再选择合适的投入，而不是把大型组织的全部做法搬到每一个项目中。

<a id="sustainability"></a>

## 01　把时间算进软件

理解这个问题，可以先看代码预计要用多久。这里的寿命是**维护寿命（maintenance lifetime）**，也就是它还会被构建、运行和维护多久，不是某一次进程运行了多少秒。一次性的数据处理程序，完成任务便结束；同一段程序若被保存下来，变成每月必须运行的结算任务，它的维护寿命就已经改变了。

书中把几分钟的一次性代码，与 Google Search、Linux 内核、Apache HTTP Server 这类难以预见终点的项目放在同一条寿命谱系上。短任务通常可以把当前环境视作已知条件：在脚本完成前，操作系统和语言运行时大概都不会变化。长期服务则需要经历多轮依赖升级、硬件替换和产品调整，今天成立的条件只能覆盖其中一段时间。

这也解释了为什么“已有十年开发经验”与“维护过一个十年项目”会产生不同经验。不断为早期产品写出新版本，能锻炼快速验证和交付；让同一套系统穿过多个技术周期，还会遇到旧数据、兼容行为、迁移顺序和团队交接。书中并不把两者排成高低，而是提醒读者，适合的实践取决于实际问题。早期公司把资源先用于验证产品，可能正是当时合理的选择。

书中把**可持续性（sustainability）**概括为：在软件的预期寿命内，团队有能力响应有价值的技术或业务变化。这里保留的是选择能力。新版本收益不大时，可以暂缓升级；当安全修复、依赖停止维护或业务方向改变使升级变得必要时，团队仍然有办法完成它。若系统已经无法修改，就只能寄望于外部世界一直不提出新的要求。

第一次升级常常特别痛苦，因为三个问题会叠加。项目从未走过这条路，许多隐含假设没有被发现；负责升级的人缺少经验，要一边学习一边排查；拖延多年又把原本可以逐步处理的差异压到同一次迁移中。一次代价很高的升级之后，团队容易得出“以后再也不升级”的结论，却把首次摸索的成本误认为每次都必然付出的成本。

更有建设性的方向，是把必要变化逐渐变成可重复的工作。每次处理较小的跨度，留下验证和恢复办法，把重复步骤交给工具。这样，今天的升级也在改善下一次升级的条件。后面编译器升级的案例，会具体展示这种能力怎样积累起来。

即使业务需求稳定，外部变化仍可能让维护产生价值。原章用 Heartbleed、Meltdown 和 Spectre 等安全问题说明，风险可以来自应用下面的网络库、处理器及其他依赖。性能机会也类似：链表和二叉搜索树在新机器上仍能运行，但处理器速度、内存延迟和缓存特征变化后，当年的高效方案未必仍然合适。向后兼容保证“还能工作”，并不保证“仍然划算”。

> **核心观点**
>
> 可持续性是在预期寿命内保留改变的能力。维护投入既要考虑这次变化的收益，也要考虑它能否降低以后必要变化的成本。

<a id="hyrum"></a>

## 02　依赖会长到接口之外

**Hyrum 定律**揭示了变化为什么会牵动许多人：一个 API，也就是程序之间的接口，只要使用者足够多，系统可观察到的各种行为，最终都会被某些人依赖。接口文档写出的承诺称为接口契约，而实际依赖还会延伸到返回顺序、错误文本等细节。

这条定律描述的是维护者会遇到的现实。一项行为只要能被看到，又恰好方便使用，就可能被写进另一段程序。即使接口文档明确说某个细节不作保证，已经存在的依赖也不会自动消失。评审和文档能够减少问题，升级时仍要为调查、识别和修复实际影响留下成本。

书中以**哈希容器的遍历顺序**为例。容器可能只承诺保存哪些元素，没有承诺这些元素以什么顺序出现。开发者在当前环境中反复观察到同一排列，便可能把它写进输出文件，或者直接保存成测试的预期结果。这个程序今天能够通过测试，证明的只是当前实现碰巧满足了额外假设。

后来，容器实现可能为了性能改用另一种哈希算法，也可能调整布局或引入安全措施，遍历结果便随之变化。原章提到的哈希洪泛攻击，是攻击者构造大量碰撞输入，使哈希表操作严重变慢的拒绝服务手段。更难预测的哈希机制可以帮助抵御这类攻击，同时可能改变遍历顺序；单纯把输出顺序打乱，并不等于解决了碰撞问题。

依赖还会沿数据路径传播。顺着原书的远程过程调用（RPC）例子，可以设想一个库先把集合序列化为响应数组，再发给另一个服务。库内部没有按位置读取元素，远端测试却把收到的数组逐项与旧快照比较。更换容器后，成员完全相同，数组位置发生变化，下游仍会报错。维护者需要追踪到这个调用方，才能看见真正需要调整的假设。

![哈希容器的遍历顺序进入响应数组，再被下游按位置比较；内部实现细节因此成为跨服务的隐含依赖。](../diagrams/exports/ch01-observable-dependency.svg)

图 1-1：箭头表示排列沿数据路径传播。本例只承诺成员内容，调用方却观察并依赖了排列；改变内部实现时，影响会出现在远端。点击[查看大图](../diagrams/exports/ch01-observable-dependency.svg)。

处理这种问题，需要先明确顺序是否属于业务要求。若接口只表示一个无序集合，测试就应比较成员；若响应必须有稳定顺序，提供方应明确排序规则，并把规则纳入契约。下面是笔记补充的 Python 小例子：假设接口约定按这几个英文名称的字典序返回，就显式排序，而不借用集合当前的遍历顺序。

```python
names = {"carrot", "apple", "banana"}
response = sorted(names)
assert response == ["apple", "banana", "carrot"]
```

这里使用的是不承诺遍历顺序的 `set`。Python 的 `dict` 从 3.7 起已经保证插入顺序，不能把所有基于哈希实现的容器统称为“无序”；应查看具体类型的契约。即使使用有序字典，插入顺序与业务要求的排序也仍是两种约定。

原章还给出一个有意思的后续：有的程序会把随机化的哈希遍历顺序当成一种低效的随机数来源。于是，连“顺序会变化”也可能被依赖。以 Python 为例，`str`、`bytes` 的默认哈希随机化在同一进程内保持固定，进程间不可预测，集合遍历并不提供可靠随机抽样的保证。长期维护的重点，是尽量让依赖落在明确、合适的抽象上，并让真实用法可见。这样，当安全性或性能使某种变化值得做时，团队才能估计代价并组织迁移。

<a id="scale"></a>

## 03　让重复工作跟得上规模

随着使用者和代码增多，一次变化还会成为组织问题。这里的**规模（scale）**既包括软件服务多少请求，也包括有多少人开发、多少代码需要维护，以及这些人靠什么流程一起工作。一个生产系统能承受流量增长，开发这个系统的方法却可能越来越难以承受。

构建、测试、取得一份代码、升级语言都需要反复进行。如果代码库增长后，每位工程师都要等待更久、处理更多维护通知，新增人力的一部分就会被这些负担吃掉。测试集群的计算消耗、版本库历史和构建依赖也会不断累积。原章特别提醒，这些问题通常缓慢恶化，没有某一天突然宣布“从此不可扩展”；团队需要留意长期趋势。

可持续性因此还包含经济条件：一件事理论上能做，但每次都需要难以承担的人力，它通常会被推迟。对重复发生的人力工作，原章总结要求投入按线性或更好的方式扩展；对每个人而言，则应尽量避免组织扩大就带来更多维护负担。计算和存储资源的消耗还要分别观察。规模越大，一次自动化、一次集中学习或一个公共工具能够惠及的工作越多。

迁移很能说明问题。原章设想，基础设施团队推出新版组件，宣布旧版将在某天删除，要求所有使用者各自完成转换。在小团队中，一条消息也许就能解决；依赖图变宽、变深后，每个团队会同时收到许多此类通知。它们都要理解升级理由、学习新接口、寻找调用点并安排验证，一处遗漏还可能使更多下游无法构建。

为减少这种反复消耗，Google 在 2012 年推行 **Churn Rule**，由基础设施团队负责迁移内部使用者，或者以向后兼容的方式原地更新。

集中迁移把工作重新组织了一次：少数人深入理解变化，识别常见形式，建立修改和验证办法，再把这些认识用于多个使用方。同一类问题不必在每个团队重新摸索，迁移中发现的特殊情况也能反馈到公共方法里。原章强调，专家经验能复用，比让每个用户临时学习、修好眼前一处、随后丢下这些知识，更容易获得规模收益。

![分散迁移时，多个团队分别学习并修改；集中迁移时，专家组深入理解一次，再把可复用方法应用到多个使用方。](../diagrams/exports/ch01-migration-expertise.svg)

图 1-2：上半部表示重复发生的学习与实施，下半部箭头表示方法复用和迁移覆盖。集中承担并未消除逐处修改与验证，而是减少重复摸索。点击[查看大图](../diagrams/exports/ch01-migration-expertise.svg)。

这种安排需要代码可见、跨团队修改有明确规则，并有可用的验证基础。产品团队仍要解释特殊业务约束，基础设施团队则承担推动变化的责任。具体迁移过程在[第十五章的弃用](ch15.md)和[第二十二章的大规模变更](ch22.md)中进一步展开；这里先抓住工作如何分配的区别。

原章还把长期开发分支作为另一个例子。为了减少主干波动，各团队把功能分开开发，等完成后才合并；每次合并又要求其他分支重新同步和测试。分支少时还可以人工协调，团队和分支数量增加后，同一项开发工作会附带越来越多整合开销。[第十六章](ch16.md)讨论的短分支与单一版本，正是在处理这一类成本。

规模也能放大有利因素。一个愿意在公共论坛回答问题的 Java 专家，可以帮助许多人跨过相同的障碍，并逐渐培养出新的专家。知识在共享空间留下来，后来者就能继续复用。[第三章](ch03.md)会把这种共享能力展开。工具、专家和政策的共同作用，是让组织增长时，经验也能一起增长。

> **核心观点**
>
> 重复工作要能随规模持续承担。把重复学习转化为共享专业知识，把相似操作转化为可复用方法，规模才有机会成为效率来源。

<a id="upgrades"></a>

## 04　把升级变成组织能力

编译器升级把时间、隐含依赖和规模串了起来。编译器负责把源代码转成可执行程序；即使新版本努力保持兼容，修正错误、调整优化，或改变原先未定义行为的表现，也可能使一部分代码出现差异。对整个代码库而言，需要判断的不只是“能否编译”，还有正确性、性能和关键业务行为。

书中记述，Google 在 2006 年进行过一次痛苦的编译器升级，此前大约五年没有更新。公司已经有数千名工程师，许多人没有经历过编译器切换，大量代码也只在一个版本上构建过。多年积累的隐含依赖，在新版本面前集中显现；主要由志愿者组成的升级团队，一边处理兼容问题，一边寻找当时能够采用的绕行办法。

脚注给出两个具体技术细节：C++ 标准库接口需要以 `std` 命名空间引用；针对 `std::string` 的一项优化，在 Google 的特定用法中反而造成性能退化，需要额外处理。这说明升级差异的来源并不单一：有些是代码需要符合接口要求，有些则是新实现对实际工作负载产生了不利影响，不能全部归成同一种程序错误。

当时还没有普遍覆盖的持续集成系统，也没有后来的 Beyoncé Rule。升级者难以事先知道哪些产品会受影响，也无法确定遗漏的回归会怎样归责。技术上的未知与组织上的风险叠在一起，使这项工作更加难以推进。

Google 后来把这次痛苦看作需要改善的组织能力，持续投入自动化、环境一致性和专业经验。自动化让一个人能处理更多重复操作；统一工具链缩小需要分别照顾的环境范围；固定专家能识别熟悉的问题，而不必每次重新开始。更规律地升级，也让相邻版本的差异变小。

代码本身同样会改变。一次次迁移会找出依赖旧实现细节的地方，使它们逐渐改为依赖语言或操作系统真正保证的抽象。工程师熟悉了过程，就更容易发现可以自动化的环节。原章写到，出版时部分语言已经积累了跨平台数百次升级的经验，有些每一两周就更新编译器；这描述的是当时部分工具链的状态，不是给所有项目规定相同频率。

其中，共享的**持续集成（Continuous Integration，CI）**系统提供了共同的验证基础。团队把重要行为写成可自动运行的测试，由公共系统构建和执行；基础设施升级者便能观察这些测试在新环境中的结果。如果每个团队各有一套只有自己会运行的验证流程，升级者就必须逐个联系、学习和协调，组织越大，成本越难控制。

**Beyoncé Rule** 则为这套机制配上内部责任政策：如果基础设施变化引发产品故障，而问题没有被共同 CI 系统中的测试检出，就不把这项故障归责于基础设施变更。原章用流行歌曲的句式开玩笑，大意是“在意某个行为，就把它放进 CI 测试”。只有少数人知道如何触发的特殊测试，无法提供同样的公共保障。

这项政策给双方提供了明确条件：产品团队把需要保护的行为表达为公共测试，基础设施团队据此推进可见范围内的升级。测试覆盖仍会有缺口，实际故障仍需处理；规则解决的是大规模协作中无法承担无限未知用法的问题，并不声称测试通过就证明一切行为正确。它把“请保证永远别影响我”转化成了可以执行、共享和改进的验证要求。

作者强调的成果，是代码库继续增长时，Google 仍能用相对稳定数量的工程师执行必要的编译器升级。这不是说计算和验证成本全部消失，而是重复工作没有要求升级人力跟着代码量一起增长。首次升级的投入，由此逐步变成以后反复受益的能力。

## 05　让问题更早出现

共同验证还可以进一步向开发过程的早期延伸。把设计、实现、评审、测试和上线排成从左到右的时间线，**左移（shifting left）**就是尽早发现问题。书中的经验是，问题越早暴露，通常越容易修复：开发者还记得上下文，修改影响的范围也较小。

原章从安全问题说明这条成本路径。上线后发现漏洞，团队要先判断影响、组织缓解，再定位和修复；部署前发现，通常能先拦住有问题的版本；若原作者提交前就得到清楚的反馈，他还掌握这段实现的上下文，可以直接调整。向左移动的既是发现时刻，也是修复工作与原始思路之间的距离。

用一个笔记的假设情境看得更具体些：团队准备让用户下载报表。若设计讨论就发现下载链接缺少访问权限约束，可以先把授权要求补进方案；实现后的评审发现，则需要改接口与测试；上线后才发现，除了修改程序，还要调查已有链接是否被越权访问，并协调产品和安全人员处理影响。越晚发现，需要处理的既有工作和外部影响往往越多。

静态分析可以及时指出工具能够识别的代码问题，评审可以补充设计和上下文判断，自动化测试可以持续检查明确的行为。它们共同组成**纵深防御（defense in depth）**：让不同手段覆盖不同的缺口，尽量把问题留在更容易采取行动的位置。

对于需要真实环境才能显现的差异，金丝雀发布和运行监测仍有价值。金丝雀发布先让较小范围接触新版本，再根据观察扩大范围。左移提供的是更便宜的早期反馈，与后面的验证配合起来，形成完整路径。[第二章](ch02.md#early-feedback)把同样的思路用于团队反馈，[第二十三章](ch23.md)则展开了各阶段持续集成的责任。

<a id="tradeoffs"></a>

## 06　比较完整成本，让取舍有依据

维护能力值得投入多少，最终要回到完整成本。书中把成本看成多类资源和影响：资金成本是直接支出，资源成本包括 CPU、内存和带宽，人力成本包括开发与维护精力；交易成本是采取行动所需的手续和协调，机会成本是选择一件事后放弃的其他可能，社会成本则关注产品对更广泛人群的影响。

这些成本会落在不同地方。一个工具采购便宜，可能需要所有工程师反复等待；一个公共服务多用一些机器，却可能省下许多人的日常操作。若只看某个部门的账面开销，就容易把成本转移到另一个部门、后来的维护者或最终用户身上。把时间和规模放进来以后，才看得到整体代价。

白板笔的例子很小，却把取舍讲得很清楚。原章先描述一种常见体验：笔被严格保管，白板旁留下的却常常已经写不出字；讨论到一半，要停下来寻找能用的笔，或者因为别的团队拿走了笔而再次中断。节省的是低价耗材，付出的却可能是多人一起思考时的注意力。

书中记述，Google 当时让员工方便地从未上锁的物资柜取得白板笔。这个选择接受了多消耗一些笔的可能，换取讨论更少被打断。它优化的对象是顺畅的共同工作；便宜、容易计算的物品数量，并没有自动成为最重要的指标。

对于可以量化的取舍，组织应当准备共同的估算基础。CPU、内存、带宽和工程师时间不必完全公开成货币价格，也可以建立相对换算关系。原章设想，用两周工程时间改进数据结构，以更多内存换取更少 CPU；判断时既要比较机器资源，还要考虑优化能持续受益多久，以及这两周原本可以完成什么。

有些价值暂时很难测量，例如 API 给后来维护者造成的理解负担，或一项产品设计对无障碍使用、公平性和滥用风险的影响。规模越大，小差异影响的人可能越多。书中要求把这些问题同样放进判断，结合经验、先例和论证认真处理，而不是因为没有现成指标就略去。[第四章](ch04.md)进一步讨论工程与公平。

“数据驱动”因此可以理解为尽量让证据支持判断，同时说明数据之外的假设。现状偏好会让人低估改变的收益，损失厌恶会让眼前支出比长期收益更显眼；明确估算依据，有助于让大家讨论同一个问题。最后仍需要有负责的决策者，在法律、客户要求和可选方案之间作出选择，并能解释为什么当前选择更合适。

共同理解也不要求每个人给出完全相同的评价。有人可以认为机会成本估得偏低，同时理解另一个人怎样得出了结论。明确的决策责任、理由和升级路径，能让工作继续推进，也为后来复查保留依据。

> **核心观点**
>
> 工程决策应比较整体成本：机器和资金之外，还有人的精力、协调与机会，以及对用户和社会的影响。能估算的认真估算，难量化的重要因素也要进入判断。

<a id="distributed-builds"></a>

## 07　分布式构建怎样改变成本，也改变行为

分布式构建展示了一个选择从产生收益，到出现新问题的完整过程。书中回顾，2000 年代中期，Google 仍依赖本地构建：工程师检出代码，再在自己的机器上编译。随着代码库增长，编译越来越慢；等待消耗人力，为每个人配置更强工作站又增加硬件成本。昂贵的机器很多时候仍然闲置，资源并没有得到很好的共享。

Google 随后开发了分布式构建系统，把构建工作交给共享计算基础设施执行。这项改变需要真实投入：工程师要开发和维护系统，用户要改变工作习惯并学习工具，公共集群也要增加计算资源。收益则是构建更快、工程师等待减少，硬件可以集中管理和共享，而不必不断提高每台个人工作站的配置。

从作者的回顾看，总体收益远大于建设和维护成本。但事情没有停在“更快了”这个结果上。本地构建时，多引入一个不必要的依赖，开发者很快就会在自己的等待时间上感到代价，因此有动力保持依赖精简。分布式系统通过并行执行缓解了等待，也把一部分浪费从个人眼前藏了起来。

久而久之，构建图里出现了越来越多膨胀或不必要的依赖。对个人来说，一次方便的引用增加了不明显的等待；对整个组织来说，许多这样的决定却共同消耗共享计算资源。原章把这种现象类比为杰文斯悖论：资源使用效率提高以后，总消费反而可能上升。这里重要的是激励条件的变化，而不只是工具速度的变化。

于是，Google 还需要重新整理使用约束和最佳实践，例如保持较小依赖，让工具帮助管理依赖，并继续投入新生态所需的维护。[第十八章](ch18.md)会详细解释构建图、依赖和缓存；本章先说明，一个看似直接的“花机器资源换工程师时间”的决策，也会产生未预见的后续行为。

这个案例提供了一种复查视角：既看方案是否解决了原来的瓶颈，也看它让什么成本变得不易察觉。新问题出现以后，可以继续改善公共能力，保留已经获得的收益。最初的选择有价值，与后来需要补充治理，可以同时成立。

<a id="dependency-or-fork"></a>

## 08　在复用与自建之间，同时考虑时间和规模

时间与规模通常相互支持：共同测试既能帮助长期升级，也能减少跨团队沟通。有时两者也会拉向不同方向，原章用“复用依赖，还是分叉或重新实现”说明这种张力。

复用通用组件，可以共享开发、修复和维护经验，但需要适应它的接口和升级节奏。**分叉（fork）**是在已有实现上维护自己的版本；为狭窄场景重新实现，则可以舍去不需要的通用能力。两者都可能带来更合适的性能、更容易加入的功能，以及对变更时机更直接的控制。

这种控制同时意味着承接维护责任。假如每个项目都复制一份公共库，各自修改，后来披露一个安全问题时，组织要先找出所有有风险的副本，再识别它们的使用者，分别修复和验证。原本能在一个公共位置积累的能力，分散成了多条需要照顾的维护路径。

原章因此特别关注分叉的寿命和边界。短期、范围明确的局部实现比较容易判断代价；数据结构、序列化格式和网络协议等可能跨版本、跨项目延续的接口，则要更加谨慎。一个选择可能在当前模块里很方便，却把格式或行为长期留给别的系统。

用笔记的假设情境说明：报表团队只想调整压缩过程中的内部缓冲策略，影响可以较容易地限制在实现内；若为方便而另造一种文件格式，历史文件、下载工具和其他读取方都可能长期需要支持它。两者都叫“按自己的需要做”，延续出去的责任却很不同。比较方案时，除了当前实现成本，还需要把维护路径数量和接口存续时间一起放进来。

一致性能够集中维护收益，通用性也有自身成本。本章给出的判断方向，是识别真正值得定制的局部，并看清它会留下多长、多广的责任。[第二十一章](ch21.md)会进一步讨论依赖版本与共同升级的条件。

<a id="revisiting-decisions"></a>

## 09　让决策能够随着证据更新

选择完成以后，时间仍然在起作用。新工具改变了人的行为，组织规模变大，资源价格发生变化，或者最初的假设被实际使用推翻，都会使旧结论需要重新考虑。原章区分了两种常见情形：当初的判断确实有误，以及当初合理、现在条件已经改变。

因此，好的决策会说明当时的证据、假设与取舍。后来的人据此能够理解，为什么选择本地构建、为什么改为分布式构建，以及为什么又要治理依赖膨胀。记录理由让方案的使用条件可见；只留下“这是规定”，则很难判断何时值得调整。

数据驱动的文化还需要允许负责的人承认错误。若每次调整都会被解释为能力不足，人就更容易维护旧说法，或者只选择支持既有立场的数据。能够说明新证据、修正判断并承担后续行动，才让“依据证据”成为持续发生的工作方式。[第二章](ch02.md#constructive-criticism)讨论的接受反馈，与这里的决策更新相互衔接。

> **核心观点**
>
> 决策依据也有寿命。把理由留下来，并在证据、规模或约束变化后重新判断，才能让项目在长期运行中继续选择合适的方向。

把这些观点连起来，本章的主线就是在时间和规模中保留改变的能力。清楚的接口减少脆弱依赖，共同测试让需求可以验证，专业知识和自动化让重复工作更容易承担，完整的成本视角则帮助团队决定哪些投入值得做。软件工程把这些政策、实践和工具，与代码一起组织起来，让软件在需要的时间里持续有用。

对于短期任务，简单直接地完成目标仍然很有价值；对于长期项目，维护和协作会逐渐成为主要约束。看清任务处在什么位置，才能选择适当的工程方法。这也是后面讨论团队、文化、流程和工具的共同起点。
