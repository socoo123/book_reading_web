# 第 22 章｜大规模变更

**Large-Scale Changes · 架构提升读书笔记**

一个公共库的名字、一次编译器升级、一种已经过时的写法，最初都只是局部技术选择。等到几百个团队依赖它们，这些选择就会变得像地基：大家知道应该改，却很难找到一个所有人同时停下来的时刻。代码库继续增长，能够一次安全提交的变更反而可能缩小，维护者必须学会让整体演进穿过许多小步。

第十五章解释怎样让旧系统有序退出，第十六章解释怎样维持共同主干与单一版本，本章补上执行层：一项跨越整个代码库的迁移，怎样被生成、拆分、测试、评审并推进到完成。核心能力是设计可用的过渡状态，再让自动化反复处理普通情况，把人的精力留给语义差异和真正的例外。

<a id="atomic-boundary"></a>

## 01　逻辑上是一件事，提交时可以是许多步

原书把**大规模变更（Large-Scale Change，LSC）**定义为：逻辑上相关，却无法在实际条件下作为一个原子单位提交的一组变更。这里的“大”没有固定文件数。一个仓库里修改几十个文件，可能轻易一次完成；相同改动分布在互不支持联合提交的多个仓库中，就已经需要非原子的迁移方法。

原子提交让版本库从一个完整状态直接跳到另一个完整状态，概念上很整齐。现实中的限制来自整条工作链：版本控制能否处理这么多文件，验证是否能及时结束，评审者能否看清修改，以及准备好的代码在提交前是否又被别人改动。Google 的经验是，随着代码和并行工作的工程师增多，实际可承受的最大原子变更反而会下降；这项能力由组织与工具共同决定，仓库容量只是其中一环。

合并冲突尤其容易形成循环。作者花时间准备全局改动，其他工程师在此期间继续开发；更新主干、解决冲突、重跑测试又要时间，期间还会出现新变化。全球团队没有一个可靠的“周末无人工作”窗口。即使版本控制能够接收巨型提交，让整个组织等待这一次修改完成，也未必是值得付出的代价。

验证和评审有同样的粒度问题。在几十个文件中定位某个测试失败，通常比在一万个文件中追查容易；分片以后，失败能落到较小的候选范围。代价是一些上层测试会被重复运行。原书明确把它当作权衡：在 Google 的条件下，多花计算资源，往往比让工程师反复调查巨型变更更便宜。其他团队仍需按自己的测试耗时和人力成本选择粒度。

常见 LSC 包括清理反模式、替换已弃用的库接口、准备编译器升级，以及把使用者迁到新系统。原章说 Google 的大多数 LSC 几乎不改变功能，适合由工具生成；定义本身也容纳有行为变化的迁移，只是后者需要额外的语义判断和验证。把改动称为“重构”，并不能自动消除这些工作。

> **核心观点**
>
> 大规模变更要保留的是一个共同目标，而非一次共同提交。先找出能够安全独立推进的单位，才能让代码库在日常开发不中断的情况下持续演进。

<a id="migration-ownership"></a>

## 02　把共性迁移成本交给最懂它的人

Google 通常由基础设施维护团队承担大量 LSC 工作。原因首先是知识集中：库的作者更清楚新旧接口有哪些差异，哪些调用可以自动改写，失败后通常应检查什么。同类问题处理得越多，迁移规则和排错经验越成熟。让每个产品团队各自重新学习，组织就会反复支付同一笔入门成本。

假设一个报表平台要统一更换压缩接口。若通知一百个团队自行迁移，每个团队都要先理解新接口，再找出自己的调用，处理相似的参数变化。平台团队若先研究这些共性，再生成可以评审的修改，产品团队主要参与自己真正了解的部分，例如某种特殊文件格式是否仍被外部使用。

激励也会影响迁移是否完成。新接口可能让全组织的维护和构建更简单，却没有给某个产品团队带来足以压过业务需求的即时收益。把更新要求发出去，并没有使成本消失，只是把它分散到别人的待办列表里。原书把没有配套投入的额外要求称为 **unfunded mandate**。让基础设施团队负责执行，并为人力计入预算，才使这笔成本能够被看见、比较和优化。

同一责任安排还照顾了尾部工作。愿意尝试新系统的团队会先迁，剩下的往往是难处理的依赖、生成代码和隐含行为。以旧系统真正退出为目标的团队，有动力继续追踪这些障碍；仅靠使用者自愿更新，容易在“多数已经迁完”时停住。这与[第十五章的迁移责任](ch15.md#advisory-and-compulsory)是一致的：产品团队仍负责业务判断，迁移团队承担可重复的共性劳动。

书中“填补路坑”的例子把这项能力的价值落到一个很小的细节上。Google 的 C++ 模板工具库中，头文件 `stl_util.h` 使用下划线，另一个 `map-util.h` 却使用连字符。工程师需要记住差别，写错以后可能等到一次较长的编译才发现。看起来只是一个字符，分散在全库中的修复成本却会使人长期容忍这个不一致。

成熟的 LSC 工具让库作者可以统一修改，而不用逐一打扰使用团队。原书记述，这项清理只用了约两周的后台任务式投入，由此导致的构建失败也确实减少了。值得关注的是成本曲线改变了：过去“不值得修”的小问题，在已有发现、改写和提交管道后，可以成为划算的维护工作。

> **核心观点**
>
> 集中迁移专长，让相同的学习和排错成本只付较少次数。公共基础设施的升级收益与迁移投入应一起核算，避免把全局改善变成每个使用团队都要自行筹资的额外任务。

<a id="machine-readable-codebase"></a>

## 03　让工具能够理解、改写并验证同一个代码库

自动化的起点是知道要改哪里。文本搜索适合找文件名、配置项和明确的旧写法；涉及重载、继承或类型时，则需要语义信息。原书介绍了 Kythe 的符号关系索引，以及 ClangMR、JavacFlume、Refaster 等基于编译器或语法树的分析、改写工具。它们让迁移者可以围绕“这个函数的调用者”生成变更，而不必把所有同名文本都当作同一实体。

工具的复杂度应服从问题。固定头文件路径的更名，可能用一个脚本即可表达；同名方法分属不同类型时，正则替换就很难代替符号判断。原章希望生成变更所需的人工投入随代码库规模次线性增长：学会并写好一条规则后，无论仓库多大，人花的时间都大致相同；扫描、解析和构建的计算量则仍会随输入增加。

原书给出过一个经验阈值：超过约五百处编辑，学习并使用内部生成工具通常比逐处手改更有效；熟练维护者的阈值更低。这个数字取决于 Google 当时的工具，更可迁移的判断是：同一规则会被反复执行、冲突后还要重做时，让规则成为可重跑的程序，收益远不止第一次节省输入时间。

改写还需要稳定的环境。每个项目各用一种版本控制、CI 入口、格式风格或特殊提交格式，都会增加机器人必须理解的分支。Google 一方面把测试等必要检查做成共同设施，另一方面会为 LSC 经协调略去某些无关的局部要求，例如特殊的变更描述格式。适用的项目检查仍然保留，省去的只是无意义的差异。

自动格式化把另一类重复工作移出了迁移规则。转换器负责语义和结构，随后由语言格式化器整理排版；评审者看到的代码便能融入周围风格，而不用在上千份修改里处理空格和换行。它延续了[第八章的一致性与自动执行](ch08.md#automated-enforcement)：同一约定同时降低人的理解成本和工具的实现成本。

测试则让不熟悉业务的维护者能够进入旧代码。原书用“闹鬼的墓地”形容那些年代久远、十分关键、无人敢碰的系统：它们只要仍依赖旧库，就能阻止整个库退出。可靠测试把部分隐藏约定变成可执行的证据，使迁移者能够发现自己破坏了什么。测试无法证明任意修改都正确，却能显著扩大可安全维护的范围；缺少测试、负责人和可理解边界的区域，会成为全局迁移的长期阻塞点。

语言也会改变自动化的难度。静态类型、明确的符号解析和编译器检查，使工具更容易锁定目标并提前拒绝无效转换；类型别名、转发函数则提供分阶段迁移的桥梁。作者据此认为，静态类型语言比动态类型语言更容易做大规模自动改写；这个判断依托的是编译器工具能提供的信息。无论使用哪种语言，真正需要寻找的，都是当前语言和工具怎样表达兼容状态、识别引用并检查转换结果。

<a id="compatible-bridge"></a>

## 04　先把新旧接口接通，才能分别迁走调用者

本章最重要的案例，是 Google 将内部 C++ `scoped_ptr` 迁到 C++11 标准的 `std::unique_ptr`。旧智能指针诞生于 C++98 环境，已经广泛承担堆对象的生命周期管理；标准独占所有权指针出现后，Google 希望与外部 C++ 生态采用共同类型。但当时旧符号已有超过五十万处引用，散布在数百万个源文件中，单次全库替换无法实际完成。

数位工程师用了数月并行推进，一边改写引用，一边逐步使旧类型的行为更接近标准类型。在迁移高峰，他们每天能生成、测试并提交七百多个独立变更，涉及一万五千多个文件；到本书写作时，改进后的实践和工具有时能达到约十倍的吞吐。

难点并不只在引用数量。若某个公共 API 的参数仍是旧类型，调用方先换成新类型后，代码可能无法编译；只修改 API 又会破坏尚未迁移的调用方。沿调用图把所有相关位置绑进同一个提交，虽然能恢复原子性，却可能再次得到一个大到无法提交的变更。

最后的突破来自**类型别名（type alias）**。在处理必要的行为差异以后，团队把 `scoped_ptr` 变成 `std::unique_ptr` 的别名。旧名字和新名字因此指向同一种类型，调用方、声明与实现才获得独立改名的空间。随后继续替换剩余文本，最后删除旧别名。兼容桥把“类型与行为的改变”和“每个文件中的名字更新”拆开了。

![兼容桥建立后，旧名 scoped_ptr 和新名 std::unique_ptr 表示同一类型，旧写法与新写法的调用者可以共同连接同一个 API；随后逐批改名，最后删除旧别名。](../diagrams/exports/ch22-compatible-bridge.svg)

下面用一个本笔记原创的 C++11 小程序演示桥梁建立后的状态，旧名另取为 `LegacyPtr`。`Take` 的旧写法声明与新写法定义指向同一个函数；两个调用者分别保留旧名和使用新名，都把所有权交给同一 API。

```cpp
#include <cassert>
#include <memory>
#include <type_traits>
#include <utility>

template <class T>
using LegacyPtr = std::unique_ptr<T>;

int Take(LegacyPtr<int> value);  // 公共声明暂时保留旧名

int Take(std::unique_ptr<int> value) {  // 同一个函数的新名写法
    return *value;
}

static_assert(
    std::is_same<LegacyPtr<int>, std::unique_ptr<int>>::value,
    "the alias must denote the same type");

int main() {
    LegacyPtr<int> a(new int(7));
    std::unique_ptr<int> b(new int(9));
    assert(Take(std::move(a)) == 7);
    assert(Take(std::move(b)) == 9);
    assert(!a && !b);
}
```

这里的参数按值接收独占所有权；`std::move` 使左值指针可以参与移动构造，实际转移发生在参数构造时。两个调用结束后，源指针为空，接收方参数负责销毁相应整数。别名没有引入新类型，因此 `int Take(LegacyPtr<int>)` 与 `int Take(std::unique_ptr<int>)` 声明的是同一个函数，只是拼写不同。

建立桥梁后，可以单独把公共声明中的旧名换掉，也可以单独迁一个调用方；尚未修改的文件仍与当前主干兼容。等旧引用和必要头文件依赖全部清理，才删除别名。若原来的 `LegacyPtr` 还是一个独立类，上述同类型结论就不成立；将类替换成别名本身仍是需要调查和验证的变更。真实案例中，行为依赖、生成代码和并行开发还形成了长尾。

这一过程与[第十六章的单一版本过渡](ch16.md#migration-and-compatibility)相通：可以为迁移安排受控的共同兼容状态，再逐步收敛，不必让每个团队停留在自己永久维护的一份基础上。

> **核心观点**
>
> 可分批迁移需要一个真实可用的中间状态。先设计兼容桥，再让调用方独立迁移，能够把无法承受的一次联合修改，转成许多与当前主干兼容的小步。

<a id="authorization"></a>

## 05　生成修改越便宜，越要照顾接收修改的人

Google 的代码开放性使工程师可以修改其他团队的文件并送去评审。手工编辑时，作者制造一份变更与评审者理解它的成本大致互相制约；批量生成以后，一位工程师能很快产生数千份修改，接收方却仍可能逐份付出阅读、提问和协调的时间。自动化把发送成本降下来，也可能把整个组织的评审队列塞满。

因此，原章把社会约定视为与生成工具同等重要的基础设施。Google 采用轻量授权：作者说明改动理由、影响范围、预计分片数，准备变更说明和常见问题，并请被修改 API 的维护者进行领域评审。一组约十余位熟悉语言和全局影响的工程师参与监督，必要时邀请具体领域专家，帮助判断这项改变是否值得让全组织一起承担。

这个入口也决定评审应由谁完成。纯机械替换通常适合由掌握相关语言与库细节的全局审批者统一审核；必须了解产品语义的改动，才需要当地代码所有者介入。若一开始就把同一问题发给上百个本地负责人，组织会重复理解迁移规则，同时仍可能漏掉只有库专家知道的细节。

代码所有者仍然可以提问，作者仍须解释并处理反馈；分歧可以向授权小组升级，由它协调判断。原书强调，本地所有者并不各自持有对整个已批准 LSC 的无限否决权。否则，只要一个项目无限延期，公共基础设施就可能永远无法更新。共同授权为整体推进提供方向，具体反馈为局部正确性提供信息，两者需要同时存在。

授权也可能得出“不值得做”。原书举过缺少防回流机制的拼写清理：即使一次改完，旧写法很快又会回来，收益可能承担不起评审负担。可见，LSC 的目标不仅是让人有能力改变全库，还包括把这种能力用于值得改变的事情。变更说明、FAQ 和过往可靠的结果，会逐步建立使用团队对迁移者的信任。

<a id="shard-management"></a>

## 06　Rosie 管理的，是能够独立落地的分片

原章把执行概括为授权、生成变更、管理分片、清理四个阶段，边界可以交错。获得授权后，作者用可重复执行的规则生成目标修改。总变更可以是一个概念上的完整集合，不要求底层版本控制真能在一个工作区里容纳它；原书说，极大的变更通常连这一步都会受到工具限制。

Google 的 Rosie 负责把修改按项目边界和所有权规则拆成**分片（shard）**，再分别推进测试、发送评审、审核与提交。分片大小要在工具能够处理之外满足一个更重要的条件：每片可以独立进入主干。头文件声明与必须同步的实现要么放在同一片，要么先有前文那样的兼容安排。把大补丁按文件数平均切开，本身不会产生独立性。

下面的图把一份迁移规则与两条执行路径分开：左边表达共同意图，右边表示各自拿到测试与评审结果后分别落地。A 片完成，不需要等待 B 片的普通冲突解决；前提是两片确实没有未处理的依赖。

![同一套可重跑规则生成分片 A 与分片 B，每片分别测试、评审并提交；某片出现冲突后仅重生成受影响分片，不要求撤回所有已完成修改。](../diagrams/exports/ch22-shard-pipeline.svg)

图 22-2：实线箭头表示生成与推进关系；上下两行是彼此独立、可以同时推进的执行管道。底部是失败后的处理原则，实际系统中的排队、重试和限流没有画出。点击[查看大图](../diagrams/exports/ch22-shard-pipeline.svg)。

自动化随后承担状态管理。某片测试失败，作者调查规则或局部例外；某片等待的时间过长、与主干发生冲突，可以在新的基线上重新生成。迁移期间，旧写法还可能由复制示例、积压分支或习惯重新引入，生成规则也要能覆盖这些新增位置。反复修一份已经过期的大补丁，通常不如修正产生补丁的方法。

原书用“宠物与牲畜”的类比表达这种工作心态。普通功能变更往往由作者长期打磨，很熟悉其中每一处细节；LSC 则会生成大量可以再生的普通分片。一个分片被退回或回滚后，维护者应能低成本重新生成，而不用把它当作必须保住的手工作品。若失败揭示的是公共改写规则的问题，就要先修正规则，再处理所有相关分片。

Rosie 同时控制对共享设施的压力：限制每个 LSC 的在途分片数，以较低优先级运行，并与测试平台协调可接受负载。原章说 Google 可以每天推进数千份变更，靠的也包括这些调度安排。若批量工具把其他工程师的 CI 和评审全部挤住，即使迁移本身吞吐量很高，也没有实现组织层面的效率。

<a id="testing-and-tap"></a>

## 07　测试先给每片证据，再共享昂贵的计算

验证总变更能通过，还不足以支持分片执行。A、B 合起来通过的状态，可能依赖二者同时存在；若先提交 A 就会失败，这种分片依旧不可用。原章要求对每片收集测试证据，并通过构建依赖图找到可能受影响的测试，而非只执行分片所在项目的几项常用检查。对依赖广泛的底层修改，这个范围可以覆盖全库。

通常的小片影响范围有限，Google 当时绝大多数分片涉及的测试少于一千项。昂贵的是公共底层变更，它们可能反复触发大量相同测试。**TAP（Test Automation Platform）测试列车**利用一项经验：这些机器生成、经过仔细检查、保持局部语义的修改，大多能通过，也很少彼此相互作用。把共同计算合并起来，就有机会让“发现多数都正常”的过程只做一次。

Adam Bender 撰写的测试案例列出了当时每三小时启动一班的五步流程：

1. 对每个候选变更先随机抽取一千项测试运行。
2. 把通过这轮筛查的变更合成一份列车变更。
3. 运行这批变更影响测试集合的并集；大批或底层改动可能让整个仓库的测试都进入范围，完成可能超过六小时。
4. 对其中失败的非偶发测试，针对每个登车变更分别重跑，找出导致失败的变更。
5. 为每个变更生成通过与失败目标的报告，作为能否提交的证据。

三小时是发车间隔，一班本身可能运行六小时以上；一千项抽样只用于筛查，受影响测试仍要在第 3 步完整运行。介绍分片测试时，原章还给出了更有针对性的复测范围：只需关注“某分片的受影响测试”与“合并运行中失败测试”的交集，共同通过的部分不必为每片重跑。

图 22-3 把这五步画成一条往返的流程：上排把多个变更合成一次运行，下排把结果拆回每个变更。多数测试在合并运行中通过，只跑一次；只有失败的那部分，才需要逐个变更重跑。

![TAP 测试列车的五步：每个变更先随机跑 1,000 项测试筛查，通过者合成一份列车变更，再运行受影响测试的并集；通过的测试只跑这一次，失败的非偶发测试对各变更分别重跑以找出致错者；最后为每个变更生成报告，分片仍各自提交。](../diagrams/exports/ch22-tap-train.svg)

图 22-3：上排从左到右是合并阶段，下排从右到左把结果拆回各变更；实线是每班都走的流程，虚线是测试失败后才走的归因重跑。省下的计算来自那些只跑一次就通过的测试。点击[查看大图](../diagrams/exports/ch22-tap-train.svg)。

再用一个假设的例子说明并集与交集。A 影响 `{甲, 乙, 丙}`，B 影响 `{乙, 丙, 丁}`，分别完整测试需要执行六次；合并先跑 `{甲, 乙, 丙, 丁}`，只执行四次。若都通过，这轮共省两次；若只有乙失败，再分别对 A、B 运行乙，总执行数又回到六次。可见节省来自重叠且通过的测试，真实收益取决于重叠度、失败数量与调度开销。

列车合并的是验证工作，最后仍然提交独立分片。通过的测试只在组合状态下跑过，它们能代表每一片，前提是变更之间很少相互作用；若只有组合状态出错、单独重跑却都通过，就需要调查变更之间的交互。原章脚注提到，可以向 TAP 申请单个变更的隔离运行，但开销很大，只在低峰时段执行。这套流程适合书中常见的窄范围机械重构；强耦合的行为修改不满足这个前提。

偶发失败测试会在这里放大成本。单个团队偶尔多重跑一次，看起来影响不大；横跨大量项目的工具却会不断碰到它们，并被迫调查与改动无关的失败。原章记述，针对保持语义的机器生成 LSC，Google 自动提交流程当时会忽略近期有偶发失败历史的测试；作者承认这可能漏过“从偶发变成稳定失败”的回归，但实际极少发生，便交给人工沟通处理。这项取舍建立在对单个变更的高度把握之上；更基础的责任仍是持续修复这些测试，让使用它们的其他维护者不必长期代付成本。

> **核心观点**
>
> 分片需要各自可用的验证依据，测试计算却可以共享。先运行受影响测试的并集，再把少量失败拆回单片调查，能利用“大多数修改正确、大多数测试通过”的常态降低成本。

<a id="expert-review"></a>

## 08　让评审者真正理解规则，让例外得到注意

测试之后，Rosie 要找到适合的评审者。对需要本地上下文的改动，它依据 `OWNERS` 文件及所有权发现服务选择人选，并按预计适合程度加权；某人长期没有响应时，会自动增加其他评审者。在发送与最终提交阶段，还会运行适用的项目检查，确保变更满足当时主干的要求。

原书特别讨论了两类会阻塞全局工作的检查。第一类是与迁移目的无关的非标准要求，如某种特殊描述格式，可以在协调后选择性关闭。第二类是改动之前就已存在的失败，迁移工具会积极忽略这类基线噪声：在单个项目里顺手修掉的做法，放到全库就无法扩展。当地负责人维持可用基线，迁移者处理自己造成的问题，构成了跨团队协作的责任边界。认定“已有失败”也需要可靠证据。

纯机械改写通常进入**全局审批者（global approver）**的队列。这类工程师有跨仓库审批权限，也具备相关语言或库的专业知识，会与作者先建立对迁移规则、预期形态和可能失效方式的共同认识。权限解决“能不能批准”，领域知识解决“是否知道自己在批准什么”；二者缺一，统一审批就容易只剩速度。

规模化评审还会审核模式。全局审批者使用基于模式的工具，自动通过符合预期的分片，把人工注意力集中到冲突、生成故障和异常结构上。人负责理解并认可一套足够具体的转换规则，再让工具识别其重复实例。若修改必须理解业务含义才能判断，就应交给拥有那部分上下文的负责人。

原书承认，本地所有者对可信基础设施团队的 LSC 有时只做粗略评审，这也是后来倾向把机械变更交给专业全局审批者的原因。信任能降低沟通成本，但有价值的信任应来自规则透明、测试证据和可靠的历史结果。最后，Rosie 在再次检查后提交每一片；评审政策保留，执行方式随重复性改变，专家的判断才没有被大量相同文本消耗掉。

<a id="rosehub"></a>

## 09　跨仓库的修复，也需要发现与执行的闭环

Operation RoseHub 把本章思路带出了 Google 内部。问题来自 Apache Commons Collections 中可被利用的反序列化工具类：不安全版本会经传递依赖进入 Java 应用，应用维护者可能并不知道自己携带它。原章说只要库出现在 classpath 中，应用就易受远程执行攻击；按 Apache 的安全说明，攻击还需要应用对不可信来源的数据执行 Java 反序列化。

原章把漏洞背景写在 2017 年初；对照 Google 的原始报道，2017 年 3 月 1 日是报道的发表时间，志愿修复行动始于 2016 年 3 月，相关漏洞的公开还要更早。

志愿者利用 BigQuery 的 GitHub 公共代码数据，寻找仍直接引用旧 Commons Collections 版本的项目，再逐个发送升级补丁。原始报道说，共找到二千六百个这样的独立开源项目，参与修补的团队有五十位员工。它们没有共享 Google 内部的 Rosie 管道，很多协调与提交工作由人完成，但仍然把“我们已经发布公告，请大家自行更新”推进成了“找到具体位置，并把可审查的修复送到维护者面前”。

这个行动的范围也很具体：报道说，能主动补到的只是 GitHub 上直接引用旧版本的开源项目；补丁送出后，还要等维护者合入、发布，下游程序再重新部署。案例展示的价值，在于主动承担迁移劳动，并借公开代码分析找到具体目标。无论仓库是否统一，发现对象、构造修改、找到负责人并跟进结果，依旧是完成改变的共同骨架。

<a id="cleanup"></a>

## 10　让完成留下来，让下一次改变更容易

LSC 的“完成”要与目标一致。有的项目必须删掉旧接口，有的只要求迁走高价值引用，允许剩余部分随生命周期退出。两种终点原章都认可；若目标是移除系统，剩余使用、生成器输出和隐含依赖都要有人跟进到底，旧系统才算退休。

与此同时，需要限制旧用法回流。迁移期间，工程师会复制旧代码，长期开发的变更会重新带回旧符号，新的使用也可能来自习惯。Google 使用 Tricorder 在评审时指出新增的弃用对象引用，与迁移工具配合，阻止已经处理过的问题反复增长。这与[第十五章的迁移与防回流](ch15.md#migrate-and-prevent-backsliding)形成闭环：存量由迁移项目推进，新增由及时检查和依赖边界约束。

以本章的类型迁移为例，收尾意味着不再需要旧别名的调用、声明和生成代码已经处理，相关测试通过，然后才能移除兼容入口。兼容层为分批执行争取时间，也是一份需要最后清理的临时责任。若外部兼容承诺要求长期保留入口，就应把它明确纳入支持范围。

作者在结尾强调，经常做 LSC 才能持续具备做 LSC 的能力。发现、改写、验证、评审和协调必须在日常维护中不断被使用，组织才知道自己的工具在哪些边界失效，哪些旧模块正在变成无人敢碰的区域。等到紧急升级才第一次试验全库迁移，原本可逐步解决的能力缺口会同时出现。

对较小团队，可带走的也不一定是一个名叫 Rosie 的平台。一条可以重跑的脚本、一份能定位调用者的索引、可工作的兼容入口，以及明确的评审与收尾责任，就能使几十处相关改动更可靠。随后再按实际重复劳动增加工具，而不必先复制 Google 的全部基础设施。

本章最终改变了技术决定的时间属性。有了可靠的迁移能力，今天的名字、文件位置和库接口就不必背负“今后永远无法更改”的重量。设计时仍应谨慎，但也可以有依据地保留修正空间：先让新旧共存的状态可用，再让许多小步不断积累，最后把旧世界真正收起来。

> **核心观点**
>
> 大规模变更的产物既包括改好的代码，也包括持续可用的改变能力。可重跑的规则、独立分片、可信验证、合适的审批者和防回流机制，共同让代码库保持可塑性。
