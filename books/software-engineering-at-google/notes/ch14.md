# 第 14 章｜更大范围的测试

**Larger Testing · 架构提升读书笔记**

一个函数在测试里正确返回，并不能告诉我们：真实程序能否带着部署配置启动，两个服务对同一个字段的理解是否一致，用户集中访问时队列会不会堆积。本章讨论的更大范围的测试，就是把这些被单元测试有意隔开的部分重新接起来，观察软件作为系统运行时的行为。

接得越完整，通常越接近真实运行，也越难保持快速、稳定和容易排查。Joseph Graves 因此把重点放在一种取舍上：先找出需要降低的风险，再选择足够真实、同时尽可能小的测试。更大测试的价值来自补上特定缺口，而它能否长期发挥作用，还取决于数据、执行方式、失败信息与维护责任。

<a id="size-scope-fidelity"></a>

## 01　先分清大小、范围与保真度

原书沿用 Google 的两个独立维度。**测试大小（size）**约束执行需要的资源：小型测试限于单线程、单进程、单台机器；中型测试可以在一台机器上启动多个进程；大型测试可以跨机器。**测试范围（scope）**描述测试覆盖了多少行为与组件：单个单元、几个组件的集成，或者较完整的用户旅程。一个测试即使覆盖多个模块，也可能在单进程内执行；一个范围很窄的远程接口测试，却可能需要跨机器。阅读本章的“更大”时，需要同时留意这两件事。

**保真度（fidelity）**是测试反映被测系统真实行为的程度；被测系统常缩写为 **SUT（system under test）**。单元测试把少量代码和测试代码一起执行，便于控制输入、快速得到结果。生产环境则包含真实二进制程序、启动参数、网络拓扑、状态与依赖。在这些环境之间，可以选择本机多进程、独立云环境、共享预发布环境等不同组合。

保真度也存在于数据中。服务部署得和生产一样，但只拿一个没有好友、没有历史记录的空白账号测试社交产品，仍然看不到真实社交图带来的行为。原书还提醒，人工编写的样本往往继承编写者的预期，机器学习的初始数据同样可能带有偏差。接入更多真实服务，只改善了保真度的一部分。

书中用地图 API 升级说明这种需求：网站本身的单元测试可能全部通过，但替换外部 API 版本后，页面仍可能不兼容。工程师通常会启动程序实际试用。把这一步里可以重复的交互和判断自动化，就能让每次升级都得到相似反馈，而不必一直依赖某个人记得手工检查。

> **核心观点**
>
> 测试大小是资源边界，测试范围是行为边界，保真度是与真实运行的贴合程度。设计更大测试时，先明确需要保留的真实行为，再决定跨过哪些执行与组件边界。

<a id="unit-test-gaps"></a>

## 02　单元测试留下哪些空白

第一类空白来自**测试替身（test double）与真实依赖的行为不一致**。延续[上一章](ch13.md)的讨论，调用方工程师可以通过打桩（stubbing）规定依赖返回什么，也可以通过交互验证（interaction testing）检查调用过程。但这些安排依据的是自己对依赖的理解。真实服务若与这份理解不同，测试只是反复确认了一份错误的约定；真实实现后来变化，而替身没有同步维护，也会产生同样问题。原书因此指出，由服务提供方维护伪实现（fake），能显著缓解这种脱节。

假设报表服务认为“没有数据”会得到成功状态和空数组，于是在测试中一直返回这个结果；真实查询服务却把“统计日尚未结算”表示为一种可重试错误。双方各自的单元测试都可能正确，连起来却会把“还不能生成”误当成“已经生成空报表”。缺口在双方的行为约定上，单看某个函数的分支覆盖发现不了它。

第二类空白是**程序与配置的兼容性**。服务除了代码，还需要启动脚本、数据文件、选项、配置数据库等才能运行。单元测试直接构造对象，可能完全没有走过真正的启动路径。原书把配置变更描述为当时 Google 重大故障的首要来源，并举出 2013 年一次未经测试的错误网络配置推送引起全局故障的案例。配置进入版本控制，则既能被带进测试，也能在故障后定位到具体变更。

第三类空白是**负载与组合行为**。逐次调用一个处理函数，很难暴露系统层面的现象，常见的有连接池耗尽、排队等待、服务间重试相互放大。原书称负载与压力下的表现是“高度涌现”的性质：它属于整个系统，而不属于某个单独部件。单元测试为了快速可靠，有意排除了真实依赖、网络和数据带来的混乱；原书将这种有用的简化比作“真空效应”。

还有一类空白来自人的预见能力。工程师能为预想到的输入编写断言，却难以列出所有真实用户的操作顺序。按照 Hyrum 定律，使用者可能依赖公开文档之外的可观察行为，例如稳定的排序或某种错误响应。验证声明过的接口契约，仍可能漏掉实际使用中形成的兼容性。探索、真实流量与版本差异比较，正是后文用来补充这一部分的方法。

<a id="smallest-useful-integration"></a>

## 03　系统越大，越要缩小每项测试

更大测试会消耗启动、部署、运行和排查的时间；共享资源还可能使两次测试互相干扰。它跨越几个团队时，失败由谁负责也变得含糊。各团队若采用完全不同的运行框架，大规模修改代码的工程师甚至不知道怎样启动这些测试。可靠、快速、可扩展，本来是测试的基本要求，却需要在更大测试中付出额外工作才能保持。

Google 很早就在使用自动化大测试：AdWords 在 2001 年已有端到端测试，Search 等产品随后也有类似测试。后来 Google 强化单元测试，并用 TAP 持续构建系统承接满足隔离、构建版本和时限要求的测试；许多既有大测试不符合这些条件，仍需要其他持续执行机制。测试基础设施的收敛，没有消除系统层面的风险。

时间也会改变测试组合。一次性脚本直接运行验证，可能已经够用；当它逐渐加入功能、共享给别人，手工检查若原样累积，就容易形成上重下轻的“冰淇淋筒形”测试套件：大量手工端到端验证，少量底层自动测试。如果实现从一开始就难以隔离，后来补自动化也只能继续堆端到端测试。作者建议，在确认代码需要持续存在的最初几天，就开始建立单元测试基础，再增加集成测试，把重复的手工回归逐步自动化。

规模继续增长时，困难来自组合。原书虚构的带广告社交网络，已经包含两组用户、两个界面、三套数据库、一条索引流水线和六个服务。需要端到端验证的情境，会随系统结构呈指数或组合式增长；把每种情境都放到一套完整系统里验证，成本很快失去控制。

书中还用两个“准确率只有 10%”的替身算出 `1 − 0.1 × 0.1 = 99%`，把它称为出现缺陷的可能性。更准确的读法是：若 10% 指每个替身在相关交互中与真实行为一致的概率，且两者相互独立，99% 是至少一个替身失配的概率；失配是否造成用户可见的缺陷，还要看具体交互。结论仍然成立：系统组合越多，靠多份未经校验的替身约定拼出整体信心就越困难。

作者提出“尽可能小的测试”：把一个长用户旅程拆成若干相邻组件的集成测试，并将前一段产生的输出保存为后一段使用的输入。这里的“链”靠持久化的样本连接，各段测试不必按顺序依次执行。这样既保留了真实交互的证据，又能让各段独立运行、定位与维护。

图 14-1：从左到右看各测试覆盖的相邻组件，再沿下方箭头看样本如何保存与复用。实线是保存输出，虚线是读取样本；拆分后仍需为关键完整旅程保留合适的端到端验证。点击[查看大图](../diagrams/exports/ch14-chained-boundaries.svg)。

图中把 A、B、C、D 分别设想为任务入口、任务服务、生成服务和存储适配器。某段失败后，首先检查这一段的两个组件与边界样本，比从整条用户旅程的最后一个错误反推全部服务更直接。样本之间的一致性需要维护，而整个系统的并发、部署和时序风险，也仍要交给相应测试覆盖。

> **核心观点**
>
> 缩小被测系统，是同时降低运行成本、偶发失败和排查难度的主要手段。拆分的依据是要验证的行为边界，并通过真实输出样本维持相邻部分的联系。

<a id="choosing-the-sut"></a>

## 04　为每次测试选择合适的被测系统

原书将大测试的基本结构归纳为四步：**取得被测系统、准备初始数据、执行动作、验证行为**。与单元测试不同，被测系统往往是独立进程甚至一组机器；测试程序负责驱动它，而不是直接调用同一进程里的类。因此，环境准备本身就可能成为主要成本与故障来源。

这里需要同时考虑保真度与[**环境自足与隔离（hermeticity）**](ch11.md#trustworthy-signals)。环境越自足、隔离越充分，测试越少受到其他用户、其他测试与共享基础设施的干扰；保真度越高，环境的程序、配置和拓扑越接近生产。两者常有张力，但可以逐项选择，而不必只在“全用替身”和“直接上生产”之间二选一。

- **单进程系统**把多个组件放进一个可执行程序，测试也可在其中运行。它容易控制，但改变了生产中的进程边界、通信和启动方式。
- **单机多进程系统**保持实际二进制程序及进程边界，尽量沿用生产启动配置，只把它们放在一台机器上。这通常能以中型测试的资源代价覆盖重要集成行为。
- **多机独立系统**更接近分布式部署，但需要额外处理机器、网络和部署引入的不稳定性。
- **共享预发布或生产环境**省下每次新建完整环境的成本，却要等待候选代码进入环境，并面对数据与其他使用者的干扰；生产还有真实用户风险。
- **混合系统**单独启动关注的服务，后端则复用共享环境。原书指出，在 Google 这样高度互联的组织里，复制所有依赖通常不可行，因此混合方式有现实必要。

共享环境还有反馈时机的问题：只有代码部署进去，测试才跑得起来；因此，生产测试无法阻止这份代码第一次进入生产。把共享预发布环境按时间预约给工程师，也会随着人员和服务增长出现排队。相较之下，能够按需创建的单机隔离环境或独立云环境，可以让多个候选版本并行验证。图 14-2 把这几种形态排在一起：越往右越接近生产，也越难隔离干扰；能否在代码进入环境之前运行测试，又把它们分成独立启动和共享环境两组。

![四种被测系统形态从左到右排列：单进程、单机多进程、多机独立、共享预发布或生产环境，越往右保真度越高、环境自足与隔离越弱；前三种可按需独立创建、并行验证候选版本，共享环境要等代码部署进去才能测试；混合系统独立启动关注的服务，后端复用共享环境。](../diagrams/exports/ch14-sut-spectrum.svg)

图 14-2：上方双向箭头表示取舍的两个方向，四个方框从左到右按保真度由低到高排列；下方括号把它们分成独立启动与共享环境两组，虚线箭头表示混合系统从两组各取一部分。点击[查看大图](../diagrams/exports/ch14-sut-spectrum.svg)。

原书的 Webdriver Torso 案例让生产风险变得很具体。YouTube 为验证真实上传与视频渲染，自动生成视频、上传，再检查质量，使用的是 Google 所有的 Webdriver Torso 频道。但频道和大部分视频公开可见，后来引起媒体关注和公众解谜，最终才公开说明与 Google 的关系。测试在工程上有明确目的，产出的内容却同时成了真实产品里的公共内容；写入生产的副作用也包括“别人会看见”。

缩小系统时，作者特别建议审视界面与后端的边界。界面外观变化容易破坏测试，异步交互又使等待复杂；如果每项后端情境都经过浏览器，就把两边的维护成本绑在一起。可以保留必要的界面测试，同时通过稳定的公开 API 驱动后端集成测试。第三方服务也是重要切分点：它可能没有可用测试环境，调用可能收费，故障与流量也不受自己控制。

书中还举出用内存数据库替代真实数据库、移除不相关服务来缩小系统的做法，关键是在保真度与成本、稳定性之间找到合理的边界。若本次要检验的正是真实数据库的查询、事务或配置行为，替换之后便丢掉了这项保真度；缩小环境时，需要留下与本次风险有关的真实部分。

<a id="record-and-replay"></a>

## 05　从真实依赖获得可回放的证据

把整个服务换成具有相同 API 的测试替身，可以显著缩小环境，但“接口长得一样”还不够。请求如何解释、错误怎样返回、哪些状态变化可以观察，都属于行为约定。原书介绍了两种把约定与真实服务重新连接起来的方法。

第一种是**消费者驱动的契约测试**：调用方描述自己依赖的输入和预期输出，提供方再用真实服务验证这些例子。契约因此同时约束两端，不能只存在于调用方自行安排的打桩里。原书举出 Pact 和 Spring Cloud Contracts 两个公开工具，并说明 Google 因大量依赖 Protocol Buffers（Google 的结构化数据序列化格式），内部并不采用它们。

第二种是 Google 当时常用的**录制／回放代理**。录制模式运行较大测试，让客户端通过代理访问真实依赖，记录请求与响应；只有这一轮测试通过，才产出可用的流量记录。回放模式运行较小测试，以记录的响应代替启动真实依赖，从而把较高保真度的一次交互转化成日常可以快速复用的材料。

![提交后较大测试通过代理记录真实服务交互，成功后保存流量；开发和提交前测试通过匹配器读取记录，未匹配的请求需要重新录制。](../diagrams/exports/ch14-record-replay.svg)

图 14-3：先看上行的真实调用，再沿向下的箭头看流量如何进入回放；横向箭头表示请求与响应，向下箭头表示记录的保存和读取。回放这一行不启动图中真实依赖。点击[查看大图](../diagrams/exports/ch14-record-replay.svg)。

请求里可能有每次变化的时间、标识符或其他非确定内容，因此回放通常需要匹配器，决定当前请求应该得到哪份响应。原书指出，这与打桩中的参数匹配相似。由此也可以推出，匹配规则本身决定了测试能发现什么：若把本应区分的请求视为相同，就可能掩盖变化；若要求无关字段逐字一致，又可能制造偶发失败。

假设报表客户端原来只查询一个统计日，后来改成同时发送时区。旧记录中没有对应的新请求，回放无法匹配。此时需要运行录制模式，与真实依赖确认新的请求行为，再生成记录，不能仅为了让测试通过就随意改一份响应。原书把较大录制测试放在提交后持续执行，把较小回放测试用于开发和提交前；这种分工成立的前提，是录制模式本身也容易启动、足够稳定，并且记录能够持续更新。

> **核心观点**
>
> 较大测试不只输出“通过／失败”，还可以产出真实交互样本，供较小测试快速回放。样本需要真实执行来更新，回放通过也只覆盖记录与匹配规则所表达的行为。

<a id="data-and-verification"></a>

## 06　准备状态、流量与判断依据

大测试的数据有两个角色。**初始数据（seeded data）**决定系统开始运行时已经存在什么；**测试流量（test traffic）**是在运行过程中发送给系统的输入。对于报表服务，已有的统计快照、账号与权限属于初始状态，随后发出的导出请求、轮询和下载请求属于流量。把两者分开，才能看清一次失败究竟来自环境没有准备好，还是系统处理动作不正确。

初始状态往往比单元测试的对象构造复杂。某些服务需要领域基础数据才能启动；社交产品需要足够的用户、关系和历史内容才像真实系统；地图测试可能需要以已有地图数据为底图。数据写入方式同样重要：直接插入数据库虽然方便，却可能绕过业务服务原本会触发的检查、索引更新和其他副作用。测试最终得到的状态，未必是正常使用可以产生的状态。

原书列出人工构造、完整复制和抽样三种来源。人工数据容易表达明确情境，但多服务之间的一致性要自己维护；复制生产数据能保存真实结构，却可能大到无法承担；抽样则试图以更少数据覆盖关键情境。原书所说的“智能抽样”，是用尽量少的数据换取尽量大的覆盖。例如在假设的报表场景中，只随机抽到小租户，就可能完全错过大租户的大文件路径；有目的地保留不同数据量与状态，才更接近这项测试的目标。

系统运行并接收输入之后，还需要一个判断依据。原书归纳了三种：人工观察、明确断言，以及两个版本之间的差异比较。人工探索适合发现原先没有想到的行为；断言适合已知且可以清楚描述的规则；差异比较则把旧版本作为参照，寻找尚未预先写成断言的变化。

这些判断各有信息来源。假设导出请求成功，明确断言可以检查任务最终状态、文件是否可读、金额总计是否符合已知样本。仅断言“HTTP 返回成功”，得到的信心就只到请求被接受这一层。差异比较则可以发现新版文件的列顺序变了，但需要人判断这是约定内的改动还是兼容性回归。环境、输入与验证方式共同决定一项测试真正覆盖了什么。

<a id="functional-config-load"></a>

## 07　围绕功能、配置和负载组合测试

原书列举的多种大测试，可以理解为对“被测系统、数据、验证方式”的不同组合。组合之前先形成测试策略：产品有哪些主要风险，哪种测试可以给出相应证据。作者把这种规划能力视为优秀测试工程师的重要能力；它同样属于软件设计的一部分。

**一个或多个真实程序的功能测试**，通常在单机隔离环境或独立云环境中运行，用人工准备的数据与明确断言验证公开 API。它补上的是进程、打包与真实通信的缺口。微服务之间不再各自面对想象出来的返回值，而是由真实二进制程序交换请求。浏览器和设备测试是它的重要特例：对终端用户而言，应用界面本身就是可操作的入口，因此仍需验证渲染、交互与平台上的行为。

**部署配置测试**往往更轻。使用实际配置启动程序，观察是否成功，就能发现缺失文件、非法选项或配置与程序版本不兼容等问题。原书称之为冒烟测试：可以不准备额外业务数据，主要判断系统能否启动。它的信号清楚，也容易加入配置变更流程；不过成功启动只证明走过的启动路径没问题，业务行为仍需另行验证。

**性能、负载与压力测试**则需要更接近真实系统的资源、拓扑和流量。原章把三者放在一起讨论，可以这样区分：性能关注某种工作负载下的运行表现，负载测试观察预期需求下系统如何工作，压力测试进一步检验接近或越过承受能力时的行为。对多个请求的处理、排队与资源竞争，本来就不是单次函数调用能充分代表的。

比较两个版本的性能时，机器差异可能冒充代码差异。原书举例：基线恰好运行在快机器上，新版运行在慢机器上，结果就像出现了回归。作者因此认为，最好让两个版本运行在同一台机器上；一台机器放不下时，可以多次运行并去掉峰谷值来校准。同机比较时还要留意，两个版本若同时运行、争用资源，也会给测量带来新的干扰。

仍以假设的报表服务为例，功能测试可以验证统计日与文件内容；配置测试验证工作进程能以候选配置启动；负载测试再让许多账号并发提交任务，观察吞吐量、等待时间与失败率。三个测试各自产生清楚信号，比用一个耗时很长的端到端测试同时承担所有任务更容易理解。真实负载的结构也很重要：若所有请求都查询同一份缓存过的小报表，即使请求数很大，也未必覆盖实际瓶颈。

<a id="exploration-and-diff"></a>

## 08　用探索和差异发现预料之外的行为

**探索性测试**让熟悉产品的人尝试新的可达路径，寻找不符合预期或直觉的行为，也包括安全问题。它与按照固定步骤重复检查旧功能的人工回归不同。Google 的 bug bash 把工程师、产品经理、测试工程师等集中起来，在有大致重点的前提下自由试用，借助不同人的经验增加操作多样性。发现可复现缺陷后，再把相应行为固化为自动测试，才能更频繁地防止重现。

人工探索有创造性，却仍需要真实的人时。系统增长后，重复所有路径不会自动变得更便宜。因此，它适合开辟未知情境，而重复回归应尽可能交给机器。原书脚注列出了 Whittaker 的探索性测试专著，可作延伸阅读。

**A/B 差异回归测试**的做法是启动基线版本与候选版本，向公开 API 发送相同输入，再比较输出。原书指出，它在 Google 多种产品中很常见，因为真实使用依赖的行为往往超出人工列出的断言。这里的 A/B 指两个版本的输出比较；下一节按用户分组衡量指标的线上实验，是这个词的另一种用法。

例如，假设新版报表把金额计算迁移到另一套实现。给两个版本相同的快照与请求，比较生成文件：多数任务一致，少数任务金额相差一个最小货币单位，另有文件只在生成时间字段上不同。差异本身还不是结论。工程师需要确认金额差异是批准过的舍入规则变化，还是计算回归；生成时间差异则可能是需要单独处理的非确定噪声。这个过程使测试能发现尚未预写断言的变化，同时把判断负担转移到差异审阅上。

原书还介绍两个变体。**A/A 比较**让系统与自身进行对照，帮助识别时间、随机性等本底噪声；**A/B/C 比较**把上次生产版本、当前基线和待提交变更一起看，区分本次变更的影响与下一次发布中已经累积的影响。两者都在改善差异的可解释性。图 14-4 把三种比较放在一起：A/A 先找出本底噪声，A/B 的差异才容易解读；A/B/C 则把本次变更与已累积的变化分开。

![三种差异比较：A/A 让基线与同一基线的另一份对比，差异是本底噪声，用来从 A/B 中剔除；A/B 对比基线与候选版本，差异包含行为变化和噪声，需要逐条判断是预期变化还是回归；A/B/C 并排上次生产版本、当前基线和待提交变更，分别看出本次变更的影响和下一次发布中已累积的变化。](../diagrams/exports/ch14-diff-variants.svg)

这类测试要持续有效，需要处理四件事：有人有能力批准或拒绝差异；尽量消除无关噪声；流量能够覆盖重要和少见情境；两套环境可以保持可比较。旧版本本身也可能有错，与它保持一致并不等于正确。差异测试省下了大量逐项编写预期结果的工作，理解每处变化的意义仍要靠人。

**用户验收测试（UAT）**从另一种缺口出发：开发者可能在实现和单元测试里重复同一个需求误解。由明确客户或客户代表参与定义用户旅程，再通过公开 API 自动验证，就能让预期行为有独立来源。书中提到可执行规格语言，同时解释 Google 当时并不大量依赖它们，因为很多产品的行为定义者本身就熟悉代码。

<a id="production-validation"></a>

## 09　在生产中验证健康、韧性与用户价值

进入生产后，仍有预发布环境无法充分回答的问题：真实部署是否健康，故障发生时系统与组织能否继续运转，用户是否真的从改动中受益。这几类验证与监控有重叠，但仍可以沿着被测系统、输入和判断方式来理解。

**探针（prober）**定期对真实环境执行带断言的功能检查。原书建议采用已知、确定、只读的动作，例如发起搜索并确认有结果返回，而不要求具体结果始终相同。生产数据会变化，断言应选择相应稳定的性质。只读动作也能减少测试污染：如果每次探测都创建数据，可能出现重复写入失败、未来无法再写或用户可见的副作用。

**金丝雀分析（canary analysis）**把验证与渐进发布连接起来：先让少量生产实例使用候选版本，对这些实例运行探针，并比较候选与基线部分的健康指标。探针提供明确的功能信号，指标比较则帮助发现错误率、延迟等变化。它能在扩大发布之前缩小问题影响，但被捕获的故障已经发生在生产；这与发布前的隔离测试承担不同位置的风险。

**灾难恢复演练与混沌工程**主动制造故障，检验恢复和容错能力。书中的 DiRT 是需要跨公司协调的大规模演练，情境可以包括数据中心火灾、攻击和设施不可达。一次模拟地震让 Mountain View 总部与公司其余部分隔离，暴露出的不只是技术依赖，还包括关键决策者无法联系时的组织运转问题。脚注还记下一段插曲：演练期间许多员工无法工作，纷纷涌向咖啡厅，给咖啡厅团队造成了额外压力。演练本身就有真实成本，原书也因此只低频组织这种大规模演练。

作者把混沌工程描述为更持续地注入背景故障，并观察系统表现的方式，提及 Netflix 的推广和 Google 当时的 Catzilla 系统。此类测试适用于具备相应容错基础、能够承担注入风险并恢复的系统；它检验的是对不稳定性的承受能力，也要求对测试本身的影响有控制。

**用户评估**检验的则是价值，而不只是技术健康。内部试用（dogfooding）让一部分员工在真实环境体验功能并反馈；线上实验向一部分用户提供新行为，以对照组比较汇总指标；人工评估员则对结果作出优劣判断并说明原因。原书举广告背景色实验影响点击率的故事，说明看似很小的界面改动，也可能明显影响使用行为。

这些方式的结果不能互相替代。没有崩溃、延迟稳定，只能说明某些技术条件得到满足；点击率变化说明被测指标变化，还需要结合产品目标理解；对于没有唯一正确答案的搜索或机器学习输出，人工评估能补充“结果是否更好”的证据。把技术正确性、运行韧性和用户价值分开，才能理解为什么一套测试组合需要不同验证者和数据。

<a id="workflow-and-ownership"></a>

## 10　让大测试成为可维护的开发日常

大测试即使不适合进入单元测试的统一平台，也需要明确的提交前、提交后和发布执行机制。原书介绍，Google 为不符合 TAP 条件的测试保留其他持续构建，并尽量在评审界面汇总结果。较快的测试在提交前直接反馈给作者，较昂贵的测试可持续在提交后运行，并进入发布流程。只在提交后发现问题，就意味着有问题的变更已经进入主干，需要再定位与撤回；执行位置是在反馈速度、资源和开发摩擦之间作出的选择。

需要人工批准的差异也可以接入流程。例如，评审要求先检查界面差异再批准修改；原书还提到，在未解决差异的情况下提交代码，会自动创建阻断发布的缺陷。关键在于差异必须有去向，而不只是生成一份大家不会打开的报告。

让这些测试容易编写与运行，需要共享的环境控制、数据准备、断言、差异比较和编排库，也需要清楚文档与示例。已有共享生产环境的启动成本低，差异比较的预期结果维护少，看起来都很省；但若人工审阅和生产安全保障耗费更多，总成本仍可能更高。作者要求从整个维护周期看成本，而不只计算一次运行需要多少机器。

提速首先考虑减小范围，以及把能够独立运行的部分拆开并行。随后是**按状态等待，而非固定睡眠**。假设生成文件通常只需几百毫秒，测试每次先睡几秒再检查，快的时候平白等待，忙的时候又可能仍未完成。事件处理器或完成通知可以在状态真正改变时继续；没有这些机制时，可以轮询状态并设定明确的总期限。原书提到轮询频率可以接近微秒级；轮询远程服务时，间隔应随操作成本放宽，以免高频请求加重服务与测试平台的负担。

测试还可能有两层等待：外部测试在等任务完成，内部服务也在等某个依赖。把本机测试中不必要的生产级延迟调小，能够提速；调得过小，又可能在调度稍慢时引入偶发失败。原书因此要求这些超时可配置，并在用户允许的行为与测试稳定性之间选择。遇到过载后所有超时一起失败，再通过更多重跑增加负载，还可能形成恶性循环。

有些系统为了保护用户，会把内部错误降级成表面上仍然有效的结果。书中举例，广告服务超过内部时限时可能选择不展示广告，而不是返回服务器错误。测试若只看到“没有广告”，就很难区分业务逻辑错误和偶发超时。因而提速与稳定性不仅关乎时长，还关乎是否留下了清楚的失败原因。

构建时间也在反馈路径里。原书讨论了一种取舍：关注的核心程序使用候选代码，其他必要依赖使用已知良好的预构建版本，可能比每次从源码重建全部依赖更快，也更接近各服务独立发布的生产现实。但这同时改变了测试的版本组合，需要明确所验证的是哪些版本之间的兼容性。作者指出，这种模式在当时的 Google 单仓构建体系中并不容易直接支持。

测试一旦失败，陌生工程师也应该能看懂。清楚的信息会写出测试了什么、预期什么、实际什么，而不仅是“断言失败”。跨进程测试还需要日志、请求关联标识或调用链材料；单个进程里的堆栈往往解释不了整个系统。原书用 Dapper 说明，通过同一请求标识关联 RPC 链上的记录，能够帮助沿服务边界寻找差异来源。以报表服务为例，任务标识、统计日、候选版本和相关日志，比一个孤立的失败栈更接近可操作的排查起点。

最后必须有具名责任人。项目内部的集成测试可以由项目负责人统筹；横跨多个服务的业务功能测试，需要有权推动整条功能健康的人负责，可能是工程师、产品经理或测试工程师。责任不仅是一个联系人，还包括评审修改、支持排查和维护测试的能力、时间与激励。原书介绍利用代码目录的 OWNERS 或逐测试注解记录责任信息，让失败能够自动找到合适的人。

> **核心观点**
>
> 一项大测试的完整交付，还包括稳定的运行入口、能理解的失败证据和能够推动修复的责任人。测试持续被运行、被相信、被处理，才会成为系统的安全网。

把本章连起来，测试策略形成了一条清楚的主线：从单元测试够不到的风险出发，为它选择必要的真实边界；通过隔离、拆分、真实样本与合适数据控制成本；再用断言、差异、人工探索和生产验证获得不同证据。最终目标是保留足够保真度，同时让每个测试尽可能小、尽可能容易维护，使系统可以在持续变化中仍然获得可信反馈。

概率读法澄清：原书称两个“10% 准确”的替身组合后，出现缺陷的可能性是 99%（`1 − 0.1 × 0.1`）→ 算术正确，但原书没有把保真度定义为概率；乘法成立，需要把 10% 理解为每个替身与真实行为一致的概率，并假设两者独立 → 正文只把 99% 解释为“至少一个替身失配”的概率，它不是系统的缺陷概率。
