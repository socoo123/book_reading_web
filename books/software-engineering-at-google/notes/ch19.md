# 第 19 章｜Critique：Google 的代码评审工具

**Critique: Google’s Code Review Tool · 架构提升读书笔记**

[第九章](ch09.md)解释了代码评审为什么值得做：让代码更容易理解和维护，让知识流动，让进入仓库的改变经过另一位工程师认真检查。第十九章把视角移到承载这些工作的工具。一次评审往往要经历阅读、评论、修改、等待和提交；每一个环节都不复杂，连接不顺时，却会消耗大量注意力。

Critique 是原书介绍的 Google 主要内部评审工具。本章值得学习的，是它如何把一次变更组织成可以持续推进的协作：用快照保存讨论对象，用差异视图降低理解成本，用注意力集合指出下一位行动者，用清楚的批准条件说明还缺什么。以下按本书 2020 年出版时的描述介绍其设计，并穿插原创的假设情境。

<a id="tooling-principles"></a>

## 01　工具的职责，是让评审容易发生

原章提出四个设计原则：简单、以信任为基础、通用沟通、融入工作流。它们共同回答了一个问题：评审工具怎样支持人的判断，同时尽量少给协作增加手续。

**简单**首先表现为日常路径短：页面加载快，文件之间容易跳转，键盘操作顺畅，当前是否达到可提交条件一眼可见。工程师每天重复使用的工具，哪怕每次只少一次查找，也能持续节省切换和重建上下文的时间。作者们因此放弃了不少只适合少量使用者的有趣功能，避免让所有人承担更复杂的界面和状态模型。

**信任**决定了工具怎样理解作者与评审者的关系。评审者给出清楚的修改意见以后，可以相信作者会认真完成，不必为每一个小调整再安排一次确认。变更及其讨论对有权查看代码的同事保持开放，也使非指定评审者能够补充信息。信任在这里有实际的流程含义：减少重复核验，同时保留明确的责任和记录。

**通用沟通**意味着优先提供评论、回复和修改建议，让人把要求说清楚。假设评审者关心某个重试条件，他可以描述触发情形、影响和建议改法；为这种讨论专门增加五六种意见类型、升级状态和确认按钮，未必比一段清楚的话更有帮助。工具提供共同的讨论场所，理解彼此仍然依赖参与者。

**工作流集成**则让工程师能够从评审跳到代码搜索、编辑和测试结果。这里存在一个有意识的克制：团队曾考虑把编辑、评审和搜索合成一个“Code Central”，最终仍把 Critique 的核心保持为评审。相关能力通过链接或少量嵌入接入，由各自的子系统实现。这样既能连续工作，又不必在评审页面中重新容纳一整套 IDE。

这些原则落实到通常的提交前评审流程：作者在工作区写代码，上传快照，查看差异和自动结果，选人发起评审；评审者阅读并集中发布评论，作者修改、回复并上传新快照；所需评审条件满足后，再发起提交检查。后面的各项设计，都在降低这条路径上的理解成本和等待成本。

> **核心观点**
>
> 评审工具应把讨论对象、下一步行动和提交条件表达清楚。简单的界面与明确的状态，让人的精力留给代码及其维护理由。

<a id="snapshots-and-diffs"></a>

## 02　快照与差异，让双方讨论同一份改变

**变更（change）**代表一项正在完成的修改，**快照（snapshot）**保存它在某个时刻的补丁状态。一项变更可以有多个快照，评论和后续修改围绕这条演进记录展开。作者继续在工作区修改时，评审者仍能知道自己刚才看的是哪一版，而不必追赶一个随时变化的文件。

上传后先看自己的 diff，是工具给予作者的一次视角转换。在编辑器里，人容易跟着“我刚做了什么”阅读；在评审视图中，则需要面对“另一位工程师实际会看到什么”。作者可以发现混入的临时改动、遗漏的文件，以及缺少说明的跳跃，还能提前留下问题、关联缺陷记录，把评审者需要的背景带进来。原章提到，关联缺陷时的自动补全会优先显示分配给作者的相关条目，减少寻找背景材料的操作。

Critique 的差异计算以经过优化的**最长公共子序列**算法为起点，再补上更适合读代码的呈现方式：语法高亮、由 Kythe 支撑的符号交叉引用、考虑词边界的行内字符差异、不同程度的空白忽略，以及代码移动识别。普通文本 diff 能找出增删，阅读代码还需要分辨哪些只是搬动，哪些确实改变了行为。

沿用本笔记的假设报表服务。小林把上传逻辑挪到辅助函数，同时调整超时判断。若界面把整段搬动都显示为删除再新增，阿岚需要自己确认哪些内容没有变；移动识别能先把结构变化标出来，行内差异再突出真正变动的条件。阿岚由此更容易把注意力放在行为变化上。涉及完整逻辑的判断，仍需要沿调用关系阅读必要上下文。

并排显示新旧代码，也是一项实际的工程取舍。原章记述，Critique 发布时针对当时典型的 1440 像素屏宽，调整字体、字号和布局，去掉差异区的多余边框与内边距，使 Java 的 100 字符行宽也能并排容纳。这组取舍的要点，是把空间优先留给需要比较的信息。图片、大文件和大型变更的加载速度，以及只跳到修改区域的快捷键，同样影响一次阅读能否连续完成。

快照比较进一步减少重复阅读。假设第一次上传为 S1，阿岚已经看完；小林回应意见后上传 S2，阿岚可以比较 S1 与 S2，先定位这一轮新改了什么，再检查相关上下文。需要重新审视整体时，也可以比较基线与 S2。Critique 允许选择任意一对快照，文件级的小型版本链还会突出有评论、已评审或有测试覆盖信息的版本，并折叠相近快照。Critique 还会预取全部内容，来回切换版本不必反复等待加载。

有些变化的结果不只存在于源码文本中。Critique 还支持自定义的产物差异，例如界面截图和生成配置的比较。它们让评审者同时看到“代码怎样改”和“产物变成什么样”，适合补足单看源码不容易发现的影响。

<a id="automated-feedback"></a>

## 03　把自动反馈送到能立即处理的位置

每次上传快照都会触发代码分析器。Critique 在变更说明下用小型状态标签汇总结果，在 Analysis 页签呈现细节，也可以把具体发现直接放到 diff 的相应位置。机器结果使用与人工评论不同的样式，帮助读者分清它们的来源。

这层呈现刻意保持简单。原章中的标签可以用红色突出需要关注的发现，黄色表示分析仍在运行，其他情况使用灰色；分析器决定一项发现是否需要突出，工具没有再提供一长串高亮等级。颜色只表达关注与运行状态，流程上的阻断另由下文的 presubmit 表示。

原书用行尾多余空格说明一条完整路径。风格检查发现问题后，作者从分析器标签进入对应代码位置，看到具体原因；如果结果附带修复建议，就能先预览，再选择应用。机械问题从“另一位同事提醒一下，作者再切回编辑器找位置”，缩短成了“发现、定位、确认、修复”相连的过程。快速分析结果可以先展示，较慢的分析继续运行，作者无需等所有工具同时结束才开始处理。

另一类自动化是 **presubmit 检查**，即发送评审或提交时执行的钩子。团队可以让它运行项目测试、校验代码与变更说明的局部约定，或自动添加知会邮件列表。最后一项也很有代表性：工作流自动化不仅检查代码，还能把需要知道这次变化的人接进来。

原章特别区分了检查时机。Tricorder 检查随每次快照上传运行；运行测试较耗资源，在 Google 属于 presubmit，只在请求评审和提交时运行。这样，作者反复调整时仍能得到较快反馈，正式跨过流程关口时再进行更完整的检查。

presubmit 的失败还带有明确的阻断含义：相关检查不通过时，变更不能发送评审或不能提交，作者也会收到邮件通知。普通分析发现与这种流程门槛需要在界面中区分。评审者若认为某项分析发现必须处理，可以点击“Please fix”，把它转成未解决评论；机器提供线索，人的判断因此进入了明确的待办事项。图 19-1 把两类检查放回评审流程：分析器随每一次快照上传运行，结果供作者当场处理；presubmit 把守请求评审和提交两处关口，失败就停在这一步。

![评审流程中的两类自动检查：分析器在每次上传快照时运行，结果供作者当场处理；presubmit 在请求评审和提交时运行，失败则不能发出评审或不能提交。](../diagrams/exports/ch19-check-timing.svg)

图 19-1：中间一行是评审流程，从左往右推进。上方虚线框和虚线箭头表示随快照运行的分析器，下方实线框和实线箭头表示 presubmit 把守的两处关口。点击[查看大图](../diagrams/exports/ch19-check-timing.svg)。

> **核心观点**
>
> 自动反馈要同时回答三个问题：发现了什么，去哪里处理，它是否阻止当前这一步。把结果放进评审上下文，比让人到另一套系统中自行拼接信息更有效。

<a id="reviewer-routing"></a>

## 04　选对评审者，才能把变更交给合适的人

在小团队里，作者通常知道谁熟悉代码，但仍要考虑同事是否休假，以及评审是否长期集中在少数人身上。原章介绍的 GwsQ 允许团队配置一个接收评审的邮件别名。作者将变更交给团队别名，工具再根据该别名关联的配置选择具体成员。它把“交给哪个团队”和“本次由谁接手”分成两步，团队可以调整内部安排，作者不必一直维护一张私人通讯录。

跨团队修改时，还要知道谁有权批准、谁真正了解相关代码。Critique 的推荐会考虑代码负责人、最近修改过相关代码的人、可用性与时区，以及 GwsQ 配置；它还能推荐足以满足批准要求的一组评审者。负责人体现维护责任，近期修改体现熟悉程度，可用性决定这次工作能否及时被接住，这几个因素需要共同考虑。

例如，假设报表服务需要迁移一个公共上传接口。小林熟悉报表逻辑，却不知道公共库的人员分工。只搜索最近一次提交的作者，可能找到刚好休假的同事；只找熟人，又可能漏掉库的维护批准。把所有权记录、修改历史与可用信息组合起来，能让请求更接近真正可以完成这次评审的人。

所需责任与参与人数的区别，沿用[第九章的三类批准](ch09.md#approval-lenses)：同伴对实现的检查、模块维护责任、语言规范资格可以由不同人覆盖，也可能集中在同一位评审者身上。工具推荐的目标是覆盖需要的责任，同时减少不必要的协调，而非一律增加会签人数。

发出请求之后，评审者仍可以退出分配或转交给别人，作者也可以暂缓评审。这样的调整让工具能承认实际工作中的信息变化：最初推荐只是一种有依据的起点，真正接手的人还可能发现需要另一位专家。

<a id="comment-and-iterate"></a>

## 05　评论应当形成一轮完整的反馈

Critique 中的评论默认是**未解决（unresolved）**，表示作者需要处理；提供信息或可选建议时，评审者可以直接使用已解决状态。作者回应未解决评论，可以通过修改代码解决，也可以解释原因、说明另一种处理方式，再将讨论标为已解决。这个模型让待办有清楚的入口，又容纳了评审中的知识交流。

评论先作为草稿保存，等评审者完整读过变更、整理好意见后，再一次发布。这样，读到后文已经说明的事情，可以先删掉前面的疑问；几处相关问题也可以合成一条更完整的解释。作者收到的是一轮经过组织的反馈，较少出现“刚改完第一处，第二个无关区域又来一条”的零碎往返。

工具也支持把建议具体化。评审者可以在最新文件版本上行内编辑，Critique 把这些编辑转成附带修复的评论，交给作者决定是否应用。对于简单命名或局部表达调整，这比用文字描述应替换的每一个字符更直接。需要解释行为原因时，修改建议仍应配上相应说明。

回应常见意见有两个快捷入口：“Done”表示已经处理，“Ack”表示已读并理解，后者通常适合信息性或可选意见。两者都能把尚未解决的线程改为已解决。按钮的便利依赖于准确使用：前者应对应实际落实，后者应对应这条评论所需要的确认；存在实质分歧时，文字回复能够留下双方可以继续判断的依据。

继续看假设的上传变更。阿岚指出，新的超时分支虽然已经正确结束任务，变更说明却还写着旧行为。小林修改说明后用 Done 回应。另一条评论介绍团队已有一个相近的辅助方法，供下一次整理时参考；小林用 Ack 确认即可。两条线程都可以结束，但它们记录了不同的回应内容。

评审进度还细化到个人与文件：每位评审者可以勾选已经看过的最新快照文件。作者改动某个文件后，这个文件的已评审标记会对所有评审者清除，提醒大家最新内容已经变化。已经给出的 LGTM 不会因此清空；是否仍然认可变更，由后面介绍的批准机制处理。

开放的评论还容纳了“路过评审”：能查看变更的同事即使没有被指定，也可以补充意见。某个调用方维护者可能及时发现兼容性问题，后续调查者也可能补上运行背景。工具把这类信息留在同一条变更记录中，减少它们散落在私人聊天里的机会。

<a id="attention-set"></a>

## 06　注意力集合，让等待有明确的对象

只记录“谁参加了评审”，还不足以组织下一步。作者已经回复，评审者可能以为对方还在修改；评审者提出意见，作者又可能以为正在等待另一位专家。参与者越多，这种互相等待越容易发生，评论数量和最后发言时间都难以直接说明当前轮到谁。

Critique 为每项变更维护一个**注意力集合（attention set）**：当前需要行动、变更正在等待他们响应的那些人。界面把这些人的名字加粗；发布评论时，系统会尝试更新集合，参与者也可以手动调整。集合可以同时包含多个人，因为代码行为、用户体验和运行维护可能需要并行检查。

图 19-2 用一个假设流程说明读法。每行左边是一项已经发生的事件，右边是接下来应行动的人；纵向箭头表示时间推进，横向箭头把事件连到随后需要行动的人。参与者始终是小林、阿岚和值班同事，变化的是当前的等待对象。

![假设评审中，发出请求后等待两位评审者；两人反馈后等待作者；作者修改并请求复看后再次等待两位评审者；两人确认后等待作者提交。参与者不变，注意力集合随交接变化。](../diagrams/exports/ch19-attention-handoff.svg)

图 19-2：每行右侧列出下一步行动者；参与者始终不变，注意力集合随每次交接更新。点击[查看大图](../diagrams/exports/ch19-attention-handoff.svg)。

这个小功能改变了协作的默认问题。打开变更后，工程师能先看到“我现在是否需要回应”，不必额外发消息询问谁在处理。尤其在跨时区评审中，一次状态含混就可能拖到对方下一次上线；明确交接能减少这种没有产生任何新认识的等待。

个人仪表盘把这一机制扩展到许多并行变更。Critique 的首页由可自定义的分区组成，每个分区背后都是对 **Changelist Search** 的查询。该系统索引可访问变更的最新状态，覆盖提交前和提交后，并支持基于正则表达式的查询。默认的首个分区显示需要本人注意的变更，作者也能查看仍在等待评审的项目，决定是否需要跟进。

这里的可定制性有明确的收益：调整自己怎样整理工作，不改变所有人共同遵守的评审协议。原章脚注提到，大规模变更的全局评审者尤其需要定制仪表盘，避免批量请求淹没日常工作。索引和查询仍需足够及时、足够快，否则整理待办本身就会成为新的等待来源。

通知则采用事件发布的方式与其他工具衔接。Critique 发出变更事件，外部消费者决定怎样提醒：原章介绍的 Chrome 扩展可以在轮到本人或检查失败时弹出通知，一些人喜欢即时提醒，另一些人觉得它打断专注而不安装。重要事件也可以发邮件，邮件回复会被转换成评论；还有使用者主要依赖仪表盘。共同状态保持一致，接收信息的方式可以适应不同工作节奏。

> **核心观点**
>
> “谁参与过”与“现在等谁”是两份不同的信息。把当前等待对象显式记录下来，能让一次评审以及许多并行评审都更容易继续向前。

<a id="approval-model"></a>

## 07　批准模型，把不同责任分开表达

评论表达具体问题，评审还需要一个整体结论。Critique 将这一层称为 scoring，但核心是三项可以分别理解的条件：LGTM、Approval，以及未解决评论的数量。它们共同构成通常评审流程中的可提交状态。

**LGTM（looks good to me）**表示评审者已经读过这项变更，认为它符合标准，处理剩余未解决评论后可以提交。**Approval**表示承担相应把关责任的人允许这项改变进入代码库。前者回答实现是否经过同伴认可，后者回答必要的准入责任是否得到覆盖。工具面板会列出谁给了 LGTM、还缺哪些批准以及原因、仍有多少条未解决评论。

通常的条件是：至少一个 LGTM，足够覆盖要求的批准，以及零条未解决评论。某些团队可以要求多位评审者的 LGTM。原章强调，即使其他批准已经满足，仍需要作者之外的人的 LGTM，以保留另一双眼睛的检查。实际常见的“作者加一位评审者”之所以可行，是因为不同责任可以由同一人覆盖。

图 19-3 把这里的三项条件并排展示。先看上方三列：前两列的认可由评审者给出，第三列记录需要处理的讨论是否已经结束。它们汇合后形成“评审条件齐备”；再往下，提交阶段的自动检查仍要通过。这样可以把“人工评审已经准备好”和“代码已经入库”分清。

![LGTM、足够的 Approval 与未解决评论为零共同构成评审条件齐备；随后还需通过提交时的 presubmit 检查才能入库。LGTM 与 Approval 由评审者授予，作者可以在回应处理后解决评论。](../diagrams/exports/ch19-approval-contract.svg)

图 19-3：三列汇合表示三项条件须同时满足；下方单列是提交检查这道独立关口。点击[查看大图](../diagrams/exports/ch19-approval-contract.svg)。

原章用“硬要求”和“软要求”解释其中的信任边界。LGTM 与 Approval 是硬要求，只能由评审者授予，提交前也能由他们撤销。未解决评论是软要求，作者可以在回复时自行改成已解决。因此，零条未解决评论仍是可提交条件；“软”指的是作者可以自行关闭线程，评审者不必逐条复核。

例如，假设阿岚已经确认超时实现和测试都合适，只剩一处说明需要补齐。她可以给出 LGTM，并留下未解决评论。小林完成修改、回复并解决线程后，如果所需批准和检查都已满足，就能继续提交，无需等阿岚在另一个时区再次上线点击同意。如果阿岚认为修法仍不明确、需要复看，她可以只提意见，暂不给 LGTM；情况变化时，也可以撤销已经给出的认可。

这套设计还改变了负面反馈的表达。早期 Critique 曾有“Needs More Work”和“LGTM++”，后来删去了这些额外等级，保留正向的 LGTM 与 Approval。认为还需改进时，就指出具体问题并保持相关讨论未解决。作者因此得到的是可以回应的事项，评审者也需要说明自己的判断依据。简单的模型在这里支持了更有内容的沟通。

工具不强制每次新快照都重新获取 LGTM。已经理解的小修正可以依赖作者落实，仍需检查的重要改变则由评审者明确要求复看、保留或收回批准。由此节省的时间，来自双方可靠地履行各自的职责。绿色页面提示表示上述评审条件齐备，之后发起提交仍要通过 presubmit 检查；界面让作者知道接下来可以做什么，也保留了不同关口的区别。

<a id="integration-and-history"></a>

## 08　让一次评审接上开发工作，也留下历史

Critique 与其他开发工具的连接，有一个共同的基础：Google 的工作区存放在基于 FUSE 的文件系统中，权威内容位于云端，能够被不同工具访问。它们因此可以围绕同一份工作区协作，而非每次把作者电脑上的状态重新复制、解释一遍。这个前提也延续了[第十六章的仓库与工作区](ch16.md)和[第十七章的代码搜索](ch17.md)之间的关系。

原章介绍的集成各自服务于具体行动：从 Critique 一次点击进入在线 IDE Cider 继续编辑，沿 Kythe 交叉引用阅读符号，通过 Code Search 查看主干代码，查看 Tricorder 分析结果，跳到 Rapid 确认变更是否进入某个发布版本。代码行是否被测试覆盖，则由 Zapfhahn 提供信息，直接显示在 diff 行号区的背景中；并非所有项目都使用这项覆盖率工具。

多数能力以链接方式接入，避免把评审页面变成杂乱的综合控制台。覆盖信息值得局部嵌入，是因为它在读某一行代码时就可能提供帮助；发布工具保留独立页面，则让需要调查发布状态的人按需进入。按行动决定连接方式，比把所有信息长期堆在同一个界面更容易保持阅读主线。

评审完成后，作者可以直接在 Critique 发起提交，不必为了最后一步切回命令行。通常仍要经过相应分析和 presubmit 检查。紧急情况下，作者也可以先强制提交、之后补做评审，这是日常提交前评审之外的特殊路径。

提交结束以后，记录还有第二段生命。开发者从 Code Search 的文件历史回到具体变更，可以查看各个快照、评论和当时的决定，理解一项改动为何出现，或者某个错误怎样被引入。Critique 也允许提交后继续评论、回滚变更并查看是否已经回滚。这样，后来的发现也能回到原来的上下文，与代码历史连在一起。

回到假设的报表服务。几个月后，另一位同事看到某类上传错误会立即结束任务，想把它改为重试。评审历史若留下了当时对凭据错误的讨论，他就能理解这个选择对应什么运行条件，再判断条件是否已经改变。历史的价值来自可找到的理由，长期阅读必需的约定仍适合整理进代码、注释或文档，正如[第九章的变更说明](ch09.md#change-descriptions)所讨论的那样。原章还提到，汇总的评审资料可以用于培训，让个别变更中的知识服务更多工程师。

Critique 的紧密集成也解释了它的适用范围。原书说明，它依赖 Google 的单仓库及内部基础设施，当时没有对外提供；Chrome、Android 等开源项目，以及不放在该单仓库的部分内部项目使用 Gerrit。Gerrit 与 Git 集成，按单个提交组织评审，支持依赖提交的堆叠、细粒度权限和插件。面向更多组织与环境，它的评分机制也高度可配置，例如评审者可以打 −2 分否决变更。两者的差别反映了服务范围不同：一个可以围绕共同文化收敛流程，另一个需要容纳更广泛的配置。

规模问题也有两层。工具本身要承受大量并行请求，搜索、加载与快照切换仍应快速；工作流还要帮助人管理许多变更、找到跨团队评审者，并处理偶发的大型重构。原章脚注说，多数变更小于 100 行，但一些需要原子执行的大规模变更会涉及数百或数千文件。偏好小变更，同时让特殊的大变更仍可检查，才是这组设计的整体取向。

把本章串起来，工具优化的对象是完整的协作链：作者先把工作整理好，评审者容易理解差异，自动反馈及时到达，评论能够集中回应，等待关系清楚可见，批准责任有据可查，提交后理由仍然可追溯。信任与沟通贯穿其中；Critique 的贡献，是让它们在每天重复发生的工程工作里更容易落实。
