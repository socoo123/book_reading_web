# 第 8 章｜风格指南与规则

**Style Guides and Rules · 架构提升读书笔记**

一份代码风格指南，表面上常常是一串命名、缩进和语言特性的约定，背后管理的却是许多人、许多年共同维护代码的成本。同事第一次进入一个模块时，要重新学多少习惯；一次评审要花多少时间讨论排版；工具能否可靠地修改一批文件；当语言和业务发生变化时，旧规则还能不能说明理由，这些都是本章关心的问题。

Shaindel Schwartz 把规则放在可持续工程的目标下讨论：共同约定需要足够明确，才能帮助组织协作；也需要有成本意识和修订机制，才能跟着环境继续发挥作用。读这一章，可以把注意力放在规则怎样产生、怎样进入日常工作，以及怎样在证据面前改变。

<a id="goals-and-costs"></a>

## 01　先说明目标，再承担规则的成本

原书首先区分**规则（rules）**与**建议（guidance）**。规则是组织要求遵守的约定，个别情况需要经过批准才能豁免；建议承载推荐做法，通常为具体情境留出选择空间。两者的区别在于约束力。某条规则仍然可能要求工程判断，例如名字应该具有足够描述性，这并不会使它自动变成可以随意忽略的建议。

Google 把这些强制约定收在各语言的风格指南中。“风格”在这里覆盖的范围很广：除了排版，还有所有权、异常、并发、继承和注释等会直接影响理解与维护的选择。各语言的指南也不必同样长。语言本身的特点、已有库和历史用法不同，需要管理的风险便不同。书中以当时的 C++、Python、Java 等指南为例，说明同一个可持续性目标可以对应不同规则，其他组织也应围绕自己的环境作取舍。

制定规则时，先确定希望改善的结果，才能判断限制是否值得。一个需要很多人轮流维护的代码库，通常重视可读性与跨团队一致性；一个受严格资源约束的模块，还需要把内存和性能纳入考虑。把目标说清，争论才有共同依据。否则，“我一直这样写”很容易变成整个组织必须接受的理由。

作者把规则分成大致三类：避开容易出错的语言用法、落实有助于维护的实践，以及在若干合理写法之间确定共同约定。这三类的理由有所不同。涉及对象生命周期的要求需要解释技术风险；注释要求需要说明读者缺少什么信息；选定一种导入排序方式，则可能主要是为了结束重复争论、支持统一工具。把这些理由写下来，比把所有条款都包装成唯一正确答案更有帮助。

规则本身也会消耗资源。每新增一条，使用者要学习，评审者要理解，负责人要维护，工具可能还要增加支持。原书因此强调，规则必须带来与成本相称的收益。如果只是个别工程师缺少某项知识，针对性指导通常更合适；不必让所有人永久背负一条新规定。指南也无法把入门者需要知道的所有工程常识都收录进去。

脚注对这一点有一个重要补充：负担不能只按条款数量计算，还要看人实际需要记住多少内容。格式化工具可以执行许多细小排版规则，人只需知道怎样运行工具。因此，一份条目较多、自动化良好的规范，实际使用成本可能比一份需要反复人工解释的短文档更低。

> **核心观点**
>
> 每条规则都应当能够说明：它保护了什么共同目标，为什么值得由所有相关工程师承担学习和执行成本。需要判断的事仍可形成规则，适合教学的经验也可以保留为建议。

## 02　把理解代码的线索留给阅读者

在长期维护中，同一段代码会被评审、排障、修改和重新接手，阅读次数通常多于最初编写次数。作者因此主张优先优化阅读者的体验。稍长的描述性名称、多写几行直接的控制流，可能让作者多付出一点输入成本，却能让后来每位读者少做一次推测。

这里的可读性，包含对行为的理解。书中强调，要在代码使用处留下**意图的证据**。例如，C++ 的 `override` 和 Java 的 `@Override` 直接表明一个方法是在覆盖父类方法，读者不必先翻遍继承关系，才能确认作者原本想表达什么。注释也承担类似责任：接口前的文档说明设计与用途，实现中的注释解释不明显的选择及重要约束。

本章最有代表性的例子是 C++ 对象所有权。所有权指谁负责管理对象生命周期、在合适时机释放对象。看到一个函数接收裸指针 `Report*`，读者单靠类型很难知道它只是临时使用对象，还是会把对象接管并保存起来。如果代码库允许这些含义混在一起，每个调用者都需要查文档、找实现，甚至询问原作者。

下面按原书思路改写成一个归档场景。假设 `Report` 是报表对象，`Archive` 负责归档，具体实现省略：

```cpp
void Archive(Report* report);

void Finish(Report* report) {
    Archive(report);  // 单看接口，无法确认所有权是否移交。
}
```

如果约定接管独占所有权的接口使用按值传入的 `std::unique_ptr`，调用就会留下更明确的线索。下面使用 C++14 及以上的 `std::make_unique` 创建对象：

```cpp
void Archive(std::unique_ptr<Report> report);

void Finish() {
    auto report = std::make_unique<Report>();
    Archive(std::move(report));
    // report 已为空；不能再通过它访问原来的对象。
}
```

`unique_ptr` 表达独占所有权，不能通过普通复制把所有权再复制一份。这里 `std::move(report)` 使函数形参能够从调用方的变量移动构造，所有权因此移交；`std::move` 这个表达式本身只是进行相应的类型转换。读者结合参数类型与调用方式，就能看出生命周期责任发生了变化，不必先打开 `Archive` 的实现。

要把“失去原对象的所有权”和“这个变量从此不能使用”分开。对于这里的移动构造，调用方的 `report` 变为空，但它仍是有效的 `unique_ptr`，可以检查是否为空，也可以重新赋予新对象。另外，`unique_ptr` 可以通过 `get()` 提供非拥有型裸指针，别处因此仍可能指向同一个对象；它独占的是所有权。原书此处措辞较简略，文末附有澄清。

作者把这种理解方式称为**局部推理（local reasoning）**：阅读当前位置与相关接口，就能够判断必要行为，减少为了一个小片段不断跳转的负担。好的类型、命名和注释共同提供这种能力。规则若能让关键意图稳定地出现在每个调用点，就把一次接口设计的投入，变成了所有后续读者都能使用的信息。

## 03　一致性让人和工具都能跨项目工作

书中用 Google 办公室作类比：不同地点可以保留当地特色，但门禁、网络和会议设备的基本操作应当熟悉。工程师换一个办公室，不需要先学一套新的工作入口。代码库中的共同约定也提供这种熟悉感，让人把注意力放在新的业务逻辑上。

这种收益首先体现在阅读。名称、文件布局和常见模式稳定之后，有经验的读者会把一组细节识别成有意义的整体。原书脚注用**组块（chunking）**描述这种认知过程：就像熟练棋手识别棋子组合，工程师也能快速认出初始化、遍历、资源管理等模式，再集中查看其中真正不同的地方。每个模块都换一套表达习惯，会不断打断这种识别。

一致性也影响工具能做到什么。假设一个维护工具要在文件中补上缺失导入，同时移除无用导入；如果各项目的导入组织方式相同，工具可以按共同约定工作。如果每个团队都另有排序、分组和插入规则，同一个维护动作就需要许多特殊分支。维护这些分支的成本，会消耗原本可以投入功能和可靠性的精力。

人员流动使共同约定更有价值。库工程师可能同时支持多个项目，站点可靠性工程师可能在故障时进入并不熟悉的代码，团队也会合并、拆分或更换维护者。稳定的公共习惯让他们带着已有知识继续工作。模块仍然需要业务文档，但不必额外花大量时间重新适应最基础的表达方式。

这也解释了为什么有些看似微小的选择值得统一。缩进究竟用几个空格，未必存在适用于所有语言和项目的技术最优答案；但当团队反复讨论、评审反复修改、工具反复适配时，拥有一个公共答案本身就有价值。选定之后，省下来的讨论空间可以用于数据正确性、接口设计和故障处理。

> **核心观点**
>
> 一致性是一种可以反复利用的基础设施：人复用阅读与协作经验，工具复用对代码结构的理解。它的长期价值，往往大于某个局部写法带来的个人便利。

<a id="layers-and-migration"></a>

## 04　一致性有层次，也需要迁移空间

共同约定经过多年演进，难免留下历史差异。本章给出的处理方式很务实：在指南明确允许依照局部习惯的地方，先维持文件内部一致，再看团队、项目和整个代码库。这样，修复一个旧文件中的问题时，不会顺便把它变成新旧风格拼接的样子。

这个顺序只用于指南允许局部选择的事项，全局要求照常适用。例如，一条导出宏的命名要求若保护的是整个代码库，就不能仅凭“我们项目一直这样命名”将其取消。保持局部阅读顺畅，与守住公共约束，需要同时成立。

原书还记录了一次目标调整。早先的 C++ 指南为了保持一致，倾向于不修改会使旧代码显得过时的规则。后来，代码库越来越大、存在时间越来越长，要求所有历史代码立刻符合每一项新实践，代价已经过高。指南负责人于是放弃“永远完全一致”这一目标，允许规则向前改进，再尽量利用大规模修改工具迁移旧代码。

这个转变保留了长期方向：新代码可以使用经过认可的改进，旧代码也有逐步迁移的路径，代价是一段时期内新旧写法并存。对一个持续成长的系统来说，迁移能力本身就是可持续性的一部分。

外部社区也是需要考虑的一层环境。书中介绍，Google 早期的 Python 主要支持 C++ 项目，因此采用过两空格缩进，希望与 C++ 保持一致。后来，Python 工程师与其他 Python 代码的接触更频繁，查阅外部示例、使用外部库、向开源社区发布代码时，这项内部选择都带来转换成本。为 Starlark 制定指南时，团队选择了四空格缩进，以贴近外部 Python 习惯。

这个故事揭示了“一致”的参照物会变化。早期最常发生的协作在 C++ 与 Python 之间，后来则越来越多发生在不同 Python 项目之间。判断规则是否仍然有用，需要观察工程师实际与谁协作、代码实际与哪些系统接触。局部、组织和外部生态的成本，都应进入同一项权衡。

## 05　让常见路径简单，让新特性逐步证明价值

阅读者不一定是原作者熟悉的语言专家。几年后的接手者可能没有参与当初的设计，值班工程师也可能在时间紧张时进入不熟悉的代码。本章因此主张谨慎使用隐晦、容易误用或带来意外行为的语言特性，把常见维护路径设计得直接一些。

Python 的反射访问是书中的例子。`getattr(object, name)` 可以通过字符串决定访问哪个属性。示例把字段名放在另一个文件的列表中，再逐个读取对象属性，读者必须追踪字符串来源，才能知道实际访问了什么。普通文本搜索某个属性的直接使用，也更容易漏掉这些间接路径。

换到订单导出的场景，可以看清这种成本。假设导出字段只有订单编号和金额，字段列表却由另一个配置模块提供：

```python
fields = ["order_id", "amount"]
values = [getattr(order, name) for name in fields]
```

当字段固定时，直接写出访问对象的属性，通常更容易理解：

```python
values = [order.order_id, order.amount]
```

原书接着设想，字段名改从远程调用请求或数据存储中读取。放到这个例子里，维护者还要检查允许暴露哪些属性、缺失属性如何处理，以及属性读取本身的行为；校验不当就可能暴露原本不应输出的数据，而且很难察觉。关键成本在于数据访问的证据被间接层隐藏，验证范围随之扩大。

对于新特性，谨慎还可以表现为分阶段开放。C++11 引入 `std::unique_ptr` 时，Google 最初禁止使用，并让工具识别这种用法。书中说明，当时多数工程师对独占智能指针及移动语义不熟悉，继续使用已有方案显得更安全。随着理解加深，团队发现它在调用点清楚表达所有权，正好支持指南希望实现的局部推理，于是接受了引入新概念的成本。

这个案例的重要性，在于限制与开放都围绕同一目标。新特性带来的学习风险需要时间观察，而实际用法、豁免请求和代码示例，会逐渐形成判断依据。当证据足够时，规则可以扩大允许范围。

实际需求也会使一般约定让步。书中以允许可能有助于优化的 `noexcept`、允许模拟标准库的接口采用标准库命名方式，以及 Java、JavaScript 指南把生成代码排除在规则范围之外等情况，说明性能、互操作性和代码控制边界都值得考虑。规则服务于真实工程环境，因此需要能够容纳理由清楚、范围明确的适应。

<a id="change-with-evidence"></a>

## 06　用证据修改规则，把例外纳入共同判断

一条规则能够说明当初的理由，后来的人才有办法判断理由是否仍然成立。本章列举了几种值得重新查看规则的信号：语言版本变化，工程师持续投入精力绕开某条限制，或者执行规则的工具越来越复杂。记录决策依据，使“重新讨论”有了可追踪的起点。

Python 方法命名的变化，把这个过程展示得很完整。早期 Python 常作为 C++ 的脚本层，许多 Python 类型包装对应的 C++ 类型。团队采用 CamelCase，重视的是跨语言调用时的熟悉感。随着独立 Python 应用增长，工程师更多使用第三方 Python 库，也更频繁阅读外部 Python 代码。内部 CamelCase 与社区 snake_case 混在一起，逐渐增加了阅读、入职和开源维护成本。

风格指南负责人据此重新比较收益与成本：改规则会损失一部分内部一致性，也需要重新学习；允许 snake_case 则更符合实际的 Python 开发环境。最终，指南允许使用 snake_case，同时要求命名选择在文件范围内一致，为已有代码保留豁免，并让项目根据自身情况决定。

Google 的修订流程强调拿出现有代码中的实际问题模式，再提出能解决它的改动。任何工程师都可以在语言社区发起讨论，提案可以从问题开始，也可以带着具体文字。社区会检查它是否必要、含义是否清楚、影响是否有利；通过讨论的方案，再由相应语言的**风格仲裁者（style arbiters）**作最终决定。这些负责人通常有长期语言与库维护经验，判断依据是共同目标下的工程权衡。

到本书写作时，C++ 的仲裁组有四人，决策通过共识形成，而非靠投票打破平局。这项安排说明，支撑流程的是明确的决策责任与共同依据：负责人要能把不同意见带回收益、成本和代码证据之中，形成可以解释的决定。

图 8-3：从左上顺时针阅读。实线表示修订工作的推进，虚线表示使用后的证据继续反馈。每一轮都能保留旧决定的理由，并说明新信息改变了什么。点击[查看大图](../diagrams/exports/ch08-rule-evolution.svg)。

个别豁免也属于这套共同判断。书中以 C++ 宏命名为例：头文件导出的宏名需要项目专属前缀，因为宏不遵守普通 C++ 命名空间的隔离，可能与别处的宏冲突。仅仅嫌名字长，或者希望与本项目的旧宏一致，并不足以抵消整个代码库的冲突风险。真正通用的工具宏，则存在由仲裁者批准的例外渠道。

另一个例子是禁止隐式类型转换的规则。对于必要、准确表达底层值的透明包装类型，隐式转换可能合理，负责人可以授予豁免。但看上去像包装类型的申请，并不一定真的满足条件。作者因此指出，即使存在一类合理例外，保留逐项判断仍可能值得；否则过宽的规则文字会放进更多误用。

从维护角度看，规则变更解决的是普遍模式，豁免处理的是具体情境。它们共享同一套目标和解释责任，也都能为后续修订提供信息。这样，遇到实际困难的人有路可走，而整个组织不必依靠各团队私下形成互不兼容的规则版本。

> **核心观点**
>
> 决策理由是规则的维护接口。留下当时的前提、收益与成本，新的代码证据才能接到旧决定上；正式修订与具体豁免则让共同约定能够适应变化。

<a id="guidance-and-learning"></a>

## 07　用建议与教学补上规则之外的知识

知道哪些特性被允许，还不足以知道怎样把它们用好。规则适合划定共同边界，语言入门材料、短文和课程则可以展开用法、解释取舍。把这些内容分开，能让强制规范保持清楚，也让教学材料有空间讲明白复杂问题。

书中介绍的语言入门材料，面向的是“已经懂这门语言，但还不知道它在 Google 怎样使用”的工程师。它解释获准采用的特性、常用库与推荐习惯，而不只是重复允许和禁止的列表。面向主要语言的全天课程还会讲内部工具、常见抽象与当地开发方式，填补从语言知识到代码库实践之间的空隙。

另一种载体是短小的 Tip of the Week。它们从实际编程问题中提炼经验，每篇聚焦一个主题，几分钟内可以读完。书中列举的主题包括对象生命周期、复制与移动语义、新语言特性，以及容易忽略的转换问题。工程师可以在代码评审中引用相关解释，避免每次从头讲起。脚注给出了 Abseil 对外公开的部分文章入口，这些文章同样属于建议资源。

这与[第三章的 Readability 导师式评审](ch03.md#readability-mentorship)衔接起来：公共指南提供共同依据，实际改动使经验能够被解释和练习。假设一位新成员已经知道归档接口使用 `unique_ptr`，却还不了解为什么按值传入表达移交，评审者可以围绕这次调用说明所有权，再指向短文或入门材料。成员获得的是可以迁移到下一次设计的理解，而不只是修正这一行代码。

成熟的知识支持还包括便于查找的并发说明、新特性指南，以及常用库抽象的索引。当工程师知道自己需要某种数据结构，却不知道公共库中把它叫什么时，这些参考材料能把人引向已有实现。经验可以先进入这类低约束材料，在反复使用中变得清楚，再视实际需要决定是否上升为强制规则。

<a id="automated-enforcement"></a>

## 08　把机械执行交给工具，把判断留给评审

规则要长期有效，不能只依赖每位工程师记住最新版本。新成员加入、项目出现新场景、规则发生调整，都会使原本靠记忆运行的检查出现遗漏。作者因此强烈倾向于在可行时用工具执行技术规则，同时保留必要的教学。

静态分析工具在不运行程序的情况下检查源代码中的某些模式，可以提醒不合适的语言用法，并提供修复建议。书中提到 C++ 的 clang-tidy 与 Java 的 Error Prone，也记录了一个经验：当废弃 API 的警告和替代建议直接出现在工作流程中时，新增旧 API 用法的问题很快就明显减少。把合规操作放在正在工作的地方，会比让作者另外查找说明更容易落实。

原书还引述了 2018 年中一次非正式调查：部分 C++ 库维护者估计，C++ 风格指南中约九成规则可以自动验证。这个估计支持的方向是：许多原先由人反复核对的事项，值得交给工具。

格式化尤其适合这样处理。书中描述的提交前检查，会先运行格式化器，再看结果是否产生差异；若有差异，就拒绝本次提交，并告诉作者怎样运行工具修复。作者不必背下全部空白、换行与大括号位置要求，评审者也能少花几个来回处理这些细节。到本书写作时，Google 使用的格式化器包括 C++ 的 clang-format、Python 的 yapf 内部包装、Go 的 gofmt，以及 BUILD 文件的 buildifier。

自动执行还减少了不同评审者对同一机械规则解释不一的情况。一个团队不必因为换了评审人，就突然面对另一套缩进要求；检查工具使用同一项定义，也更容易让各项目得到一致反馈。这种收益要靠工具与正式规则同步维护才能保持。

有些要求仍然需要人理解上下文。原书讨论“小改动”时指出，同样的一行修改重复到几百个文件，可能比二十行带复杂副作用的逻辑更容易审查。因此，单凭修改行数设置自动拒绝阈值，会把可读性问题错误地简化成计数问题。模板是否过于复杂、某个类型标注是否有助于阅读、改动是否适合拆开，都更适合在具体代码中作判断。

> **核心观点**
>
> 让工具稳定执行可以明确定义的检查，人把时间用于意图、正确性和上下文。降低遵守规则的成本，往往比增加提醒更能让规则持续生效。

<a id="formatting-and-change"></a>

## 09　统一格式，为未来的自动修改铺路

本章最后的 gofmt 案例由 Sameer Ajmani 署名。它把格式化的价值又向前推了一步：统一外观能减少评审争论，还能为机器修改代码建立可靠基础。Go 在 2009 年 11 月 10 日开源时就包含 gofmt，团队认为，如果先让大量代码形成各自的格式，日后再统一会困难得多。

gofmt 不提供让各团队另选一套排版风格的配置。工程师、编辑器和自动修改工具使用共同格式后，一次语义改动就不必同时带出一大片空白与换行变化。评审者看到的差异，更接近真正需要理解的语言或 API 变化，也更容易检查机器到底做了什么。

书中以 Go 1.0 发布前的迁移为例：2012 年前后，团队使用 gofix 自动更新早期代码，使其适应稳定版本的语言与库。gofmt 让这些修改保持统一外观，减少与迁移无关的差异。Go 官方 2013 年文章也从维护角度解释了同一机制，并举出将 `os.Error` 迁移到内建 `error` 等更新的例子。

把这条因果关系放回项目实践：工具要替换一个废弃 API，如果还必须猜测每个文件的个人排版习惯，实现和审查都会复杂得多。公共格式把这部分自由度收束起来，使自动修改可以专注于语义，评审也可以专注于修改是否正确。今天结束的一次缩进争论，可能因此成为明天整批迁移更容易实施的条件。

已有代码库仍然可以补上这项基础设施，只是需要承担迁移成本。书中记述，Google 在 2012 年为 BUILD 文件引入 buildifier；这些文件描述使用 Blaze 构建软件的规则。为让约二十万个既有 BUILD 文件的格式化改动获得各负责人接受，一位工程师花了六周，而期间每周还新增一千多个 BUILD 文件。

统一之后，自动修改 BUILD 文件的工具也能沿用相同格式，不再因为每个项目的排版差异打扰维护者。这个案例把整章主线连了起来：明确的约定帮助人形成共同语言，工具降低执行成本，统一结构又让更大范围的维护成为可能。规则与建议最终保护的，是代码和工程师在时间、规模与变化之中继续工作的能力。
