# 第 20 章｜静态分析

**Static Analysis · 架构提升读书笔记**

一位评审者发现某个 API 很容易被用错，可以提醒眼前的作者；如果把这条经验写成检查，后来的每位使用者都能在相近的位置得到帮助。静态分析把一部分代码知识变成了可以反复执行的规则，让问题在提交之前出现，也让人工评审把精力留给设计、需求和难以机械判断的行为。

本章真正关心的，是这种规则怎样进入日常开发。分析器算得出一个问题，还只是起点：结果要及时到达掌握上下文的人，说明问题在哪里、为什么值得修改，并让修改的成本足够低。Google 的 Tricorder 经验把分析技术、工作流和用户信任连成了一件事。

<a id="what-static-analysis-checks"></a>

## 01　把代码中的知识，变成可重复的检查

**静态分析（static analysis）**通过检查代码及相关表示，寻找无需实际运行被分析程序就能判断的问题。“静态”指的是不运行被分析的程序，分析器本身仍可以读取构建产物或查询其他服务。与之相对，动态分析要观察目标程序运行时的行为，例如通过测试、运行时检测或性能采样获得信息。

最熟悉的一类静态检查已经在编译器里：语法、类型和某些可确定的语义条件。专门的分析工具在这些基础上继续检查更具体的模式，例如某种位移写法使一个字段完全不参与哈希，日志格式串与参数不匹配，或者测试方法没有满足测试框架的识别条件。这些写法都能顺利通过普通编译。

原章也把可维护性纳入静态分析的用途。检查命名约定、建议等价但更清楚的表达式、指出弃用 API，都可能帮助代码长期演化。这里有些规则回答“运行结果可能错在哪里”，另一些回答“共同的开发约定是否得到执行”。这两类结果都可能有价值，影响和处理方式却不同，要分别决定以什么级别执行。

一个很实用的场景是 API 迁移。[第十五章的弃用过程](ch15.md#migrate-and-prevent-backsliding)需要在搬迁已有使用者的同时，阻止新代码继续依赖旧接口。文档负责解释迁移理由，自动改写负责消化存量，静态检查则在新增调用出现时提醒或阻断。知识因此不再只依赖某几位维护者记得在评审里提醒。这也为[第二十二章的大规模变更](ch22.md)提供了持续防回流的条件。

静态分析与测试覆盖的是不同侧面。一个局部检查可能不需要构造任何业务数据，就能识别整个错误模式；测试则可以把真实输入、状态转换和组件交互连起来验证。检查没有报告问题，只说明它在自己的规则范围内没有发现问题。把明确、重复的检查交给机器，才会给更昂贵的人工判断与运行验证腾出空间。

<a id="scaling-useful-results"></a>

## 02　规模化的对象，也包括人的注意力

Google 当时面对的是数十亿行代码。若每一项小改动都重新分析整个大型项目，再交给一个中心团队分发结果，计算和人工都会堵塞。本章提出的扩展能力有三层：让分析能够分片、增量运行；让更多领域专家贡献检查；让结果直接送到相关工程师，不把人工分诊变成必经环节。

**分片**把可以独立处理的工作交给多个执行者；**增量分析**利用已有信息，把新计算集中到受当前变更影响的部分。书中的日常路径以待提交变更涉及的文件为重点，通常只在修改过的文件或行上展示诊断。分析读取的上下文与展示给作者的范围是两回事：检查一条新增调用，仍可能要读取类型、构建依赖或其他文件，界面上却只显示一行结果。

这样的范围选择还降低了修复成本。作者正在修改这段代码，通常知道它为什么存在，也有机会在同一次评审中验证修复。相比之下，突然要求某位工程师清理一大片多年未动的代码，首先就要重新恢复上下文；清理本身还可能改变行为。原章用死代码告警说明这一点：为了消除“无人调用”的提示而增加调用，可能让未经充分测试的旧逻辑开始执行。把诊断数量压到零，不能代替理解真正需要改变什么。

因此，日常反馈优先关注新引入的问题或被编辑代码上的问题。严重安全缺陷和重要正确性问题仍值得跨全库清理，区别在于它们有明确收益和专门的处理安排。这个取舍把“减少新增债务”和“治理已有债务”分成了两种工作，不让后者无差别地阻塞每次正常开发。

大代码库也给简单检查带来机会。一个错误模式即使在单个项目里很少发生，放到全组织仍可能找到许多值得修复的实例。由此看，分析的实际收益不只由算法复杂程度决定。一条范围清楚、速度快、诊断可信的局部规则，配上广泛使用的入口，可能比一项难以部署的精密分析产生更多持续改进。

> **核心观点**
>
> 可扩展的静态分析同时节省机器计算与人的注意力：只重做必要的分析，把相关结果直接送给正在修改代码的人，并为确有价值的全库清理单独安排工作。

<a id="effective-false-positives"></a>

## 03　技术上报对了，还要让人用得上

分析工具首先要区分**误报（false positive）**与**漏报（false negative）**。误报是把不存在的目标问题报告出来；漏报则是代码确实包含工具原本要找的问题，工具却没有发现。研究分析能力时，漏掉多少真实问题很重要；把工具部署给大量开发者时，每个人要为多少无用报告付出时间，同样决定工具能否继续被使用。

原书进一步提出**有效误报（effective false positive）**，用来描述从使用者角度没有促成积极行动的诊断。一个报告可能技术上正确，却因为消息含糊、问题无足轻重或修复成本不合适而被忽略。它在这条工作流里没有产生预期价值，作者也把它归到有效误报。反过来，一条判断即使没有猜中作者意图，只要开发者愿意据此改善可读性或可维护性，就不算有效误报。

书中的 Java 哈希表示例很能说明区别。`Hashtable` 的 `contains(x)` 查找的是值，功能等同于 `containsValue(x)`，容易被误当成查键。若作者本来想查键，应该改为 `containsKey(x)`；若本来就是查值，改成 `containsValue(x)` 也能把意图写清楚。无论原意是哪一种，这条提醒都能促成更清楚的代码。

![有效误报的四种情况：技术上报对且作者据此修复，是有用的诊断；报对了却因消息看不懂或问题无足轻重而没人行动，计入有效误报；技术上报错了但改写后意图更清楚，例如把 contains 改为 containsValue，不计入；误判又被忽略，计入有效误报。](../diagrams/exports/ch20-effective-false-positive.svg)

图 20-1：行按报告在技术上是否准确，列按开发者看到后是否采取积极行动，虚线框内的右列计入有效误报。报对了却没人行动同样算有效误报，报错了却促成更清楚的代码则不算。点击[查看大图](../diagrams/exports/ch20-effective-false-positive.svg)。

这个口径也不同于常见的统计指标。用 TP、FP、TN 分别表示真阳性、假阳性、真阴性，可以对照两个指标：精确率 `TP / (TP + FP)` 关心报告中有多少真问题；假阳性率 `FP / (FP + TN)` 关心没有目标问题的样本中有多少被误报。有效误报的分母则是展示给使用者的诊断，看的是其中有多少没有促成有益行动。

假设在一次试用中，100 条已被阅读的诊断里，92 条促成了有益修改，另 8 条因为误判、说明不清或收益太低而没有产生积极行动，有效误报就是 8%。实际统计时，“应用修复”的点击和“不有用”的点击都只是间接信号，还要结合反馈、样本复核和实际质量来判断。

到本书写作时，Tricorder 要求新检查的有效误报低于 10%，整体有效误报率略低于 5%。脚注还提到，对能发现严重问题的安全分析，评审者可能愿意容忍高得多的误报率：风险收益不同，合适的信号门槛也就不同。

> **核心观点**
>
> 工具的成功需要同时回答两件事：报告判断是否可靠，以及看见报告的人是否能据此改善代码。有效误报衡量的是后一种使用效果，前一种仍要靠精确率、召回率等指标。

<a id="review-platform"></a>

## 04　把分析放进评审，而不是再建一个待办箱

在 Google 的日常工作中，代码提交前通常已经要经过评审。作者发送变更时，正处在愿意继续调整代码的状态；评审者尚未给出意见，也给几分钟级的异步分析留出了时间。把结果直接显示在差异旁边，就无需作者另开一个仪表盘、找到自己的报告，再猜它对应哪一版代码。关于评审工作流的背景，可以衔接[第十九章的 Critique](ch19.md)。

评审还有一个独特优势：结果是作者和评审者共同看见的。作者若决定保留某种写法，可以在同一处解释理由；评审者可以要求处理确有意义的问题。工具自动指出常见错误以后，人类便不必反复检查同一种机械模式。它既帮助作者，也让评审者的注意力更容易落在设计与行为上。

Tricorder 将这条路径做成了共享平台。系统携带变更元数据向分析服务器发送请求；服务器通过基于 FUSE 的文件系统取得对应版本的源码，也能使用缓存的构建输入和输出。各分析器运行后把结果写入存储，Critique 在差异视图中展示各类别的最新结果。较慢的分析会发送运行中与完成状态，使作者和评审者知道是在等待结果，还是分析已经结束。

图 20-2 从左向右表示一份待审版本怎样成为可行动的反馈，下方虚线是使用者向检查作者反馈的路径。图中合并了服务器与存储细节，只保留版本上下文、就地展示和反馈责任这条主线。

到本书写作时，Tricorder 每天分析超过 50,000 项代码评审变更，支持超过 30 种语言，包含超过 100 个分析器，其中 7 个本身还是带有更多检查的插件系统。大部分分析器来自平台团队之外。“分析器”和“检查”因此是两个计数单位：一个分析器可以装载许多具体检查。

平台负责公共接入能力，领域专家提供具体知识，是另一个可扩展点。配置格式的维护者知道什么配置组合危险，库的维护者知道哪个接口容易误用，刚修复某类缺陷的人知道什么模式值得防止重现。Refaster 则用修改前、修改后的代码模板表达一部分规则，降低编写简单重构检查的门槛。它适合能清楚写出前后形态的转换，更复杂的语义条件仍要另写分析。

Tricorder 对新检查提出四个相连的要求：工程师能理解输出；结果可行动且有修复指导；有效误报低于门槛；对代码质量有足够影响。评审建议的修复可以比编译检查更费时间和思考；贡献是开放的，每条新检查仍要先满足这四项要求。

## 05　一段能编译的表达式，怎样丢掉一个字段

原章用 Java 哈希代码展示局部语义检查的价值。下面这一行把一个 `long` 字段 `f` 的高、低 32 位折叠到一个 `int` 中，再并入已有的哈希累积值：

```java
result = 31 * result + (int) (f ^ (f >>> 32));
```

对 `long`，无符号右移 32 位会把高半部分移到低半部分的位置；异或以后，再截取低 32 位，使两半都影响结果。如果字段后来变成了 `int`，却沿用了同一个表达式，普通 Java 编译仍能成功。问题是 Java 对 `int` 位移只使用位移量的低 5 位：`32 & 31` 等于 0，因此 `f >>> 32` 实际等于 `f`，而 `f ^ f` 恒为 0。结果只剩 `31 * result`，这个字段对哈希的贡献彻底消失。

下面把原表达式补成一个可运行的演示，保存为 `ShiftDemo.java`：

```java
public class ShiftDemo {
    public static void main(String[] args) {
        int seed = 1;
        long wide = 0x0000000100000002L;
        int narrow = 17;

        int longHash = 31 * seed + (int) (wide ^ (wide >>> 32));
        int reusedHash = 31 * seed + (narrow ^ (narrow >>> 32));
        int fixedHash = 31 * seed + narrow;

        System.out.println("long: " + longHash);
        System.out.println("int reused: " + reusedHash);
        System.out.println("int fixed: " + fixedHash);
    }
}
```

运行 `javac ShiftDemo.java`，再运行 `java ShiftDemo`，输出为：

```text
long: 34
int reused: 31
int fixed: 48
```

第二行中的 17 没有参与最终值；第三行直接把这个 `int` 字段并入累积值，恢复了“该字段应当参与哈希”的意图。对任何 `int` 值，错误表达式的异或部分都会归零，所以工具只凭类型和运算规则就能指出这种模式，无需构造具体的业务对象。

Google 在 Error Prone 中把这项检查启用为编译错误时，修复了代码库里 31 处此类问题。今天 Error Prone 的 `BadShiftAmount` 检查仍把这种模式列为 ERROR，并说明右移 32 等价于右移 0。这项检查由 Error Prone 提供：标准 `javac` 会照常编译这份合法程序，上面的演示就是这样运行的。

Error Prone 与基于 Clang 的 clang-tidy 都能利用**抽象语法树（AST）**及类型信息识别这类代码模式。AST 保存的是表达式、调用与声明的结构，比单纯搜某段字符更有语义依据。不过，clang-tidy 是基于 Clang 的独立模块化检查工具，需要单独运行或接入构建流程。分析实现、接入位置与错误级别是三件可以分别配置的事。

Tricorder 中的分析还包括跨文件关系：Deleted Artifact Analyzer 查找被删除文件在文档等非代码位置的引用；IfThisThenThat 让维护者声明两处内容必须同时变更；Chrome 的 Finch 分析器检查实验配置的审批与人群干扰，还会查询外部服务。另有检查针对构建后的二进制体积。共享平台因而容纳了源码 AST 之外的多种工程产物分析。

到本书写作时，几乎所有分析器都以**过程内分析（intraprocedural analysis）**为主，即围绕单个函数的代码进行判断。上面的跨文件检查比对的是文件之间的关系，与沿调用链推导多个函数的行为是两种能力。**过程间分析（interprocedural analysis）**可以利用函数摘要，把某个函数的行为信息供调用者继续分析，但要建设摘要的计算、保存和增量更新机制。书中认为它在技术上可行，只是需要额外的基础设施投入。

<a id="feedback-and-fixes"></a>

## 06　把“不有用”变成规则作者能处理的信息

用户信任来自工具长期表现出来的可靠性，也来自发现问题后能否得到回应。Tricorder 在诊断旁提供 `Not useful`，点击后可以直接向检查作者报告问题，并预填分析结果的信息。评审者则可以点击 `Please fix`，要求作者处理某条诊断。前者让不满能够到达有能力修改规则的人，后者让建议在评审中得到明确回应。

平台团队会跟踪“不有用”的点击情况，尤其关注它与评审者要求修复的情况相比是否异常。如果分析器作者长期不改进，可以停用该分析器。这使规则作者承担持续维护责任。只有把诊断显示出来，却没有反馈归属和退出机制，最终很容易把维护成本转交给每天忽略它的人。

原章的 Guava 格式串案例说明，改进未必需要新的分析算法。一项检查原先报告“参数过多”，用户看到格式串里有 `%d` 等占位符，觉得数量明明匹配，每周都有人提交“不有用”的报告。真正原因是相应的 Guava 接口只接受 `%s`，并不支持完整的 `printf` 格式。当团队把消息改为直接说明只支持 `%s` 后，这类报告便停止涌入。用户先前缺少的是 API 约定，不是数数能力。

今天 Error Prone 的 `PreconditionsInvalidPlaceholder` 检查也说明，Guava `Preconditions` 的错误消息模板只接受 `%s`，并会关注占位符与参数数量。好的诊断把“发现了什么、为什么会这样、怎样修改”放在开发者当下最需要的位置，本身就在传递知识。

**建议修复（suggested fix）**进一步降低行动成本。工具给出补丁，开发者可以在 Critique 中直接应用，也可以用命令行一次处理整项变更。补丁还是另一种解释：将隐含意图写成明确调用，或展示格式串应怎样改，往往比一条抽象规则更容易理解。不是每个分析器都能给出修复，能自动修的就自动修，其余结果给出足够的指导。

尤其是缩进、空白和统一排版，原章倾向于交给格式化器直接处理。让人工评审者一次次提醒格式，既占用时间，也容易使真正影响行为的意见淹没在机械修改里。书中提到，当时作者每天应用自动修复约 3,000 次，分析器每天收到约 250 次 `Not useful` 点击。两者是不同动作的次数，不能相除当作有效误报率。

> **核心观点**
>
> 检查的输出也是产品界面。清楚的消息、可审查的修复补丁、直接到达规则作者的反馈，以及停用低价值检查的能力，共同决定诊断能否持续产生帮助。

<a id="project-level-policy"></a>

## 07　把差异放在项目里，把问题留在反馈里

不同项目确实需要不同规则。一个全新的服务，可以从开始就采用较严格约定；一个历史系统，可能要先治理存量。某项检查只有在特定数据或发布模型下才有价值，也适合由项目统一启用。Tricorder 在建立高置信默认检查以后，才增加可选分析器和有限的项目级定制。

原章以 Proto Best Practices 分析器为例，说明持久保存序列化数据的项目需要关注历史格式的演化。假设一个报表系统会在对象存储里保留旧版任务消息，新程序下周仍可能读到旧数据：源码里的格式定义改了，历史字节却还是旧格式。检查具体格式变更，可以让团队在修改定义时就看到存量数据带来的约束。

这里要收窄原文的一句概括：原章说这些破坏性变化“只有保存了序列化数据才会出问题”，但格式兼容风险并不限于存储。Protobuf 官方最佳实践提醒，客户端与服务端不会总在同一时刻升级，还可能回滚；滚动发布时，新旧进程照样要交换消息。因此，项目可以按实际语义启用针对存储的额外检查；没有持久化消息的项目，也仍要检查协议兼容性。

项目级选择还意味着团队成员看到一致结果。假设一人不断修复一条规则，另一人因为个人设置隐藏了它，又不断写回同种模式，那么团队实际上没有共同标准。把差异绑定到项目，使作者、评审者和自动化看到同一套要求，也让规则能随项目迁移阶段统一调整。

书中曾有一次很有启发的逆向操作。早期 Critique 允许用户按置信度过滤结果、隐藏某些分析器；团队移除这些个人设置后，抱怨立即增加。他们没有恢复隐藏选项，而是追查原因，发现 C++ linter 被错误地用于 Objective-C 文件，产生了无效结果；HTML linter 则误报很多、信号很少，最终被停用。原来“用户已经把它关掉了”，掩盖的是规则与基础设施需要修复的问题。

这段经验的核心是反馈责任。项目语义不同，可以维护明确的项目政策；检查本身不好用，应当修好、缩小适用范围或停用。把一条可选规则从小范围逐步推广，也能积累真实反馈与用户信任。原章的 Java 可读性分析就经历了从担心噪声，到用户希望看到更多结果，再到默认启用的过程。默认规则应建立在可证明的使用价值上。

<a id="presubmit-gates"></a>

## 08　提交前检查，是工作流门禁，不是一种分析算法

评审中的建议允许作者解释后不修改。有些约定则需要在进入主干前强制满足，这时可以接入**提交前检查（presubmit check）**。它的身份由工作流位置和阻断能力决定：在发送评审、准备提交或开发者手动触发时运行，失败就要求先处理，而不只是多显示一条评论。

原章列出的检查很广：提交说明不能留有 `DO NOT SUBMIT`，某类代码改动应同时带上测试文件，格式必须合规，也可以规定某类 Tricorder 问题不能遗留。提交前流程还可以运行测试。因此，提交前检查指的是工作流中的一道门禁，里面可以同时放元数据规则、静态检查和动态测试。

团队可以在公共要求上增加项目专属检查，让新项目采用更高的最佳实践标准。这种自由也带来跨项目维护成本：一次全库机械修改，可能碰到许多互不相同的门禁。为此，书中提到一些团队级检查会跳过变更说明含 `CLEANUP=` 的清理变更。

适合门禁的规则，需要让负责修改的人能够理解并解决失败。检查越接近强制执行，误判与不明确消息带来的阻塞就越直接。它与评审建议可以分层配合：机械且确定的部分成为稳定底线，需要上下文判断的部分继续在评审里讨论。团队也要考虑这些规则怎样支持[第二十二章的跨项目变更](ch22.md)，避免局部方便变成全局维护障碍。

<a id="compiler-integration"></a>

## 09　先清理存量，再让编译器阻止回流

对足够明确的正确性问题，Google 希望再把反馈前移到编译过程。工程师还在本地构建时就得到错误，问题便不用等评审或提交。编译失败很难被忽略，但它直接打断开发，因此对检查的要求比评审建议更严格。

原章要求这类检查速度快、可行动、容易修复；尽可能提供机械修复；没有有效误报，不应因正确代码阻断构建；检查针对正确性，而非单纯风格或最佳实践。大量有价值的建议达不到这个门槛，适合留在评审入口。

新增编译错误还面临一项迁移问题：仓库里可能已有许多旧实例。若先启用检查，所有相关项目会因为编译器升级同时失败，业务开发者不得不在自己的工作中临时消化历史问题。书中的顺序是先全库运行分析，生成修复，准备并测试清理变更，提交后再启用阻断，建立新基线。

图 20-3 从左到右读，上方处理已有实例，下方表示同一条规则启用后负责阻止新增。两段工作使用相同的模式知识，分别承担迁移与维持约束的责任。

![新增编译检查先全库发现已有实例，生成并验证修复，提交清理后再启用编译错误；以后新增同类问题会导致构建失败。](../diagrams/exports/ch20-clean-then-enforce.svg)

图 20-3：先清理已有问题，再建立阻断规则，避免把规则升级的代价突然分摊给所有项目。下方箭头是后续新增实例的反馈路径。点击[查看大图](../diagrams/exports/ch20-clean-then-enforce.svg)。

Google 当时已有把 clang、javac 等编译器分布到集群上、像 MapReduce 一样覆盖全库的基础设施。在这种批量清理模式下，检查需要产出可自动应用的修复，才不会把发现的每一项都变成人工待办。修复同样要经过测试，结构匹配生成的补丁仍需验证行为。这正是一次性清理成本与长期防回流收益的权衡。

原章还介绍了常用 Java、C++ 工具链中的一项政策：尽量不输出可以长期忽略的编译警告，合适的检查作为错误执行，其余不在编译输出里显示，或转到评审工具。这里的分层保留了建议，只改变其入口。全库使用同一套编译选项，“什么是底线”就成了全局决定。

这是 Google 的组织配置。开源 Error Prone 允许把每项检查设为 `OFF`、`WARN` 或 `ERROR`，文档上标的 ERROR 只是默认级别；项目是否接入、采用什么级别，由各自的构建配置决定。

> **核心观点**
>
> 强制检查的收益来自“清理旧问题后，长期不再新增同类问题”。先完成迁移、验证与基线建立，再启用阻断，才能让更严格的工具成为公共保障，而非突然制造全库故障。

<a id="editing-and-browsing"></a>

## 10　不同入口，容纳不同的时间与上下文

编辑器是更早的反馈入口。工程师写下表达式时，就地显示一个可靠提示，可以立即纠正问题。不过，书中给 IDE 分析的时间预算通常小于 1 秒，理想情况下小于 100 毫秒；一项适合评审等待窗口、需要几分钟的分析，不适合在每次敲键后同步运行。

正在编辑的代码也往往不完整。函数已经写好，调用处还没补上，死代码分析此时可能报告一个很快就会自然消失的问题。评审时则能看到一项相对完整变更的上下文。Google 又没有强制所有人使用同一个 IDE，确保多种编辑器中的规则、配置和消息一致，也需要额外维护。书中因此以评审作为公共主入口，同时认可适合的 IDE 集成。

图 20-4 把本章出现的四个入口按强制程度排开：越往右越难绕过，误判和含糊消息造成的阻塞也越直接，对检查的要求随之提高。

![编辑器、代码评审、提交前检查、编译器四个入口按强制程度从弱到强排列：编辑器就地提示且通常要在 1 秒内返回；代码评审是公共主入口，建议可以解释后不改，新检查有效误报须低于 10%；提交前检查阻止提交；编译器让构建失败，不容有效误报。全库浏览另成一类。](../diagrams/exports/ch20-entry-strength.svg)

图 20-4：从左到右强制程度渐强，每格依次写发现问题后会怎样、何时运行、对检查有什么要求；虚线框中的全库浏览服务另一类读者，不在这条轴上。点击[查看大图](../diagrams/exports/ch20-entry-strength.svg)。

浏览代码则对应另一种需求。安全团队规划全库治理时，需要看见所有相关实例，不能只看本周被编辑的行；维护者准备清理时，也需要知道历史问题的分布。日常变更入口少打扰作者，全库浏览入口帮助专门负责的人掌握范围，这两种展示方式可以共用底层结果，不必强求相同的信息密度。

从个人工具或小团队起步，最可迁移的做法也很朴素：先把少量可靠检查放进大家已经使用的流程，让结果有明确责任人和反馈渠道；能机械改好的内容提供修复，真正必须遵守的底线在清理旧代码后再阻断。规模上来以后，再围绕分析耗时、领域规则数量和全库治理需求增加基础设施。共享平台和复杂程序分析，是服务这些目标的手段。

本章最后归结为三条相互支持的原则：关注开发者体验，把静态分析放进核心工作流，让使用者能够贡献知识。体验带来信任，公共入口带来持续覆盖，开放贡献让局部经验变成组织能力。工具找到的问题越容易被理解和处理，人就越愿意继续使用它；这个正向循环，才使一次检查变成代码库长期的改进力量。

- `int >>> 32` 实际位移为零：[JLS §15.19 Shift Operators](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.19)规定 `int` 位移量只取低 5 位、`long` 取低 6 位，[Error Prone BadShiftAmount](https://errorprone.info/bugpattern/BadShiftAmount)将这种写法列为 ERROR。完整演示在 JDK 21.0.2 下编译运行，输出 34、31、48；Error Prone 本身未运行。
