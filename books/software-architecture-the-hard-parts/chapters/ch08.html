READING NOTES / CHAPTER 08

第 8 章｜复用模式

Reuse Patterns · 共享一份实现，也是在选择变化怎样传播

第 7 章讨论服务应当多大；进入第二部分以后，问题变成：已经分开的服务，怎样继续使用相同的能力？格式校验、工单查询、日志采集都可能有重复实现，但把它们统统塞进一个公共库，或统统改成远程服务，会带来很不一样的发布节奏和故障范围。

本章围绕四种安排展开：代码复制、共享库、共享服务，以及 Sidecar／服务网格。贯穿它们的不是“复用越多越好”或“绝不共享”，而是三个实际问题：谁需要共同变化，谁能选择升级时点，以及谁必须在一次请求中等谁。Sysops Squad 是原书虚构案例；本章的两个决定分别处理基础设施能力和工单领域逻辑，不能混为一种通用复用政策。

01复用改变的不只是代码数量，还有变化的传播路径

在单体里，两个组件调用同一个校验函数，通常随同一次构建、测试和部署交付。拆成服务后，原来隐含的共同发布条件消失了：一个团队想立即修改规则，另一个团队本周不准备发布；某些服务用 Java，另一些用其他语言；客户请求可能必须实时得到结果。这时，相同函数放在哪里，就成为架构选择。

原书开场的争执正是如此。Skyler 想把共享代码做成一个 DLL，Taylen 主张拆成多个库，又坚持授权逻辑应该成为共享服务。Addison 没有按职位或偏好裁决，而是把库的粒度、变更控制和运行时影响分别拿出来分析。只说“这是公共功能”还不足以决定它的交付方式。

沿用第 2 章的语言，静态耦合关注服务运行所需的接线依赖，包含库、数据库和运行环境；动态耦合关注运行时怎样协作。共享库主要把共同实现接进各服务的构建与部署产物；共享服务则把它变成请求过程中的远程依赖。前者也会在运行时执行代码，后者也有部署与配置依赖，不能将二者机械理解为“只有静态”或“只有动态”。

下面用一个笔记假设说明差别：甲、乙服务都需要规则 R，甲现在需要新规则。若 R 已被复制，甲直接改自己的副本，但共同缺陷需要分别修；若依赖版本化库，甲采用新版，乙可暂留旧版；若两者访问同一个服务实例集合，替换其实现就可能同时改变两者的结果。最后一种只部署一处，却可能需要更广的验证范围。

减少重复实现、减少同步发布、减少运行依赖，是三个不同目标。 选择复用方式，就是决定优先满足哪个目标，并把其余代价放到能够承担的位置。

02代码复制：允许各自演进，也接下分别修复的责任

代码复制（code replication）把相同源代码放进各服务自己的代码库。它避免了对同一发布制品的依赖，也让各团队可以删除无用部分，按自己的限界上下文调整实现。例如，从单体迁出的通用工具类包含十个方法，某个服务只需要其中两个，复制后便可以缩减它，而不必先与所有使用者协商公共接口。

收益来自副本的独立性，成本也来自同一个地方。假设三个服务各有地址格式处理函数，其中一个团队修复了某种地址被截断的问题，另外两个服务并不会自动得到修复。更麻烦的是，经过独立修改，三份代码的名称和结构可能已经不同，修复者甚至不知道还有副本。代码不再共享，知识和缺陷传播的责任仍然存在。

作者给出的合适候选很小：极少变化的标记、注解、属性或简单工具。例 8-1 的 Java ServiceEntrypoint 注解和例 8-2 的 C# 同名属性，都只是标记服务入口类，并不执行工单规则或数据操作。为这样一个一次性小定义建立库、发布版本、通知升级，可能比复制本身更贵。

这里需要给原书的绝对措辞加上边界。印刷 222 页将该标记描述为“没有 bug、今后大概也不会有”；更准确的理解是实现简单、预期变化少，而不是可以证明永不变化。标记的名称、保留策略、适用目标仍是工具读取它的契约。如果一个共享扫描器要求特定类型身份，任意复制并改包名也未必还能被识别。这是笔记对适用前提的补充，不是案例已经发生的故障。

表 8-1 所说的“没有跨服务版本化能力”，也应理解为没有一个共同制品版本来统一表达升级关系；每个仓库仍然可以有自己的版本历史。复制适合确实允许各自演进、且同步修改需求很低的片段。一项规则若必须对所有服务同时保持一致，或者缺陷必须迅速覆盖所有消费者，复制通常只是把一次改动拆成多次协调。

03共享库：按共同变化划分，而不是做一个万能工具箱

共享库（shared library）将公共实现发布为 JAR、DLL 等制品，由多个服务引用。源码有一个主要维护位置，各服务部署时携带自己选定的版本，执行时通常是进程内调用。原书将其简写为“编译期绑定”；这里强调的是构建、依赖解析及部署时选择代码版本，并不表示所有语言都静态链接，也不表示库不在运行时加载或执行。

库的大小会改变变更的波及范围。一个 SharedStuff 库同时包含格式化、折扣计算、身份验证和日志工具，表面上很好管理：每个服务只依赖这一个东西。但若折扣规则频繁变化，旧版本按政策停止支持，完全不使用折扣的服务也可能被迫升级整个库、重新测试和发布。依赖清单短，并不等于共同发布负担小。

原书图 8-4—8-5 把这个交换画得很清楚：粗粒度库的一次变动影响多个服务；将功能拆开以后，C7 的变动只波及使用它的 D、E，但整个依赖图多了许多连接。作者总体倾向于按功能划分较小的库，把变更控制放在依赖数量之前。原因不是“小一定好”，而是无关消费者不应该不断替别人的变化付出测试和部署成本。

可以把这个原则落到一个假设：日志格式稳定，价格计算每周变化，二者应有独立版本节奏；但一组总是共同修改、共同使用的格式化方法，未必需要每个方法一个包。拆分的依据是功能内聚、实际使用集合和变化频率，而不是机械追求制品最小。库太碎，会增加发布顺序、版本组合与兼容关系的管理成本。

依赖还可能是传递的。服务引用校验库，校验库又引用某个解析库，即使服务的依赖文件只写了一行，实际运行的代码也不止一层。作为笔记的工程解释，记录“服务构建最终解析出了哪些直接和传递依赖”，比仅统计库的数量更有用：它能帮助回答一次修复要通知哪些服务，以及重建时是否会选入另一组依赖。

共享库因此更适合语言／运行环境相容、公共逻辑变化较少到中等的场景。异构服务可能无法直接使用同一制品，转而维护多种语言版本；这时，库的低延迟优势要与重复实现和行为一致性成本一起比较。代码位于进程内，也不意味着它没有资源消耗：计算过慢、内存泄漏或数据库争用仍然能影响所在服务。

04版本化的价值，是把升级时点交还给使用方

原书以十个服务共用 Validation.jar 为例。某一个服务急需新的校验规则时，如果公共库可以发布新版本，只有该服务需要立即选入、测试并部署新版，其余九个仍使用已验证版本。一次小需求不必等待十个团队同时准备好，版本化由此支持敏捷性。

真正提供隔离的是旧制品仍可用，且使用方明确选择了哪个版本。版本号本身不会自动使不兼容的逻辑向后兼容；保留旧版本只是让旧服务暂时不接收新行为。将所有依赖写成 LATEST 会破坏这种控制：团队本来只想发布紧急修复，却在重建时意外选入新库，于是必须同时处理另一项兼容问题。对传递依赖也应知道最终解析结果，必要时固定解析集合。

外部补充可用 SemVer 2.0.0 把“版本号表达什么”说清：它要求先明确公共 API；不兼容 API 变化增加主版本，向后兼容功能增加次版本，兼容缺陷修复增加修订版本，已发布版本的内容不得原地修改。它是一种兼容性沟通规则，不是自动检验器。一个版本标成修订版，仍需要验证真实行为是否符合契约。

版本管理还有组织的一半。维护者需要让使用方知道改了什么、谁受影响、迁移步骤是什么，以及旧版何时停止支持。仓库里多出一个文件，并不等于相关团队收到可执行的信息。反过来，使用方也需要知道自己的服务仍在哪个版本上，才能将通知对应到实际发布计划。

原书比较了两种旧版本退役策略。逐库策略按各库变化速度分别设定支持窗口，更贴近现实，但要逐个维护；全局策略统一规定只支持最近若干版，容易治理，却会让高频库的消费者不断升级。作者举例说，低频库保留两三版可能足够，每周变化的计算库若也只留两三版，会产生频繁重测；十版只是用于说明差异的示例，不能当作推荐阈值。版本数要换算成消费者实际得到的迁移时间才有意义。

印刷 227 页还说，严重缺陷或破坏性变化会使所有服务短期内采用最新版。这里要区分两类情况：严重漏洞、旧版无法继续运行，确实可能使正常退役安排让位于紧急迁移；单纯发布一个不兼容的新版本，并不自动使旧版本不可用。如果旧版仍受支持，仍可有计划地迁移；紧急修复也未必只能通过升级最新主版本交付。这是对原书一般化措辞的限定，而不是否认版本维护的成本。

由此可以看到库粒度和版本策略的关联：包得越大，一次退役或紧急修复越容易推动无关消费者发布；拆得合理，升级窗口才更有机会对应真正受影响的使用方。

05共享服务：集中部署，意味着集中传播行为变化

共享服务（shared service）把公共能力放进独立部署的服务，使用者通过网络请求它。Java、C# 或其他语言的消费者可以使用同一份实现，公共逻辑升级时也不必重新打包每个调用方。它适合需要跨语言共享、且公共实现经常变化的能力，但这些收益以运行时依赖为代价。

这里复用的是一个行为，而不是继承一组远程类。原书强调，共享服务需要通过组合（composition）调用能力：服务发送必要输入，接收结果；把一个父类放到另一个进程，并不能让本地子类自然获得远程继承。原有复用大量依赖继承、进程内对象或内部状态时，服务化还需要重新设计契约，不能只把类文件搬走。

“只部署一个服务”最容易被误读为“只测试一个服务”。假设共享折扣服务修改了某类订单的计算方法，响应字段和 HTTP 状态都不变，但金额含义发生变化，结算和账单服务仍可能受到影响。调用方代码没有改，也可以因为收到的新行为而失效。这就是原书图 8-7—8-8 先展示集中变更的便利、再展示故障扩散的原因。

给端点加版本可以降低风险，却不是给每次提交换一个 URL 就完成了版本治理。原书用 /1.0/discountcalc 到 /1.4/discountcalc 说明，团队仍需决定哪些变化值得新版本、旧调用方如何迁移、旧实现支持多久。若多个版本背后仍共用已改变的计算逻辑，仅保留旧路径并不能隔离旧行为；需要保留相应的契约语义，并对版本路由与实现一起验证。这是对例子的进一步解释。

共享能力还可能通过消息或 gRPC 暴露，而不只通过 REST 路径。版本约定必须覆盖这些入口使用的消息结构、方法和行为；URL 中的数字解决不了另一个协议的兼容问题。同样，接口结构兼容不等于业务语义兼容：旧消费者若以为金额包含税，提供方却改为不含税，即使字段仍叫 amount，合作也已经被破坏。

因此，共享服务把“每个消费者何时换库”的问题，部分转成“提供者如何保证运行时兼容”的问题。高变更频率让集中交付更有吸引力，也让兼容责任更重；必须同时看这两个方向。

06运行时的三笔账：延迟、容量与故障传播

进程内调用变成远程调用后，一次操作增加了序列化、传输、排队、安全处理等开销。客户创建工单如果每一步数据库操作都要先访问共享数据服务，这些等待会进入用户请求路径。原书图 8-9 对比的是这种新增远程跳转的开销，而不是说本地库的计算时间为零。

印刷 231 页提到使用 gRPC 或异步消息缓解性能问题。这里应收紧其含义：协议选择可能改善编码、传输和连接使用成本，但不能承诺显著缩短任何环境中的网络往返；异步请求允许调用方在等待结果时做别的工作，也不意味着结果更早生成。如果下一步必须拿到结果才能继续，端到端等待仍存在；消息还会带来排队及关联响应的管理成本。是否改善，取决于工作流能否真正重叠执行以及实际测量。

容量问题来自流量汇聚。多个调用方各自扩容，都会把请求送到同一个共享能力；它的承载需求与各方调用量及每次调用成本有关，不能只观察某一个消费者。共享库的执行容量随所在服务实例一起增加，共享服务则需单独配置容量和伸缩策略。原书图 8-10 的“跟着扩展”表示要协调容量，并不是两边实例数量必须一比一增加。

故障方面，共享服务不可用时，依赖它才能完成的业务路径也可能不可用。增加实例可以缓解单个进程或机器故障，但不能自动隔离所有实例共同使用的数据库故障、错误发布或坏配置。超时、熔断、缓存或降级能够改变失败传播方式，是否允许继续工作却取决于业务含义：展示旧折扣与给客户按旧折扣扣款，不是同一种后果。

原书图 8-11 把共享库一侧标成没有容错问题，表 8-2 也强调其运行特性不受影响。应准确读成：库没有额外引入这一项共享远程服务故障点。库本身仍可能崩溃、阻塞线程或访问不可用数据库；版本化也只能减少未经选择的升级传播，不能保证实现正确。这些是原图简化的边界，不应延伸成“用库就不会故障”。

把这些成本连起来，就能理解一个看似矛盾的选择：非常稳定、低延迟要求高的公共算法，放库里可能更划算；频繁更新、跨语言、且调用次数与等待方式可控的公共能力，则可能值得成为服务。比较的单位是具体业务路径，不是给“共享库”和“共享服务”各打一个永恒分数。

07Sidecar 与服务网格：让运行治理横跨领域边界

此前讨论的是相同功能怎样复用。微服务还面对另一种需要：领域模型应允许不同团队独立演进，日志、监控和身份验证却通常希望统一。每队自行实现一套监控，再要求运维团队把它们看成一个整体，会产生格式、覆盖范围和升级节奏的不一致。这里有价值的恰恰是某种受控的共同约束。

Sidecar（边车）模式把技术性能力放在随应用实例部署的伴随组件中，领域逻辑通过明确接口与它配合。原书借六边形架构／端口与适配器说明这个分离：业务在中心，技术连接位于边缘。书中又提醒把数据语义和事务边界纳入服务边界；这不意味着数据库驱动不能放在适配器后面，代码依赖的分层与数据责任的归属是两个不同视角。

当各服务都具有一致的伴随能力，并通过共同机制配置、观察和治理，原书将其组织为服务网格（service mesh）。图 8-14—8-15 重点表达横跨服务的运维联系，而不是给出某款产品的完整拓扑。一个附带日志进程的服务可以使用 Sidecar 模式，却不因此自动拥有完整网格；网格的治理、通信与接入约定仍需要实际实现。

作者把这称为正交耦合（orthogonal coupling）：领域划分是一条组织轴，运维共性是另一条组织轴，二者在系统中相交，但不必共享业务模型。图中统一日志采集，并不要求两个服务共同使用一个 Customer 类。所谓正交，是职责可以分别组织，而不是运行时互不影响；代理开销、错误策略或统一配置仍可能影响业务请求。

Sidecar 也不是万能工具箱。每实例的额外进程或组件会消耗资源，增加部署与生命周期管理；把少数服务才需要的工具放进去，会让所有实例承担成本。原书表 8-4 提到每个平台都要实现 Sidecar，是其写作时采用的集成语境，不能泛化成“每种业务语言必须重写一份”。外部官方模式说明明确指出，独立进程／容器可通过语言无关协议供不同语言应用使用；仍需适配实际平台与接口。

本章保留 2021 年原书以 Sidecar 组织网格的讨论范围，不将其当作现行网格实现的穷尽分类，也不把日志、监控、发现、认证、授权都视为任意产品开箱即有的同一功能集。Sidecar 是放置和隔离能力的方式，服务网格是协作治理安排，两者不是一份固定产品清单。

责任边界尤其需要清楚。身份验证检查请求者是谁，基础设施授权可以执行通用访问策略；“该专家能否关闭这张工单”若依赖工单当前状态和业务规则，就仍需要领域判断。类似地，重试机制不知道一次扣款是否已经生效，不能自动提供业务幂等；代理也不会自动把多个数据库操作变成全有或全无的分布式事务。它们可以承担通信机制，业务正确性仍需要自己的状态与契约。

08Sysops Squad：先明确谁负责日志，再决定共享什么

原书的基础设施案例发生在 2 月 10 日。团队把公共代码整理成库后，发现 Message Dispatch 库和服务自身都写日志，导致同一事件留下重复记录。问题不只是某一行日志应该删掉，而是没有一致的责任边界：谁生成什么记录，谁采集，谁维护公共行为，其他团队怎样知道自己已经正确接入。

Addison 将问题扩展到监控、服务发现、熔断等运行共性。团队已在推进 Sidecar 与服务网格，希望把统一行为交给共享基础设施团队维护，让服务团队作为其使用者。原文还说明，基础设施团队建设了部署流水线，在 Sidecar 与服务绑定后运行架构适应度函数。这样，“每个服务都带有正确的运维能力”才能从口头约定变成可检查的条件。

本笔记据此补充一个实现层面的理解：采集机制可以集中，但领域事件发生的意义往往仍由业务代码掌握；统一 Sidecar 不会凭空知道某张工单为何被拒绝。若两个位置仍主动生成同样的事件日志，仅增加一个采集进程也不能自动去重。模式解决的是划分和执行责任的机会，重复日志是否消除要靠约定及实际检查。原书没有提供测试代码或运行后指标，不能替案例补造效果数据。

最终 ADR 列出的能力是监控、日志、服务发现、身份验证和授权，由共享基础设施团队拥有和维护。熔断出现在讨论中，但没有列进这份 ADR 的五项清单；把两者分开，有助于避免把对话中的候选都写成最终承诺。

团队还讨论了 JSONtoXML 工具库。约 16—17 个团队中，只有约 5 个因对接大型机需要它。放进 Sidecar 会让这五队少配一项依赖，却使所有团队的组件变大；即使库本身不大，未使用者也在承担安装、资源或维护负担。Addison 因而决定暂不纳入，将来再评估。“少于一半不值得”是这段案例中的判断，不能作为通用比例门槛。

另一个明确后果是，不把 Address、Customer 等共享领域类塞进 Sidecar。共享类型变化会要求多个领域协调，恰好重新引入想避免的业务耦合。技术上能够塞进去，不代表在此架构中值得这样做。最终选择是统一运行治理、保留领域边界，并为工具纳入建立共同评估，而不是禁止所有业务复用。

09平台复用的关键，是稳定对外承诺而非冻结内部实现

原书接着用一家保险公司的示意说明过度复用。车险、寿险、旅游险等部门都认识“客户”，便可能有人要求建立一个收纳所有客户信息的统一服务。这个抽象看起来消除了重复，却可能变得异常复杂：每个部门的特殊需求都要进入同一模型，简单使用者也要面对其他领域的细节。

更深的问题是变化互相牵连。某个领域增加客户能力时，其他领域都必须确认共享模型和行为没有改变。图 8-16—8-17 的重点不是“客户永远不能集中管理”，而是仅凭名称相同就合并所有语义，会把原本不同的变化原因绑定到一起。如果集中的是稳定标识或明确界定的共同能力，结论可能不同；这属于根据作者论点作出的边界解释。

勘误：年代。 印刷 242 页／PDF 页序 260 将编排驱动 SOA 的风潮写成 “early 20th century” → 出版社已确认该年代错误，且本地 PDF 原页确实如此 → 应为 21 世纪初，不是 20 世纪初。此处是已确认勘误，不是译法选择。

作者提出，抽象帮助我们发现复用候选，但复用真正可用还取决于变化速率（rate of change）。操作系统、框架或公共基础能力之所以常值得依赖，是因为使用者可以在相对清楚的契约和升级节奏下行动；若公共能力每天改变消费者必须理解的内容，就会不断产生协调成本。这里的“慢”应看消费者可观察的变化，不能仅统计内部提交次数，也不能假定所有外部框架都天然稳定。

通过平台复用（reuse via platforms）是在明确能力边界后，用良好定义的 API 隐藏实现。以一个笔记假设为例，地址校验平台可以不断改进内部数据源和匹配算法，同时维持“输入结构、结果含义、错误约定”这些对消费者的承诺。业务方复用的是能力，而不是绑定某个内部地址对象、数据库表或一组类。

这并没有消灭共享服务的延迟、容量与可用性代价。平台也不是给一个庞大的公共服务换名字：必须真正收窄可见契约、明确所有权和升级方式。若原来“有效地址”表示可投递，后来改成只要格式正确就算有效，即使 API 结构不变，消费者仍需重新理解业务语义。原书明确承认平台封装挡不住领域间信息语义变化；它能控制破坏性变化的范围，不能取消合作本身。

10Sysops Squad：稳定的工单数据逻辑，为什么选择库

本章第二段案例在书中排在后面，故事日期却是 2 月 8 日。这里保留原书叙述顺序，不将章内顺序当作日历顺序。输入状态已经明确：核心工单功能分为工单创建（Ticket Creation）、工单分派（Ticket Assignment）和工单完成（Ticket Completion）三个服务；它们复用查询与更新逻辑，并共享工单数据域的一组表。

这与第 6 章的数据域划分相容：数据域是一组相关数据对象的边界，不意味着其中每个服务都有自己的数据库。第 7 章还决定把分派和投递（Ticket Routing）保留在一个服务内，因此这里的工单分派服务包含该合并职责。不能因为本章画了三个服务框，就推断它们已成为三个数据独立的架构量子。

Taylen 提议建立 Ticket Data 共享数据服务，把数据库访问集中成一层；Skyler 希望发布共享 DLL。Addison 先假设共享数据服务是合适方案，再逐项检验。这样做让讨论从“我喜欢哪一种”变成“什么证据足以支持它”。

第一组证据是请求路径。所有查询和更新都先经过共享服务，会增加远程调用；该服务不可用时，三者需要它的路径都会受影响。Taylen 最初认为后台处理可以接受这些代价，Addison 则指出工单创建直接面向客户，因此不能用“多数是后台”掩盖最敏感的入口。工单创建扩容时，还要确认共享数据服务有足够容量，原来的单点封装就多了一项运行协调。

第二组证据是变化传播。共享服务确实可以只部署一次，但公共逻辑的新行为会同时到达调用方；为了降低风险，需要覆盖三个工单服务的相关行为。共享 DLL 则允许使用方通过选定版本、测试、部署逐步接入变化。它不会自动减少总测试责任，却能控制何时让哪些服务接收某次变化。

候选方案也有真实优点。数据服务可以隐藏数据库访问细节，并减少调用方直接管理连接的需要。但库同样能在代码层面封装 SQL；数据服务独有的额外收益，是把访问能力变成独立运行边界。连接池集中化的收益在这个案例中也有限：数据服务仍需要多个实例，并非整个系统只剩一个池，而且目前只有三个调用服务、实例数量也不大。

最关键的一步是查看代码库历史。Taylen 原以为公共数据库逻辑经常变化，实际历史显示变化很少。原书没有给出次数或统计窗口，因此这里只保留“相当稳定”的定性结论。这条证据削弱了共享服务“频繁变更时只部署一处”的主要优势，却没有减轻它每次请求都会付出的远程调用与故障依赖成本。

最终 ADR 选择共享库。理由是公共逻辑稳定，库避免增加远程数据服务依赖，更符合工单创建和分派对性能、可扩展性及容错的需要；必要时通过版本化让变化分批采用。被接受的代价也很明确：采用新库的服务要重新测试和部署，公共逻辑变更不像单点服务更新那样迅速，每个服务实例还要管理自己的数据库连接池。

这个决定的影响有边界。三个服务仍访问共同数据，数据库容量、schema 兼容和跨服务数据规则仍需协调；旧版库若遇到不兼容 schema 变化，也不能靠保留版本继续运行。本章没有解决表的写入所有权或跨服务事务，那是下一章继续讨论的内容。把“少了一个远程服务”写成“彻底解耦”，会丢掉本章最重要的权衡意识。

11把复用决定写成可以解释的责任安排

回看这一章，四种安排没有形成从低级到高级的阶梯。复制把维护留给每份副本；共享库统一实现，却让使用方控制采用时点；共享服务统一运行行为，也汇聚流量、兼容与故障责任；Sidecar 把横切技术能力组织到伴随层，但不替代领域契约。平台复用则进一步要求把可复用能力藏在稳定承诺后面，而不把内部模型向所有消费者铺开。

Sysops Squad 的两个决定体现了这种区别。日志与监控需要一致的运行方式，团队愿意接受基础设施层的共同治理；工单数据访问逻辑变化少，团队更愿意承担库升级与各自连接池，换取少一次远程依赖。二者都使用复用，却把共同责任放在不同位置。

真正值得保留的判断过程是：先确认共享的是什么，再根据实际变化历史、消费者范围和关键请求路径比较方案，最后记录谁维护、谁升级、谁承担运行后果。这样，一旦变化频率、语言环境或容量需求改变，团队也知道哪条原有依据需要重新评估。下一章将从这些已经存在的数据依赖继续追问所有权与事务，而不把复用形式误当作数据边界的答案。
