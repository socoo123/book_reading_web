第 11 章｜管理分布式工作流

Managing Distributed Workflows · 把步骤连起来，也把状态与恢复责任交代清楚

工单已经受理，却没有送到专家手中；订单已经扣款，却发现商品缺货。每个服务都可能完成了自己的那一步，整体业务仍然没有完成。把服务拆开以后，架构师必须重新安排一项原先容易隐藏在单个程序里的责任：谁知道流程走到哪里，谁决定接下来做什么，谁在失败后把事情收好？

第 11 章围绕编排与协同展开。它真正比较的不是中心节点的数量，而是工作流知识放在哪里，以及这种安排怎样影响异常处理、状态查询、伸缩与变化传播。Sysops Squad 是原书的虚构案例；本章最终为主工单工作流选择编排，但没有把编排提升为所有流程的统一答案。

01服务各自成功，不等于工作流已经成功

工作流（workflow）是为完成一项业务目标而组织起来的步骤、依赖和分支。下单服务知道订单已创建，支付服务知道一笔付款已成功，履约服务知道仓库是否能发货；这些局部事实共同决定用户最终得到什么。协调（coordination）要解决的，就是把这些事实接成可以推进、判断和恢复的整体过程。

先区分两类状态。领域状态属于服务的业务事实，例如订单金额、付款记录、专家分派结果。工作流状态记录某一次流程的进度与控制信息，例如付款请求是否发出、正在等哪一个结果、失败后是否进入退款、哪些步骤尚未完成。原书称后者为 transient state，表示它伴随流程而存在；这里的“暂态”不意味着只应放在内存里，持续很久或需要故障恢复的流程往往必须可靠保存这些信息。

作为笔记假设，订单可以同时处于“付款已成功”和“等待退款完成”。前者是支付服务掌握的已发生事实，后者是整体流程的当前处置方向。只给订单写一个笼统的 failed，无法回答钱是否已退、是否还应重试、客户能否再次下单。状态描述必须足以支撑下一项业务决定，才不只是日志里的标签。

因此，工作流状态拥有者与业务数据拥有者不一定是同一个服务。编排器可以知道“支付成功、履约失败、等待退款”，但真正执行退款、验证金额并保存付款账目，仍然是支付服务的责任。让编排器直接改所有服务的数据库，会绕开领域规则，也会把原本清楚的数据边界重新连成一片。

本章开场，Austen 想写一份“只使用协同以保持解耦”的 ADR。Logan 的回应不是换成“只使用编排”，而是要求看实际流程。只有先识别正常步骤、可选分支、失败与查询要求，才能判断哪一种责任安排更省力。单看成功路径上的箭头，往往会低估真正的协调成本。

02通信回答怎样等待，协调回答谁来决定

第 2 章将动态耦合分成通信、一致性、协调三个维度。本章聚焦第三个维度：编排（orchestration）由专门的协调者掌握工作流推进；协同（choreography）没有这样的中心指挥，参与服务依据约定分担推进责任。原书小节标题使用 Communication Style，但按它自己在章首的三维定义，这里讨论的主要是协调方式。

同步与异步回答另一个问题：当前调用是否必须等到结果才能继续。编排器可以发送一条命令后保存“等待结果”，等回执到来再推进；它仍然是编排器，因为下一步由它决定。几个服务也可以没有专门协调者，却以同步调用逐个传递控制；这仍是协同，只是运行时等待关系比较紧。

协调责任 同步通信可以怎样用 异步通信可以怎样用
编排 协调者调用支付，取得结果后选择分支 协调者发出履约命令，收到结果消息后选择分支
协同 服务按约定直接调用下一服务并等待 服务发布事件，订阅者按本地规则推进

这是依据第 2 章三维定义整理的说明表，不是四种方案的性能排名。实际工作流可以混合通信方式：本章原图 11-4 就让编排器同步调用下单、支付，再异步交给履约与邮件。不能把一个流程中的某条异步边，当成整个流程已经采用协同的证据；有消息代理也不等于有业务编排器，代理通常只负责投递机制。

一致性还要另行决定。原书第 1、2 章曾用“各部分始终一致”概括 atomicity → PostgreSQL 的事务与隔离文档将整体提交效果和并发可见性分别说明 → 本文继续区分：原子性约束一组修改整体生效或不生效；隔离性约束并发事务之间的可见性与干扰；业务一致性要求状态满足实际业务规则。 增加编排器、等待同步响应，都不会自动把各服务独立提交的修改变成一个跨服务 ACID 事务。

最终一致的流程也可以由许多本地原子事务组成。例如允许“订单已创建、付款尚待确认”，必须说明这一暂态能持续多久，以及失败后如何结束。第 12 章会把三个维度重新组合成事务 Saga 模式；在本章，首先要把管理这些状态和转换的责任放到明确的位置。

03编排：把整条流程的判断集中到一个责任边界

编排器（orchestrator，也称 mediator）主要负责顺序、分支、工作流状态、错误处理和后续通知。领域服务各自保留行为与数据，例如支付服务判断支付是否可执行，履约服务处理库存和发货。编排器知道这些结果怎样共同构成一次购买，却不需要把每一项领域规则复制到自己内部。

原书特别强调微服务中的编排器通常按工作流划分，而不是用一个企业级 ESB 掌管所有业务。这里的“一个”首先是逻辑责任，不是生产环境只允许一个进程。为购买流程建立协调者，不意味着客户注册、报表导出、工单维修也必须排队经过同一段全局流程代码。反过来，也不必机械地为每个 API 新建一个服务：重要的是协调责任有内聚范围。

以 Penultimate Electronics 的购买示例为例，客户先把下单请求交给 Order Placement Orchestrator。它调用下单服务保存订单并取得结果，再调用支付服务验证并处理支付。只有相应结果允许继续，才进入后续履约。这两项同步交互让编排器能够直接选择下一步，但这是示例的通信选择，不是编排的定义。

履约不要求在同一次前台等待内完成。原书假设仓库可能一天只处理几批订单，因此编排器异步交出发货请求，再请求邮件服务发送下单成功通知。这样，客户不用等仓库真正出货就能得到当前阶段的结果。此处的“下单成功通知”也不等于“商品已经送达”；响应和通知应表达已经确认的阶段，不能把受理当作完成。

这个安排把两种变化分开：支付内部算法可以在契约稳定时独立调整；购买过程若增加一个审批步骤，主要需要修改编排逻辑及相应协作契约。领域服务不必各自知道“全流程如今多了审批”。代价是编排器必须理解足够多的步骤契约，成为跨步骤变化、容量与运行恢复的重要耦合点。

04支付拒绝与缺货，为什么不是同一种失败

原书先讨论支付被拒绝：订单已经建立，信用卡却可能过期。支付服务将失败结果交给编排器；编排器通知邮件服务说明失败，并要求下单服务调整订单状态。此时没有成功扣款，不应平白执行退款；恢复动作必须依据已经发生的事实，而不是所有失败都套用同一份“逆向流程”。

第二种失败发生得更晚：支付已经成功，履约才发现缺货、需要延期交货（back order）。在原书这项业务策略下，编排器要求支付服务退款，并更新订单状态及通知客户。退款是案例采用的策略，不是“缺货”一词必然推出的普遍规则；允许客户等待、保留预授权或换货，都需要另外的业务约定，原章没有据此给出完整方案。

两种失败暴露了集中协调的价值：编排器既知道已完成哪些步骤，也知道新的失败结果，因此可以把处理范围限制在需要改变的服务。原图 11-5、11-6 的恢复仍使用编排器与领域服务之间已有的关系，没有为了每个错误再让支付、订单、履约互相认识。成功路径和异常路径在同一处表达，比较容易看清它们怎样衔接。

然而，“有一处写恢复逻辑”不等于“恢复必然成功”。退款请求可能失败，也可能支付服务已退款而回执丢失。编排器必须区分发出了请求、确认动作成功、等待再次确认这些事实。这里是笔记对原书 recoverability 的工程展开：工作流记录的目的，是让下一次执行能够判断从何处继续，而不是发生异常后只留下一条堆栈。

补偿（compensation）与数据库回滚不同。 本例各领域服务自行提交事务，付款成功已经成为事实，之后的退款是另一次业务操作。它可能留下扣款与退款两条历史，也不能撤回用户已经读到的邮件。Microsoft 的补偿事务模式进一步说明，补偿必须考虑并发修改，可能失败，并不保证把所有数据恢复成起始时刻的逐字副本。第 12 章会继续展开这种跨步骤恢复。

05协同：把推进交给参与者，也把异常关系交给它们

协同不是服务临时自由发挥。原书借舞蹈说明：动作由架构师预先安排，执行时没有指挥者逐步下令。购买流程由下单服务开始，保存订单后发送消息；支付服务处理成功后产生下一条消息；履约服务安排交付，再触发邮件通知。消息可以表达事件，也可以表达命令，关键在于没有一个专门服务承担全流程的推进决定。

这条成功链很简洁：少了编排器，各服务只需理解自己的输入和输出。对可独立响应的事实，还可以让多个消费者分别处理，而不用让发起服务等它们逐个完成。可这份简单来自当前路径的形状，不是“去掉中心”就把业务约束删除了。

当支付失败，原本走向履约的路径停止，支付侧需要让邮件侧得知失败，也让订单侧更新状态。缺货发生得更晚，履约侧要发出适合自身领域的事实，订单、支付、邮件分别据此作出相应处理。原书建议可以广播一个领域事件，由这些服务订阅；这能避免履约服务逐个调用全部消费者，却不能免除消费者对该事件含义、顺序和处理责任的约定。

沿图 11-1 比较，两个方案都必须更新订单、处理退款和通知客户。编排将“缺货以后要做这三件事”集中在协调者，协同则将规则分散在订阅者中。后者的发布者可能不知道全部订阅者，但团队依然必须知道是否每项责任都有接收方，如何判断所有必要处理已经结束，以及其中一项失败时由谁继续追踪。

原图 11-10 用新增通信关系展示这种增长。这里的关系应理解为需要维护的逻辑协作契约，不只是一条 HTTP 连接；改用同一个 topic，并不会让多方对事件的理解成本归零。若异常很少、处理简单，分散责任可能十分合理。若撤销、重派、等待与补偿互相交叉，流程知识会散布在多个服务中，改一个分支就可能需要沿整条链排查影响。

06业务本来就相互依赖，架构能控制的是额外复杂度

作者把问题域本来要求的联系称为语义耦合（semantic coupling），把具体组织和调用方式引入的联系称为实现耦合（implementation coupling）。客户请求维修后，必须结合技能、服务地点和可用时间选择专家；这些信息之所以需要相遇，是业务目标决定的，不是因为团队碰巧用了一个编排器。

在业务要求固定的条件下，实现不能把这些必要联系变成不存在。它可以让联系更集中、更清楚，或把同一条规则散落在许多技术边界之间。协同把关系改为事件订阅，改变的是执行和变化传播方式；如果仍要求付款成功后才能履约，这个先后条件不会因为箭头画成虚线就消失。

原书用技术分层单体与按领域组织的模块化单体作对照。前者把 Catalog Checkout 分散到展示、业务规则、服务、持久化各层；后者将相应业务内容集中在领域模块及相关数据中。两种仍都可以是单体，比较重点是某个业务变化要穿过哪些实现边界，不是“画成领域框就获得独立部署”。

技术分层也可能有值得承担的理由，例如统一数据库连接管理、复用持久化机制。作者并未要求删除所有层，而是让团队把节约的技术成本与增加的业务协调成本放在一起。对于一个本来只需要局部规则的变化，如果不断要求跨很多实现模块同步改动，就要调查这些边界是否在放大复杂度。

原书“实现不能减少语义耦合”的结论，前提是业务语义不变。若产品负责人同意把“必须当场确认”改成“先受理、稍后确认”，就是改变了需求约束，确实可能减少即时协调，但不属于单靠技术替换获得的免费解耦。这个限定也解释了为什么架构师需要和业务方讨论流程，而不能只比较消息产品。

07前置控制器：在协同里找一个状态住所

协同没有专门的编排器，却仍可能需要回答“订单现在怎么样”。原书给出三种常见状态管理方式。第一种是 Front Controller（前置控制器）：让链条最先接收请求的领域服务兼管流程状态。在购买示例里，下单服务既保留订单领域行为，也保存支付、履约等步骤的进展；相关服务需要向它回报或查询。

它让状态查询变得直接。客户带着订单号回来，下单服务有机会返回已汇总的进度，而不必每次重新询问全部服务。但这个方便是通过增加状态更新通信得到的：支付处理完成后，不仅要推进后续履约，也可能要更新下单服务掌握的进度。字段、更新时机、失败重试都成了新增契约。

原书称这种方式在协同内部形成 pseudo-orchestrator，即类似编排器的角色。它比纯粹的领域服务更复杂，又可能成为查询与状态写入的热点。不过，拥有状态与指挥流程仍是两项不同责任：如果它只接收进度，不决定各步骤何时执行，控制仍然分散；如果它进一步开始派发命令、决定重试和补偿，协调方式就已经向编排移动。

这一差别是笔记对原图 11-13 的责任拆解。不要仅凭服务名叫 Order Placement 就认定它只处理订单，也不要仅凭它有状态表就认定它是完整编排器。观察谁能决定下一步，比观察代码放在哪个类中更能说明真实结构。

08无状态协同：省去持续汇总，把成本留给查询

第二种是 stateless choreography（无状态协同）。这里没有持续保存一份完整的工作流暂态，需要查看进展时，才查询各领域服务并组合结果。支付与订单仍然有自己的持久化数据，所以“无状态”只指没有独立汇总的工作流状态，不是整个系统没有数据。

在查询很少、流程很简单的情形下，这能避免每一步都向状态中心写入。领域服务按本地责任继续处理，不必同时承担一套集中进度协议。原书表 11-3 将性能、伸缩和解耦列为收益，主要是相对于持续维护共同状态这一条执行路径而言。

一旦用户频繁刷新订单进度，代价就移到了查询路径。每次查询要访问下单、支付、履约等服务，整体响应依赖这些请求的延迟和可用性；即使并行访问，仍要决定某个服务超时后返回什么。增加一种流程步骤，也可能要求修改进度聚合逻辑。不能把“不维护状态中心”读成“不再需要理解流程”。

原书把查询组合称为实时快照。范围澄清：原表述是逐服务查询得到 real-time snapshot → 各服务在不同时间回答，原章并未定义跨服务一致快照协议 → 应理解为查询时拼装的最新可得视图，不能承诺所有结果属于同一瞬间。 例如先读到订单待付款，随后支付已成功，组合界面就可能暂时出现不协调的事实；这是笔记假设，不是原书实测。

因此，原表的高性能倾向与正文对查询开销的警告并不该被压成一个总分：前者可以描述低查询负载下的执行路径，后者描述重建全局状态的成本。选择这种方式，需要业务能够接受相应的查询延迟、暂时不完整和状态解释，而不是因为表格中出现“高性能”就忽略实际读负载。

09让消息携带状态：信息随流程走，查询入口仍要安排

第三种方式利用印记耦合（stamp coupling）：契约携带一个包含更多上下文的数据结构，参与服务只使用或更新其中的一部分。本章具体用它在消息中附带工作流状态；服务处理后更新自己的部分，再把这份上下文交给后续服务。这里先讲它的工作流用途，契约耦合的系统讨论留到第 13 章。

作为笔记假设，一条消息携带订单标识、支付结果和履约进度；履约服务收到它时，可以知道前面的支付状态，处理后再追加自己的结果。邮件服务不必为了理解这条消息而重新访问前面每一个服务。节约的是某些状态查询，不是所有服务从此都不再需要共享语义。

图 11-2 的最后一行强调了原书称它为“部分解决方案”的原因：消息接收者知道这份消息已经携带的进度，但用户未必知道最新消息当前在哪个服务里。消息在传输、某步骤仍未完成、多个副本处于不同阶段时，都不能凭“消息里有状态”就直接提供一个随时可查的权威入口。若另建查询投影或专门状态服务，那就是需要额外设计的责任，不是这个模式自动附送的能力。

代价也进入契约本身。所有步骤都传一份较大的结构，会增加网络与序列化成本；流程状态字段改变，可能牵动本来只关心局部领域的消费者。若流程从单链改为并行分支，还要定义不同分支更新如何合并，不能让后返回的旧消息覆盖较新的结果。这里的并行合并是笔记的适用边界说明，原章没有提供通用合并算法。

三种方式可以结合，但每次组合都要说清谁负责什么：前置控制器便于集中查询，按需重建减少持续汇总，消息携带状态减少沿途查询。它们是在不同位置支付状态管理成本，不是三个从低级到高级的阶段。

10恢复需要可判定的进度，不只是再发一遍请求

原书把恢复能力列为编排的重要优势：协调者知道工作流状态，能够在领域服务短时不可用后尝试继续。为了理解这项优势的成立条件，本节依据 Microsoft 官方 Retry 与 Compensating Transaction 模式作工程补充，不将其写成 Sysops 已实施的设计。

第一步是区分失败性质。信用卡过期是明确的业务拒绝，原样重试通常不会使它有效；连接短暂中断可能适合有界重试；请求超时则首先表示调用者没有及时拿到结果，不足以证明对方没有执行。支付服务已经扣款、响应却丢失时，盲目重新扣款反而会破坏业务结果。

因此，工作流关联标识与操作幂等标识承担不同作用：前者把一张工单或一笔订单的多条消息串起来，后者帮助接收方识别同一业务动作的重复尝试。仅传一个标识不会自动带来幂等性；接收方还要把“此前是否执行、产生什么结果”与实际业务效果可靠关联。重试间隔、次数和终止条件也要由理解业务上下文的一层负责，避免网格、客户端、编排器同时无限重试。

第二步是让进度在故障后仍可解释。若协调者只在内存里记录“退款请求已发出”，进程重启后就可能不知道该重发、查询还是等待。把状态写入可靠存储有助于恢复，但状态保存与消息发送之间仍可能发生故障，不能把一行 saveState() 当作可靠工作流的全部实现。本章说明责任要求，不假定某个框架已替团队解决消息交付与状态一致记录。

第三步是定义恢复的结束条件。退款尚未确认，不能仅因退款命令进入队列就把流程标记为“已退款”；客户取消后又收到迟到的分派成功消息，也不能不看当前状态就恢复为“专家前往中”。可用的恢复逻辑需要识别当前阶段、已确认动作及过期结果，才能阻止旧消息使流程倒退。具体状态机与补偿顺序属于下一章。

同样的责任在协同里也存在，只是由各参与者、状态拥有者或专门的恢复机制共同承担。编排通常让这份知识更容易集中；协同可以实现相同业务结果，却需要更明确地分配谁发现停滞、谁重试、谁处理补偿再次失败。两种方式都不能把“最终一致”解释成无需机制就一定会收敛。

11耦合与量子：少一个中心，不等于没有共同约束

原书表 11-1 与表 11-5 呈现大体相反的趋势：编排更易集中管理流程、状态与恢复，协同通常有更多独立推进和伸缩机会。这些是典型拓扑的定性权衡，不是性能实验，也不意味着编排不能并行或协同必然更快。若三个步骤业务上必须依次完成，去掉编排器不会自动把它们变成同时执行。

编排器可能汇聚所有流程消息与状态更新，形成吞吐瓶颈。多实例能缓解单个进程故障，但相应状态存储、同一流程的并发推进与实例接管仍需设计。把同一张订单交给两个协调者同时退款，不是高可用。相反，逻辑上集中负责，也不要求用一个全局锁串行处理所有不同订单。

协同少了这个特定中心，领域服务有机会独立扩展；但共享代理、共同数据库、热点分区、跨服务同步请求仍可能限制吞吐和可用性。故障容忍还要与恢复能力分开：暂时失去一个中心后还能否接收新工作，是可用性问题；已有工作中途失败后能否正确完成，是恢复问题。不能只因某种拓扑少了一个框，就把两项都算作已经解决。

沿第 2 章的量子分析，先检查启动和运行必需的静态依赖，再看具体工作流的同步等待。编排器是一个需要纳入分析的协调与契约依赖点，但不能单凭“出现编排器”就宣告所有服务必须同包部署。异步编排能够减轻同时在线的等待要求；同步协同仍可能把延迟、容量和故障紧紧牵连。

Sysops 前面已经选择版本化共享 DLL，并让工单创建、分派、完成共用工单数据域。换成协同不会抹掉这份数据库契约；换成编排也没有自动重划表的写所有权。服务数据边界、流程协调边界、运行时等待范围，需要分别说明再一起判断。 量子用来解释这些联系，不适合只按编排器和服务框的数量机械计数。

原图 11-14 用一条上升线表达：语义流程越复杂，编排的帮助通常越大。它不是可以用步骤数计算收益的线性公式。一个只有三步却涉及不可逆动作和并发取消的流程，可能比十步独立通知更难恢复；异常的种类、交互和业务后果，比单纯数步骤更有解释力。这是笔记对定性趋势的具体化。

12Sysops Squad：主工单流程连接了什么

本章案例的输入来自前面逐渐形成的边界。第 6 章列出 Customer、Survey、Payment、Profile、Knowledge Base、Ticketing 六个数据域；第 7 章让分派与投递聚合，以保留失败后重选专家的闭环，也让客户注册在一个服务内完成本地事务并保留访问控制；第 8 章让三个工单服务复用稳定、可版本化的数据库逻辑 DLL，并继续共用工单数据域。这些决定都不能由本章“选择编排”默默撤销。

主工单流程先有一个面向客户的阶段：客户提交问题，系统接收后给出工单号。随后才是后台阶段：寻找适合的技术专家，将工单投递到专家的专用移动应用，通知客户专家将来处理；专家完成维修后提交完成信息，系统再联系调查服务邀请客户填写问卷。工单投递（Ticket Routing）是把工单送到设备，不是安排车辆行驶路线。

原书此处以四个领域服务讨论协调：Ticket Management、Ticket Assignment、Notification、Survey。图 11-15、11-16 的 Ticket Management 框内含 Ticket Creation 与 Ticket Completion 两项；这与第 8 章三个独立工单服务的画法不同。本章没有提供一份解释这次边界调整的粒度 ADR，因此本笔记按本章的工作流视图使用“工单管理”，不倒推第 8 章决定已被正式撤销，也不补造服务合并的实施过程。

图 11-3 的重点是等待边界。用户拿到工单号时，专家不一定已经选出，更不可能已经完成上门维修。这个长过程需要持续追踪，但不意味着保持最初 HTTP 连接或一个数据库事务直到维修结束。客户看到的受理结果、专家的业务完成、调查流程的完成，是不同里程碑。

两种候选方案承接同样的业务步骤。协同图让工单管理推进分派，分派侧负责投递并触发通知，专家完成后回到工单管理，再触发调查；编排图增加 Ticket Orchestrator，将主要推进集中在它周围。正文的阶段清单把投递归于分派，但原图 11-16 将与手机的 route／complete 连线画在编排器上。原表述／图示 → 差异 → 阅读限定：第 7 章的投递职责与本章文字、编排图的外部交互端点并不完全一致；可确定的是主流程集中协调，不能仅凭连线断言投递算法已经迁入编排器。实际部署映射原章没有进一步交代。

这种差异值得保留，因为它正说明流程视图与部署／组件视图承担不同任务。学习本章时，应追踪谁需要知道进度、谁负责恢复；若要据此实施，就必须再确定手机消息先到谁、谁执行投递及幂等规则，而不是把示意箭头直接当作完整接口规格。

13最终选择编排：因为异常需要被持续接住

Addison 与 Austen 将两个候选带给 Logan，讨论没有从吞吐量假设开始，而是从实际困扰业务的问题开始。第一项是丢失或投错工单。集中流程记录和控制有利于知道工单已经交给谁、还在等哪一步，使定位和恢复有一个明确入口，因此原书表 11-6 先把 workflow control 记在编排一侧。

第二项是随时查询工单状态。最初有人认为这只能依靠编排器，讨论随即纠正：协同也能查询各服务，或借助携带状态的契约。因此表 11-7 给两侧都记上 state query。这个过程很重要：一个方案实现起来更直接，不等于另一个方案做不到。 不过前文已经说明，单靠消息携带状态还缺少随时可查的入口；表格表达的是可实现性认可，不是两侧实现成本或查询一致性完全相等。

第三项使选择更清晰：客户可能取消工单；专家可用性改变、手机连接丢失、在上一位客户处延误，又可能要求重派。取消和重派不是只有一条“错误通知”就结束的动作，它们会改变尚未完成的工作以及随后到达消息的意义。把这些判断分散到领域服务，团队要在多个位置保持流程理解一致；集中在编排器中，更容易管理分支与恢复。

此表重组原表 11-6—11-8 的逐步推理，并将其隐含成本用正文已解释的语言展开；没有给方案打分，也没有把空白格改成“不支持”。三项不是等权投票，流程可靠性已经是业务优先问题，因而更能决定当前选择。

最终 ADR 的决定是：主工单工作流使用编排。 背景是必须容易追踪丢失或错向消息，具备良好错误处理，并能够查看工单状态；两个方案都能工作，编排在这些具体要求下更合适。它不是因为“微服务应该有中心”，也不是因为“要查询状态只能集中”，而是集中协调减少了此工作流最重要的异常管理负担。

ADR 接受的后果同样明确：单个逻辑编排点可能成为伸缩限制，若容量要求改变，需要重新评估。原书没有提供编排产品、持久化模型、实例数量、性能基准或证明丢单已经消失的上线数据。引入编排器提供了履行责任的位置，可靠投递、状态恢复与正确的领域行为仍需实现。

至此，案例的推理链完整了：已有服务与数据边界，加上丢单、取消、重派和状态查询要求 → 建模编排与协同两个候选 → 确认查询两者皆可、流程控制和异常处理更偏向编排 → 选择主工单编排并接受集中协调的伸缩风险。 下一章事务 Saga继续追问这些步骤怎样提交、失败后怎样补偿；本章选择的是谁管理过程，不是已经为所有步骤提供了一个共同事务。
