READING NOTES / CHAPTER 04

第 4 章｜架构分解

Architectural Decomposition · 从代码现状选择一条可控的迁移路径

上一章说明了 Sysops Squad 为什么需要改变：工单系统难以修改和测试，报表与调查问卷会牵连核心业务，部署和扩容也受整个单体制约。业务方已经同意迁移，但“同意拆分”离“知道怎样拆分”还有一段距离。把某个功能搬到网络另一端，可能只是把原来藏在进程里的纠缠变成远程调用。

本章的主线是先理解现有结构，再选择分解方式。传入／传出耦合、抽象度、不稳定性和主序列距离帮助我们辨认代码的依赖形状；基于组件的分解与战术分叉，则是面对不同代码现状的两条工作路径。指标提供调查线索，最终选择仍要回应业务目标、共享代码和团队协作的实际成本。

01先看整体结构，再决定第一刀落在哪里

原书开头，Austen 想先把报表搬出去，因为报表会使系统卡住。Addison 随即指出：如果报表还访问同一个数据库，单独部署并没有消除数据负载的争用；若同时建设报表数据库和数据同步，第一次迁移又可能过大。两人于是改想知识库和调查问卷，这些功能看起来比较独立，但仍说不清接下来怎样做。

Logan 将这种只凭“这一块好像容易”不断选下一块的做法称为 Elephant Migration Anti-Pattern（大象迁移反模式）。问题不在于增量迁移；本章推荐的方法本身也可以增量执行。真正的问题是缺少全局结构判断：服务边界由提取时的偶然便利决定，跨边界依赖却没有整理，最终可能得到必须一起修改、测试和发布的“分布式单体”。

原书图 4-1 的判断顺序包含三个不同的问题。首先，模块化是否有足够理由？这是上一章完成的业务论证。其次，现有代码是否值得沿分解路线继续改造？最后，在可分解的前提下，能否辨认出组件？如果已有清楚或可以整理出来的组件，就从组件出发重构和提取；如果内部结构很弱，但仍能按目标行为逐步删减，则考虑战术分叉。

这里的“可分解”不是一种由编译器决定的绝对属性。它包含工程判断：现有行为能否被理解，依赖能否被识别，保留功能能否被验证，以及整理结构的投入是否合理。原书明确说，没有单个度量能作出这个决定。图 4-1 对没有足够模块化理由或不适合分解的情况指向保留单体，并未给出一个“指标超过多少就重写”的规则。

“没有组件”与“无法分解”也不能合并成同一判断。前者可能仍能通过复制后删除来缩小系统；后者意味着，在当前约束下，连这条路线也未必值得推进。先评估投入是否可行，再选工作方法，能避免因为已经决定采用微服务，就把所有发现都解释成“继续拆”的理由。

02Ca 与 Ce：同一条依赖，从两端看有不同含义

传入耦合（afferent coupling，Ca）描述外部对当前单元的依赖；传出耦合（efferent coupling，Ce）描述当前单元对外部的依赖。图中的箭头统一从使用方指向被依赖方。如果 Ticket → Address，对 Ticket 而言这是一条传出关系，对 Address 而言则是一条传入关系。箭头不是业务数据流，也不表示调用次数。

这两个方向分别提示两种迁移负担。Ca 较高时，移动或修改这个单元的对外契约，需要考虑更多使用方；Ce 较高时，想把它单独搬走，往往会发现还需要带上许多依赖。原书以共享的 Address 类说明这种变化：在单体里复用同一个地址概念很自然，拆分时却必须重新判断，哪些业务真应共享同一份模型，哪些只需要独立保存相似信息。

为了使计数可复现，本笔记的数值例采用 JDepend 的包级口径。对包 P，令 E 为有向包依赖集合，则：

Ca(P) = |{ Q ≠ P : (Q → P) ∈ E }|
Ce(P) = |{ Q ≠ P : (P → Q) ∈ E }|

竖线表示集合元素数。同一个外部包中有十个类依赖 P，按这个口径仍只贡献一个 Ca；P 在十处使用同一个外部包，也只贡献一个 Ce。图 4-1 因而得到 Ca = 2、Ce = 3，而不是把源码引用次数相加。

需要区分一个重要的工具差异。Martin 1994 年原始论文按类定义这两个量：Ca 是依赖当前类别内部类的外部类数量，Ce 是当前类别内依赖外部类的类数量；JDepend 官方文档则明确说明，它改用相互依赖的包数量。因此，原书将它们宽泛介绍为“进入／离开代码单元的连接数”便于理解，但实际分析时仍须注明对象和工具。不能把按类统计的 Ca 与按包统计的 Ce 代入同一公式，也不能直接比较不同过滤规则产生的报告。

这些指标主要观察可识别的代码依赖。配置引用、反射、共享数据库及运行环境依赖，需要根据工具能力另外调查；它们并不会因为没出现在导入关系里就消失。第 2 章的静态耦合范围比这里的类／包依赖更广。包依赖图是架构分析的一层材料，不是完整运行系统的替身。

03抽象度 A：计算抽象类型占比，而不是评判代码是否优雅

抽象度（abstractness，A）测量一个分析单元中，抽象类型占全部类型的比例。在 Java 一类面向对象语言中，可以把接口和抽象类计入抽象类型，把普通实现类计入具体类型。令 Na 为抽象类型数量，Nc 为具体类型数量，则非空单元的公式为：

A = Na / (Na + Nc)       0 ≤ A ≤ 1

这里的 Na、Nc 分别对应原书式 4-1 的抽象元素总数与具体元素总数。A = 0 表示全是具体实现，A = 1 表示全是抽象类型。例如，一个包有 2 个接口、1 个抽象类和 7 个普通类，A = 3 / (3 + 7) = 0.3。分母是 10 个类型，而不是 7 个实现类。

原书文字纠正：分母应是全部类型。 印刷页 67 的定义及页 68 的解释写成了“抽象元素相对于具体元素的比值” → PDF 页图中的式 4-1 实际是“抽象元素 ÷（抽象元素 + 具体元素）”，也与 Martin 原论文和 JDepend 官方定义一致 → 本文以公式为准。若误按 Na/Nc 计算，上例会成为 3/7 ≈ 0.429，而且全抽象包还会出现除零，无法满足该指标的 0—1 范围。

为什么拆分前要看抽象度？一个被许多地方依赖的包，如果主要暴露稳定的接口，内部实现就有机会在不改变这些接口的情况下演进。反过来，若依赖方直接知道大量实现细节，搬动或替换实现就更容易牵连外部。A 为这种结构提供了一个粗略观察角度，但它不检查接口是否设计得好，也不证明抽象真的被正确使用。

因此不能把“接口越多越好”当作目标。为每个只有一种实现、没有变化需求的类机械增加一个接口，可能让 A 上升，却增加阅读和维护成本。一个清楚、稳定的值对象包即使 A = 0，也可能十分合理。这个度量源于面向对象的类型结构，不能不加转换地拿来评价 SQL、函数式模块或整个业务领域的“抽象水平”。

当 Na + Nc = 0 时，数学上的比例没有定义，应标记为不适用；若工具返回 0，要知道那是工具约定。JDepend 的实现正是对空包返回 0。记录这个口径比把空包与“有很多具体类的包”混为一谈更有用。

04不稳定性 I：依赖位置，不是故障率或修改频率

不稳定性（instability，I）将两个方向的耦合放到同一比例里：

I = Ce / (Ca + Ce)       0 ≤ I ≤ 1，前提是 Ca + Ce > 0

当 Ce = 0、Ca > 0 时，I = 0：当前单元不依赖其他已计入的单元，却被外部使用。外部使用方形成了修改它的阻力，因此称为结构上“稳定”。当 Ca = 0、Ce > 0 时，I = 1：它需要依赖外部，却没有其他已计入的使用方要求它维持原有契约，因此处于相对容易被修改的依赖位置。稳定在这里不是赞美词，也不是“运行中从不出错”。

原书页 68 给出 Ca 同为 2 的两个例子。第一种 Ce = 0，因此 I = 0/(2+0) = 0；第二种 Ce = 3，因此 I = 3/(2+3) = 0.6。后一种有更多外部依赖可能把变化传入当前单元。这正是图 4-1 的情况：要提取 TicketAssign，不能只看到它有两个使用方，还要处理它对专家资料、区域规则和分派存储的依赖。

这个比例不包含规模信息。Ca = 2、Ce = 3 与 Ca = 200、Ce = 300 的 I 都是 0.6，迁移时需要理解的关系数量却完全不同。它也没有记录这些依赖多久变化一次、接口是否兼容、测试覆盖怎样，不能解释为“60% 的概率出故障”。如果 Ca 和 Ce 都为 0，原式成为 0/0，应标记为无依赖样本；JDepend 将它约定为 0，这并不表示一个孤立包具有与大量依赖者支撑的基础包相同的责任。

原书解释的适用边界。 页 68 将 I 与代码波动、修改时易损坏联系起来，并将高稳定性的代价概括为缺少复用 → Martin 的定义测量的是依赖结构对变化的约束，JDepend 也把 volatility 另作配置；从公式看，增加使用方 Ca 反而会降低 I → 更准确的解释是：I 描述依赖位置，不能直接替代历史修改频率、缺陷率或复用程度。“每个组件完全自给自足可能造成重复”是某种设计策略的代价，不是低 I 必然造成的结果。

把 I 与 A 联合起来，才看得出这个位置是否值得担心。一个低 I、低 A 的共享包，可能既难改，又缺少通过抽象扩展的余地；一个低 I、高 A 的接口包，则可能把不容易变的契约留在中心，把容易变的实现放在外围。这就是主序列的来由。

05主序列距离 D：把两个指标放在一起读

令横轴为 I、纵轴为 A，主序列（main sequence）就是从 (I=0, A=1) 到 (I=1, A=0) 的直线，方程为 A + I = 1。两个端点代表两种相容的角色：左上方是被依赖的稳定抽象，右下方是较少承担外部契约责任、依赖其他单元的具体实现。中间位置则体现二者的不同混合。

左下方接近 (0,0)，称为痛苦区（zone of pain）：很多人可能依赖一份具体实现，改变困难，扩展也缺少抽象出口。右上方接近 (1,1)，称为无用区（zone of uselessness）：抽象很多，却缺少依赖它的使用者，同时又依赖外部。名称是提醒检查角色是否失衡，不是看到坐标就判定代码无用。

原书式 4-3 使用的是归一化距离，本笔记记作 D；Martin 原论文将这个归一化量记作 Dn。为了避免同一字母指两种距离，几何距离另记 d：

D = |A + I − 1|              归一化距离，范围 [0, 1]
d = |A + I − 1| / √2         几何垂直距离，范围 [0, 1/√2]
D = √2 × d

几何公式来自点到直线的距离：直线 A + I − 1 = 0 的两个系数都是 1，分母因此为 √(1²+1²) = √2。在单位正方形里，离主序列最远的两个角距直线都是 1/√2；再除以这个最大值，便得到范围为 0—1 的 D。原书图 4-3 用垂线表达距离方向、图注称“归一化距离”，不能把纸上量得的线段长度直接当作 D。

提取纠错，不是原书漏印。 本地纯文本把式 4-3 提成 D = A + I − 1 → 实际回看印刷页 69／PDF 页序 87，原式明确有绝对值符号 → 正确公式为 D = |A + I − 1|。不取绝对值时，主序列下方会得到负数，那是带符号偏差，不是这里定义的距离。

原始资料也需要交叉核对。Martin 1994 年论文第 7 页的可获取 PDF 将几何式显示为 |(A+I−1)÷2|，同时写其上界约 0.707 → 这两者不一致，除以 2 的上界只会是 0.5；按点到直线公式，分母应为 √2 → 本文采用上述几何推导，并保留该文另行明确给出的归一化形式 |A+I−1|。这是所获取原始 PDF 的显示／公式不一致记录，不把这个问题归给本书式 4-3。

实际使用时，应看组件分布和具体异常，再回到代码调查：这个低 A、低 I 的包是常改的业务规则，还是极少变化的基础值类型？高 A、高 I 的包是尚无使用者的过度设计，还是分析范围漏掉了外部客户端？JDepend 官方文档明确提醒，好指标不必然是好设计，坏指标也不必然是坏设计。工具还支持用 volatility 配置改变报告距离，所以比较报告时要核对配置。D 是结构失衡的线索，不是可分解性的裁判，也不是服务边界的生成算法。

06基于组件的分解：先整理积木，再组合服务

基于组件的分解（component-based decomposition）以已有的、或能够通过重构明确起来的组件为起点。组件是有明确职责和操作集合的代码组织单元，通常体现为包、命名空间或目录；服务则是能够独立执行和部署的内聚功能集合。一个目录提供了寻找组件的线索，但只有目录名，没有职责和依赖边界，并不等于已经拥有好的组件。

原书图 4-5 将 penultimate/ss/ticket/assign 作为 Ticket Assign 组件，其中包括专家位置、技能匹配和分派逻辑。这个例子说明，分派能力由一组协作文件实现。若只把某个类提成服务，其余文件仍需频繁远程访问它，就把原本便宜的内部协作变成了分布式协调。作者因此强调：从组件构建服务，不从单个类构建服务。 这也不是“每个组件都必须单独成为一个服务”；多个相关组件可以组成一个领域服务。

这条路线先在原代码库里改善边界：把职责相近的实现整理到一起，识别共享功能，理解组件之间的依赖，再按领域关系形成较粗的服务。其增量性体现在，团队可以先让组件边界变清楚，之后再把选定分组变成部署边界。此时提取不再是不断追着某个类的依赖跑，而是在已理解的功能集合上决定哪些连接应留在内部、哪些需要明确契约。

本章将基于服务的架构（service-based architecture）作为适合的终点或中间站：应用拆成粗粒度、按领域组织、分别部署的服务，而数据库可以暂时共享。这样先解决功能组织，再另行处理数据库分解；之后也可以只细化那些确有独立扩展、故障隔离或变化需要的领域。这里使用的是本书的特定风格定义，不是对一切使用服务的架构的泛称。

这一安排的价值在于减少同一阶段必须同时改变的东西。原书指出，领域服务可以沿用原有 EAR、WAR 或 Assembly 等部署产物，不把容器化和全自动运维作为开始拆分的硬前提。它还说，这种转移通常偏技术性，不要求先重组整个组织。应把这些读作降低迁移前置条件的建议：拆出多个部署单元仍可能需要调整发布、监控、测试和责任分工；当用户流程或可用性受影响时，也仍需要业务方参与。

尤其不能把“数据库可以暂不拆”读成“数据问题已经解决”。报表服务即使单独部署，只要仍对工单库施加同样负载，开头的争用仍然存在。第 2 章也提醒，共享数据库可能继续构成共同耦合点。这条路线允许分阶段处理问题，并没有承诺每完成一次代码提取就自动得到独立架构量子。组件整理的具体模式留给第 5 章，数据与最终粒度分别在第 6、7 章继续展开。

07战术分叉：带着依赖复制，再删除不需要的行为

当内部结构很弱时，提取经常呈现一种反复扩张：想拿走 A，发现要带 B；带走 B，又要带 C；最后几乎把单体一起搬走。战术分叉（tactical forking）换了一个工作方向：先让每个目标团队拿到整个应用的副本，再从各自副本中删除不属于目标范围的部分。原书将模式命名归于 Fausto De La Torre。

这不是让耦合消失，而是先保留已有依赖，使每份副本具有完整起点，再从“能够删除什么”逐步缩小它。原书图 4-8—4-11 用几何形状表示不同领域行为：两个团队分别保留其中两种行为与另一种行为，最终形成两个粗粒度服务。代理将用户请求送往相应应用；它提供入口路由，本身并不负责替团队整理内部结构。

具体过程从目标范围开始。假设甲负责 X、Y 两种业务，乙负责 Z：团队先复制完整应用；甲逐步移除 Z 的入口和实现，乙移除 X、Y；每次删除后确认需要保留的行为仍能工作，再继续缩小依赖和资源。最终得到的不是从零重写的程序，而是两个继承旧代码、体积更小的应用。这一假设只解释原书流程，不是 Sysops Squad 实际采用的服务划分。

这种做法的一个现实优势是反馈较直接。静态语言中，删除仍被引用的类常会导致编译失败；相应测试也可能立即暴露被误删的必要路径。与从混乱代码中先规划完所有可提取单元相比，团队可以更早开始动手，并在删除过程中逐步理解依赖。

但原书“通过编译或简单测试验证”的说法只覆盖能够被这些检查观察到的行为。反射注册、配置驱动任务、低频批处理和数据库副作用，可能不在编译器或少量测试的视野里。实际删减要围绕该副本仍负责的业务路径进行验证；不能把编译成功直接解释为“这段代码从未被使用”。这也是前面可分解性判断里，行为能否被理解和验证仍然重要的原因。

复制还会带来一个容易被图示隐藏的事实：代码副本不是数据库副本，应用分叉也不会自动确定数据所有权。哪些数据继续共享、哪些操作只由一边执行、哪些任务应在某个副本关闭，仍需另行处理。战术分叉解决的是获得较小应用的一条路径，不是完整的数据迁移方案。

08两种方法交换的是启动速度与后续整理负担

战术分叉最吸引人的地方是启动快：先复制，再由各团队删减，可以省去大量提取前的结构整理。对于难以看出组件、又急需把某块关键能力隔离出来的系统，这是实际收益。作者称它为“战术”，正是因为它优先提供能够前进的办法，而不是承诺把整个内部设计重新整理好。

删减后，每份应用可能仍残留很多暂时未执行的代码；依赖之所以留下，有时只是团队还不能证明删掉安全。即使应用确实更小，原来混乱的内部结构也不会自动变好。更棘手的是共享代码的多份演进：同一段逻辑在甲乙两边改了名字、改了行为，后来的人可能连它们曾经相同都认不出来，更难同步缺陷修复。

基于组件的分解则把更多工作提前到共同代码库中。团队一起识别共享能力、组件边界和领域边界，再按整理后的结构提取，通常较慢，但更容易保留统一认识，也减少无意维护同一份业务规则多个副本的机会。它同样不能消除全部重复或依赖，收益来自整理过程，而不是方法名称。

判断维度基于组件的分解战术分叉
合适起点能辨认或整理出职责明确的组件缺少内部组织，提取总牵出大批依赖
主要动作重构边界、聚合组件、逐步提取复制整体、按目标范围逐步删除
边界形成服务范围随组件与领域分组逐步明确开始时就需知道副本数量和大致保留范围
短期收益更受控的迁移与共同结构认识更早并行启动，删除反馈较直接
主要代价迁移时间较长，前期整理投入较大残余代码、继承混乱、重复实现与协调成本

表中的比较不是普适评分。已有清楚组件时，为了“更快”而复制整个系统，可能主动丢掉一个有价值的起点；组件已经难以辨认时，坚持先得到完美模块再行动，也可能让迁移迟迟无法开始。合理选择要比较当前最难承受的是前期等待，还是今后同时维护多份相同逻辑的成本。

09Sysops Squad：选择较慢、但更可控的组件路线

原书章末的分析发生在 10 月 29 日。Addison 和 Austen 查看抽象度与不稳定性后，发现大部分代码落在主序列附近，只有少数离群点。他们将其视为可以继续分解的支持证据；原书没有给出各组件的完整数据表，所以不能替案例补造具体 A、I、D，也不能把本笔记的计算例当作 Sysops Squad 实测。

Austen 最初喜欢战术分叉，因为复制后删减很像从石材中雕出目标形状。Addison 关心的是分叉以后谁来维护多份共享实现。系统已有日志、安全等基础设施代码，以及不少共享持久化访问逻辑；如果这些逻辑散在多个服务副本里，同一变化就可能要求多个团队协调修改。这恰好会重新放大他们想解决的可维护性、可测试性和可靠性问题。

更关键的是，Sysops Squad 已经有较清楚的组件边界。团队不必先靠分叉才能获得可理解的功能范围。采用组件路线，可以让服务定义随着组件分组逐步浮现；采用战术分叉，则需要提前决定建几份副本以及每份保留哪些职责。后者会让尚未充分理解的服务边界过早固化。

因此，两人决定使用基于组件的分解，并由 Addison 记录 ADR。决定的理由不是“主序列分数好，所以只能采用这种方法”，而是一条完整的推理链：结构允许继续改造，组件边界提供了可用起点，共享代码使复制维护的风险较高，当前业务问题又要求迁移过程尽量安全、渐进、可控。

原书 ADR 明确接受一个后果：迁移很可能比战术分叉慢。作为交换，开发者可以协作识别共同能力、组件和领域边界；不必立即分成围绕各副本工作的独立小组，再增加组间同步。这是一种有意识地用短期时间换取结构整理和协作连续性的选择，不是无代价的最佳实践。

本章结束时，确定的是迁移方法，尚不是最终服务数量、数据库归属或已经改善的运行结果。后续第 5 章将落实组件整理，第 6 章处理数据分解，第 7 章继续判断服务粒度。读到这里，最重要的联系是：架构分解的方式，应当帮助解决上一章提出的问题，而不是在追求启动速度时把同一种维护困难复制到更多地方。
