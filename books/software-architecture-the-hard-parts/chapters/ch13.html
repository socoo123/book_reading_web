第 13 章｜契约

Contracts · 让必要的共同理解稳定下来，让无关的变化各自发生

服务已经分开，工作流也有了编排器，接下来很容易直接讨论采用 REST 还是 gRPC。原书开场却把问题往前拉了一步：参与者究竟必须共同知道什么，哪些变化允许一方先发生，怎样发现双方已经无法合作？协议实现只是承载这些决定的机制。

本章把契约放在静态依赖、运行时协作与发布节奏之间理解。严格和宽松并非好坏两端；关键是约束是否覆盖了真正需要共同变化的部分。Sysops Squad 是原书虚构案例，本章为手机应用选择宽松契约，并明确把更多验证责任留给编排器和应用，未提供上线后的效果数据。

01契约连接的不只是请求，还有部署与运行条件

本书将契约（contract）广义定义为架构各部分传递信息或表达依赖所使用的形式。远程接口当然是契约，函数签名、库及其传递依赖、数据库结构、缓存记录也在讨论范围内。它们共同回答：一方可以依赖另一方提供哪些东西，变化后哪些约定仍然成立。

沿第 2 章的定义，架构量子结合独立部署、功能内聚、静态依赖与同步动态耦合分析。服务需要某版库、某些数据库列才能启动运行，是静态接线的约束；请求必须等待另一服务答复，因而共同承受延迟与故障，是动态协作的约束。把请求体改为 JSON，既不会消除必需数据库，也不会让原来的同步等待自动消失。

例如第 8 章的三个工单服务可以选择不同版本的共享 DLL，但都使用工单数据域。如果旧 DLL 仍要求某列存在，数据库删列就可能破坏旧部署。库版本化提供了采用新版的时间选择，却不能保证其外部数据契约永远相容。因此，不应从“服务使用宽松消息”直接推导“每个服务都成为完全独立的量子”。

契约也横跨通信、一致性、协调三个维度。异步消息仍需要明确字段及结果含义；最终一致仍需要说明哪些暂态可接受；协同仍需要知道下一步依据什么推进。契约严格度是贯穿这些选择的一组约束，不是把第 12 章八种 Saga 再乘出一套机械分类。原子性、隔离性和业务一致性也继续分开：一个结构完全合法的消息，不会自动获得跨服务事务保证。

02严格与宽松：约束写在哪里，比格式叫什么更重要

严格契约（strict contract）明确限定名称、类型、必需项以及适用的其他规则。远程方法调用容易让人像使用本地方法一样理解接口：调用哪个操作、传入哪些参数、得到什么结果，都有明确声明。收益是错误更早暴露，工具可以生成代码、验证结构和提供文档；代价是共同声明越宽，变化越容易触及无关消费者。

宽松契约（loose contract）让参与者只依赖必要的名称和值，允许其他信息独立增加或调整。宽松不是没有约定：status 拼错、必需的工单号缺失、完成状态的含义改变，照样会破坏业务。区别在于哪些约束由统一 schema 强制，哪些由消费者、契约测试或运行时逻辑兑现。

原书图 13-2 把 XML／JSON Schema、对象和 RPC 放在较严格一端，把 REST、GraphQL 放在中间，把简单 JSON 和键值映射放在较宽松一端。这是作者帮助讨论的示意谱，不是这些技术不可改变的属性。JSON 可以严格校验；GraphQL 本身有强类型系统；Protobuf 也支持特定的兼容演进。应比较实际字段范围和兼容政策，而不是把协议名当作耦合等级。

下面保留例 13-1 的三个字段，修正引号，并显式增加根对象类型，说明 schema 怎样把“一个 JSON”收紧为可验证的信息结构。它是笔记修订示例，不是原例逐字复制。

{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "type": "object",
  "properties": {
    "acct": {"type": "number"},
    "cusip": {"type": "string"},
    "shares": {"type": "number", "minimum": 100}
  },
  "required": ["acct", "cusip", "shares"]
}

这里 required 要求三项存在，type 限定值类型，minimum 要求份额至少为 100。它仍允许额外字段；若需要封闭字段集合，才另加 additionalProperties: false。根 type: object 也有实际作用：只写 properties 和 required 不会使字符串等非对象实例自动失败，因为这些对象关键字只约束对象。$schema 声明 schema 使用的方言，不会单靠这一行自动启动业务消息验证。

原例核查。 印刷 368 页／PDF 386 的 shares 行把 number 前的引号印为弯引号 “ → 原页回看确认不是纯文本提取误差，RFC 8259 第 7 节要求字符串界定符为 U+0022 → 应改为普通双引号 "。原例未限定根对象、未禁止额外字段，也不能读成“所有细节都严格匹配”。这是笔记的语法修正与能力说明，不冒称出版社已确认勘误。

同样，例 13-4 的简单 JSON 没有附带显式业务 schema，不等于 JSON 值没有类型："2003" 是字符串，2003 才是数字。读者应区分序列化格式已有的值类型、额外声明的结构规则，以及业务语义。

03结构兼容与语义兼容，是两道不同的门

结构兼容关心接收者能否继续读写预期的数据形状；语义兼容关心读到以后是否仍代表原来承诺的事实与行为。前者通过了，后者仍可能失败。以下是笔记假设：某响应始终包含数字 amount，原来表示含税金额，后来变成未税金额。JSON 解析、类型检查乃至字段齐全的测试都可能通过，但结算方按旧含义扣款便会出错。

兼容还具有方向。服务端增加一个可选响应字段，旧客户端若忽略未知字段，通常可以继续工作；服务端增加一个必填请求字段，却可能立即拒绝旧客户端发来的请求。“都是加字段”不足以得出相同结论。已有消息、离线设备以及尚未升级的消费者，使这种新旧组合成为正常状态，而不是罕见边角。

变化（笔记假设）结构上要看什么语义上要看什么
响应新增可选 displayHint旧读取者是否容忍未知字段缺少它时能否保留原行为
请求新增必填 repairType旧请求没有该字段会否被拒绝旧流程是否有合理的旧语义入口
status 新增一个取值枚举、分支或校验是否接受不认识的状态能否被误当作已完成
amount 类型不变但单位改变解析可能完全正常金额单位与计算含义已破坏旧约定

第 12 章提供了一个更贴近案例的语义边界：COMPLETED 表示维修完成，CLOSED 止于调查已经发送，并不表示客户回答了问卷。若移动端把三者显示为同一件事，接口即使字节完全一致，用户理解也会错误。契约应表达能够被消费方依赖的里程碑，而不是仅列几个字符串。

原书印刷 370 页用“严格契约一变，双方都要改”概括耦合代价 → Protobuf 官方 proto3 文档明确允许若干二进制 wire-safe 演进，例如增加字段，并提醒线格式兼容不等于应用代码兼容 → 更准确的解释是：破坏已依赖约定的变化才要求协调；严格类型并不意味着每次新增都要同步发布。 对应地，宽松 JSON 也不会自动保护字段删除、单位变化或新业务状态。

04GraphQL 的选择能力，不来自放弃类型

原书用 Wishlist 与 Profile 说明“按需要知道”：愿望清单只想把客户 ID 对应到姓名，而资料服务还管理地址、国家等大量信息。若清单契约要求整个资料对象一字不差地匹配，地址结构调整也会牵连清单。这项推理有价值，但需要把 GraphQL 的机制说清。

技术澄清。 印刷 368 页把 REST 与 GraphQL 并称较宽松的“格式”，并以只读聚合介绍 GraphQL → Fielding 原始论文将 REST 定义为架构风格；GraphQL 2021 规范明确强类型、查询、变更和订阅三种操作 → REST 不是序列化格式或某个传输协议，GraphQL 也不是无类型、只读的数据接口。只读聚合是其一种用法；减少客户端请求不保证减少服务端远程调用，执行成本仍取决于字段解析与后端访问安排。

下面是对原例 13-2／13-3 的笔记改写。服务端定义一个包含多种能力的类型系统，客户端查询只选择姓名；两段应分别作为 schema 与请求使用。

type Query {
  profile(id: ID!): Profile
}

type Profile {
  name: String
  addr1: String
  addr2: String
  country: String
}
query WishlistName {
  profile(id: "123") {
    name
  }
}

第一段声明提供方允许查询什么，ID! 表示必须提供非空标识。第二段声明本次实际需要什么。若示例数据的姓名是 Mei，成功结果的数据部分便只需包含 profile 下的 name: "Mei"，不用附带地址。查询仍须通过 schema 校验；删除 name 会破坏它，而在不改变现有字段和参数约定时新增一个地址输出字段通常不影响它。这里的 Profile 和 name 都可为空，消费者也应按这个声明处理空值。

原书两段 type Profile 是两种视图的概念比较，不应直接拼成同一 schema 中两个同名类型；第二段的 . . . 也是省略标记，不是合法字段。实际 GraphQL 服务中，各类型名须唯一，字段选择表达消费者需要的投影。这个区分使“只取必要字段”可以与强类型验证同时成立。

REST 的资源表示也能采用类似的兼容策略，但“给飞机资源增加发动机信息，不影响读取座位”成立的前提，是旧读取者只依赖座位且容忍新增表示内容。若它对所有键做精确相等校验，或者新增信息改变了分页、语义与错误行为，仍可能失败。资源建模创造演进机会，不能替代实际兼容规则。

05版本既隔离变化，也积累需要维护的承诺

原书表 13-1 同时把 versioned 列为严格契约的优点和缺点，原因并不矛盾。保留旧接口可以让旧消费者继续按旧约定运行，新消费者采用新能力；但每保留一版，就多一组需要实现、验证、修复和最终退役的承诺。版本标签若指向已经改变语义的同一实现，并未真正隔离行为。

第 8 章的库版本由使用方选入部署，网络接口的旧版本则通常需要提供方继续运行和维护。两者都能减少一次性集体升级，却把成本放到不同位置。移动应用无法随服务器同步发布时，支持窗口尤其应对应消费者实际升级节奏，而不是仅规定“最多保留两个版本”。原书没有给 Sysops 规定这个窗口。

宽松契约的收益，是减少不必要的共同声明，让实现与无关字段更容易独立变化；代价是校验责任不再全由统一类型工具承担。少一份 schema，不代表少一份必须一致的知识。字段拼写、必需信息、未知值处理仍要有维护者，缺失时还要产生可理解的失败结果。

安排原书强调的收益必须承担的代价
严格契约明确结构保证；版本隔离；易于构建期检查；文档清楚契约变化的共同影响；多版本维护与退役
宽松契约较少实现耦合；更自由的演进名称及字段管理；适应度函数和应用验证

此表重组原表 13-1—13-3，不是把三种安排排成互斥等级。严格接口也可以采用消费者驱动测试；宽松消息也可以用局部 schema。适合的组合取决于共同变化是否真实存在、工具能检查什么，以及团队能否持续运行并维护这些检查。

06各自的 Customer 模型，需要一个窄而清楚的交界

原书图 13-3、13-4 比较两个具有独立事务边界的服务共享客户信息。两者都认识 Customer，不意味着必须共享同一个完整类。配送可能关心可投递地址，结账可能关心客户标识与购买关系；让它们各自保留内部模型，再在边界交换必要值，能避免内部类的一次调整变成多个团队的发布任务。

这类映射不是纯粹的多余代码。它明确指出“本服务从对方实际需要哪些信息”，也让 Java 服务改用另一种技术栈时不必要求邻居一并改变。但公共字段的含义仍要一致：如果一侧的地址是当前资料地址，另一侧需要的是下单时地址，换成键值对并不能消除这个差别。真正应共享的是经商定的信息语义，而不是恰好同名的所有字段。

沿图比较，应关注的不仅是传了多少字节，还有接收者把多少东西当作必须稳定的承诺。传来一个额外字段但完全忽略它，与把整个对象绑定到封闭共享类型，并不是同样强的变化耦合。后者会让消费者为自己不使用的信息支付协调成本。

07消费者驱动契约：把真实依赖变成提供方能够执行的检查

消费者驱动契约（consumer-driven contract）让消费者表达自己所需的交互，由提供方在构建或交付流水线中验证。原书把它称为由 push 转为 pull，指的是契约需求从谁出发，不是把网络通信改为拉取，更不是要求提供方执行消费者任意提交的程序。

以前述愿望清单为例，消费者声明：查询存在的客户标识时，我需要可处理的姓名；客户不存在时，我也需要约定的空值或错误结果。清单自己的测试先证明它会发出正确请求，并能处理这些响应；提供方再对自己的实现验证相同交互。资料服务内部即使新增几十个字段，只要这些必要交互继续成立，清单就无须跟着修改。

Pact 的官方说明把这一过程拆成消费者测试与提供方验证：消费者通过模拟提供方检验真实客户端代码，生成描述交互的契约文件；提供方重放请求，把实际响应与最小期望比较。对于消息，检查的是消息生产与消费的交界，不需要假装整个消息代理已经受测。工具也不限定所有团队使用完全相同的内部对象。

这种安排避免“为了灵活性完全不要检查”和“为了检查共享全部模型”之间的假两难。但它需要工程纪律：消费方变更时更新契约，提供方运行相应验证，失败时阻止不兼容发布。测试只覆盖实际描述的交互，不能证明未建模的业务含义、并发恢复、消息送达或性能都正确；若把当前整个响应做成精确快照，又会重新制造不必要的印记耦合。

schema 能力澄清。 印刷 375 页说多数 schema 能限定数值类型却不能限定范围 → 同章例 13-1 已使用 minimum，JSON Schema draft-04 也明确提供 minimum／maximum 等关键字 → 数值范围不应被当作必须放弃 schema 的理由。消费者驱动检查更独特的价值，是表达实际消费依赖并由双方持续验证；更复杂的业务行为另用合适的业务测试。这里是对原书概括的修正，不是官方勘误。

08印记耦合：整份文档传递，局部服务只使用一角

印记耦合（stamp coupling）指参与者传递一个较大的数据结构，而每个参与者只读写其中一小部分。原书以旅行行业标准 XML 文档说明其合理来源：不同系统各更新行程的一段，完整文档作为跨系统协作载体。因此，传递整体并非天然错误；它可能减少反复取数，并保留后续处理所需的上下文。

问题常出在“以后也许会用到”。Wishlist 现在只需要姓名，团队却让完整 Profile 成为共同契约；资料服务调整清单不关心的 state 字段时，清单也可能因严格匹配而失败。原书图 13-7 展示的正是大结构加严格绑定造成的过度耦合，而不是声称每个额外 JSON 字段都会必然破坏客户端。

要判断这种代价是否值得，先找每个参与者真正读取、写入和原样转交的范围。需要姓名的服务没有理由顺便依赖全部联系方式；需要转交整份行业文档的服务，则必须知道哪些部分属于自己，哪些应保留给后续步骤。这里收窄的是共同承诺，不是简单把所有对象拆到只剩单个标量。

过小的契约也会产生另一种成本：消费者为了完成一个业务步骤，被迫连续请求多次，或者把本来应一起理解的信息拆散。比较应以完整业务交互为单位。一次交付恰当的一组字段，与一次交付全域数据库模型，是两种不同规模的选择。

09带宽账：载荷大小必须乘上请求频率

印记耦合还有不依赖类型绑定的成本：无论接收者用不用，多出来的字节都要序列化、传输并处理。原书给出每秒 2,000 次请求、每次 500 KB 的假设，说明单次看起来无害的完整资料，在高频交互下会累积成很大的吞吐需求。

按十进制口径 1 KB = 1,000 B，只计算这一路每次传输一次的应用载荷，有以下结果。它们是原书假设的算术复核，不是 Sysops 的实测，也没有计入请求／响应另一方向、协议头、重试、压缩和其他链路。

单位修正。 印刷 377 页／PDF 395 把缩减后的单次载荷写成 “200 bytes per second”，结果又写成没有时间单位的 “400 KB” → 与前文每秒 2,000 次的计算维度不一致 → 应读为每次 200 B，每秒合计 400 KB/s。前一项 1,000,000 KB/s 是这类调用的累计流量，不是单次调用的大小。该修正来自原页与量纲计算，不冒称出版社确认。

在这些假设下，两者相差 2,500 倍。这个倍数解释了“先收窄契约”为什么有时比更换编码协议更有价值，但它不是对任意姓名响应大小的预测。实际应测量序列化后字节数、峰值调用率和经过的链路；同一载荷若沿四段流程转发，每段都要承担流量，不能只看入口一次。

10让契约携带工作流状态，也就让参与者承担共同协议

第 11 章已经提出，在协同中把状态随消息传递。第 13 章进一步解释为何它是印记耦合的正当用途：服务需要的不只自己的业务字段，还包括前序是否完成、当前流程处于什么阶段、出现过什么错误。把这些信息放进共同信封，可以减少后续逐个询问先前服务的需要。

以下是依据原图 13-8 作出的笔记假设，而非 Sysops 已选方案：A 完成本地动作后记录 A 的结果，B 接收并更新自己的结果，终端接收者据此解释本次流程。每一步读取必要领域内容，但也转交其他步骤的状态；由此获得的整体上下文，正是增加契约耦合换来的。

状态责任没有随编排器一起消失。流程中途停住时，谁保存待办、谁发现超时、谁继续推进，仍须明确；若还需要任意时刻查询最新进度，消息本身并不自动构成查询入口。前置控制器可以汇集状态，查询投影也可承担读取，但这又是新的责任安排。并行分支尤其不能简单用“最后到达的完整对象”覆盖先前结果，否则旧副本可能抹掉另一分支已完成的进度。

一致性边界。 印刷 378 页说把契约重新广播给此前服务，以恢复 atomic consistency，原图还画出 Transactional boundary → 仅广播状态无法撤回已经独立提交、被其他业务观察到的效果；Microsoft 补偿模式明确要求业务补偿、可靠进度和失败恢复 → 应理解为凭状态组织后续恢复或补偿，不是消息再次走一遍便获得原子提交或隔离。补偿也可能失败，需要保留未完成责任。

原表 13-4 的交换因此很清楚：印记耦合能支持较复杂的协同工作流，却增加参与方共同理解状态协议的负担，并可能放大带宽。协同可能改善吞吐和独立伸缩机会，但有严格先后依赖时，换成信封不会让它们自动并行。若集中处理异常已经更简单，不能只为去掉中心而把所有复杂度搬进每条消息。

11Sysops：同一工作流里的契约，不必同样严格

先恢复案例输入。第 6—8 章保留三个工单服务共享稳定 DLL 和工单数据域，分派包含投递；第 9 章明确用户维护拥有专家资料，Survey 独占调查写入；第 10 章让分派复制技能、服务区域和标准排班，实时位置另有来源。这些数据责任不会因契约宽松而改变。

主工单已经在第 11 章选择编排，以管理丢单、取消、重派与状态查询。第 12 章提出保留维修完成事实、后台补发调查的思路，并比较 Fairy Tale／Parallel 候选，没有最终 Saga 模式 ADR。因此本章要决定的是参与者怎样交换信息，而不是宣布已有某种完整的最终一致实现上线。

Sydney 最初提议全部使用 gRPC，因为听说它快。Addison 先让团队决定契约类型，再允许开发者选择满足适应度函数的实现。这并非排斥 gRPC，而是避免速度印象替代兼容与发布分析。原书没有给出最终通信框架或相关适应度函数的可执行代码。

在章末对话里，编排器与工单管理、工单分派采用较严格契约：这些信息语义上联系紧密，新增需要管理的工单类别时，分派必须理解相应变化。通知和调查则可以宽松，因为它们在此交界处需要的信息变化较慢，紧密绑定整个工单模型收益不大。这里判断的是跨服务接口的变化；第 6 章调查内部问卷变化频繁，并不意味着调查启动接口也同样频繁改变。

原图继续使用 Ticket Management 合框，里面包含创建与完成，也继续把手机连线接到编排器。这与第 8 章的部署画法、第 7 章的投递职责视图不同，原书未补充新的服务合并或职责迁移 ADR。本节保留其工作流契约视角，不据此推翻前述边界。通知和调查契约宽松，也不表示可以缺少调查建档所需信息或绕过 Survey 的写所有权。

12手机端的例外：语义紧密，发布却不能紧绑

Sydney 注意到专家手机也直接处理工单，直觉上应像分派一样采用严格契约。这个候选并不荒谬：设备必须正确理解工单身份、处理内容及完成结果。但它遭遇另一项硬条件——应用通过公共应用商店发布，审核过程可能延迟更新；服务器团队不能假定所有接收方都能按同一时点升级。

若服务器改动立刻要求新版字段，尚未获批的应用就无法合作。宽松契约的价值不是让旧应用理解任何新业务，而是让不影响既有必需语义的扩展可以先出现，减少每次小扩展都触发同步发布的需要。这一判断综合了领域联系和交付控制权，而不是只根据谁调用谁决定严格度。

最终 ADR 的背景是商店发布带来的契约更新延迟；决定是在编排器与专家手机之间双向使用宽松的名称—值契约，并建立允许短期临时扩展的机制。后果有两项：如果商店政策允许更快甚至持续部署，应重新审视决定；编排器和手机应用内部必须承担更多契约验证逻辑。

原书没有给扩展机制的字段结构、版本协商协议或退役时限。作为笔记的工程解释，临时扩展只有在旧端能够忽略、缺失时保留正确旧行为时才真正降低发布压力。新增一个可选显示提示与新增一个必须执行的维修确认步骤不同：后者改变了业务承诺，不能放进扩展袋就假装旧应用已经支持。若新行为不可省略，就仍需明确支持能力与迁移安排。

更多校验逻辑也不是“遇到坏数据都尽量猜”。收到缺失工单号、错误类型或不认识的关键状态时，两端要按约定拒绝、提示或保留待处理，而不能把它们默认为成功。这里承接第 12 章：维修完成的确认和调查发送的确认是不同语义，字段宽松不能使手机错误宣布全部后续工作已经完成。

案例链条至此完整：主工单已编排且协作方不同 → 比较统一实现与逐交界选择、手机严格绑定与宽松扩展 → 内部工单协作较严格，通知／调查较宽松，手机因不可控发布节奏选择宽松名称—值并记录 ADR → 接受两端更多验证及将来重评。 原书没有证明该方案已缩短审核、避免所有升级故障或达到某个性能指标。

13好的契约，把必须共同变化的范围说明白

这一章的核心并不是尽量删掉约束，而是让约束与真实依赖相匹配。类型、必填项和工具验证能让错误更早显现；较窄的投影、兼容演进和消费者驱动检查能减少无关变化的传播。两类能力可以结合，前提是团队知道哪些承诺来自结构，哪些来自业务含义。

印记耦合又展示了同一个原则的两面：为了“将来可能有用”传完整模型，常常扩大不必要的依赖与流量；为了让协同中的参与者理解进度而携带共同状态，则可能值得承担这些成本。但消息结构不是事务、恢复器或全局查询入口，相关责任仍必须有人兑现。

Sysops 的手机 ADR 把契约问题落到发布现实：业务上有关联的两端，未必拥有相同交付节奏。把稳定核心与可兼容扩展区分开，能给不同节奏留出空间；一旦真正的业务语义改变，协调仍然不可避免。下一章将把边界与契约的讨论带到分析数据，而不把运营服务的内部模型直接当作所有分析消费者的公共模型。
