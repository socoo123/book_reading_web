# 第 4 章｜存储与检索

**Storage and Retrieval · 一次查询背后的数据布局、维护工作与恢复路径**

同样一张销售表，查一笔订单、统计全年销量、搜索商品描述，所需的数据访问方式很不一样。[第 3 章](ch03.md)讨论怎样表示数据和提出查询，本章把视角移到数据库内部：记录以什么顺序进入存储，索引怎样缩小读取范围，更新之后留下哪些旧版本，以及突然断电后怎样恢复。

理解这些机制，不是为了重新实现数据库，而是为了把配置与实际工作联系起来。增加索引会增加哪些写入？合并线程为什么占满磁盘？内存够大后还需不需要列式存储？答案不能只从“关系型”“NoSQL”或产品名称推断。本章先沿小规模业务读写展开 LSM-tree 与 B-tree，再转向分析扫描、全文搜索和向量检索。

<a id="log-and-index"></a>

## 01　日志让写入简单，索引让读取有方向

原书从两个 Bash 函数开始：写入时把 `key,value` 追加到文件末尾，读取时扫描文件，返回指定键最后出现的值。假设文件依次保存 `12,London`、`42,Golden Gate`、`42,Exploratorium`，查询 42 应得到最后一条。更新没有擦掉旧值；“最新记录胜出”是读取过程执行的规则。

这里的**日志（log）**是按顺序追加的记录序列，不特指给人看的运行日志。追加通常不必移动已有记录，容易形成连续写入；但这个简陋实现没有解决并发、编码转义、半条记录或持久化确认。尤其不能把一次 `echo` 成功理解成已经承诺断电不丢。它展示的是数据布局，而不是可直接替代数据库的程序。

读取的代价很直观：为了确认没有更晚的版本，必须从头扫到尾，工作量随日志长度增长，记作 O(n)。即使只有少量不同键，反复更新也会让日志越来越长。假设用十进制单位，100 GB 文件以持续 500 MB/s 扫描，单是搬运数据就约需 200 秒；这是忽略解析和竞争的算例，不是数据库实测。

最直接的改善是在内存放一个哈希表，保存“键 → 最新记录的字节偏移”。每次追加完成，就把该键的偏移改成新位置。查询 42 时先找偏移，再跳到那里读值；若对应文件块已在操作系统缓存里，可能没有物理读盘。**索引（index）**因此是一份为访问模式组织的派生结构：它让一次查询少做工作，也要求写入时同步维护。

这个方案仍留下四个相互关联的问题。旧版本不断占用磁盘；进程重启后要重扫日志重建哈希表；不同键太多时哈希表放不下；哈希只解决等值定位，不把相邻键放在一起。要查编号 10000—19999，必须枚举可能的键或扫描索引，不能像有序目录那样直接走过一段连续范围。

把哈希表放到磁盘上并非不可能，但随机访问、扩容和冲突处理会增加代价。原书由此转向有序索引。重要的不是宣布哈希无用，而是看清：**索引的结构必须对应问题的形状**。按 ID 找一行、按日期找一个区间和按任意词找文档，本来就不是同一个查找问题。增加普通派生索引不改变已有记录的内容；唯一性约束等额外语义则需要另行理解。

<a id="sstable"></a>

## 02　SSTable：排序使文件可查，也使文件可合并

**SSTable（Sorted Strings Table，排序字符串表）**把键值对按键有序保存。在本章的简化模型里，一个文件中每个键只保留一个值；实际支持多版本的引擎还可能把版本信息编码进内部键。这里的重点是文件写好后保持不可变，而不是把应用每一次更新插入已有文件中间。

假设一个文件有三个数据块，首键分别为 `apple`、`grape`、`pear`。查 `mango` 时，它不在这三个首键里，却位于 `grape` 与 `pear` 之间，所以只需读第二块，在块内查找即可。索引无需列出每一条记录，只保存足以定位数据块的边界键与偏移，这叫**稀疏索引（sparse index）**。原书图 4-2 用 `handbag` 与 `handsome` 之间的 `handiwork` 展示同一个道理。

每块通常只有几 KiB，读取并解码一块，比扫描整个文件便宜。稀疏索引本身可以放在文件的独立区域，采用树、trie 等结构，按需要缓存；它较小，不等于无论数据库多大都能全部驻留内存。块还可以做**压缩（compression）**：减少磁盘与网络搬运，以额外编码、解码计算换带宽。是否值得取决于压缩率、CPU 余量和访问模式。

排序还有第二个收益：两个有序文件可以顺序归并。不必把所有内容读入内存再排序，只需各保留一个读取位置，每次输出当前最小键；同键发生冲突时，用版本顺序选出需要保留的记录。这样，大文件的整理可以主要依赖连续读取和写出。

但排序也提出写入难题。已有 `apple, grape, pear` 时，新到的 `banana` 应插在中间。若每来一条都重写整个文件，索引让读变快，却把写变得太昂贵。接下来的 LSM-tree 正是把“即时接受更新”与“形成有序磁盘文件”分开，再用后台合并连接两者。

## 03　LSM 的读写路径：先接收更新，再整理文件

**LSM-tree（Log-Structured Merge-tree，日志结构合并树）**把近期更新放在内存中的有序映射，即 **memtable（内存表）**。它可由红黑树、跳表或其他支持有序遍历的结构实现。写入顺序可以任意，读出时却能按键排序。内存表达到阈值后被冻结，顺序写成一个新 SSTable；新的写入由另一张活动内存表接收。

仅有内存表会在进程崩溃后丢失。引擎因此还把更新追加到持久化日志，通常称为**预写日志（write-ahead log，WAL）**。日志按更新顺序写，不要求按键排序；它负责恢复近期内存状态，SSTable 则负责长期、有索引的读取。两者都可能是追加式文件，但职责不同，不能把 WAL 当成“已经完成压缩合并的 SSTable”。

假设这里采用同步持久化、只讨论单机崩溃：收到 `put(b,4)` 后，生成并追加日志记录，更新内存表，并在所需日志已可靠同步后确认成功。内存更新与同步可怎样流水化属于实现细节；关键不变量是**不能在持久性所需的信息尚未可靠保存时，给出相应的成功承诺**。批量提交可以让多次写入共享一次同步，并不要求每条记录单独调用一次 `fsync`。

读请求要同时考虑活动内存表、仍在落盘的冻结内存表，以及已发布的 SSTable。若在最新状态找到 b=4，就无需再返回旧文件里的 b=2。简单模型可按新到旧查；经过分层合并后，文件生成时间不等于其中每条记录的业务版本时间，因此真实引擎还依靠序列号、版本和层级规则判断新旧，不能只把文件按修改时间排序。

图 4-1 将两种责任分开：上方是接受更新并为它保留恢复依据，下方是把冻结内存表发布为新的有序文件。读取必须覆盖所有仍有效的状态。

### 一次合并，以及为什么不能随手丢弃墓碑

用三份小文件说明**压缩合并（compaction）**。它是归并文件并淘汰不再需要的版本，与压缩字节编码的 compression 不同。以下是笔记假设，S0 最旧，S2 最新，暂不保留历史快照：

```text
S0：b=2
S1：a=1，b=4，d=6
S2：b=†，c=5       （† 是删除标记）
```

若合并 S1 和 S2，读取位置首先遇到 a，输出 a=1；随后两边都到 b，较新的 `b=†` 胜出；再输出 c=5、d=6。结果是 `a=1，b=†，c=5，d=6`。查询 b 看到删除标记便返回不存在，不能继续去旧文件找一个“非空值”。删除因此也要写一条记录，称为**墓碑（tombstone）**。

现在若把结果里的墓碑也删掉，S0 仍保存 b=2。之后读取在新文件找不到 b，继续查 S0，已经删除的数据便“复活”。只有确定所有可能遮盖的旧版本都已被本次合并处理，且没有需要保留的历史读取等约束，才可丢掉墓碑。原书把它概括为合并到最老段后移除；这里展开的是这条规则背后的原因。

![只合并S1和S2时，b的删除标记必须留在输出中，因为未参与合并的S0还保存b等于2；过早移除墓碑会让旧值重新可见。](../diagrams/exports/ch04-merge-tombstone.svg)

图 4-2：实线进入本次合并；虚线标出未参加合并的更旧文件。先跟随 b 的三个版本，再检查输出为何保留 †。点击[查看大图](../diagrams/exports/ch04-merge-tombstone.svg)。

### 崩溃发生在“写好”与“发布”之间

不可变文件让恢复更容易推理：合并过程中仍可从旧输入文件读取；新文件完整写好并安全发布后，才切换有效文件集合，随后回收不再被读者或快照引用的旧文件。这个顺序意味着合并到一半崩溃，可以丢弃未发布的半成品，继续使用旧文件，而不是修补一个已经覆盖一半的文件。

内存表落盘也是类似过程。若 SSTable 只写了一半，对应 WAL 还必须保留，重启后可以重放日志重建内存表；若新文件已经完整持久化并被恢复元数据纳入，才可以回收其所覆盖的日志。**文件写出函数返回，不等于文件和发布信息都已达到崩溃安全条件。** 提前截断 WAL，再失去未持久化的 SSTable，会同时丢掉数据与恢复依据。

日志末尾也可能只有半条记录。长度和校验和帮助恢复器识别不完整尾部，保留有效记录并按恢复规则处理尾部。校验和负责检测，不负责重造数据；不能把“尾部未完成写入可忽略”扩大成“日志任意位置损坏都直接跳过”。旧稿示例只有语言层 `flush()`，且在 SSTable 输出后立即截断日志，不能据此声称已经实现断电安全。这里保留机制推演，不把缺少元数据提交协议的伪实现当作可用存储引擎。

## 04　Bloom 过滤与合并策略：把读取、重写和空间连起来

LSM 的一个弱点是“不存在”也可能很贵。查一个从未写过的键，不能在第一份文件没找到后就结束；查很久没更新的键，也可能穿过许多新文件。**Bloom filter（布隆过滤器）**用一个较小的位数组先判断某文件是否可能包含该键。

原书的 16 位例子中，`handbag` 映射到位置 2、9、4，`handoff` 映射到 9、15、5，索引从 0 开始。构建时把这些位置设为 1。查询 `handheld` 映射到 6、11、2，其中 6 和 11 为 0，便能排除这个文件：若键曾正确加入，它对应的位理应全部为 1。若某个不在文件里的键恰好映射到 2、4、9，检查全为 1，却只是其他键留下的痕迹，这叫**假阳性（false positive）**。

所以过滤器返回的是“肯定不在”或“可能在”。后者必须继续查块索引和数据；假阳性只让系统多做一次无用工作，不把错误值交给用户。这个不漏报的性质以正确构建、键编码一致、数据未损坏为前提。对不可变 SSTable 很方便，因为过滤器不必跟着每次原地更新复杂地撤销位；墓碑对应的键也不能被错误排除。

原书给出约 10 bit/key 对应约 1% 假阳性的经验值；分配更多位可以继续降低误判，但要多占内存或存储。它不是“全部数据都查一次”的替代物，而是把一次廉价检查放在昂贵读取前。普通按完整键构建的 Bloom 也不能直接回答任意范围是否为空：知道怎样检查一个键，不等于能够枚举范围里所有可能的键。

文件越来越多时，只有过滤器仍不够，需要控制合并。**大小分级压缩合并（size-tiered compaction）**把若干大小接近的段合成更大的段。原书假设四份 256 MB 文件合出 898 MB，少于 1024 MB，是因为旧版本、删除和过期数据被清理。较大批次能摊薄维护工作，但大合并完成前旧文件还在，临时空间需求可能很高；同一键也可能分散在更多候选文件中。

**分层压缩合并（leveled compaction）**则把段组织成 L0、L1、L2 等越来越大的层，L0 之后同层文件的键范围通常不重叠。若 L1 分成 a—m 与 n—z，点查 k 只需考虑前一份，而不是遍历整层。上层文件超出容量限制时，与下一层范围重叠的文件归并，写成目标大小的新文件。读候选数和空间冗余可以更低，但维持范围不重叠通常需要更频繁地重写数据。

选择因此不只是“开哪个选项”：写多读少、允许较多临时空间的负载可能受益于大小分级；更关注读取和空间的负载可能偏向分层。冷热键比例、值大小和层级配置都会改变结果。合并虽然能在后台运行，仍占用 CPU、磁盘带宽与缓存；“后台”表示并行安排，不表示成本消失。

持续写入超过 flush 和合并能力时，冻结内存表和待合并文件会积压，引擎需要**背压（backpressure）**，让新写入减速或等待。原书印刷 129 页及旧稿说 RocksDB 会“暂停所有读写” → 官方 Write Stalls 文档描述的是放慢或阻塞写请求 → 更准确地说，写入可被主动停顿，读取也可能因资源竞争与读放大而变慢，但不能把这种间接影响写成统一暂停读取的协议规则。

## 05　B-tree：用页与范围边界组织一棵浅树

**B-tree**采用另一种布局：把存储分成固定大小的**页（page）**，页间通过页号或引用连接。内部页保存范围边界和子页引用，叶页保存记录或记录位置。本章沿原书用 B-tree 统称这一类结构，主要示意常见的 B+ tree 组织，不纠缠命名变体。

原书图 4-5 查键 251：从根页选择 200—300 的范围，下一层再选 250—270，最后在叶页找到 251。区间边界须有明确归属，例如 `[250,270)` 表示包含 250、不包含 270，这样恰好落在边界的键不会失去位置。若叶页只保存位置，还要沿引用读取实际行。

一页能容纳的子页引用数叫**分支因子（branching factor）**。它常远大于二叉树的 2，因此每走一层就能排除大部分范围，树高增长很慢。内部页又比较少，根和上层页通常容易缓存。一次逻辑查询经过四页，不意味着一定发生四次物理 I/O；缓存命中、数据是否内联、读取并发都会改变真正的设备访问。

范围查询也利用相同排序。查 250—280，先定位开始位置，再沿相邻叶页继续取记录，到超过上界时停止。兄弟页引用可省去反复返回父页找后继的工作，但逻辑相邻并不保证物理相邻；页分裂和长期更新可能让它们散布在不同位置。

更新已有键时，先定位叶页，再修改该页；页通常先在缓冲区中变脏，稍后写回。插入则可能触发**页分裂**。原书图 4-6 中，负责 `[333,345)` 的叶页已有 333、335、337、340、342，插入 334 后放不下，于是在 337 处分开：左页为 333、334、335，右页为 337、340、342。父页增加边界 337，以及指向新右页的引用。

若父页也满，需要继续向上分裂；根分裂时新建一个根，所有叶子的层数一起增加。这样保持的是树的平衡，而不是保证任何请求耗时相同。删除可能涉及页内回收、合并或其他调整，实现比这个插入示例复杂；并发维护和事务版本也会影响代价。

这里需要校正原书的一个数量级。印刷 127 页写“四层、4 KiB 页、分支因子 500，可存约 250 TB” → 若根到叶总共四层、数据放在叶页，最多有 `500³` 个叶页，其总容量是 `500³ × 4096 = 512,000,000,000` 字节，约 **512 GB**，还没扣页内开销与空闲空间 → 约 256 TB 对应 `500⁴` 个叶页，即根到叶五层。若叶页引用树外数据，还需另算记录大小。本文保留“高扇出使树较浅”的结论，不沿用口径不清的 250 TB。

<a id="wal-recovery"></a>

## 06　B-tree 的恢复：日志先行，不要求每次提交都刷完数据页

原地修改省去了把每次更新保留成新文件的需要，却增加了恢复责任。上一节的分裂至少涉及左叶页、右叶页和父页。假设右叶页已写入、左叶页也删去了搬走的记录，父页的新引用尚未写入就崩溃，恢复后树可能无法到达右页里的记录。若设备不能原子写完整个页，单页还可能一半是旧内容、一半是新内容，称为**撕裂页（torn page）**。

常见解决办法同样是 WAL。这里“预写”的关键约束是：**数据页对应的日志必须先可靠持久化，数据页的修改才可以写入持久存储。** 它不要求先把日志刷盘，才准修改内存里的缓冲页。PostgreSQL 17 官方文档也以这个持久化顺序解释 WAL；忽略“内存页”和“磁盘页”的区别，会把实现顺序讲错。

在一个简化的单事务更新中，引擎生成描述改动的日志，并修改缓冲区页；提交时把包含必要提交信息的 WAL 同步到可靠存储，随后确认成功。数据页可以尚未刷盘。此时若进程崩溃，重启后根据有效恢复起点与日志记录重做尚未反映到数据页的修改，让已提交结果重新出现。对页分裂，恢复协议还要使页和引用关系回到可用状态。

如果日志尚未可靠持久化，数据库就不应给出同步持久性承诺；若已持久化、却在回复客户端前崩溃，修改可能已经提交，只是客户端不知道。恢复存储状态与消除客户端不确定性是两个问题，后者将在后续事务与分布式故障章节展开。这里也不把“重放 WAL”理解成盲目重做所有业务操作：未提交状态、版本可见性和重复重做均由具体恢复协议处理。

图 4-3 用三个时点说明数据页落后于日志并不必然丢数据；真正重要的是落后时仍保存足够恢复依据。

![WAL先持久化；随后数据页可能只刷出一部分并发生崩溃；重启根据日志恢复缺失的页修改和引用关系。](../diagrams/exports/ch04-btree-recovery.svg)

图 4-3：由上向下读时间顺序。第二行是允许被恢复协议处理的中间磁盘状态，不是可直接对外使用的一棵完整树。点击[查看大图](../diagrams/exports/ch04-btree-recovery.svg)。

WAL 也不是只写几个字段就自动修复任意损坏。撕裂页保护可能需要完整页映像、双写等具体机制；日志与设备同步还依赖存储栈兑现相应保证。原书在这里建立原则，[第 8 章](ch08.md#acid)再展开持久性与事务。旧稿用“装修前拍照”解释 WAL，容易让人以为日志只有旧状态；更准确的理解是保存足以执行恢复协议的信息，其中常包含重做修改所需的数据。

另一条路线是**写时复制（copy-on-write）**：将修改后的叶页写到新位置，再写指向它的新父页，逐层形成新根；在新页可靠保存之后，安全发布新根。崩溃前若新根未生效，旧树仍可用；旧读者也可继续使用旧版本。它把问题转成新版本的发布与旧页回收，而不是“没有 WAL 就没有恢复协议”。

其他优化围绕减少工作展开。内部页只需保留足够区分范围的键前缀，可提高分支因子；叶页兄弟引用有利于扫描；尽量按键顺序布置叶页有利于顺序读取。它们各自解决一个成本来源，不能仅凭“用了 B-tree”推断这些优化全部存在。

## 07　三种放大：比较完成同一工作付出的总代价

原书把“LSM 常适合写密集、B-tree 常有利于读”作为经验起点，同时要求用自己的负载测量。要理解为什么结果可能反转，可以分别问三件事：为了得到目标数据读了多少，为了保存一次更新写了多少，为了表示当前数据占了多少空间。

**读放大**描述额外读取。本章以读取字节与 I/O 次数作为观察口径，不把二者混成一个数。B-tree 点查走一条根到叶路径，LSM 可能检查多份候选文件；但 memtable、Bloom、块缓存和页缓存都能减少设备读取。LSM 范围查询要合并相关有序段并消解旧版本与墓碑，不能直接把每个段的行连接起来；也不必读取键范围完全无交集的文件。大结果集时，输出本身的搬运还可能占主要成本。

**写放大**按原书的字节口径，是实际写入存储的总字节数，除以若仅将同样逻辑更新追加到无索引日志所需的字节数。假设一批逻辑更新为 100 MB，WAL 写 100 MB，首次 SSTable 写出 80 MB，后续相关合并又写 220 MB，则这个观察窗口内写放大为 `(100+80+220)/100 = 4`。这里假设已把这批数据的相关后续重写计入，数字只是示意。

LSM 的放大来自日志、首次落盘和多轮合并；大值若跟着小键反复搬运，代价尤其明显。键值分离可以让 SSTable 只存键与值的位置，减少合并时搬运大值，但会留下值文件读取和垃圾回收工作。B-tree 的放大来自 WAL、数据页刷写、分裂及可能的整页保护。只改几字节却写整页可能很贵，但同一缓冲页上的多次更新也可能合并成一次刷盘，因此“每次应用更新必然独立写一个整页、放大固定至少两倍”不是可靠的测量结论。

顺序与随机写也有硬件背景。机械盘的随机访问需要移动磁头；SSD 没有这一步，但闪存按较小单位读写、按较大块擦除，回收混有有效数据的擦除块时要搬走有效页。于是设备内部又有一层写放大。数据库写出的连续文件、数据失效顺序、设备控制器和剩余空间共同影响它；不能把原书的页／块示意尺寸当作所有 SSD 的固定规格，也不能保证删除一个文件就恰好零搬运擦除一个物理块。

**空间放大**则比较物理占用与逻辑有效数据量，应说明是否包含索引、日志、快照和临时文件。LSM 会保留尚未清理的旧值，合并时新旧文件还短暂并存；B-tree 会有页内空隙、可复用但尚未归还系统的空闲页。压缩能减少两类引擎的某些占用，快照又可能让旧数据长期不能回收。

这里有两处需要纠正。旧稿写“B-tree 删除彻底性：立即” → PostgreSQL 等系统可为多版本并发控制保留旧行，WAL 和备份也可能仍含记录 → **查询不可见不等于字节已经物理清除**，不能用树的类型判断删除完成。原书印刷 131 页把 PostgreSQL 的 vacuum 当作移动页面、重新摆放的后台整理例子 → PostgreSQL 17 文档说明普通 `VACUUM` 主要清理死版本并标记空间可复用，通常不把中间空洞归还操作系统 → 重写压紧表的 `VACUUM FULL` 是不同操作，且有额外空间与锁成本。

不可变 SSTable 确实有利于快照：冻结当前状态，保存有效文件集合并阻止所需文件被删，可以共享文件而不立即复制全部数据。但这不是免费备份；元数据要完整，文件保留会增加占用，同一设备损坏仍可能同时失去当前数据和快照。

最终测试要覆盖系统已经积累数据、合并持续运行的状态。只往空 LSM 写几十秒，看不到后续重写代价；只测缓存全命中的热键，也看不到冷读与不存在键的成本。选型时将键值大小、覆盖率、范围长度、缓存预算、持久化配置与尾延迟一起固定，才有可解释的比较。[第 2 章](ch02.md)讨论的响应时间分布，在这里比单独一个平均吞吐量更有用。

## 08　二级、复合与覆盖索引：一次加速怎样改变更新路径

主键唯一标识一条记录；**二级索引（secondary index）**提供其他入口。假设订单表有 `order_id、user_id、created_at、amount、address`，按用户查订单需要 `user_id` 索引。同一用户可有多笔订单，所以索引要么将用户映射到订单 ID 列表，要么用 `(user_id, order_id)` 作为唯一索引项。B-tree 与 LSM 都可承载这种键值映射，二级不是另一种树算法。

若常查“用户 7 在某时间段的订单”，可将键按 `(user_id, created_at, order_id)` 排列，形成**复合索引**。所有用户 7 的记录相邻，内部再按时间排列，查询能定位到一个较紧的区间。若只按 `created_at` 查所有用户某天的订单，时间值分散在各用户分组里，不能靠同一排序直接定位一个连续区间；实现可能采用扫描或跳跃扫描等优化，但不应把有这个复合索引等同于有单独时间索引。

索引叶子放什么决定了后续读取。**聚簇索引（clustered index）**直接将行存入索引组织中，按该键范围读取时相关数据有局部性。另一种是叶子仅存行位置，行放在无指定键顺序的**堆文件（heap file）**；也可以存主键，再沿主键索引找行。原书以 InnoDB 主键聚簇、二级项引用主键，以及 PostgreSQL 的堆文件说明这些不同布局，不能把“二级索引”直接等同“指向堆文件”。

若查询只需要时间和金额，可在用户／时间索引中附带 `amount`。此时索引中已有查询需要的列，称为它**覆盖（cover）了这个查询**。覆盖是相对于具体查询的性质；加查 address 后原索引便不再覆盖。物理执行也可能还需其他检查，例如 PostgreSQL 的仅索引扫描要利用可见性信息判断是否需要访问堆；有列值不自动意味着所有情况下零回表。

代价可以沿一次更新追出来。将某订单从用户 7 改归用户 8，主记录要更新，旧的用户索引项要移除，新的项要插入。若 amount 是索引附带列，修改金额也需要维护该索引副本；若不包含金额，可能避免这部分工作。行变长而搬到新位置时，直接保存物理位置的索引还涉及指针维护或转发机制。索引不是创建后只收取一次成本的静态目录。

这与**内存数据库（in-memory database）**的选择又是不同轴。将数据与索引主要放在 RAM，可避免部分面向磁盘页的编码、解码和缓冲管理，直接使用集合、队列等结构。磁盘数据库在热数据全被缓存时也可能没有读盘，所以内存数据库的收益不只是介质快，而是整个内部表示与处理路径可以不同。

但需要持久性的内存库仍要记录日志、生成快照或复制状态。仅周期快照会留下快照后的恢复缺口；异步日志可能在故障时丢掉尚未同步的更新；多个仅驻内存的副本也不能自动覆盖所有副本同时失去内存的情况。旧稿说内存库省掉“全部编码和崩溃恢复格式”，范围过大：它省的是部分磁盘主存储布局开销，日志编码与恢复责任可能依然存在，持久性应按配置和故障模型判断。

最后，**嵌入式数据库**描述运行方式：引擎作为库进入应用进程，通过函数调用访问，典型如 SQLite、RocksDB、DuckDB。它既可能做事务，也可能做分析，不等于纯内存或某一种索引。数据能由单机承载、访问边界清楚时，进程内方案可能简洁有效；多租户各自独立也可考虑每租户一个库，但跨租户查询与共同事务就需要另行安排。

## 09　云分析存储：文件、表与查询引擎各负什么责任

[第 1 章](ch01.md)区分运营型与分析型系统：前者支撑日常业务的小批量读写，后者经常扫描大量记录以计算聚合。两者都提供 SQL，并不意味着内部布局相同。所谓 HTAP，即混合事务与分析处理，也可能在一个产品内维持不同存储表示和执行路径，再处理它们之间的同步。

云数据仓库把大量持久数据放在对象存储，将查询计算与存储容量分离。计算节点不必始终拥有全部本地文件，可以按查询需要读取、缓存和并行处理；增加存储与增加计算不再必须同步扩容。这改变的是资源组织方式，不意味着传输没有延迟、计算没有启动成本，或任意负载都能无限加速。

原书第二版特别解释了开放分析系统的四层职责。可以沿一次“查询销售表”理解：**数据目录（data catalog）**告诉引擎有哪些表及如何找到它们；**表格式（table format）**的元数据说明某版本的表由哪些文件组成、采用什么模式；**存储格式（storage format）**说明单个文件内怎样编码列与记录；**查询引擎（query engine）**解析 SQL、制定计划，再调度计算去读这些文件。

例如，Parquet 解决文件内部表示，Iceberg 一类表格式解决文件集合与表版本，目录提供表的发现与管理入口，查询引擎负责连接、过滤和聚合。文件能被多个引擎读取，确实有助于共享数据，但是否能共同读写同一张表，还取决于双方支持的表格式、版本与提交协议。不能只看“都支持 Parquet”就推断事务兼容。

这里再次遇到不可变文件与发布顺序。笔记假设：一次批量导入写出 A、B 两个文件，第二个只写到一半时进程失败。仅靠列举对象存储目录，读者可能看到不完整的一批；表元数据把“哪些完整文件共同构成一个表版本”固定下来，才能区分已提交版本和未发布产物。具体事务保证由所用表格式与目录提交机制提供，不是对象不可变本身提供。

保留旧版本元数据及所引用文件，可以支持时间旅行查询；垃圾回收则在保留策略允许后回收不再需要的文件。它不会使任意历史永远可查。查询、格式、表与目录拆开后，各自可演进，也让元数据治理系统能访问目录；与此同时，兼容与生命周期管理成为必须明确的接口责任。

## 10　列式存储：少读几列，仍须保留同一行的联系

原书例 4-1 想比较 2024 年不同星期几的水果与糖果销量。它将销售事实表与日期、商品维度表连接，过滤年份与类别，再按星期和类别汇总数量。事实表可能有上百列，查询却主要需要 `date_key、product_sk、quantity`。问题由此从“怎样快速定位一条记录”变成“怎样少搬运大量无关字段”。

**列式存储（column-oriented storage）**把同一列的值集中保存。分析查询只加载所用的列，避免在大量行的完整记录之间跳转。下面是笔记假设的小销售表，后续位图和聚合都使用它；日期、商品编号只为说明布局：

| 行位置 | 日期 | 商品 | 门店 | 数量 |
| --- | --- | --- | --- | ---: |
| 1 | 11-01 | 31 | 3 | 2 |
| 2 | 11-01 | 68 | 3 | 1 |
| 3 | 11-01 | 31 | 4 | 4 |
| 4 | 11-02 | 69 | 3 | 3 |
| 5 | 11-02 | 31 | 3 | 5 |
| 6 | 11-02 | 68 | 4 | 2 |

商品列是 `[31,68,31,69,31,68]`，数量列是 `[2,1,4,3,5,2]`。两列第三个值必须属于同一条销售记录，才能还原“商品 31、数量 4”。列式布局把字段分开保存，却不能丢掉行位置的对应关系。实际系统通常先把表分成许多行组或块，块内按列保存，而不是将万亿行的一整列放进一个不可分割的巨大文件。

若块按日期分布，查询 11-02 可先跳过只含 11-01 的块，再读取所需列。**块裁剪**减少要碰的行组，**列裁剪**减少每个行组要碰的字段，两种收益可以叠加。行式引擎也可能通过覆盖索引减少读取，不能说每个行式查询都必然解析全部字段；列式的优势主要在大范围、少列扫描的布局适配。

### 位图把筛选变成集合运算

对于商品列，可为每个不同值建立一个位图，第 i 位表示第 i 行是否等于该值。商品 31 是 `101010`，商品 68 是 `010001`；两者按位 OR 得到 `111011`，即商品属于这两个值的行。门店 3 的位图为 `110110`，与商品 31 按位 AND 得到 `100010`，只留下第 1、5 行；这两行数量之和为 `2+5=7`。

![商品31的位图101010与门店3的位图110110按位与得到100010，选中数量列第1与第5项2和5，求和得到7。](../diagrams/exports/ch04-column-mask.svg)

图 4-4：每列从左到右都是同一组行位置，竖向对齐是运算正确的前提。箭头表示从列条件到结果选择，不表示逐个磁盘请求。点击[查看大图](../diagrams/exports/ch04-column-mask.svg)。

当不同值很少、或位图具有合适的稀疏与重复模式，编码可很紧凑。**游程编码（run-length encoding）**把一长段相同位存成“值和长度”，例如一百万个连续 0 不必逐位列出。但不同值很多且分布零散时，为每个值保留完整位图并不合算；压缩方式要随数据分布选择。

原书印刷 140 页及旧稿把 Roaring 简化为逐位与游程两种表示切换 → 官方说明还包括稀疏整数数组，并按区块选择数组、位图或游程容器 → 因而准确的启发是“局部分布决定表示”，不是所有位图都只能二选一。位运算能高效处理批量数据，也不意味着几亿行在任意硬件与压缩率下都可瞬间完成。

### 排序与批量写入要一起理解

如果常按日期筛选、再按商品分组，可按 `(日期,商品)` 排整行，再将各列分别写出。不能各列独立排序，否则原来第 3 行的数量可能被错误拼给另一商品。第一排序列往往形成长重复段，有利于游程压缩；第二排序列只在第一列相同的范围内有序，收益可能较小。选择哪列优先，仍由查询模式决定。

向已排序、压缩的列文件中间插一行可能牵动多个编码块，因此列式引擎常先积累更新，再批量写新文件并整理旧文件。这又借用了日志结构的思想。读最新状态时，要合并已发布列文件与近期增量，避免同一行的新旧版本重复计数，并正确应用删除。能否读到刚写入的数据取决于系统的提交与查询可见性约定，不能从“用了列存”推出即时可见。

列式也不等于**宽列／列族（wide-column / column-family）**模型。后者描述一行可有大量、甚至不同集合的列，Bigtable 一类系统主要围绕行键及列族组织；它不等同于跨大量行集中扫描某几个属性的分析型列存。类似地，列式文件也可以表示嵌套文档，只是需要额外保存结构与行对应信息。

## 11　执行与预计算：减少搬运之后，还要减少重复工作

读入内存不是查询结束。一个分析 SQL 还要执行过滤、连接、聚合等**算子（operator）**。若每处理一行都重新解释“比较哪列、用哪个运算、调用哪个函数”，大量短操作会被分派开销淹没。原书将两条优化路线并列讨论。

**查询编译（query compilation）**为当前计划生成专用代码，再编译执行。例如把“商品等于 31 且门店等于 3，则累加数量”写成紧凑循环，不必每行重新解释整个表达式结构。它付出生成与编译成本，换取大量重复执行时较低的单行开销；特别短的查询不一定能摊薄准备成本。

**向量化处理（vectorized processing）**则让预定义算子每次处理一批值。把一批商品交给等值算子，得到一个选择位图；门店列也生成一个位图，再求交、汇总匹配数量。解释与函数调用成本被一批数据分担。这里的“向量”是批量值的表示，不是语义搜索的嵌入向量；批处理也不必然等于每一步都用了 SIMD。

两条路线都可以利用连续内存访问、紧凑循环、多线程及**单指令多数据（SIMD）**，减少缓存未命中、分支和数据复制；它们也可在系统中组合。某些运算可直接利用压缩表示，比如同值重复 N 次的数量汇总可以按运行长度处理，而不先展开 N 个对象。能否这样做由编码与算子决定，不能泛称“压缩数据从来不需要解码”。

再往前一步，若同样的报表反复运行，可以保存它的结果，这就是**物化视图（materialized view）**。虚拟视图只是查询定义的封装，读取时仍展开执行；物化视图持有实际结果，原数据变了就必须维护或刷新。它与[第 2 章](ch02.md)的时间线预计算共享一条思路：把某些读时工作提前到写入或后台处理阶段。

**数据立方体（data cube）**是一类按多个维度预聚合的物化结果。将上一节六行销售按“日期 × 商品”汇总数量，便得到：

| 日期 | 商品 31 | 商品 68 | 商品 69 | 当日总量 |
| --- | ---: | ---: | ---: | ---: |
| 11-01 | 6 | 1 | 0 | 7 |
| 11-02 | 5 | 2 | 3 | 10 |
| 两日总量 | 11 | 3 | 3 | 17 |

每个格子是一组原始行的 SUM；沿某一维再求和，就得到减少一个维度的汇总。三维、五维原理相同，不必真的画成立体方块。新增一条 11-02 商品 31 数量为 2 的销售，要更新相应格子及受维护的汇总；若存在撤销或纠错，也要使聚合与当前事实保持约定的一致性。

不是所有聚合都能直接相加。笔记补充：两组平均数 10 与 20，若样本数分别为 1 与 9，总平均为 `(10×1+20×9)/10=19`，不是 15。需要保留 SUM 和 COUNT 等足够的中间统计。删除当前最小值时，单独保存一个 MIN 也不足以知道新的最小值，可能需要其他状态或重算。

预聚合还会丢掉自由度。上表去掉了门店维度，再问“门店 3 的商品 31 卖了多少”，就无法从格子还原原来的 7；原书同样指出，若未保留价格维度，不能凭立方体回答某个价格门槛下的销售比例。于是物化聚合适合作为常用问题的加速路径，原始事实仍是新问题、重新分组与纠错的重要依据。

## 12　多维与全文：查询条件不总是一条连续键范围

复合索引把多个字段排成一条顺序。按 `(姓,名)` 排的通讯录，能很好地找一个姓或一个姓名，却不能同样直接地找到所有同名不同姓的人。这不是它不含“名”，而是相同的名不连续。地图查询更加明显：用户想找屏幕矩形内的餐厅，需要同时限定经度与纬度。

假设只建 `(纬度,经度)` 索引，查询某段纬度时，符合条件的候选可能横跨很宽的经度；第二列可继续过滤，却通常不能把整个二维矩形变成一个紧凑的一维区间。交换列顺序只会交换优先收紧的方向。**多维索引**按空间区域组织数据，让两个方向的条件一起排除大块候选，R-tree、Bkd-tree 是原书介绍的代表；也可通过空间填充曲线或规则网格映射到可索引的区域。

空间索引常先用包围区域找到候选，再检查精确几何条件。若区域与查询矩形只有部分交叠，不能把里面每个对象都直接当成命中；点、线和多边形的关系也不同。原书的天气例子说明这不只用于地图：二维 `(日期,温度)` 索引也能缩小“某年内 25—30°C”的候选，比只按一个维度扫描再过滤更贴合问题。实际收益仍取决于分布和选择性。

**全文搜索（full-text search）**面对另一种多条件问题：找文本任何位置出现了指定词的文档。将每个词看作一个维度，文档包含这个词就记为 1，查同时包含 `red` 与 `apples` 就成为两个集合求交。核心结构是**倒排索引（inverted index）**：从“词 → 包含它的文档 ID 列表”，该列表称为 **postings list（倒排列表）**。

笔记假设：`red → [1,3,4]`，`apples → [2,3,4]`，两个有序列表双指针推进，遇到相等 ID 时输出，得到 `[3,4]`。若用位图表示，同一位置代表同一文档，就可像列式筛选那样按位 AND。词本身到列表的映射又可以用有序段保存和后台合并；原书以 Lucene 说明搜索引擎也会复用日志结构思想。

但“同时含两个词”不等于短语“red apples”。文档 4 可能先写 apples，几段以后才写 red；若要求相邻或顺序，就要保存词位置或进一步核对文本。中文分词、词形归一、同义词和排名也属于额外处理。倒排结构提供候选定位，不独自定义全部搜索语义。

需要子串搜索时，可将 `hello` 拆成三元片段 `hel、ell、llo`，为 **n-gram** 建索引。长模式提取出片段后可缩小候选，但通常还要复查完整子串或正则条件；片段都出现，不代表它们按要求连续出现。容错搜索则可结合词典自动机与编辑距离，寻找经过少量插入、删除或替换可以得到的词。它们扩大可检索的表达形式，也带来更大的索引或更多候选检查工作。

<a id="vector-search"></a>

## 13　向量检索：近邻是候选，不是事实证明

原书用帮助页说明关键词的边界：页面写“取消订阅”，用户搜“如何关闭账户”或“终止合同”，词可能不同，意图却相关。**向量嵌入（vector embedding）**由模型把文本或其他媒体映射成一组数，将输入表示为高维空间中的点；训练使某些语义相关的输入在所用相似度下靠近。模型并不保证每次都抓住业务上重要的区别，“取消订阅”和“删除账户”也可能在具体产品里是两个不同操作。

原书给出三维示意：农业 A=`[0.38,0.83,0.41]`，蔬菜 B=`[0.36,0.64,0.67]`，星型模式 C=`[0.85,0.10,-0.52]`。欧氏距离为各维差值平方和的平方根，`d(A,B)=√0.1041≈0.323`，`d(A,C)=√1.6187≈1.272`，所以这个例子里农业与蔬菜更接近。坐标是原书说明用的数字，不是真实模型输出或质量测试。

**余弦相似度**比较方向，公式为 `cos(q,x)=(q·x)/(‖q‖‖x‖)`，非零向量才有定义；值越大表示方向越接近。欧氏距离还会受向量长度影响，二者不能对任意向量随意互换。查询和文档也必须使用兼容的嵌入空间与相应距离函数；换一个模型后，旧向量的坐标含义通常不能原样沿用。

**Flat（扁平）检索**逐个计算查询与所有候选向量的距离，再选最近的 k 个，在给定表示和度量下得到精确最近邻。N 个 d 维向量的距离计算量随 N×d 增长，但小集合、充分并行或严格筛选后的集合仍可能适合精确扫描。它也提供一个重要基准：没有精确结果作对照，很难量化近似算法漏了多少近邻。

**IVF（inverted file，倒排文件）索引**先将向量聚类，各簇有代表性的中心点（centroid），并保存分配到该簇的向量列表。查询先找较近的中心，只扫描选中的若干簇；探查簇数通常叫 probes。它减少距离计算，却可能在簇边界漏掉真正近邻。中心点是分区的代表，不是分区本身。

下面把空间简化到一条数轴，以便亲手检查遗漏：两个中心分别为 0 和 10，分界在 5；数据点 A=0 属于左簇，B=5.1 属于右簇，查询 q=4.9 更靠近左中心。只探查左簇会返回距离 4.9 的 A，却漏掉距离仅 0.2 的 B。增加探查范围才能把 B 纳入比较。这是笔记构造的反例，不代表实际数据只有一维。

![数轴上中心0与10的分界为5，查询4.9选择左簇，但最近的数据点5.1在右簇；仅探查左簇会漏掉它。](../diagrams/exports/ch04-ivf-boundary.svg)

图 4-5：先比较查询与中心的距离，再比较查询与数据点的距离；两种“最近”不是一回事。虚线是簇分界，底部比较查询与两个数据点的距离；点的位置作示意。点击[查看大图](../diagrams/exports/ch04-ivf-boundary.svg)。

**HNSW（Hierarchical Navigable Small World，分层可导航小世界）**使用多层近邻图。节点是向量，边提供可继续探索的邻居。上层节点少，可较快接近相关区域；到下一层，从对应节点继续探索；底层节点更多，进行更细的候选搜索。实际搜索会保留候选集合，并不只是每层做一次“选最近”就完成证明。

旧稿图把底层写成“精确找到最近向量”，但原书印刷 149 页明确说 HNSW 也是近似的。**ANN（approximate nearest neighbor，近似最近邻）**意味着搜索未必覆盖全体候选，不能保证总返回数学上真正最近的 k 个，也没有不依赖数据与参数的统一成功概率。增大搜索候选规模通常可提高召回，同时增加距离计算、访问量与延迟；更密的图还增加内存、构建和更新成本。

以向量近邻集合评估时，可定义 `recall@k = 返回结果与精确 top-k 的交集大小 / k`。精确前五为 `[A,B,C,D,E]`，近似结果为 `[A,B,C,X,Y]`，召回率就是 3/5=60%。这衡量的是找回向量近邻的能力，仍不等于找回全部业务相关文档，更不等于答案正确率。pgvector 官方文档也建议以精确搜索对照召回；它的 HNSW `ef_search`、IVF probes 都体现了搜索预算与召回之间的交换。

现实查询还常带租户、时间、权限或类别过滤。若先近似召回一小批再过滤，最后可能不足 k 条；扩大搜索或提前缩小合法候选集合会改变代价。评估应包含这些真实条件，而不只对无过滤向量测一个平均延迟。语义检索也可与关键词检索互补，但怎样合并与排序需要任务证据，不能仅凭“双路”宣布效果必然更好。

最重要的边界是：**语义相似不是事实保证。** 已过期的政策、否定某个说法的文档、名称相近却不同的业务操作，都可能在向量空间很近。检索增强生成把候选资料交给语言模型，增加可用依据，却没有自动证明资料有效、推断正确或引用支持结论。存储层能优化找到候选的过程，来源、版本与事实核对仍是应用解释结果的责任。

<a id="workload-conclusion"></a>

## 14　把结构选择还原为一条实际访问路径

回到一开始的销售系统：按订单 ID 查询，要看索引定位后是否还需读行、热点是否命中缓存；频繁写入商品状态，要看日志同步、页刷写或压缩合并是否跟得上；全年聚合，要看能否裁剪行组与列，以及算子是否把 CPU 用在有效计算上。相同表名背后，每种任务都在支付不同的维护与读取成本。

若业务改为搜商品描述，倒排索引提供词到文档的入口；若再希望理解近义表达，嵌入与近邻索引增加另一条候选路径。每一条新路径都需要随原数据更新，处理删除与失败，说明数据何时可见。读得更方便，往往意味着提前安排了更多表示、维护或计算，并没有免费消除工作。

本章最有用的习惯，是在选型与调参时走完三个过程：一条更新从接受到可恢复，一次查询从条件到实际读取，一次后台整理从旧状态到安全发布。能说清这些过程，再看吞吐、尾延迟、空间与恢复时间，性能数字才有原因。[下一章](ch05.md)将转向这些数据如何编码，以及新旧程序怎样在格式变化时共同工作。
