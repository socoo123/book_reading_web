# 第 6 章｜复制

**Replication · 多份数据怎样传播变化、承受故障并处理分歧**

用户改完头像，刷新却看到旧照片；一台服务器宕机，另一台接手后，刚刚确认的订单不见了；两个人离线修改同一份清单，联网后又都希望保留自己的工作。这些现象背后是同一个问题：数据有了多份，变化就不再同时发生在所有地方。

[第 5 章](ch05.md)讨论变化怎样编码并跨越版本边界，本章讨论变化怎样跨越机器边界。阅读时抓住三件事：谁决定写入顺序，成功响应等待哪些副本，以及不同副本出现分歧后怎样处理。先理解单主复制的正常与恢复路径，再看多主和无主为何主动放宽顺序与等待要求，最后用版本信息区分“覆盖已有修改”和“并发作出另一项修改”。

<a id="replication-purpose"></a>

## 01　复制保存多份当前状态，备份保存回到过去的机会

**复制（replication）**是在通过网络连接的多台机器上保存同一份数据；每份拷贝及承载它的节点，按语境称为**副本（replica）**。本章先假设完整数据集能放进一台机器。下一章的[分片](ch07.md)才把数据拆成不同子集；复制与分片可以组合，但解决的问题不同。

原书给出几种实际动机。把数据放到用户附近，可以减少访问的网络距离；一台机器失效后仍有其他拷贝，可以提高可用性和持久性；把读请求分散到多台机器，可以增加读取吞吐量。设备本地有可写副本时，还可能在断网期间继续工作。这些收益不是只要配置“三副本”就同时获得：读走远方主节点仍有远程延迟，三份都在同一故障域里也不能承受整个地域永久损毁。

如果数据永远不变，复制主要是一次文件传输。真正困难的是持续变化：新增、更新和删除要传播；节点暂时离线后要补齐；两个节点可能独立修改同一对象；系统还要在这些工作没完成时回答读写请求。复制协议因此必须规定中间状态可以怎样被观察，而不只是承诺最后磁盘内容相同。

复制也不能替代备份。假设管理员误删一张表，复制协议工作得越正确，删除通常越快传播到所有在线副本。它保证的是大家跟随变化，无法判断这次变化是否符合管理员本意。备份保存旧时间点及相应恢复材料，才可能回到删除之前。

两者又可以互相配合：用快照初始化新副本，用归档复制日志恢复快照之后的状态。数据库内部保留的不可变历史快照，也提供一定回溯能力，但与当前数据共用存储时，仍可能一起受到介质故障影响。原书还指出，把低频访问的历史数据放到对象存储，可能比长期挤在主存储里更经济；这属于存储安排，不等于已经解决备份保留与恢复的全部责任。

<a id="single-leader"></a>

## 02　单主复制：先统一写入顺序，再传播结果

**单主复制（single-leader replication）**指定一个副本为**主节点（leader）**，客户端把写请求交给它；其他副本是**从节点（follower）**，接收主节点的复制日志或变更流。主节点处理写入，从节点按相应顺序应用变化。客户端可以读取主节点，也可以读取提供查询能力的从节点，但从节点不直接接受普通客户端写入。

用一个笔记假设说明顺序的作用。主节点先插入 `user=7, name=林`，再将该用户改名为 `琳`。从节点若先执行更新，可能找不到用户；之后再插入，最终反而停在旧名字。单主将这两项变化组织成一条有顺序的流，从节点不必各自猜测哪项操作应先执行。

这里说的“相同顺序”，是复制协议需要保留的操作效果与依赖顺序，不意味着数据库内部禁止并行应用任何互不相关的事务。具体引擎可以并行化工作，只要最终可见结果满足其承诺。主节点也不一定把客户端原始请求直接发出去：发送 SQL、行变更或物理日志，会有不同的约束，后面再展开。

单主的主要收益是提供一个明确的排序位置。两个客户端都改同一个标题，主节点至少能决定先处理哪次写，其他副本沿同一历史前进。但这不等于所有业务操作都自动正确：两个客户端先读旧值、各自计算、再依次写回，仍可能发生应用层丢失更新，相关隔离问题见[第 8 章](ch08.md)。单主消除的是多入口独立形成复制历史的分歧，而不是所有并发异常。

如果系统已经分片，各分片可以分别有一个主节点，主节点又可分散在多台机器上。整套集群里有多个主节点，不一定是本章所说的“多主”：判断应落到**同一份数据是否允许多个独立写入口**。同一分片只有一个主节点，仍然是单主复制。

这一模型在关系数据库、文档数据库和消息日志中都很常见，也可与共识协议结合自动选主。但“单主”只描述复制组织方式，不完整定义持久性或一致性；这些承诺还取决于下一节的确认规则、读路径及故障切换协议。

## 03　同步与异步：成功响应究竟等到了哪一步

原书图 6-2 用更新头像说明同步与异步。主节点收到写入，把变化发给两个从节点。其中一个从节点必须先确认，主节点才向客户端报告成功，这条复制路径是**同步（synchronous）**的；另一个从节点可以稍后才收到和处理变化，主节点不等待它，这条路径是**异步（asynchronous）**的。同一次写可以同时使用这两种路径。

假设主节点 L 与从节点 F1 都可靠保存了写 W，F2 尚未收到。若 L 随即永久损坏，只要从 F1 正确恢复并让它接管，W 仍有副本。反过来，完全异步时，L 可以只在自己保存 W 后就回复成功；若 W 尚未到任何从节点，L 又无法恢复，剩下的机器根本没有信息可以重建它。**客户端收到成功，不自动意味着写入已进入多个故障独立的持久副本。**

同步的成本也沿相同路径出现。若当前策略必须等 F1，而 F1 不响应，L 即使完全健康，也不能继续按原承诺确认这些写入。可以等它恢复、切换到已经具备必要状态的候选副本，或明确降低保证；不能在未满足条件时悄悄把同一种“成功”当作已经等到了 F1。

图 6-1 只画确认依赖，不画并发执行细节。虚线到 F2 表示客户端成功不等待该路径；它不是“可以永远不复制”。

![主节点将写入复制给F1和F2；F1完成约定确认后，主节点才回复客户端成功，F2的异步完成可以更晚。](../diagrams/exports/ch06-sync-ack.svg)

图 6-1：由上向下读步骤。实线是本例成功响应必须满足的先后关系，虚线是未纳入该响应等待条件的复制。确认究竟代表接收、落盘还是应用，必须另行约定。点击[查看大图](../diagrams/exports/ch06-sync-ack.svg)。

等待所有从节点，意味着任意一个节点或链路故障都可能阻断写入；副本越多，等待全部的可用性代价越明显。因此常见安排是等待一个从节点、其他异步，原书称这类配置有时为**半同步（semisynchronous）**；也可以等待多数派，例如五副本中包含主节点的三个。后者属于法定人数思想，但计数只是协议的一部分。

这里必须把原书的简化示意和真实产品分开。旧稿把“同步副本确认收到”直接扩展成“从库立即可读且故障不丢” → PostgreSQL 17 官方文档区分 `remote_write`、`on` 与 `remote_apply` → 在配置同步备库的前提下，三者分别等待远端文件系统写入、远端可靠存储刷新、远端重放至查询可见；其中 `remote_write` 不能承诺远端操作系统崩溃后仍保存数据。**收到、持久化、可查询，是三个不同进度。**

同样，原书的半同步概念不能直接代替某个产品的超时降级规则。评估配置时，要把等待对象、确认层次、超时处理和新主资格连起来。就算已有两份数据，故障切换却选中第三个落后副本，客户端仍可能看不到已确认写。复制的持久性承诺必须覆盖“确认之后怎样选出继续服务的历史”。

## 04　初始化副本：把一致快照与后续日志准确接起来

正在运行的数据库不能靠普通文件复制获得一个可靠新副本。假设转账从账户 A 扣 10，再给 B 加 10；文件复制分别在不同时间读到两边，就可能拿到“扣款前的 A”和“入账后的 B”。文件都能打开，不表示它们属于同一个数据库状态。

原书的初始化过程有四步：取得一个一致快照，复制到新节点，找到快照对应的精确日志位置，再重放快照之后的变化。副本追平积压后，继续接收实时变更。快照能力通常也服务于在线备份，因此不必为了复制全过程停掉所有写入。

笔记假设：快照 S 精确对应已经应用到日志位置 100 的状态。复制 S 花了十分钟，期间主节点继续产生 101—160。新副本安装 S 后，应从 101 开始接收；从 102 开始会漏写，若不按协议处理重复而从 100 重做一次非幂等增量，则可能重复效果。这里的数字是解释位点衔接的逻辑序号，真实产品可能用字节位置、日志文件加偏移或事务标识。

这也说明为什么快照与位点必须配套获取。先随意抄一个目录，过几秒再查询“当前位点”，不能证明目录包含的状态恰好覆盖到那里。实现需要数据库支持的备份／快照协议，重放还要处理事务边界与恢复规则，不能仅凭文件最后修改时间猜起点。

快照加归档日志也可以存进对象存储，既用于新副本引导，又用于灾后恢复。第二版进一步讨论直接以对象存储承载在线数据：冷数据下沉到便宜存储，热数据保存在内存或 SSD；有些架构把数据文件放到对象存储，WAL 仍交给低延迟持久层；**零盘架构（zero-disk architecture，ZDA）**则把全部持久数据放在对象存储，计算节点的磁盘和内存只作可重建缓存。

“零盘”不是系统中没有磁盘，更不是没有复制，而是把持久状态及其复制责任移到存储服务中。计算节点失效后不必抢救其本地权威数据，但新节点仍要取得有效元数据、装载缓存和恢复服务容量。原书提到对象存储的条件写，即只在版本仍满足条件时更新对象，可作为比较并交换（CAS）一类原语；数据库可以在此基础上构建元数据发布和选主协议，单次条件写本身并不等于任意多对象事务。

收益伴随代价：对象访问延迟通常高于本地设备，按调用计费会推动批处理，批处理又增加等待；大对象原地随机修改常不便宜；挂载成文件系统也不意味着具备全部 POSIX 语义。因而原书列出的几种结构是对延迟、成本和运维的不同取舍，不是所有数据库都该走向同一种“终极形态”。

<a id="failover"></a>

## 05　节点故障：补数据与换主节点是两种不同工作

从节点故障通常从**追赶恢复（catch-up recovery）**开始。假设它已可靠应用到位置 120，断线期间主节点走到 200；恢复后从自己的持久进度出发，取得并应用 121—200，再接回正常日志流。若只记得“收到过 200”，却不知道哪些写已经可恢复地应用，就不能随意从 201 开始。

追赶需要真实资源。新写继续涌入，恢复节点又要处理历史积压；主节点也要读取并发送旧日志。如果副本消费能力长期不高于新的日志生成速度，追赶就无法完成。另一个边界是日志保留：一直等离线副本可能耗尽主节点磁盘，删掉它所需的日志则意味着回来后要重新用快照初始化。恢复路径本身因此会影响仍在线用户的延迟。

主节点故障还多出**故障切换（failover）**。系统要怀疑旧主已不可用，选择合格新主，重定向客户端和从节点，并处理旧主可能恢复的情况。原书把自动流程分成检测、选择和重配置三步；它们不是一个不可失败的瞬时动作。

第一步通常靠超时。没收到心跳可能是进程退出，也可能是网络中断、机器暂停或负载过高。较短超时缩短真实故障的等待，也增加误判；较长超时减少部分误切换，却使用户等得更久。计划维护若可正常通信，可以先安排有序交接，问题通常比突然失联容易。

第二步要尽量选择包含已确认历史的副本。笔记假设 L 已写到 105，F1 到 104，F2 到 98，复制完全异步。L 消失后选 F1，仍可能失去 105；选 F2，还会让 99—104 一起不见。日志进度有助于比较，但应在可比较的复制历史和成员资格内判断；它不是看到任何数值更大就允许升主。若要求严格保留已提交写，选举与提交规则必须一起设计，[第 10 章](ch10.md#shared-log)会继续讨论。

第三步要防止旧主继续接写。L 可能只是与选举参与者断网，却仍能被一部分客户端访问。若 L 与新主都接受同一份数据的写入，又没有合法多主的合并协议，就形成**脑裂（split brain）**。约束或隔离旧主写权限的机制称为 **fencing**；通知它“你已退位”只有在消息到达并被执行时才有效。更具体的隔离令牌与资源端校验属于[第 9 章](ch09.md#fencing)。

旧主恢复后也不能简单把两条历史拼接。它可能保存新主从未见过的 105，而新主已经从另一个状态接受 106。常见单主系统会舍弃旧主未进入新历史的写；这正是异步复制下“已确认写仍会丢失”的路径。恢复旧数据和接受新业务决定之间，已经出现了无法靠机械重放消除的分歧。

原书转述 GitHub 2012 年事故：落后的 MySQL 从节点升主后重复分配曾经发出的自增主键，而 Redis 仍保留旧主键关联，最终让私密数据关联到错误用户。这个历史案例说明，数据库回退的影响会穿过系统边界，不能只统计“少了几行”。本笔记按原书转述，不补写未核查的事故细节。

旧稿还写“使用 GTID 就能保证故障切换不丢已提交事务” → MySQL 8.4 文档把 GTID 定义为事务身份，并用于识别和跳过已经执行的事务 → 应修正为：GTID 帮助知道复制过哪些事务、从哪里继续，却不能凭空重建从未传出的事务。唯一标识、可靠传播与安全选主，承担的是不同责任。

## 06　三种复制日志：传命令、传物理变化，还是传行变化

**基于语句的复制（statement-based replication）**把主节点执行的写语句送到从节点再执行。它可能很紧凑：一句修改一万行的 SQL，比记录一万份行结果短。但紧凑依赖一个重要条件：同样初始状态下，按相同规则执行，应得到同样结果。

例如 `UPDATE item SET token = RAND()` 在每台机器重新抽随机数，就不再是同一次修改；依赖当前时间、触发器、外部函数或已有状态的语句，也可能产生不同结果。主节点可以把某些非确定输入固定进日志，但需要真正覆盖这些输入，不能只要求 SQL 文本相同。依赖自增序列或查询条件的操作，还要保留足够的执行次序。

在明确的确定性约束下，按共同日志执行命令是一条可行路线，与[第 3 章的事件溯源](ch03.md)有相近思想；它并非天然错误。问题是普通应用容易引入隐藏的非确定性，因此不少系统选择复制更接近执行结果的信息。

原书印刷 207 页写 MySQL“默认”在语句有非确定性时切为行复制，旧稿也沿用此句 → 回看原 PDF 确认不是文字提取错误；MySQL 8.4 官方文档明确默认是 `ROW`，自动在语句与行之间切换属于 `MIXED` 模式 → 本文按版本修正：**行日志是 MySQL 8.4 默认方式，混合模式另行配置。** 这是笔记依据官方资料作出的修正，不称为出版社已确认勘误。

**预写日志传送（WAL shipping）**复用存储引擎用于恢复的日志。[第 4 章](ch04.md#wal-recovery)已说明，WAL 包含重建页和索引状态所需的信息；把它传到另一台机器，从节点便可重放出相应存储状态。这类日志靠近存储内部格式，复制效率与恢复机制可以共用，但存储格式、日志解释和软件版本之间耦合较紧。

因此，若新旧版本不支持同一物理日志格式，就无法直接把旧主与新版本从节点混在一起做这种复制。旧稿把它说成“任何不同版本都不行、升级必然停机”则过于绝对；应检查具体版本兼容范围及迁移方案。核心取舍是物理日志的兼容责任更多落在存储内部，不能从“WAL”三个字推出所有产品的升级结论。

**逻辑行日志（logical row-based log）**描述表和记录层面的结果。插入包含新行值；删除包含足以定位旧行的信息；更新包含行标识及变化后的列值。一个多行事务产生多条记录，并有提交等边界信息。主键常用于行定位，没有可用唯一标识时可能需要更多旧值。

逻辑格式与磁盘页布局解耦，更有机会让主从使用不同软件版本，或让外部程序消费变化。原书说明，MySQL 的 binlog 与存储引擎恢复日志承担不同职责，PostgreSQL 则可从 WAL 解码出逻辑行事件。**逻辑与物理是描述层次的区别，不要求产品一定维护两份完全独立的源日志。**

这种格式也适合**变更数据捕获（CDC）**：将数据库变化送到数仓、搜索索引或缓存。它降低解析内部页的难度，却仍要安排初始快照衔接、事务边界、模式演化和消费进度。逻辑复制能帮助低停机升级，不等于只要打开一个开关，任意模式变更与切流都自动安全。相关编码问题可回看[第 5 章](ch05.md#compatibility)，持续数据流在[第 12 章](ch12.md#snapshot-handoff)继续展开。

<a id="read-your-writes"></a>

## 07　读己之写：成功之后，自己的修改不能像没有发生过

增加只读从节点，可以分摊主节点的查询负载。若每次写必须等所有新增节点都应用完成，任意慢节点都会拖住写入，因此大规模读扩展通常让部分读取副本异步追赶。代价是同一查询发到不同副本，可能得到不同新鲜度的结果。

当不再有新写、通信与处理最终能继续时，副本逐步追平，称为**最终一致性（eventual consistency）**。它没有单独给出延迟上界；平时几十毫秒同步完成，不代表网络故障时一分钟之后必然追上。停止写入但永远断网、修复流程永远失败，也不会因时间过去而自然恢复一致。

原书第一个例子是用户提交内容后立即重新读取。笔记假设用户 U 把头像从 A 改为 B，主节点在日志位置 42 确认；页面刷新却命中只应用到 41 的从节点，返回 A。数据可能并未丢失，但用户看到的行为与提交失败几乎一样，甚至因此重复提交。

**读己之写（read-your-writes，也称 read-after-write consistency）**要求该用户之后的读取反映自己的已完成写入，不能仅因复制落后退回写前状态。它不保证马上看到别人的全部更新；若后来有合法修改覆盖自己的值，也不要求永久显示旧的自写值。

最简单的方法是按访问责任路由：自己可以编辑的个人资料读主节点，别人的资料读从节点。若人人可以编辑大部分对象，这会把多数读取又集中回主节点。另一种办法是写后短时间内读主节点，但固定一分钟窗口只是经验策略；除非同时确保窗口结束时选中的副本已追平，否则延迟超过一分钟仍会破坏保证。

更精确的做法是携带**会话进度**。写成功时得到位置 42，后续读请求声明“至少看到 42”。服务端若发现当前从节点只到 41，就等其应用到 42，换一个足够新的节点，或转回主节点。这里必须比较查询可见的应用进度，而非仅网络接收进度；位置也应属于可比较的日志历史。跨分片时，一个标量位点往往还不够。

用墙上时钟代替日志位置，会引入时钟同步误差。用逻辑位置则直接表达“已经包含哪些变化”，更贴近需求。成本是把进度元数据放进请求链路，并在慢副本上决定等待、换路还是返回暂不可用。数据库若已提供相应会话保证，可以减少应用自己实现这些细节的负担。

跨设备会让状态传递更难。手机刚写完，电脑并不知道位置 42；仅保存在手机内存或 cookie 中的令牌不能自动实现跨设备读己之写。需要共享这份用户进度，或用能够确保该保证的统一读路径。手机蜂窝网和电脑宽带还可能路由到不同地域，低延迟本地读与立刻看到远方写之间仍有真实等待成本。

<a id="session-order"></a>

## 08　单调读与一致前缀：不倒退，也不先看到结果再看到原因

第二类异常不需要用户亲自写过。用户先从 F1 看到别人发布的新评论，下次刷新被路由到落后的 F2，评论又消失了。**单调读（monotonic reads）**允许看到旧状态，但同一会话后续读取不能比已经见过的状态更旧。它关注的是观察历史的方向，而非是否最新。

把同一用户固定到同一个持续前进的副本，可以减少这类倒退。但副本故障后换到另一台，或者原节点从更旧状态恢复，保证可能再次断裂。若要完整保留承诺，切换后仍应检查新节点已达到用户曾看到的进度；“按用户 ID 做哈希”只是路由策略，不是覆盖所有恢复情境的证明。

读己之写与单调读也不能互相替代。一直读同一个落后副本，观察可以不倒退，却仍看不到刚在主节点完成的自写；反过来，只保证包含自己的某次修改，也未必包含之前在其他副本见到的所有他人更新。它们约束的是不同依赖。

第三类异常是因果顺序被打散。原书用先问“能看到多远的未来”、再回答“约十秒”的对话说明：回答者先看到问题才回答，但第三个人从不同复制路径读取，可能先看到回答，稍后才看到问题。下面改用会议讨论这一笔记假设：

1. A 发布问题 Q：“会议改到周五吗？”
2. B 看见 Q，发布依赖 Q 的回答 R：“可以，周五见。”
3. Q 所在分片复制较慢，R 所在分片较快；观察者读到 R，却读不到 Q。

**一致前缀读（consistent prefix reads）**要求观察到的状态保留相应写入顺序：不能跳过必要前项，却展示后项。对一条统一有序日志，完整应用并读取某个前缀可满足这个直觉；多个分片独立复制时，不能用各自的“最新”拼出一个因果上合理的整体。

将强相关数据放在同一分片，可能让共同日志承担排序责任；无法这样划分时，可以显式追踪依赖，在 Q 尚未可见之前暂缓展示 R。只给两条记录附上墙钟时间，仍无法证明接收方已经拥有前置数据。时间戳可以辅助排序，不会传输缺失的 Q。

| 保证 | 要防止的现象 | 不额外承诺什么 |
| --- | --- | --- |
| 读己之写 | 自己的写成功后读回写前状态 | 马上看到所有其他用户的新写 |
| 单调读 | 先看到新状态，后看到更旧状态 | 第一次读就是最新状态 |
| 一致前缀读 | 看见回答，却未看见它依赖的问题 | 所有客户端在同一时刻看到同一状态 |

原书建议认真问：复制延迟变成几分钟甚至几小时，应用会怎样？如果无法接受，应该选择或设计足够明确的保证。支持事务和更强副本一致性的分布式数据库，可以替应用承担许多协调工作；它们仍有延迟与网络故障下的可用性取舍。不能把“分布式必然只能最终一致”当作选型前提，也不能仅凭“单主”推断所有从节点读取已线性一致。

<a id="multi-region"></a>

## 09　多主复制：允许本地继续写，也接受独立历史需要合并

**多主复制（multi-leader replication）**允许同一份数据有多个写入口。每个主节点接受本地写，把变化传给其他主节点，同时接收对方的变化。本文沿原书重点讨论异步多主：远方暂时失联时，本地主节点仍可确认写入。

同步多主并非不存在。原书只是指出，若写 A 必须等 B，A—B 断网时 A 仍不能独立完成写入，这没有取得本节希望讨论的断连可写收益，因而不再展开。旧稿“实践中多主都指异步、同步多主不存在”的说法，应改成这一范围说明，而非对所有系统的分类断言。

跨地域是典型用途。**地域（region）**是一个地理区域内的部署范围，通常包含多个相对独立的**可用区（availability zone）**；同地域跨区可以抵御部分可用区故障，但不覆盖整个地域失效。跨地域副本有更远网络距离，也可能增加流量成本。

单主跨地域时，远方用户每次写都要与主节点所在地域往返。多主则可以在各地域本地处理，并异步交换。正常路径是本地写、本地确认、稍后远端合并；地域间网络中断时，两边照常形成各自修改；网络恢复后补发并处理并发冲突。当地还可以配从节点防护机器或可用区故障，地域内与地域间采用不同复制安排。

收益是把地域间等待移出本地响应路径，代价是双方短时间内不知道对方的决定。假设同一账户余额 100，两个地域断网后分别批准支出 80，单独看都没有透支，合起来却支出 160。这不是等网络恢复就能消除的历史事实；后续合并必须撤销、补偿、拒绝部分结果，或事前限制各地可独立支出的额度。本节模型不提供无条件的全局约束保证。

### 拓扑改变传播路径，不消除因果依赖

两个主节点通常双向交换；更多节点可组成环形、星形或全互联。环形把变化逐跳传下去，星形由中心转发，全互联让各节点直接交换。需要转发他人写入时，还要用来源／操作身份或经过节点等信息避免循环传播；“看见已处理过的写就忽略”要求能可靠识别同一项写。

环形某条路径断裂、星形中心故障，都可能阻断其他节点之间的传播，恢复要修链路或重配。全互联有更多传播路径，却仍可能乱序到达。原书图 6-8 中，A 在节点 1 插入一行，节点 3 看到该行后再更新；节点 2 若从节点 3 很快收到更新，却迟迟没有收到节点 1 的插入，就先得到一个不存在对象的更新。

这两项写并不并发：更新依赖插入。正确做法应保留依赖并等待前置数据，或由具体协议提供等价处理；不能简单把到达顺序当作业务顺序。后面的版本信息用于识别这种关系，但检测依赖与保证按依赖应用仍是两个步骤。更多链路提高部分故障下的连通性，不会自动建立全局顺序。

## 10　同步引擎与本地优先：设备本身也成为可写副本

日历应用离线时仍能查看和新增会议，意味着设备保存了可读写的本地数据。联网后，它把离线改动同步到其他设备，也接收期间别人作出的改变。从复制角度，每台设备都是一个可写副本，离线一天只意味着这条复制路径有一天的延迟。

实时协作也会遇到类似问题。用户敲字后立即看到本地变化，不等待每个字符都经服务器确认，多个浏览器标签便可能同时形成修改。即使产品不允许长期离线，它仍需协调“本地已经显示、远方尚未处理”的变化。原书以此把协作编辑纳入多主的讨论；具体服务还可以在服务器上安排最终排序或其他协调逻辑。

**同步引擎（sync engine）**负责捕获本地变化、持久保存待发送修改、联网后传播、接收远端更新、合并数据，并把变化通知界面。普通前端往往显式调用每个读写 API；同步引擎则把日常交互放到本地数据上，把网络通信变成持续后台过程。失败没有消失，而是更多集中在同步、恢复与冲突处理层。

图 6-2 用两台设备与一个中转服务说明职责。实线发生在设备内部；虚线经过网络。断网时仍能完成本地步骤，恢复后才继续虚线步骤。中转服务不因位于图中央就自动成为所有编辑的唯一排序主节点。

![手机和电脑各自拥有界面与持久本地副本，本地编辑直接进入本地副本；两端通过可暂时断开的网络同步，中转服务传递变更，远端接收后合并并更新界面。](../diagrams/exports/ch06-local-first.svg)

三个相关概念需要分开。**实时协作**强调尽快呈现他人的修改；**离线优先（offline-first）**允许无网络时继续工作；**本地优先（local-first）**还关注软件服务退出之后，用户能否继续访问、编辑并控制自己的数据。仅有一份只能由厂商服务解锁的离线缓存，不足以支撑后一种目标。原书以 Git 作说明：本地仓库可工作，协作可以换用不同托管方，它并不因此必须提供实时编辑。

本地状态可以显著降低交互等待，原书用 60 Hz 屏幕约 16 毫秒一帧说明响应目标。它不是所有同步引擎的性能保证，而是解释为何把网络往返移出按键路径有价值。配合响应式更新，收到远端数据后，界面可以自动刷新相应视图，不必每处代码都维护轮询和刷新逻辑。

局限来自数据规模与可用范围。提前下载用户自己的文档通常可行，提前下载整个大型商品目录则可能不合理；未同步到本地的数据无法凭空离线查询。设备存储、权限变化和数据保留也仍需处理。本章重点是复制模型，不把某个框架名当作已经解决这些问题。游戏的 netcode 也处理本地响应与异步远端动作，但有专门的预测和回滚要求，原书没有在此展开。

## 11　冲突避免与最后写胜：先问被放弃的修改能否接受

原书的 wiki 例子从同一个标题 A 出发：用户 1 把它改成 B，用户 2 在没看到 B 时把它改成 C，两地都立即确认。交换变更后，系统不能仅凭“本地最后收到哪一条”决定结果：一地最后收到 C，另一地最后收到 B，会永久分歧。合并规则必须让所有副本对同一组写作出一致解释。

第一种策略是**避免冲突**。若某记录的写始终路由到唯一归属地域，就不会有多个主节点独立决定该记录的更新。不同用户可有不同归属，整套系统分散负载，但单条记录仍像单主。要迁移归属或在故障时切换，就必须处理交接窗口；旧归属与新归属同时接受写时，原来的避免条件已经不成立。

有些冲突可通过分配互不重叠的范围避免。原书举例两个主节点分别生成奇数与偶数 ID，避免给不同新记录分配相同自增编号。但 ID 不冲突，不等于业务实体不冲突：两个不同 ID 的记录仍可能申请同一个用户名或同一会议时段。应先确定约束针对哪一个字段或资源。

第二种策略是**最后写胜（last write wins，LWW）**。给每次写一个可比较的时间戳，再为时间戳相同的情况规定一致的决胜规则。所有副本保留排序最大的值，便可收敛。它解决了“大家最后选同一个值”，同时丢掉其他并发写的效果，即使那些写曾向各自用户报告成功。

“最后”容易使人误以为它保留了用户意图中的正确结果。实际上，对互不知情的并发写，并不存在由因果关系决定的最后一项；排序只是选出唯一胜者的规则。原书以“随机选择”强调语义上的任意性，本笔记补充：实现仍须是确定性的，不能每个副本真的独立随机挑一个值，否则无法收敛。

旧稿的时钟反例值得保留，并明确为假设：真实时间 100 时，A 的钟快十秒，写 `x=1@110`；该值传到 B 后，真实时间 105，B 按准确时钟写 `x=2@105`。这次写已经知道并试图覆盖 `x=1`，却因时间戳较小被 LWW 丢弃。即使物理上明确后写，错误的时钟排序仍可能让它失效。

采用恰当传播的逻辑时钟，可以避免这一类因果上后写却时间戳更小的问题；它不会使两个独立修改都被保留。唯一键上的只插入、永不更新，通常减少 LWW 冲突机会；经常改动同一个用户文档时，就必须明确“丢掉另一个成功修改”是否可接受。**收敛是复制性质，保留意图是应用语义，两者不能互相代替。**

<a id="merge-crdt"></a>

## 12　保留并发版本，再用数据类型定义合并

若不能随意丢写，可以保留所有尚未被因果后继覆盖的并发值，称为 **siblings（并发兄弟版本）**。读一条 wiki 记录时，数据库返回 B 与 C；应用可以请用户选择，或者自动形成新值并带上读到的上下文写回。它无需暂停整条复制流等待人工处理，但 API 从“一个字符串”变成了“可能多个候选值”，应用必须知道怎么显示和解决。

自动取并集看似保留最多信息，却可能违背删除语义。原书购物车起初含 `{Book, DVD, Soap}`：设备 1 删除 Book，得到 `{DVD, Soap}`；设备 2 未见此事，删除 DVD，得到 `{Book, Soap}`。两个最终集合取并集，又变回三个商品。问题在于只保存“还剩什么”，没有保存“哪些已观察到的项目被明确删除”。

合并自身也可能并发。一边把 B 与 C 拼成 `B/C`，另一边拼成 `C/B`，再次拼接会积累重复文本。仅说“应用会处理冲突”并未指定一个能稳定收敛的规则；需要考虑顺序、重复到达以及新修改与合并同时发生。

**强最终一致性（strong eventual consistency）**强调：在更新最终传播等前提下，已经处理同一组更新的副本得到相同状态，不因到达顺序不同永久分歧。这里的“强”修饰收敛性质，不表示读取一定最新或操作已线性一致。

**无冲突复制数据类型（conflict-free replicated datatype，CRDT）**把这样的合并规则放进数据类型。文本和列表追踪元素身份及增删，集合明确处理添加与删除，计数器区分不同节点的增量，映射可以逐键组合其他数据类型。它们不是一个通用的“把两个 JSON 合起来”函数；元数据和语义决定哪些更新被保留。

一个补充算例可说明为何需要元数据。假设只允许递增，两个节点 A、B 各维护自己贡献的计数，初始向量 `[0,0]`。A 点赞两次得到 `[2,0]`，B 点赞一次得到 `[0,1]`；状态合并取逐分量最大值得 `[2,1]`，总数为 3。重复收到 B 的 `[0,1]`，结果仍为 3，不会加到 4。这里不是把“总点赞数 2 与总点赞数 1”盲目相加，而是累计每个来源已观察到的最大贡献；撤销点赞还需要额外设计，不能让这两个只增分量直接回退。

### 同一个 ice→nice!，OT 与 CRDT 怎样做

原书图 6-11 的两个副本起初都是 `ice`。一边在索引 0 插入 `n`，得到 `nice`；另一边在原字符串索引 3 插入 `!`，得到 `ice!`。理想合并结果是 `nice!`。

**操作转换（operational transformation，OT）**记录基于位置的操作。已经应用前插 `n` 的副本，如果直接执行“在索引 3 插入 !”，会得到 `nic!e`。它必须考虑并发的前插，将这个索引转换成 4；另一边在 `ice!` 的索引 0 插入 n，便同样得到 `nice!`。转换函数负责把一个操作改写成适合当前上下文的等价操作。

原书展示的文本 CRDT 则给原字符稳定 ID：`i=1A、c=2A、e=3A`。插入叹号表达为“在 3A 后插入新字符 4B”，前插 n 则引用字符串开始位置。n 的出现不改变 e 的身份，因此叹号仍定位到 e 后；同位置的并发插入还要按确定规则排列。不能把“有唯一 ID”单独当作完整算法，删除、依赖交付与排序规则也必须配套。

两类方法都能实现自动合并，具体性能与支持操作取决于算法。原书没有把它们化约成“OT 只能在线，CRDT 完全不需协议”，本笔记也不作这种推断。自动合并的目标是尽量保留可表达的修改效果，不保证合并后的自然语言符合作者原意，更不保证所有业务约束自动满足。

<a id="business-constraints"></a>

## 13　值不冲突，业务仍可能冲突

原书的会议室案例说明，冲突不只发生在同一个字段被改成两个值。假设一个房间周五十点空闲，两个地域各自查询后，都插入一条预订记录。记录有不同主键、字段没有互相覆盖，合并可以无损保存两行；但业务要求“同一时段只能有一组使用者”已经被破坏。

把两行组成集合 CRDT，只会让所有副本稳定收敛到“两笔预订都存在”。它没有判断谁应该获得房间。又如列表最多五项：两边各自看到四项，都离线添加一项，保留两次添加就变成六项。若仍要求上限五项，必须拒绝／取消部分修改，或事先采用限制独立决策权限的安排。

因此选择合并策略，应从业务动作出发。编辑便笺时保留两段文字、之后人工整理可能很好；给唯一座位发出两个不可撤销承诺，不能只把冲突留到网络恢复后。应用可以将离线结果标成“待确认申请”，再由有权做唯一决定的路径确认，但这已经改变了最初“立即成功”的含义。

单主可以提供一个协调位置，却仍需要正确的原子检查、唯一约束或事务隔离，才能防止“各自先查再插入”的竞态。多主也不是不能实现任何约束；它是在**允许各处任意独立接受这类写且不协调**的前提下，无法同时确保相关全局不变量。预分配互斥权限等特殊设计有自己的适用范围，不能由通用 CRDT 自动获得。

这正是本章与[第 8 章事务](ch08.md#write-skew)的衔接：复制回答副本怎样传播与合并，隔离回答并发操作怎样共同维持规则。[第 13 章](ch13.md#coordination-boundary)还会讨论允许暂时违反、事后修复的业务情境。把这两个问题分开，才能避免把“所有副本一致地错了”误认为系统已经正确。

<a id="leaderless-repair"></a>

## 14　无主复制：向多个副本读写，并修补缺失的数据

**无主复制（leaderless replication）**没有负责该键全部写入排序的主节点。客户端可以直接联系多个副本，也可以把请求交给一个**协调者（coordinator）**代为转发、汇总响应。协调者承担这次请求的通信工作，不因此成为其他请求必须服从的唯一排序者。

原书把受 Amazon 2007 年 Dynamo 启发的结构称为 Dynamo-style。这里要区分 Dynamo 与 DynamoDB：前者是原书所引论文里的内部系统，后者是后来的云数据库；原书依据其架构资料，将 DynamoDB 的基础复制讨论为基于 Multi-Paxos 的单主结构。名称相近不能用来推断相同复制机制，也不能把基础复制结构替代产品所有跨地域功能的说明。

先跟一次正常写与故障恢复。某键有 A、B、C 三个副本，旧值都是 `x=6`。客户端并行发送 `x=7`，A 与 B 保存并确认，C 正在重启没有收到。若策略要求两个确认，这次写成功，无需选出一个新主节点。C 恢复后仍是 6；读若只找 C 就会读旧，读若同时取得 B 的 7 与 C 的 6，就有机会发现差异。

发现差异后必须知道版本关系。这里假设 7 是因果上覆盖 6 的版本，读可以选择 7，并将它补给 C。真实值本身不是版本号；不能因为商品价格 7 大于 6，就认定 7 更新。若返回两个并发值，可能应保留 siblings 并合并，而不是任意挑数值较大者。

**读修复（read repair）**在读取时比较副本结果，发现陈旧数据便补写更新版本。常读的键有较多修复机会；长期不读的键可能一直留旧。因此它不能单独保证所有冷数据被修复。修复由客户端还是协调者执行、是否等待修复完成再响应，属于具体协议，后面的反例会显式区分。

**提示移交（hinted handoff）**是在目标副本不可用时，由另一节点暂存“应交给谁的哪次写”。目标恢复后，把这些提示所带的变化交回去，再清理已交付提示。它不依赖用户再次读取，适合修补临时断连期间漏掉的更新；但仍依赖提示的保存与成功转交，不是任意长期故障的永久保险。

**反熵（anti-entropy）**则在后台比较副本状态，找出并修补差异。它不要求按单主日志的一个全局顺序补写，可能较晚才发现差异，却能覆盖只依赖读修复与提示留下的缺口。三者作用互补：读修复借访问发现差异，提示移交保存已知遗漏，反熵主动查找尚未发现的不一致。

没有主节点故障切换，不代表没有恢复协议。副本身份、数据版本、补写资源和不可用节点的判断仍存在；只是一次普通读写本来就跨多个副本，单个节点消失通常无需切换到完全不同的执行模式。

## 15　法定人数的推导：交集保证了遇到什么信息

设一个键通常存放在固定集合 N 中，副本数为 `n`；写入必须得到 `w` 个成功确认，读取必须取得 `r` 个响应。**法定人数（quorum）**表示操作满足所需参与条件。在本节简单计数模型中，它由响应数量描述；法定人数不总等于多数派。

假设写 W 已经在集合 Wset 的 `w` 个节点保存，之后一次读取得集合 Rset 的 `r` 个响应。两集合都来自相同 N，由集合关系可得：

```text
|Wset ∩ Rset| = |Wset| + |Rset| − |Wset ∪ Rset|
             ≥ w + r − n
若 w + r > n，则交集至少有一个节点。
```

例如 `n=3,w=2,r=2`，新值在 A、B，C 仍旧。读任意两个正常副本，组合只能是 AB、AC、BC，都至少碰到 A 或 B。图 6-3 取 BC，展示交集节点 B；返回值需要按版本选择，不是让多数值投票。即使读到的是“一份新、一份旧”，也应识别新值。

![三个固定副本A、B、C中，完成写的集合为A和B，随后读的集合为B和C；交集B保存已完成写，因此读取可以取得新版本。](../diagrams/exports/ch06-quorum-intersection.svg)

图 6-3：实线框为已完成写的确认集合，虚线框为随后读的响应集合，重叠处 B 属于两者。前提是同一固定副本集合、相关写已完成且版本未丢失；图不宣称线性一致性。点击[查看大图](../diagrams/exports/ch06-quorum-intersection.svg)。

这条数学关系很确定，但它证明的是**集合必相交**。要进而返回目标写的值，还需交集副本确实保存有效版本，读会正确比较版本，而且所谓“最新”有清楚含义。先在没有并发写、没有成员变更与数据回退的模型中理解它，后面再放宽这些条件。

在原书常见发送模式里，请求并行发到全部 n 个副本，r、w 决定等多少个响应；它们不等于实际发送数量。旧稿把“通常如此”写成“永远必须如此”过强，真实系统还可能按延迟与读摘要等方式组织请求。本章算例只用明确写出的响应集合推理，不依赖所有产品统一实现。

可用性也可以计算。在同一固定成员集合、可达节点能成功执行请求的前提下，写最多容忍 `n−w` 个不可用副本，读最多容忍 `n−r` 个；两者都继续时取两数较小者。

| n / w / r | 写可容忍不可用数 | 读可容忍不可用数 | 主要取舍 |
| --- | ---: | ---: | --- |
| 3 / 2 / 2 | 1 | 1 | 读写都要等两个响应 |
| 5 / 3 / 3 | 2 | 2 | 多数派读写，交集至少一个 |
| 5 / 5 / 1 | 0 | 4 | 读只需一个响应，写依赖全部副本 |
| 5 / 1 / 5 | 4 | 0 | 写只需一个响应，读依赖全部副本 |

后两行满足 `r+w>n`，却并非读写都用多数派。若选择 `n=3,w=1,r=1`，写可能仅在 A，读仅从 B 返回，两集合不交，旧读就直接成立。降低等待数量通常提高部分故障下的可完成性，也可能减少尾部等待，但多副本请求本身的网络与处理成本仍在。

还有一个范围容易混淆：n 是**某个键的副本数**，不是整套集群的机器总数。集群一百台，一个键只放三台，那么本式的 n 仍为 3；[第 7 章](ch07.md)会说明怎样选择这组三台及迁移其数据。

<a id="quorum-limits"></a>

## 16　为什么 r+w>n 仍不是完整的一致性协议

旧稿前面称“只要满足公式，读就一定最新”，后面又称“只是概率” → 原书印刷 233—234 页列出的边界说明，问题不是集合定理失效，而是额外假设未满足 → 应修正为：固定集合上的交集是确定结论，完整读取语义还取决于写入完成、版本规则、恢复、成员变化及读协议。不能用一个算式替代这些条件。

### 一个仍在进行的写，足以让两次读倒退

以下是按原书并发边界构造的笔记反例。设 `n=3,w=2,r=2`，初始 A、B、C 都是旧值 0；读按版本返回较新值，但**响应前不做阻塞式写回修复**。

1. 新写 `x=1` 已到 A，发往 B、C 的消息延迟；只收到一个确认，写尚未成功完成。
2. 读 R1 取得 A=1、B=0，返回较新值 1。对 B 的修复若有，也尚未完成。
3. R1 结束后发起 R2，取得 B=0、C=0，返回 0。
4. 之后写才传到 B，达到两个确认；这不能改变前两次读已经倒退的事实。

R2 的集合 BC 必然与某个**已完成的二节点写集合**相交，但在第 3 步，新写还只有一份，正好没满足该前提。更强的读写协议可以用写回等步骤消除这类行为，本章不把此反例推广到所有 quorum 实现。它足以证明“设置 r=w=2”单独不能保证单调读或线性一致性。

![写x等于1暂时只到A，尚未达到两个确认；第一次读AB返回1，未等待修复；随后读BC返回0。两次读之间新写仍未传播到B或C。](../diagrams/exports/ch06-quorum-inflight.svg)

图 6-4：从上到下是操作顺序；三列是同一组副本。每次读取都有两个响应，但新写尚未完成。图假设读前没有完成阻塞式写回，不是所有数据库的实际读协议。点击[查看大图](../diagrams/exports/ch06-quorum-inflight.svg)。

### 报失败，不等于所有副本都没写过

若新写只在 A 成功，随后协调者超时，返回未达到 w 的错误，A 上的数据通常不会自动回滚。下一次读 AB 仍可能看见它，读 BC 可能看不见。应用因此不能把“写报错”直接翻译为“系统肯定没有任何效果”；后续如何重试及辨认同一业务操作，属于端到端协议。

原书还列出几类边界。第一，保存新值的节点永久丢数据，却从旧副本重建并立即恢复计数资格，会让新值持有数降到原来的 w 以下；节点重新上线不等于已正确恢复状态。第二，再平衡时，写方认为副本集合是 ABC，读方却认为是 CDE，即使双方都各自满足二选三，具体响应集合 AB 与 DE 仍可能不交。

第三，并发写可能在各节点以不同顺序到达。单靠“本地最后收到的值”会分叉；LWW 虽能统一胜者，却可能丢弃并发写，或因墙钟偏差丢掉真正因果后继。第四，写在部分节点成功、部分失败的暂态，会与后续读写交错，不能靠一个全局“成功／失败”标签消除。

这些情形也说明为什么“读到了某个副本认为的新值”与线性一致性不同。后者还对跨客户端操作的实时先后施加约束，需要完整协议说明。[第 10 章](ch10.md#linearizable-reads)会讨论共识和相关读路径；本章先保留正确结论：**quorum 交集是一项重要构件，不是整个数据库保证。**

<a id="performance-regions"></a>

## 17　无主的性能与跨地域：少等慢节点，但不能忽略修复

单主系统若所有关键读取都走主节点，读吞吐受该节点容量限制；主节点慢会直接影响用户，主节点失效还需等待检测与切换。无主请求原本就可并行发到多个副本，只要足够多副本及时响应，就可以绕过部分慢节点。

笔记假设三个副本分别在 5、8、500 毫秒响应，r=2 时，单看本轮网络与服务等待，约 8 毫秒就能取得两个结果，而非等待 500 毫秒；若 r=3，就需要等到最慢者。版本合并、修复及协调者开销尚未计入这个小算例。并行或追加冗余请求以减少尾部等待，通常称为**请求对冲（request hedging）**，实际发送时机可不同。

这种路径对**灰故障（gray failure）**有价值：节点没有完全退出，只是异常缓慢，无主请求不必先做一次选主决定才能利用其他副本。旧稿说“慢节点问题天然不存在”则过强；足够多副本变慢、共享网络拥塞或协调者过载，仍会拖住整个操作。

副本恢复也可能造成额外压力。提示移交与反熵要搬运数据，读修复可能增加写入，恰好发生在系统本已缺少容量的时候。增大 r、w，又会改变必须等待的响应位置。不能只看没有 failover，就认为恢复免费或吞吐必然优于单主。

### 宽松法定人数改变了集合边界

大规模网络中断时，有些系统允许暂把写存到该键通常副本集合以外的可达节点，称为 **sloppy quorum（宽松法定人数）**。假设正常副本是 ABC，客户端联系不到它们，临时将写交给 X、Y；之后另一个客户端按正常规则从 B、C 读，完全可能读旧。虽然数字上也凑到两个确认，确认集合已不属于原来 n=3 的同一集合，交集证明不能套用。

后续可用提示移交把变化送回 ABC。此策略提高某些断网场景下的写可用性，但仍取决于能找到足够的临时接收者和保存提示，不能保证任何分区都写成功。原书列出不同产品的对应选项；本文保留机制，不把名称相似的选项视为语义完全相同。

跨地域部署也必须先问“在哪个集合里凑 quorum”。假设东、西两地各三个副本，各地本地读写都等二个：东部写在 E1、E2，西部读 W1、W2，两个本地多数派仍然互不相交。两边各自写出 `2+2>3`，不能据此推出跨地域最新。全局 quorum、每个地域分别满足 quorum、本地 quorum，是不同等待与故障条件。

原书以 Cassandra／ScyllaDB 说明一种转发优化：本地协调者联系本地副本，并向每个远端地域先发一份，由远端节点继续分发，减少重复跨地域流量。这里按原书说明原理，不提供未经版本实测的配置承诺。本地确认可减少跨地域往返，但远方的新鲜度要等后台传播。

最后，陈旧程度需要监控。单主日志里可以比较主从位点，但位点差可能是字节数或记录数，**不能直接当作秒数**；收到、刷盘、应用也有不同进度。无主没有一条所有节点共享的日志前缀，提示积压量、修复进度与抽样读取可提供线索，却不能从单一 hint 数精确推断所有键的陈旧时间。最终一致性没有规定时限，不等于运维可以不观察它。

<a id="causality"></a>

## 18　先发生关系：判断覆盖，依据是知道什么而非几点几分

两个客户端给同一个键写 A 与 B，三个副本可能分别收到“只有 A”“A 后 B”“B 后 A”。若每个副本都直接保留最后到达的值，最终分别留下 A、B、A。网络恢复并不自动让它们一致，因为所有消息都到齐后，节点仍按照不同顺序作出了覆盖决定。

需要先区分两类关系。若 B 基于 A 的结果作出，例如先看见记录插入，再将其中计数加一，那么 A **先发生于（happens-before）** B，记为 `A → B`。若两个写都基于未包含对方的状态作出，彼此没有这样的先后，它们就是**并发（concurrent）**的。

这是一种因果关系，不是墙钟比较。设备 1 上午离线写标题 B，设备 2 下午仍未见过 B，基于旧标题 A 写 C，两次写相隔数小时，仍可能并发。反过来，看到远端修改后立刻作出的回应，即使两台钟显示同一秒，也有明确先后。

先发生关系具有传递性：A 的结果进入 B，B 的结果又进入 C，那么 C 也承接了 A 的因果历史。对两个不同操作，只可能 A 在 B 之前、B 在 A 之前，或二者并发；不是所有操作都必须排成因果全序。把所有时间戳排序可以人为给出全序，却不能从“数字较小”反推该操作确实被另一个操作观察过。

原书以“后写覆盖先写，并发写保留待合并”引出算法。这里的覆盖是版本存储语义：新版本已经把所知旧版本合并或按用户意图替代，所以旧版本无需再作为独立候选。它不表示业务上应该任意删除历史审计记录，也不代表数据库可以从最终字符串内容可靠猜出用户是否见过另一项修改。

因此，客户端必须传递**因果上下文（causal context）**：这次写是基于哪些已读取版本。服务器只看值 B 与 C，无法区分“看过 B 后刻意改成 C”与“没看过 B、独立写 C”。接下来先用一台服务器演示如何保留这份上下文，再推广到多个副本。

<a id="version-number"></a>

## 19　单副本版本号：新分配的序号不等于客户端的知识

原书图 6-15 的教学算法每个键有一个递增版本号。每次写到达服务器，服务器分配新版本；读或写响应都返回当前所有 siblings 与最新版本。客户端下次写回时，携带上次读到的版本号，并合并当时返回的全部值。

两个数字的角色要分清：**请求携带的上下文 c**表示客户端知道到哪里；**服务器新分配的版本 v**表示这次新记录的身份。服务器接收上下文 c 后，可以移除版本不大于 c 的旧候选，但必须保留大于 c 的候选，因为客户端并未看过它们。未携带上下文的写按此模型视为不知道任何已有写，不应自动覆盖其他候选。

下面完整重走原书的五次购物车写，商品名改为中文以便阅读。初始两客户端都读到空车；随后响应有交错，任何一方都没有及时看到全部服务器状态。

| 步骤 | 客户端发送的值与上下文 | 分配的新版本 | 服务器保留的候选 |
| --- | --- | --- | --- |
| 1 | C1：`{奶}`，空上下文 | v1 | v1：`{奶}` |
| 2 | C2：`{蛋}`，空上下文 | v2 | v1：`{奶}`；v2：`{蛋}` |
| 3 | C1：`{奶,面粉}`，带 c=1 | v3 | v2：`{蛋}`；v3：`{奶,面粉}` |
| 4 | C2：`{奶,蛋,火腿}`，带 c=2 | v4 | v3：`{奶,面粉}`；v4：`{奶,蛋,火腿}` |
| 5 | C1：`{奶,面粉,蛋,培根}`，带 c=3 | v5 | v4：`{奶,蛋,火腿}`；v5：`{奶,面粉,蛋,培根}` |

第 2 步不能因为 v2 大于 v1，就用 `{蛋}` 替换 `{奶}`。C2 的请求仍基于空车；v2 只是服务器收到第二项写后分配的号码，不表示客户端已知道第 1 步。服务器返回两个候选及进度 2，C2 从这个响应开始才知道奶与蛋都存在。

第 3 步，C1 只得到过第 1 步响应，所以发 c=1。`{奶,面粉}` 可覆盖旧的 `{奶}`，却不能覆盖 C1 尚不知情的 `{蛋}`。服务器给新值编号 v3，同时返回 v2、v3。第 4 步中，C2 已见过 v1、v2，合并成 `{奶,蛋}` 后加入火腿，带 c=2；此时 v1 已不在候选里，v2 被覆盖，v3 因为大于 2 而保留。

第 5 步同理。C1 基于第 3 步响应，知道奶、面粉、蛋，却不知道第 4 步的火腿；带 c=3 写入新增培根的结果，只能覆盖它知道的历史。服务器留下 v4 与 v5，直到某个客户端同时读到并合并这两者。最终合并得到五种商品，但本例只有添加；若允许删除，仍须采用前文能表达删除意图的规则。

图 6-5 把服务器收到写的数字顺序与客户端因果关系分开。每条实线表示后项继承了前项信息，不是“服务器先收到了它”。v3 与 v4、v4 与 v5 都没有因果路径，因此应保留并发分支。

![购物车五次写的因果图：v1通向v3和v4，v2通向v4和v5，v3通向v5；v3与v4以及v4与v5无因果先后。](../diagrams/exports/ch06-causal-versions.svg)

算法能不解释商品内容就区分覆盖与并发，依靠的是一个重要约定：客户端确实合并了响应里的全部候选，再原样带回对应上下文。若客户端只取第一个值，却声称已经处理全部候选，服务器可能合法移除它实际上忽略的数据。版本元数据不能替应用修复虚假的上下文声明。

<a id="version-vectors"></a>

## 20　版本向量：多个写入口需要保留多个进度分量

单副本教学算法有一处方便条件：所有写都由同一台服务器分配新版本号。多个无主副本独立接受写时，A 可以生成自己的第 1 次写，B 也可以生成第 1 次写，一个裸数字 1 无法区分来源，更不能表达双方各自知道哪些历史。

**版本向量（version vector）**为每个键记录多个副本的版本进度，例如 `[A:2,B:1]`。各副本为本地接受的新写推进自己的计数，并在传播中保留已知的其他来源进度。读把相应因果上下文交给客户端，之后写必须带回；数据库据此决定哪些旧值被覆盖、哪些仍是并发候选。

先看一个明确简化的两节点算例：每个节点的这条写入分支都建立在该分支此前操作之上，省略的分量按 0 处理。客户端读空值后分别在 A、B 写入：

```text
u：在 A 写“奶”                 版本 [1,0]
v：在 B 独立写“蛋”             版本 [0,1]
w：客户端读到 u、v，合并后在 A 写“奶、蛋、面粉”
   合并上下文 max([1,0],[0,1]) = [1,1]
   A 分量推进后，w 的版本为 [2,1]
```

比较向量用**逐分量偏序**：若每一分量 `x[i]≤y[i]`，且至少一项严格小于，则 x 的历史被 y 覆盖，记作 `x<y`。`[1,0]` 与 `[0,1]` 一项大、一项小，谁也不支配谁，所以并发；二者都小于 `[2,1]`，所以合并后的 w 可以替代这两个候选。

现在假设 B 尚未收到 w，但沿自己已知的 v 分支又加了火腿，得到 z=`[0,2]`。比较 w=`[2,1]` 与 z=`[0,2]`：A 分量 w 更大，B 分量 z 更大，仍然并发。不能把分量相加后认为 3 大于 2，于是 w 更新；求和丢掉了“分别知道哪些来源”的信息。

若客户端同时读到 w、z，合并上下文是 `[2,2]`，在 B 创建下一项新写可得到 `[2,3]`，这时它才因果上覆盖两者。向量合并取逐分量最大值，表示合并知识；业务值如何合并，则仍由购物车或文本的数据类型决定。两个过程需要配合，不能因为向量能合并，就自动把两个余额直接相加。

这些向量说明比较规则，不是完整多客户端数据库实现。特别是，服务器先收到某写，不代表后到客户端知道那项写；若把服务器全部已见历史盲目加进客户端上下文，就会把并发误当覆盖。原书提到的**点式版本向量（dotted version vector）**等变体，进一步区分一次新写的独立标识与其因果上下文，以处理这样的精细关系。本章按原书范围介绍职责，不展开实现协议。

版本向量还允许“从一个副本读，再向另一个副本写”：上下文跟着请求移动，新接收方可识别这次写建立在哪些历史上。它可能仍生成 siblings，且必须补齐相关依赖与正确合并；仅发送一个向量，不会让未到达的业务值自动出现。

原书最后提醒，版本向量与**向量时钟（vector clock）**经常混称，但并不完全相同。这里讨论的是数据版本及其覆盖关系，沿用版本向量一词；不把每个进程所有事件的时钟模型直接等同数据库每个键的版本实现。理解本章最重要的是：**版本号／向量用于识别因果关系，冲突解决规则负责决定并发结果，传播机制负责让信息最终到齐。**

<a id="conclusion"></a>

## 21　把复制选择还原为一份可检查的承诺

单主、多主、无主的区别，首先是排序与写入口的安排。单主集中决定一份历史，简化复制，却需要处理主节点依赖及安全切换；异步多主让各处先独立推进，换来本地响应和断连工作能力，也必须解释并发修改；无主让一次请求联系多个副本，利用响应集合与修复过程承受部分节点故障，但完整语义仍取决于版本和读写协议。

为一个实际系统选择复制方式时，可以沿一次写追问：用户收到成功时，哪些副本已经保存到什么层次？下一次读允许看到哪些历史？若负责节点此刻消失，谁可以接手？网络隔离期间哪些操作仍能完成？恢复后哪些修改可能被合并、丢弃或撤销？这些问题比“用了几副本”更能界定真实保证。

本章的三个阅读保证分别约束自己的写、会话观察方向和因果前缀；quorum 提供集合交集；版本上下文区分覆盖与并发；CRDT 等机制提供特定语义下的收敛。它们各自有用，却没有任何一个可以独自替代完整的正确性设计。
