# 第 5 章｜编码与演化

**Encoding and Evolution · 让不同年代的代码与数据继续合作**

给用户资料增加一个头像地址，看起来只要改一下结构体和数据库字段。真正上线时，却可能有一半服务器已经更新，另一半仍运行旧代码；手机里的旧客户端几个月没有升级，备份中还保存着几年前的记录。改变一个字段，因此不仅是“新版能否运行”，还包括新版怎样理解过去、旧版怎样面对未来，以及数据绕过旧版再回来时还剩下什么。

[第 4 章](ch04.md)解释了数据怎样可靠地写入和读出，本章进一步追问：读出的字节由谁解释？我们先沿同一条记录比较几种编码，再把它放进数据库、服务调用、持久化工作流和消息系统。共同目标是允许各部分独立演化，同时保住数据含义和失败后的恢复责任。

<a id="compatibility"></a>

## 01　兼容性先画方向：谁写，谁读

服务端的**滚动升级（rolling upgrade）**每次更新一部分实例，观察正常后继续推进。这样可以减少停机，并在错误扩大之前停止发布。代价是新旧实例会同时工作。客户端的升级更难统一：用户可以暂不更新，设备可能长期离线。即使所有运行中的程序都已升级，旧记录也不会因此自动换成新格式。

本章按**读者相对写者的版本**定义兼容性。**向后兼容（backward compatibility）**是新代码能读旧代码写的数据；**向前兼容（forward compatibility）**是旧代码能读新代码写的数据。前者通常较容易，因为编写新版时知道旧格式；后者要求今天的程序为尚未出现的新增内容留下处理办法，例如忽略不认识的字段，而不是一见陌生字段就拒绝。

![向后兼容从旧写者流向新读者，向前兼容从新写者流向旧读者；API请求和响应分别判断，旧版读改写还要保留未知字段。](../diagrams/exports/ch05-compatibility.svg)

图 5-1：箭头只表示数据从写者流向读者，不表示发布时间。上面两行是两个独立的兼容方向；下面提醒读者，“成功读出”与“再写回时保留信息”不是同一项能力。点击[查看大图](../diagrams/exports/ch05-compatibility.svg)。

服务 API 有来回两条数据流。旧客户端调用新服务时，请求由旧代码写、新代码读，要求向后兼容；响应由新代码写、旧代码读，要求向前兼容。新客户端调用旧服务时，恰好相反。只说“API 向后兼容”，却不说明消息方向，很容易把请求和响应混为一谈。

原书图 5-1 更进一步：新版写入 `userName、favoriteNumber、interests、photoURL`；旧版的对象模型只有前三个字段。旧版读出记录，把最喜欢的数字从 1337 改成 42，再把整个对象编码写回。读取没有报错，数字也更新成功，但 `photoURL` 消失了。损失发生在**读—修改—写回**过程中，而不在最初的读取动作中。

可行的处理取决于更新路径：在对象中保留未知字段，或只更新自己负责的字段而不替换整条记录。局部更新能避免这一种丢失，但仍需单独处理并发覆盖。若中间还有 JSON 转换、模型映射或消息转发，每一跳都可能丢信息；仅在入口选一个“支持兼容”的编码格式并不足够。

最后要分清结构和语义。一个整数可以被正确解码，但把金额单位从“分”改成“元”，旧程序仍会算错。兼容性检查首先帮助我们读懂数据；业务含义、默认值和操作效果是否仍符合约定，还需要沿具体用法判断。

<a id="representations"></a>

## 02　编码把内存结构变成能够独立解释的字节

程序运行时的数据通常放在对象、数组、哈希表或树中，节点之间可以用指针连接。这种表示适合 CPU 访问，却不能把地址直接发给另一个进程：另一个进程的相同地址未必存放相同对象。写文件或发网络消息时，通常要把结构转成自包含的字节序列。

内存结构变成字节叫**编码（encoding）**，也常称序列化、marshaling；反向叫**解码（decoding）**或解析。这里的序列化与[第 8 章](ch08.md)事务隔离中的**可串行化（serializability）**是两个问题：前者讨论数据表示，后者讨论并发事务是否具有等价的串行执行结果。

转换并非所有系统都必需。原书提到 Cap’n Proto、FlatBuffers 一类零拷贝格式，允许程序直接访问适合存盘和传输的表示；列式查询也可能直接处理压缩数据。这减少某些转换或复制步骤，但“零拷贝”不是所有网络、磁盘与应用操作都零成本，也不免除格式版本的约定。

Java 原生对象序列化、Python `pickle`、Ruby `Marshal` 很方便：存一个对象，再恢复同类对象，不必先设计独立协议。问题在于，它们常把持久数据与语言、类名和对象内部结构绑在一起。短期缓存可以和进程一起淘汰，五年后仍需读取的记录却可能阻碍换语言、重构类或与其他组织集成。

恢复对象还可能触发对象构造或可执行行为。对能恢复任意对象的解码机制，不可信字节可能成为代码执行入口；这不是“所有二进制格式都危险”，而是数据解释过程具有额外执行能力。原书同时指出，语言内建格式往往没有把跨版本兼容和紧凑编码放在首位。选择时因此应问：数据是否会比当前程序活得更久，是否会跨语言、跨信任边界，而不是只比较写入函数有几行。

<a id="json-contract"></a>

## 03　JSON 易于交换，约定却不会自动消失

JSON、XML、CSV 的主要优势是广泛支持、便于查看、容易在不同组织之间达成一致。CSV 适合表格，JSON 能直接表示嵌套对象和数组，XML 有自己的结构与模式体系。对跨组织接口，大家能够正确交换数据，往往比字节是否最省更重要。

文本可读并不意味着类型含义完整。CSV 和没有外部模式辅助的 XML 文本，不能直接区分数值 123 与编号字符串 `"123"`。JSON 有 number 和 string 的区别，但数值本身不声明固定精度或机器整数宽度。JavaScript 的 `Number` 使用双精度浮点数，在 2⁵³ 附近已不能连续表示所有整数：`9007199254740993` 会被舍入成 `9007199254740992`，而 `9007199254740994` 仍能精确表示。

所以“超过 2⁵³ 的整数全部不能表示”过于绝对；准确说法是**超过安全整数范围后，不保证每个整数都可精确区分**。JavaScript 另有 `BigInt`，但普通 `JSON.parse` 不会自动把这些数字转换为它。对大整数 ID，双方约定用十进制字符串传输，通常比先解析成 `Number` 再补救可靠。原书以 Twitter／X 早期 API 同时返回数字和字符串 ID 为历史说明，这里不将它当作现行 API 的完整契约。

原始 JSON 没有任意字节串类型。若要在字符串中放图片片段或密钥字节，常用 Base64：每三个输入字节对应四个字符，带填充的长度为 `4 × ceil(n / 3)`。300 字节变成 400 字符，约增加三分之一；1 字节则占4字符，短数据的比例更高。XML 也可通过模式约定 Base64 文本，关键是双方必须知道该字符串还需进行第二次解码。

**JSON Schema**将类型与校验规则显式写出来，例如端口必须是 1—65535 的整数。它与 JSON 的区别是“数据”与“对数据的约束”。只写一个对象字段的 `properties` 不会自动要求它存在，必填通常由 `required` 指定；未声明字段默认允许出现，可用 `additionalProperties: false` 关闭。因此，新增字段能否被旧程序接受，要看旧 schema 与解析代码，而不能只看 JSON 语法允许它。

原书例 5-1 用以下约束表达“由数字字符组成的键 → 字符串值”的映射：

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "patternProperties": { "^[0-9]+$": { "type": "string" } },
  "additionalProperties": false
}
```

其中 `{"42":"Martin"}` 满足约定，`{"name":"Martin"}` 的键不满足，`{"42":7}` 的值不满足。但键仍是字符串，正则还允许 `"042"`；它没有自动建立整数键的唯一性，也没有限制为正数。模式越强，可以表达的规则越多，组合条件、远程引用与演化检查也越复杂。一个字段从可选变成必填，即使类型没变，也会让旧数据失效；收紧取值范围同样可能破坏向后兼容。

<a id="bytes"></a>

## 04　同一条记录怎样从 81 字节变成 33 字节

原书用同一条小记录比较编码。这里保留它，以便看到省下的是哪一部分，而不是仅记住“二进制更快”：

```json
{"userName":"Martin","favoriteNumber":1337,"interests":["daydreaming","hacking"]}
```

这些字符均为 ASCII，也是单字节 UTF-8；去掉空白后的 JSON 共 **81 字节**。MessagePack 为相近的数据模型提供二进制表示，本例是 **66 字节**。它把结构符号换成短前缀，但仍保存 `userName、favoriteNumber、interests` 三个字段名。

开头 `83` 表示有三个键值对的 fixmap；随后 `a8` 表示长度为8的短字符串，后面八个字节是 `userName`；`a6` 加六个字符表示 `Martin`。`favoriteNumber` 的名字占14字节，1337 则编码成 `cd 05 39`：`cd` 表示 uint16，`05 39` 按大端解释为 `5 × 256 + 57 = 1337`。兴趣列表前缀 `92` 表示两个元素。

这笔账可完整复算：外层 map 前缀1字节，三个键分别占9、15、10字节；三个值分别占7、3、21字节；合计 `1 + 9 + 15 + 10 + 7 + 3 + 21 = 66`。本例节省约18.5%，但不代表所有 MessagePack 数据都只节省这么多，更不能据此推断解码速度。整数分布、长字段名、二进制值、压缩方式和库实现都会改变结果。

原书印刷168页及旧稿把 `a8` 解释为“高4位类型、低4位长度” → MessagePack 官方规范的 fixstr 实为 `101xxxxx`，低 **5** 位表示0—31的长度 → 本例长度8的结果没错，位划分应修正；例如长度24的短字符串前缀是 `b8`，用低4位就会误读成8。

Protocol Buffers 改用模式中的数字编号表示字段。原书的 proto3 定义是：

```proto
syntax = "proto3";
message Person {
  string user_name = 1;
  int64 favorite_number = 2;
  repeated string interests = 3;
}
```

每个字段的头部由 `(字段编号 << 3) | wire_type` 得到，再作为变长整数写入。**wire type（线格式类型）**说明后续字节怎样切分，不是完整的业务类型：字符串、字节串、嵌套消息都可使用长度界定的类型2。编号1的字符串头是 `0a`，编号2的整数头是 `10`，编号3的字符串头是 `1a`；它们在本例中各占一字节，大编号不保证仍是一字节。

```text
0a 06 "Martin"        → 1字节头 + 1字节长度 + 6字节内容 = 8
10 b9 0a              → 1字节头 + 2字节整数 = 3
1a 0b "daydreaming"   → 1 + 1 + 11 = 13
1a 07 "hacking"       → 1 + 1 + 7 = 9
合计：8 + 3 + 13 + 9 = 33 字节
```

**varint（变长整数）**每字节留下7位存数值，最高位表示后面是否还有字节。1337 等于 `57 + 10 × 128`，所以先写低7位57，再写10；第一字节还要置继续位，得到 `b9 0a`。这种布局让小非负整数更短。两个兴趣通过同一个编号3重复出现来表示；这是 `repeated string` 的布局，不能推广成所有重复数字也逐项带头，后者在 proto3 中通常采用 packed 编码。

这里原书印刷170页和旧稿有一处实质性混淆：“−64—63 都只需一字节” → 这属于先做 ZigZag 的 `sint32/sint64`，不是示例中的 `int64` → `int64` 的0—127占一字节，负数的值编码占10字节；`sint64(-1)` 先映射到1，只占一字节。二者即使共用 wire type，也不能不经迁移就互换。原图中1337的 `b9 0a` 本身正确；若换成 ZigZag，1337先变成2674，字节会是 `f2 14`。

<a id="protobuf-evolution"></a>

## 05　Protobuf 的演化依靠稳定身份，而非字段排版

Protobuf 数据没有字段名，字段编号便成为持久身份。把 `user_name` 在代码里改名，不改变二进制数据中的编号1；把编号1改成7，却相当于删除旧字段、增加另一个字段。旧字节可能仍能被解析，但它们不再落入你预期的字段，因此“解析没报错”不能证明改号安全。

笔记假设新版给 Person 增加 `string email = 4`。新读者读旧记录，编号4不存在，访问该标量字段得到默认空字符串；旧读者读新记录，看到未知编号4，可依据 wire type 跳过它。这就把向后和向前兼容分别接起来。能否在业务上把“没有 email”和“空 email”看成同一状态，则是另一项决定。

原书采用的 proto3 隐式存在性标量，通常不区分“字段没出现”和“显式设为默认值”。若业务需要表达“尚未填写”与“用户明确填写0”的区别，可以使用显式存在性的 `optional` 等机制。这是依据官方指南的补充；不能把“没有 required”简化成“任意添加字段都不改变应用行为”。新版若把缺失值0解释成“免费”，就可能错误处理全部旧记录。

| 变更 | 字节层会怎样 | 还要确认什么 |
| --- | --- | --- |
| 加新编号字段 | 旧读者跳过；新读者处理缺失值 | 默认含义是否可接受；旧读改写链是否保留未知字段 |
| 删除字段 | 新读者不使用旧字段；旧读者面对缺失 | 旧业务是否能接受缺失；把编号放入 `reserved`，不再复用 |
| 改字段名、编号不变 | 二进制身份不变 | ProtoJSON、文本表示、生成代码接口仍可能受影响 |
| `int32` 扩为 `int64` | 新读者可接收旧范围；旧读者可能截断大值 | 在旧读者退出前，仍只写入旧范围内的值 |
| 保持类型却改变单位 | 解码照常成功 | 业务语义已不兼容，应显式迁移或引入新字段 |

删除后复用编号尤其危险。假设原来的编号4是邮箱，几年后改成收货地址，历史数据仍可能含编号4；由于两者都是字符串，解码器可能把邮箱安静地当成地址。`reserved 4;` 让后续定义不能误占这一身份。保留字段名也有利于避免文本表示的重用问题。

类型扩宽同样需要发布顺序。原书指出，新代码写出超过32位范围的值时，旧代码可能只留下低32位。例如 `4294967297 = 2³² + 1` 被按32位截断后是1。做法不是只把 `.proto` 改完，而是先让读取端接受宽类型，再允许写入超出旧范围的值；如果仍必须支持回滚到窄类型，就尚未解除这个约束。

官方 proto3 指南说明，二进制消息对象会保留未知字段并在再次编码时写出。但转成 JSON，或只枚举已知字段重新构造对象，会丢掉未知字段。这里应保留的是未知信息，而非承诺输出字节顺序逐字不变。格式能力必须贯穿整个转换链，这正是开头头像地址例子要提醒我们的地方。

<a id="avro-resolution"></a>

## 06　Avro 用两份模式，把“字节怎么读”与“应用想要什么”分开

Avro 同样需要模式，但记录中没有字段编号，也没有逐字段名称和类型标记。它按写入模式的顺序连接各字段值。原书的 Person 仍有姓名、最喜欢的数字和兴趣，不过数字类型写为 `union { null, long }`，允许没有值，默认值为 `null`；兴趣是字符串数组。

同一条记录在这种模式下是 **32 字节**：姓名为1字节长度加6字节内容；数字为1字节 union 分支索引加2字节值；兴趣为1字节元素数量、两段带长度的字符串以及1字节结束标记。合计 `7 + 3 + (1 + 12 + 8 + 1) = 32`。

Avro 的 `int/long` 采用 ZigZag 后再变长编码，长度和计数也遵循相应整数编码规则。因此长度6写成 `0c`，数字1337写成 `f2 14`；`[null,long]` 中 long 的分支索引是1，写成 `02`。两个兴趣前面的数量2写成 `04`，两个字符串长度11和7写成 `16` 与 `0e`，数组最后以 `00` 表示结束。这些值不是每个字段都携带的类型说明，必须结合模式理解。

若只拿新版字段顺序直接读旧字节，就可能把姓名长度当成数字，把后续所有边界都读错。Avro 解决演化的办法是显式区分两份模式：**写者模式（writer’s schema）**描述这段字节实际怎样写成；**读者模式（reader’s schema）**描述当前程序希望得到哪些字段与类型。解码必须知道实际写者模式，读者模式则可以新、可以旧。

笔记假设写者的 Person 顺序是 `userName、favoriteNumber、photoURL`，读者希望按 `favoriteNumber、userName、locale` 使用数据，`locale` 默认 `"zh-CN"`。解析器先按照写者模式识别字节，再按字段名对应到读者结构：前两个字段保留，头像被读者忽略，缺少的 locale 从读者默认值补入。读者字段重排不要求回写所有历史记录。

图 5-2：实线为按写者模式读取与投影的过程，虚线表示读者模式提出的目标结构。图中 `favoriteNumber` 两侧均为 long，`locale` 明确有默认值；箭头不表示忽略的头像会自动被保存到输出对象。点击[查看大图](../diagrams/exports/ch05-avro-resolution.svg)。

原书图5-6把 `favoriteNumber` 从写者的 `union {null,long}` 连到读者的 `union {null,int}` → Avro 1.12.0 的模式解析只允许规定方向的类型提升，**不允许 long 自动缩为 int** → 当实际分支为 long 时，即使数值1337装得进 int，也不能把图中连线视为有效的一般转换。本文使用两侧同为 long 的例子；新增字段也显式给出读者默认值，避免把图示省略当成无条件兼容。

旧稿说“Protobuf／Avro 都支持保留未知字段” → Avro 规范对读者没有的字段规定为忽略，并不保证投影对象保存它们 → 用旧读者模式解码后，再按旧模式重新编码，头像仍可能消失。若要完整读改写，需要有意识地保留原记录或用包含全部所需字段的模式处理。**模式解析解决可读性，不自动提供无损往返。**

<a id="avro-evolution"></a>

## 07　默认值属于读者；模式本身也必须保存

Avro 的新增、删除规则可以从“读者需要而写者没有怎么办”直接推出。新增一个有默认值的 `locale`，新读者读旧记录时填默认，旧读者读新记录时忽略多出的字段；若新增字段没有默认，新读者就无法补足旧记录，向后兼容被破坏。删除字段时方向反过来：新读者忽略旧字段通常容易，旧读者读新记录却需要它自己的旧模式原本就有默认值。

因此，“只增删带默认值的字段”是同时追求两向兼容时的实用规则，不是说任何没有默认值的新增都会破坏两个方向。给新模式临时添加默认值，也不能追溯改写已经发布的旧读者模式；必须看每个实际版本的读取规则。可空与默认更不是同义词：`[null,string]` 表示值可以为 null，只有显式的 `default: null` 才告诉读者在写者缺字段时怎样补。

默认值也不是“编码时可省略该字段”的指令。Avro 的值按写者模式顺序编码，即使某字段等于默认值，也仍按该模式写入。这个区别与 Protobuf 的缺失字段处理很重要：Avro 默认值主要服务于两份模式之间的解析，而不是给字节流增加一种无标记的任意缺省方式。

原书印刷175页及旧稿说“null 必须是 union 第一分支才能作为默认值” → 本章参考文献所列的 Avro **1.12.0** 规范已表述为默认值匹配 union 中第一个与该值匹配的分支，并不要求分支索引为0 → 本文仍使用 `[null,long]` 配 `default: null`，以得到清楚且便于兼容旧工具的写法，但不把“null 必须放第一位”作为1.12.0的通用规则。这是规范版本限定的修正，具体库还应按所用版本确认。

改名则依赖读者模式的 `aliases`。新读者可把 `displayName` 的别名设为旧字段 `userName`，从而识别旧写者；旧读者却不知道未来的名字，不能反向自动匹配。类似地，给 union 增加 string 分支，新读者仍可读原有 null／long；旧读者遇到真正使用 string 的新记录就失败。兼容性不仅关乎 schema 看起来多了一项，还关乎写者开始实际使用哪些值。

紧接着的问题是：读者从哪里得到写者模式？原书给出三种安排。一个包含大量同模式记录的 Avro 对象容器文件，在文件头保存一次模式，成本由全部记录分摊；不同版本混存的数据库或消息流，在每条记录附带模式标识，由注册表查回对应模式；双向通信可协商协议并缓存模式，Avro RPC 对有状态连接与无状态传输有不同握手安排，并非所有 HTTP 请求都只在最初协商一次。

这也意味着“32字节”只计裸记录，不计容器头、模式ID、网络封装或模式注册表。历史模式不是可随意清掉的旧文档：只要还有数据依赖那个ID，就仍需找到对应描述。模式注册表可以辅助部署前检查，但注册成功不替代业务语义检查，也不能凭空恢复已经遗失的模式。

<a id="schema-value"></a>

## 08　模式的价值，是把长期约定变成工具能检查的材料

Avro 不需要稳定编号，因此适合根据已有结构动态生成模式。原书的例子是把关系数据库导出为文件：表对应记录，列名对应字段名，每次导出都从当前表结构生成模式，并把它一起写入对象容器。增加或移除一列时，生成器不必另行维护“列名对应哪个历史编号”的表。

Protobuf 也不是绝对不能自动生成，但生成器必须保存编号分配历史，不能按当前列位置随手重新编号。假设原列为 `name、age、email`，删除 age 后若把 email 从3改为2，旧数据中的年龄就与新的邮箱发生身份冲突。动态生成的困难在这里，而非“Protobuf 只能人工填写文件”。

Avro 的便利也有前提：列名仍承担匹配身份，改名需要相应别名策略，删除无默认值字段仍会影响旧读者。因此，“重新生成即可”只简化导出器如何产生模式，不代表所有数据库变更都天然兼容。旧稿由此推到“Kafka／数据湖选 Avro 一定最佳”，超出了原书论证；选择还要看语言工具、已有消费者、模式治理和实际负载。

模式驱动格式有四种相互关联的收益：省去重复字段名；把结构保留为可检查的文档；部署前检查新旧读取关系；为静态类型语言生成访问代码。JSON Schema 擅长额外值约束，Protobuf／Avro 的核心模式相对简洁，具体业务校验常在应用中完成。它们回答的问题不同，不能把更短的定义自动等同于更完整的验证。

模式也不能保证文档里所有说明都正确。解码所需的字段与类型必须相符，但 `amount` 代表什么货币、时间戳用什么时区、默认值表达未知还是零，仍要显式记录并保持一致。原书提及 ASN.1 和数据库专有协议，是为了说明“模式加二进制”有很长历史，不是某一种新产品的独有优势。

本章四种大小为81、66、33、32字节，是同一小记录、指定模式和未压缩表示下的结果。它们解释字段身份信息放在哪里，不构成一般性能排名。能否持续演化，往往比再省一字节更值得优先考虑；同时活跃的版本越多，操作、测试与故障恢复需要覆盖的组合也越多。

<a id="database"></a>

## 09　数据库让不同时代的程序发生通信

写数据库的进程负责编码，读数据库的进程负责解码。即使只有一个应用，也可以把持久化理解为给未来的自己发送消息：今天写入的对象，可能由一年后的代码读取。因此数据库最直观的要求是向后兼容，而滚动升级又带来新版写、旧版读的向前兼容需求。

原书用“五毫秒前”和“五年前”的记录说明**数据比代码活得久**。一轮服务发布可能几分钟就结束，数据库却不会顺便改写每个冷门记录。若只有最新两版程序在运行，仍可能存在许多历史编码版本；备份恢复和长期归档还会把这些旧版本重新带回读取路径。

这里需要区分应用看到的逻辑模式与磁盘中的物理表示。关系数据库可以对外呈现一个当前表结构，同时让旧行以较早的存储格式存在。例如某些简单新增可空列不必重写每行，读取时为缺少的列补 null。原书还以 LSM 压缩合并时改写格式说明渐进迁移的可能性，但不能推成所有 LSM 引擎都会理解并自动升级应用编码的 value；不透明字节中的业务格式仍由应用处理。

复杂变更不能靠补空值完成。把单个电话号码改成多个号码，必须决定旧值怎样成为列表、新值怎样被旧版读取；把一段数据拆到新表，还改变了更新和查询的位置。即使两种格式都能解码，也仍要安排迁移中的写入归属和并发更新，不能只运行一次复制就认定在线迁移完成。

一个笔记假设的新增字段流程是：先部署能接受缺失和未知字段的读取／更新代码，再开始写新字段；确认旧写回路径不会删除它；历史记录按需要回填或惰性处理；只有旧版本和必要回滚窗口退出后，才收紧依赖。这个流程强调的是先建立兼容通道，再启用新含义，并非所有表结构迁移的通用脚本。

归档时的条件有所不同。若将数据库逻辑内容导出成一个新的不可变文件，既然已经读取并复制所有记录，就可统一使用该次导出的模式；Avro 容器适合共享模式的一组记录，Parquet 适合后续列式分析。物理备份未必做这种重新编码，不能把逻辑导出的结论套给所有备份。无论哪种方式，都要让恢复工具找到对应版本和解释依据。

<a id="services"></a>

## 10　服务封装内部变化，接口仍需承受新旧共存

数据库提供较通用的查询和更新能力，服务则暴露业务定义的输入、输出和操作。例如调用方只能“提交支付”或“查询状态”，不直接修改服务内部的任意表。这样，服务拥有者可以改变内部表结构、存储产品甚至整体实现，只要外部契约保持一致，调用方不必同时发布。

通过 HTTP 访问的服务可用于浏览器、手机应用、组织内部调用，也可用于跨组织集成。**REST**是一组围绕资源与 HTTP 的设计原则，例如用 URL 标识资源、利用缓存和内容协商；它不是某一种编码格式。“HTTP 加 JSON”也不足以完整定义一个 API，客户端仍要知道访问哪个地址、用什么方法、提交什么内容以及错误怎样表示。

**接口定义语言（IDL）**把这些约定机器可读化。原书用 OpenAPI 的 `/ping` 例子说明：`GET /ping` 的200响应为 JSON 对象，其中 `message` 是字符串。这个定义可以支持文档、客户端生成和检查，却不会自行实现返回 `Pong!` 的业务代码。FastAPI 可从代码生成 OpenAPI；gRPC 常先写 Protobuf 服务定义，再生成服务端骨架和客户端。两种方向都把接口与实现联系起来，但契约一致仍需维护。

服务演化能否简化，取决于发布控制。若**确实保证全部服务端先升级，再升级客户端**，主要需满足旧客户端请求能被新服务读取，以及新响应能被旧客户端读取，即请求向后、响应向前兼容。若新版客户端会遇到未更新服务、服务发生回滚，或流量仍进入旧实例，就不能省略另外两个方向。

在这个前提下，新增一个可选请求参数，新服务对缺失使用保持旧行为的默认值，通常可兼容旧客户端；响应新增字段，只有旧客户端容忍未知字段才可行。旧 JSON Schema 若关闭额外字段，或者客户端用固定键集合做校验，“只新增”也可能失败。旧稿把“响应加字段、旧客户端忽略”直接叫向后兼容，方向应修正为本章定义下的**向前兼容**。

跨组织服务更难收回旧契约，因为提供方不能命令所有客户端今天升级。若必须改变已有字段的含义，常要维持多个 API 版本。版本可以放在 URL、HTTP 头，或与客户端配置绑定，原书没有宣布唯一正确方式。版本号的作用是让双方选择契约；长期维护成本、停止支持的条件和实际使用者仍需明确。调用日志也未必能看出客户端究竟读取了响应中的哪些字段。

<a id="rpc-failure"></a>

## 11　远程调用的困难，是超时之后仍不知道发生了什么

**远程过程调用（RPC）**提供类似函数调用的接口，但位置透明不能抹掉网络边界。局部函数通常共享语言与地址空间，可以传对象引用；远程调用必须编码参数，承受传输与排队，并与可能使用另一种语言的服务交换类型。网络延迟会随拥塞和过载变化，调用成本不能按本地函数估计。

最关键的差异不是“慢”，而是结果不确定。笔记假设客户端发送一次扣款请求，等待后超时。世界A中，请求根本没到支付方，重试是完成工作的必要条件；世界B中，支付方已扣款，只是响应丢失，重试可能再扣一次。客户端看到的都是“没有及时拿到响应”，因而**超时不能证明远端没有执行**。

给请求设置更长超时，可以改变等待成本，却不能从根本上区分这两个世界。直接把超时当作业务失败并提交新的付款，可能重复产生效果；完全不重试又可能遗漏未执行的操作。解决要落到协议：同一逻辑支付携带稳定请求标识，接收方能识别重复并返回已有结果，或提供按该标识查询结果的方式。

这就是**幂等性（idempotence）**在此处的用途：同一逻辑操作重复到达时，效果与执行一次一致。请求标识必须在重试间保持不变；每次重试都生成新 UUID，得到的只是多个独立请求。接收方还要正确协调判重与业务修改，不能“查一下没有”以后在并发重试中各扣一次。这些实现细节将在事务与流处理章节继续展开，本章先把责任留在真正执行副作用的边界上。

让客户端找到服务，是另一个独立问题。**服务发现**回答有哪些可用地址；**负载均衡**决定这次请求选哪一个。硬件或软件负载均衡器可以提供稳定入口，在后面分发给多个实例；DNS 可以让一个名字对应多个地址，但缓存可能让调用方继续使用过期地址。注册表加心跳适合更动态的实例集合，还可携带区域、分片等元数据；注册表认为实例存活，也不等于下一次调用一定成功。

服务网格把发现、转发、传输加密和可观测性放到代理或库等基础设施中。原书介绍了客户端和服务端旁置代理的典型拓扑，但部署方式并非只有 sidecar 一种；也不能照旧稿说“所有工作下沉，业务完全无感”。自动重试仍可能重复扣款，调用超时和认证身份仍影响业务结果。网格改善调用路径的管理，不能替业务定义幂等键、兼容字段或跨服务原子性。

<a id="durable-execution"></a>

## 12　持久化执行把调用栈中的进度变成可恢复历史

原书第二版新增的支付例子，把一次支付分成风险检查、信用卡扣款、银行入账。高风险时直接拒绝；低风险才尝试扣款，扣款被拒绝则不继续入账。这样一组带顺序和分支的任务叫**工作流（workflow）**。定义可写成程序、领域专用语言或图，工作流引擎安排何时、在哪台机器执行各步，以及失败后怎样继续。

概念上，引擎有负责调度的编排者与负责执行的执行者。时间计划、HTTP请求或人工操作都可以触发一次工作流。数据编排引擎常围绕 ETL 作业，业务流程引擎可能强调图形化建模；Temporal、Restate 则是原书举出的**持久化执行（durable execution）**框架。产品各有不同执行语义，以下用 Temporal 的工作流与活动边界说明，不把一种实现推广给全部引擎。

普通函数可以按顺序写三次调用，但进程若在扣款成功后、银行入账前崩溃，内存中的“进行到第二步”消失。外部信用卡系统却不会随进程一起回滚。重新从头执行可能重复扣款，完全放弃又留下半完成支付；跨第三方接口也不能简单套一个本地数据库事务。

持久化执行保存工作流的事件历史。Temporal 把会访问外部世界的步骤通常放在**活动（Activity）**中；工作流代码负责分支、安排活动并等待结果。活动参数与返回值也要编码并进入历史，因此长时间运行的流程同样受本章模式演化约束。它不是把每一个 Python 局部变量都直接持续刷到磁盘，而是借助历史与确定性执行恢复逻辑进度。

沿一次正常支付，可以这样理解其过程：

1. 保存工作流开始所需输入，安排风险检查活动。
2. 执行者调用风险服务，把结果报告给引擎；引擎记录完成结果。
3. 工作流依据“低风险”结果安排扣款活动；扣款返回交易标识，完成结果被记录。
4. 工作流用该结果安排银行入账；入账完成被记录后，流程才到达成功终点。

现在假设第3步的完成结果已可靠记录，但负责运行工作流代码的进程重启。恢复时再次运行控制逻辑，遇到风险检查和扣款这两个已完成活动，框架从历史返回结果，而不是为了重建调用栈再执行它们；随后继续尚未完成的入账步骤。这称为**重放（replay）**。重放的是控制决策与历史，不是要求支付方再次扣钱。

原书例5-5的关键接口是 `await workflow.execute_activity(...)`，不是对支付接口直接执行普通网络请求。下面用笔记伪代码保留这一职责分离，`activity` 表示引擎管理的活动调用，不是可独立运行的 SDK 程序：

```text
payment_workflow(payment):
    risk = await activity(check_fraud, payment)
    if risk.reject:
        return REJECTED
    charge = await activity(debit_card, payment, key=payment.id + ":debit")
    if charge.declined:
        return REJECTED
    await activity(credit_bank, charge, key=payment.id + ":credit")
    return COMPLETED
```

持久化进度使长流程不必依赖同一个进程持续存活，也能把等待和重试交给引擎。但正确性仍取决于哪个结果已经被历史确认，以及外部世界已经做了什么；两者之间的缝隙，是下一节必须单独处理的失败路径。

<a id="durable-boundary"></a>

## 13　已完成的活动可重放结果，未确认的副作用仍可能重试

更棘手的故障发生在活动内部：信用卡服务已经扣款，活动执行者却在报告完成之前崩溃，或者完成报告没有到达引擎。引擎历史只知道“安排了扣款”，还没有可信的完成结果。超时之后若允许重试，它就会再次运行扣款活动；此时再次调用外部支付方是可能发生的。

![上行表示活动完成结果已进入历史，恢复时直接返回旧结果；下行表示外部已扣款但完成报告丢失，引擎会重试活动，支付方须用同一幂等键识别既有扣款。](../diagrams/exports/ch05-durable-boundary.svg)

图 5-3：两行是两种不同失败时点，不是连续步骤。实线表示恢复动作，虚线标出“外部副作用已发生、引擎尚无完成记录”的间隙。先看历史掌握了什么，再判断活动是否可能重跑。点击[查看大图](../diagrams/exports/ch05-durable-boundary.svg)。

原书印刷188页概括“失败任务重跑时跳过此前成功的所有 RPC／状态变化”，旧稿进一步写“不会真再扣一次款” → 原书189页本身要求外部接口幂等；Temporal 官方说明，活动完成但未报告成功时仍会被重试，活动内部普通调用不被逐一自动记录 → 应限定为：**已记录完成的活动在工作流重放时复用结果；未记录完成的活动可能执行多次，外部副作用要靠幂等协议等机制约束。** 这不是一份跨支付方和工作流历史的共同原子提交。

笔记假设扣款活动每次携带 `payment-742:debit`，支付方将该键与扣款结果可靠关联。第一次已扣款，第二次收到相同键，就返回同一结果，不新增扣款；引擎终于拿到并记录完成后，继续入账。若第一次根本未到达，重试则执行首次扣款。一个协议让两个不可区分的网络世界都得到正确处理，而不是靠超时猜测哪个世界发生了。

但这个结论依赖幂等键的作用域、保留期与参数约定。同一键不能被用于另一笔不同金额的请求；支付方若早已清理去重信息，就不能仅凭客户端还记得旧键断言不会重复。伪代码中的 `payment.id` 应是这项业务操作的稳定标识。如果用户重发整个工作流会生成另一个全新 payment.id，单个活动的重试幂等也无法自动识别两次其实是同一笔付款。

如果一个活动先扣款、再发邮件、再写文件，第三步失败时，整个活动重试可能再次执行前两步。更细的活动边界可让已确认步骤复用结果，但也增加调度与历史成本；而任何单次活动的“外部成功、报告未保存”窗口仍存在。可以用任务粒度改善恢复位置，不能用拆步骤取代外部副作用协议。

持久化执行还要求**确定性（determinism）**：面对同一段已记录历史，工作流应发出与它相容的命令序列。若旧历史先安排扣款，新代码却先安排银行入账，重放时就无法对应；这不是普通的无害重构。直接用当前时间或随机值决定分支，也可能让同一历史走进另一条路。应使用框架支持的重放安全 API，外部读取与副作用放进活动，并为工作流代码采用版本策略。

原书建议旧实例继续使用旧实现，新实例进入新版；Temporal 也提供版本化与补丁机制，并非永远不能修改工作流。重要的是为仍在运行的历史保留可解释路径。工作流输入、活动结果以及代码版本，都可能比一次部署存活更久，这使本章的“数据比代码长寿”再次出现。

最后，流程可恢复不等于所有步骤立即原子生效。扣款后银行长期拒绝入账，仍需业务决定继续处理、退款或人工核对；退款是另一个业务动作，不会让已经发生的扣款从历史消失。这些是笔记对副作用边界的解释，原书示例没有提供完整的支付补偿实现。[第 8 章](ch08.md#idempotent-consumer)会进一步区分事务原子性、重试和幂等；[第9章](ch09.md#partial-failure)再解释不确定性来源。

<a id="messages"></a>

## 14　消息与 actor 改变等待方式，不取消数据契约

事件驱动架构通常让发送者把消息交给**消息代理（message broker）**，由代理暂存并转交消费者。发送者无需等待业务消费者完成，也不必知道消费者的当前 IP。接收方短时离线时可以积压，多个订阅者可收到同一事件，生产与消费的部署时间因此更容易解开。

“不等消费者”并不要求“发完完全不管”。生产者仍可能等待代理接收的确认，代理接收也不等于消费者业务已完成。如果需要请求—响应，可让调用方在另一通道等待带关联标识的回复；这样底层是消息，业务交互仍可能是同步等待。旧稿额外说这种方式“很少使用”，原书并未给出相应普遍性依据。

原书归纳两类分发：队列把某条消息分配给一位竞争消费者处理；主题将消息分发给各订阅者。二者描述的是分配关系，不是恰好一次保证。一个消费者处理完消息却在确认前崩溃，代理可能再次投递，甚至交给另一消费者；旧稿图中的“多个消费者之一收到，因此每条只处理一次”把正常分配与故障重投混在了一起。

不同代理和配置有不同持久性、确认与保留规则。有的消费确认后删除消息，有的按日志保留期保存、允许消费者重新读取。前者便于完成后回收，后者有利于重放与事件溯源；“曾经写过磁盘”既不说明能保留多久，也不说明消费者是否只执行一次。代理提供缓冲仍有容量上限，长期生产快于消费时，积压和保留窗口必须被管理。

对编码来说，代理通常只搬运字节加元数据，不替消费者解释全部业务模型。JSON、Protobuf、Avro 都可作为消息载荷，模式注册表帮助保存版本和检查读取关系，AsyncAPI 可描述消息接口。若消息保留数月，新消费者要读历史消息，向后兼容就不只面对上一版；若旧消费者仍在线，新生产者还要考虑向前兼容。

中间消费者重新发布消息时，也会重现头像地址的丢失问题：新版生产者加字段，旧转换器只复制已知字段，下游新版就永远收不到那一项。消息系统将依赖关系从一次调用改成持续数据流，并没有消除字段身份、默认值和无损转发的责任。更完整的发布、重投和流处理保证留到[第12章](ch12.md#delivery-contract)。

**actor（参与者）模型**则把并发逻辑封装为拥有私有状态的实体，实体之间以异步消息通信。在本章的基本模型里，每个 actor 一次处理一条消息，因此对其内部状态的访问可以避免多线程同时修改；这不意味着跨多个 actor 的业务操作天然原子，也不保证消息不丢失或不重复。

分布式 actor 框架把同一消息接口扩展到跨机器通信，必要时编码、传输和解码。原书认为这种位置透明比伪装本地函数的 RPC 更自然，因为程序模型已要求面对异步消息和失败。只是“由框架处理网络”不等于“每条消息已有持久队列语义”；具体重入、投递和持久化仍看框架约定。滚动升级时，新 actor 发给旧 actor、旧 actor 发给新 actor，照样需要本章的兼容规则。

<a id="conclusion"></a>

## 15　演化能力来自整条路径，而非一种格式的名称

回到开头的头像字段：格式要能表达它，新读者要能处理旧记录缺少它，旧读者要能接受新记录多出它，读改写与消息转发还要保住它。若这个字段进入持久化活动结果，未来的恢复代码也要读懂；若经 API 返回，客户端的校验与使用方式又成为兼容边界。每经过一处数据流，责任都会重新出现。

原书的核心取舍因此不是“JSON 还是二进制”这么窄。文本格式降低跨语言与跨组织交换门槛，模式驱动格式提供紧凑表示和明确工具支持；数据库让版本差异延伸到未来，RPC暴露网络不确定性，工作流保存恢复进度，消息与actor改变协作方式。没有一种通道自动免除数据含义与副作用约定。

实际讨论一项变更时，可以沿正常与失败路径分别走一遍：哪版写者产生什么字节，哪版读者用什么规则解释；缺失、未知、改名和越界值怎样处理；程序在外部成功之后崩溃时，谁知道完成，谁会重试，哪一方防止重复效果。能把这些步骤说清，才能判断各部分是否真的可以独立发布。

本章建立的是跨版本的协作基础。[下一章](ch06.md)把同一数据放到多个副本，进一步讨论更新怎样传播、读取会看到什么，以及主节点故障后怎样恢复。编码兼容让副本能够交流；交流之后是否一致、哪些写入已被可靠确认，则是接下来要解决的问题。
