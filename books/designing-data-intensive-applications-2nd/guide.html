01先找问题，再沿失败路径回读

全书有一条连续的主线：先决定系统为谁处理什么数据，再选择表示与存储；数据跨版本、机器和服务传播以后，明确并发与故障下还承诺什么；最后把这些局部机制组成端到端流程，并判断它对人的影响。读完某种技术，最好能回答三个问题：它减少了哪一种困难，把哪一种责任交给了别人，发生失败时依据什么恢复。

例如，“订单已经成功”可能指请求已被接收、数据库已提交、派生视图已追上，或现实支付已经完成。这些状态不是一回事。沿保证范围辨认成功的含义，再回到各章的操作顺序，才能判断一个承诺是否足够。只读术语和结论表，会跳过使结论成立的条件。

02选型与性能：1→2→3→4→7→11

第1章 → 第2章 → 第3章 → 第4章 → 第7章 → 第11章。

先定义工作，而不是先挑产品。 第1章把运营型点查与分析型聚合区分开，再分辨权威记录和派生数据。同一种数据库可以承担不同角色；读副本、搜索索引和数据仓库也不会因为保存同一事实就拥有同样的更新权。第2章接着把“快”变成可测量的要求：记录请求起止点、有效请求、负载分布和统计窗口，区分响应时间与数据新鲜度。异步投递可以让页面快速返回，却留下较旧的时间线。

模型决定要表达什么，布局决定付出什么。 第3章的关系、文档与图模型不直接规定磁盘布局；GraphQL属于接口层，也不会自动选择图数据库。第4章把一次查询还原为日志、页、索引与合并工作。LSM与B-tree不能只按“写快／读快”排胜负，必须固定键值大小、缓存、范围查询、持久化条件和稳态合并负担。向量近邻提供候选，召回率也不能替代事实正确性。

扩展以后，把数据移动计入查询。 第7章的全局索引可能只把“找ID”局部化，取原记录仍跨片；哈希均匀也不能拆散一个热键。第11章把同一问题推进到批量连接：shuffle让相同键相遇，广播减少大表搬运，却要求小表能在每个执行位置容纳；共分片还需布局兼容。现代dataflow引擎的价值在于按整个计算图安排这些工作，而不是只把MapReduce换一个名字。

可沿首页时间线 → 只物化帖子与作者ID → 索引与预计算回读计算怎样从读路径移到写路径。然后用尾延迟、全局索引回表和批结果发布反查代价：投递积压、慢分片和半成品输出都可能使“局部更快”失去用户意义。这里没有全书统一的性能倍数，也没有据教学算例得出的产品基准排名。

03一致性与故障：6→8→9→10

第6章 → 第8章 → 第9章 → 第10章。

第6章先问副本知道什么。 收到日志、可靠保存、应用后可查是不同进度。读己之写、单调读和一致前缀读各自排除一类观察异常；它们不是所有副本瞬间相同的同义词。多主合并与CRDT收敛可以保存并发修改，但两地独立批准同一时段的会议室预订，仍可能一致地保留两个互相冲突的承诺。

第8章再问并发决定能否共同成立。 医生分别修改不同的行，仍可能因写偏斜破坏“至少一人值班”。快照隔离提供稳定读取，却不自动排除这类循环依赖；可串行化要求完整事务能解释为某个串行顺序。两阶段锁负责隔离，两阶段提交负责多参与者共同提交或中止。参与者已准备、最终决定未知时，不能靠本地超时擅自回滚。

第9章解释为什么不能猜测远端。 超时既可能对应请求未到，也可能对应效果已发生但响应丢失；旧进程暂停后还会恢复，租约服务撤销资格不会让它自动停止。隔离令牌要在资源端原子检查并持久保存，且新持有者应先推进资源代次，再读状态继续工作。安全性与活性分开后，网络异常可以使请求等待，但不应在协议声明的故障模型内允许错误提交。

第10章把承诺落实到操作历史。 线性一致性保留非重叠操作的实时先后，可串行化保留事务串行解释，严格可串行化把两者结合到完整事务。共识还需要跨任期继承、持久投票与提交规则；交集本身不够。线性一致读既要取得适当的领导权证据，也要等待状态机应用到安全读取位置。

两处对照尤其值得一起读：第6章的2写／2读反例与第10章的3写／2读反例阈值不同，但都让尚未完成的新写先被一次读取暴露，随后另一读返回旧值；不能把两例的w混写。再对照2PC存疑状态与原子提交和共识：事务参与者全员准备与保存决定的副本法定人数是两种集合，“多数派”不能替代某个业务参与者的准备承诺。

04演化与数据流：5→11→12→13

第5章 → 第11章 → 第12章 → 第13章。

演化首先是新旧解释共存。第5章按写者和读者版本确定兼容方向：新读旧是向后兼容，旧读新是向前兼容；API请求和响应分别判断。能解码不代表能无损写回，旧转换器可能丢掉新字段；金额从分改成元，也不会因字节仍可读而保持语义兼容。历史schema、工作流历史与仍运行的旧代码，都是迁移的一部分。

接着是产生新结果而不破坏旧读取。第11章用有界输入组织可重跑计算，把任务尝试与正式产物分开。V18构建完成之前继续读V17；发布要求完整分片集合及消费结束边界，不能把一条“作业完成”消息等同于所有下游已应用数据。每个下游原子切换，也不等于全系统共同切换。

第12章把这个问题延伸到持续写入：初始快照对应明确日志切点，后续变化从正确位置接上，才能避免遗漏和旧快照覆盖新值。CDC观察数据库变化，事件溯源以业务事件作为权威记录，CQRS分离读写模型，三者有关联而不等同。历史税率、汇率等维度必须选择版本或时间语义；恰好一次处理不会替你选择正确税率。

第13章最后把演化组织成回填→追赶→切换。旧视图持续维护，新视图在独立空间验证，切换后保留实际可用的退路。若旧格式已无法解释新数据、历史被清理或错误输出已触发现实动作，改回路由就不能完成回退。可重放依赖输入、顺序、代码及外部依赖仍可恢复；选择延长保留期时，还应沿数据责任路线检查用途与删除要求。

这条路线中的失败检查很具体：在旧版读改写、发布通知先到、快照和日志错位、旧视图停止维护四个位置各放一次中断，观察究竟丢了字段、记录、可见性还是回退能力。它们分别需要相应契约，不能靠一个“零停机迁移”标签解决。

05端到端正确性：8→9→10→12→13

第8章 → 第9章 → 第10章 → 第12章 → 第13章。

从一次“提交成功，但回复丢失”开始。第8章把消息ID、业务修改与结果纳入同一本地事务，允许重投而不重复数据库效果。第9章提醒我们，重复消息和旧持有者是两种威胁：稳定ID识别同一操作，隔离令牌拒绝陈旧授权，两者互不替代。第10章的共识日志可以可靠决定顺序，但若同一次意图重试时换了ID，日志仍可能正确地记录两次扣款。

第12章要求沿四层检查恰好一次：输入位点、内部状态、输出记录、外部副作用。检查点若恢复到不匹配的状态和位点，会漏算或重复计算；Kafka事务输出也不自动包含应用自行修改的外部数据库。邮件、支付等效果必须由接收方承担相应去重或提交责任。准确说法是“在这些输入与恢复条件下，这个范围内的效果等价于一次成功处理”，不是代码只运行了一次。

第13章将请求身份从意图产生端传到最终效果。相同参数可能是两次合法支付，不能无条件以表单内容哈希代替请求ID。多分片支付进一步说明：记得见过请求还不够，还要记得未完成的输出。批准、预留、待发责任和分录身份必须可以恢复；重启时仅跳过已见ID可能永久漏掉手续费或出账分录。

请把局部事务去重和三分片支付当作不同模型。前者的11元教学事务共同更新两个账户；后者的100元初始余额、30元收款与1元手续费是另一组假设，先预留31，再形成69＋30＋1的最终结果。三分片模型要求目的账户可接受入账；中途任意跨账户读取不保证总和为100。这里的最终完整性既不承诺即时原子可见，也不包含所有银行拒付与补偿规则。

最后读审计：比较应有与已应用分录时，要固定共同事件边界或显式计入在途状态。同一错误代码重算两次得到相同结果，仍可能一直算错；独立不变量与来源检查提供的是另一种证据。

06数据责任：1→14，并回看12—13

第1章 → 第14章，再回看第12章保留与重放、历史与删除、第13章重处理和审计来源。

第1章把保存数据的成本从存储账单扩展到泄露、追踪、纠正与删除责任。第14章进一步追问用途及后果：预测会改变机会分配，决策又会影响后续训练数据；删除敏感字段不能保证消除代理变量，群体概率也不能直接判定某个人。作者的价值判断、历史案例与已取得的实证材料，需要分别阅读。

这与前面强调“保留输入，便于重算”存在真实取舍。第12章说明保留期限制恢复期限，日志压缩合并可能只保留当前状态，墓碑过早清理会使离线消费者错过删除。第13章要求重建具有来源与版本，却没有要求所有个人历史永久保留。确定可重算范围以后，应相应限定未来可恢复的内容；不能一边删除必要输入，一边继续承诺恢复任意历史输出。

笔记整合的假设场景：搜索改进只需要短期点击统计。先限定字段、用途和保留期限；需要执行删除时，沿权威库→日志／快照→分析表→客户端副本查找已有表示，再检查旧快照恢复和新版视图回填会不会把它重新带回。删除标记必须传播到应处理它的消费者，已越过保留边界的离线设备可能需要重新初始化，而非盲目从旧位点续读。具体实现随系统而异，这里给出的是应核对的数据路径。

同一场景还说明为什么“追加删除事件”和“销毁密钥”不自动等于完成所有删除义务：旧明文、派生文件、备份和密钥副本仍可能存在，训练样本移除也不自动证明既有模型影响被消除。原书提出了这些工程张力；本笔记没有给出通用机器遗忘算法或完整法律合规方案。

法律口径统一参见第1章的用途／删除／跨境限定与第14章的同意、用途与最小化：GDPR约束不相容的进一步处理，并非一律禁止新用途；同意不是唯一处理依据，删除权也有条件与例外。第14章德国定价案例仅取得作者摘要，不把市场利润率变化扩大成算法内部学习过程的已证实机制。

07关键术语：按作用域理解同一个词

术语以原书Glossary（印刷603—608）及对应正文校对。Glossary本身说明定义是简写；下列边界按章节展开，不把一个短定义当作完整协议。

英文／本站译法 统一含义与入口
operational / analytical，运营型／分析型 前者支持日常业务，不指运维监控；OLTP／OLAP按访问模式区分。1章
system of record / derived data，权威记录系统／派生数据 权威是事实接受与纠正的角色；派生可重建依赖输入与转换条件。1章
latency / response time / throughput，延迟／响应时间／吞吐量 说明计时边界和单位；本书的latency与业界宽泛用法有差别。2章
percentile / tail latency，分位数／尾延迟 说明样本、窗口和取秩约定，不能平均机器p99得到整体p99。2章
fault / failure，故障／失效 部件问题与服务未兑现承诺分开；容错有明确故障范围。2章
scalability / elasticity，可扩展性／弹性 承载增长与动态调整资源分别讨论；增加机器不自动拆散热点。2章
backpressure，背压 接收方跟不上时减慢发送；缓冲和背压都不创造处理容量。2章、12章
normalization / denormalization，规范化／反规范化 减少事实冗余与有意预存冗余；后者增加维护责任。3章
materialized view，物化视图 提前计算并保存读取结果；新鲜度取决于更新路径。4章、13章
model / query API / storage，模型／查询接口／存储 数据关系、请求表达与物理布局三个层次；GraphQL不等于图数据库。3章
log / WAL，日志／预写日志 存储、复制、事件日志职责不同；WAL保存恢复依据，不记录全部业务意图。4章、6章
compaction / compression，压缩合并／压缩 前者清理覆盖版本并组织文件，后者减少编码字节；压缩合并不保留所有历史。4章、12章
serialization / serializability，序列化或编码／可串行化 数据表示与事务隔离两个问题。5章、8章
backward / forward compatibility，向后／向前兼容 新读旧／旧读新；读改写无损及语义兼容另行判断。5章
schema，模式 这里主要指字段与类型约定；writer／reader schema及历史版本需可定位。5章
durable execution，持久化执行 已记录完成的活动可复用结果；未确认完成的活动及外部效果可能重试。5章
replication / sharding / network partition，复制／分片／网络分区 同数据多份／逻辑数据拆分／网络通信故障。7章、9章
leader / follower / replica，主节点／从节点／副本 属于指定复制范围；单主不消除读改写丢失更新。6章
failover / fencing，故障切换／隔离陈旧授权 选出接管者和资源拒绝旧操作是不同职责。6章、9章
quorum / majority，法定人数／多数派 法定人数不总等于多数派；交集不是完整一致性协议。6章
happens-before / concurrency，先发生关系／并发 无因果先后即并发，不要求墙钟同时；向量保留已知来源进度。6章
local-first / CRDT，本地优先／无冲突复制数据类型 设备参与持久状态与同步；收敛不自动满足所有业务不变量。6章、业务约束
rebalance / skew / hot key，再平衡／倾斜／热键 数据移动、负载不均、单键热点；与clock skew的时钟偏差分开。7章
atomicity / isolation / durability，原子性／隔离性／持久性 整体提交、并发干扰、确认后保存分别解释；原子操作另有不可分割效果语境。8章
snapshot isolation / MVCC，快照隔离／多版本并发控制 隔离保证与实现机制有别；MVCC并非只能实现一种隔离级别。8章
read skew / lost update / write skew，读偏斜／丢失更新／写偏斜 跨时点拼读／覆盖他人修改／不同记录共同破坏规则。8章、更新、偏斜
2PL / 2PC，两阶段锁／两阶段提交 隔离算法与原子提交协议，不以“两个阶段”互换。8章、提交
timeout / lease / fencing token，超时／租约／隔离令牌 怀疑故障、限时授权与资源端拒绝旧代次分别处理。9章、令牌
monotonic / time-of-day clock，单调／墙上时钟 间隔与时间点用途不同；单调钟不可直接跨机器比较。9章
safety / liveness，安全性／活性 不发生坏事／最终取得进展；此处安全性不是信息安全。9章
linearizability / strict serializability，线性一致性／严格可串行化 操作实时顺序／完整事务串行解释加实时顺序。10章
consensus / atomic commitment，共识／原子提交 共同决定与事务全员准备条件分别解释。10章
total / partial order，全序／偏序 任意两项能否比较；排序不等于已经知道所有竞争请求。10章
deterministic，确定性的 相同输入和状态产生相同结果，外部时间、随机值与维度须纳入恢复条件。9章
bounded / unbounded，有界／无界 数据流是否有可到达的终点，不要求预知精确大小；网络模型中的有界另指延迟等上限。11章、9章
shuffle / join，重分布／连接 让相关记录相遇／组合记录；连接不是网络连接，shuffle不一律意味着排序。11章
CDC / event sourcing / CQRS，变更数据捕获／事件溯源／命令查询职责分离 行变化、权威事件和读写模型划分，三者不互为必要条件。12章
offset / checkpoint，消费位点／检查点 本书消费例子以“下一条位置”为约定；恢复切面还须包含对应状态与所需输出责任。12章、检查点
event time / processing time / watermark，事件时间／处理时间／水位线 事件发生、系统处理与进度假设；水位线不证明所有旧事件绝不会再来。12章
exactly-once / idempotence，恰好一次语义／幂等性 效果等价于一次／重复操作效果不增；都须说明保护范围和恢复条件。12章
timeliness / integrity，及时性／完整性 状态足够新／无丢失重复损坏且派生与不变量正确；完整性不只是字段齐全。13章
unbundling / federation，拆分数据库／联邦数据库 写传播职责组合／读取侧统一查询；前者不是分片，后者不是微服务的同义词。13章
purpose limitation / data minimization，用途限制／数据最小化 为何处理与需要哪些数据；保留期限另行决定。14章

12跨书补充与阅读后的应用

以下是跨书阅读补充，不归为DDIA两位作者的章节内容，也不把其他书的术语强行换成本书定义。

  • George Fairbanks《Just Enough Software Architecture》：第3章风险驱动方法。可与DDIA的负载与测量配合：先说明当前最重要的技术不确定性，再决定需要多深的模型或验证。风险驱动方法不是数据库一致性协议。
  • Neal Ford、Mark Richards、Pramod Sadalage、Zhamak Dehghani《Software Architecture: The Hard Parts》：数据所有权与事务、八种Saga与补偿、契约兼容。它们补充服务和团队边界的权衡；Saga补偿是新的业务动作，不等于DDIA第8章数据库回滚，也不把第13章日志支付自动归为一个完整Saga实现。
  • Titus Winters、Tom Manshreck、Hyrum Wright编《Software Engineering at Google》：第2章团队协作。可与DDIA的人的因素与可靠性相互参照，理解为什么系统运行依赖团队沟通与可学习的事故处理；它不替代数据系统的故障模型。
