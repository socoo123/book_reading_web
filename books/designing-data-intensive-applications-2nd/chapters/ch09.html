第 9 章｜分布式系统的困难

The Trouble with Distributed Systems · 在网络、时钟和进程的不确定性中，守住正确性的边界

一次写入超时，数据库可能没有收到请求，也可能已经提交，只是成功响应没有回来。一个节点还能运行代码，并不证明它仍有权作为主节点写入。机器上的时间精确到纳秒，也不意味着两台机器能据此正确排列相邻事件。这些不是少见的接口瑕疵，而是分布式系统必须正面处理的知识边界。

01部分失败：系统还在工作，却不知道哪一步完成了

部分失败（partial failure）指系统的一些部分发生故障，其他部分仍继续运行。与整个进程一起终止不同，客户端、服务器、数据库和网络各自拥有生命周期；一方停止，其他参与者不会同步停止，也不会自动获得一份准确的事故说明。因此，“这次操作失败了”常常不是足够精确的状态描述。

原书从单机抽象解释这种差别。程序通常可以依赖 CPU 指令、内存和磁盘所提供的相对稳定契约；内部严重错误最好被转换成明显崩溃，而不是悄悄返回错误结果。但这是方便推理的抽象，不是“单机绝对只有全好、全坏”这条定律。原书自己也指出静默数据损坏和 CPU 错误；单机上的线程调度、外部输入同样会带来非确定性。分布式场景的变化，是独立失效和通信不确定性成为无法绕开的常态。

本书主要讨论无共享架构：各机器有自己的内存和存储，必须通过网络才能知道别人做了什么。即便所有节点都使用同一个对象存储，它们与该服务之间仍隔着网络。共享服务名称并不等于共享一个可以原子读取的内存变量。

按照原书图9-1，一次没有得到响应的请求至少可能经历六条路径：请求丢失；请求仍在排队；远端崩溃；远端暂时暂停；远端已经执行但响应丢失；远端已经执行但响应还在排队。最后两种和前两种，对客户端呈现的现象可以完全一样：到此刻仍没有响应。 单凭沉默，无法区分“没有发生”和“已经发生但我不知道”。

笔记假设：客户端请求把计数器加一，等待一秒后超时。如果原请求丢了，重试能补上工作；如果服务端已经加一，重试又可能多加一次；如果原请求只是在队列里，两次请求还可能先后执行。改成等待十秒，只改变发生歧义的概率，没有从逻辑上消除歧义。需要的是稳定请求 ID、结果查询或幂等处理等应用协议，第8章的同事务去重就是一条解决路径。

容错也因此不只是“有备用机器”。它要求系统在参与者看到不同事实时仍有一致的行为约束。代价是更多协议；收益则是一个节点维护、重启或故障时，其余部分仍可服务。滚动升级正利用这种能力：允许局部中断，避免把局部中断放大为全站停机。

02TCP 的可靠性，停在应用结果之前

TCP 提供有序字节流，会检测并重传丢失的数据段、处理乱序和重复，并用校验和检测部分传输损坏。它还控制发送速度：流量控制避免压垮接收端，拥塞控制响应网络容量；背压是处理速度不足时向上游传递压力的更一般概念。它们有关联，但不是三个完全相同的术语。

沿一段数据走一遍，就能看见这份可靠性的边界。应用调用 socket 写入，通常先把字节放进本机操作系统的发送缓冲区。TCP 根据窗口和拥塞状态发包；经过交换机、路由器后，接收端内核把字节放入接收缓冲区并发送确认。应用随后才可能读取、解析、执行请求，最后生成业务响应。写入本地 socket 成功、远端 TCP 确认、业务操作提交，是三个不同的事件。

TCP 的 ACK 证明的是对端传输层接收了相应字节，不证明应用已经执行，也不证明数据已持久化。远端可以在 ACK 之后、应用读取之前崩溃；也可以在数据库提交之后、响应发出之前崩溃。客户端仅观察到连接错误时，这两种历史都可能成立。

TCP 重传也不能把断开的网线接好。它等待确认，超时后重传，继续失败则最终向应用报告错误。连接上的去重依据属于这条连接；应用建立新连接后重新发送同一业务请求，接收应用可能再次执行。传输层没有自动识别“这是上次那笔转账”的业务身份。

因此，应用需要一个明确的成功响应，其语义应说明成功到哪一层：只是接收、加入队列，还是已经持久提交。收到这种响应能增加确定性；没有收到仍可能结果未知。服务端还可能在客户端超时后执行排队请求，所以客户端取消等待也不等于远端取消执行。取消本身通常是另一条可能失败的消息，需要服务端协议配合。

TCP 依然极有价值：它替应用处理了分段、重传、连接复用和有序交付。但字节流没有天然的消息边界，上层还需长度头、分隔符或其他帧格式；一次读取也不保证恰好得到一个完整请求。原书指出，许多关于结果不确定性的结论同样适用于 QUIC 等传输协议。更换传输层不会自动赋予业务“恰好一次执行”的承诺。

03故障检测：获得的是可采取行动的怀疑

负载均衡器要停止向不可服务的节点分配请求；单主复制要在主节点失效后进行故障切换。两者都需要故障检测（failure detection），但“检测器宣布失效”和“远端在物理上已经停止”不是同一件事。

有时能取得快速反馈。目标端口没有监听进程，建立 TCP 连接时可能收到 RST；连接的有序关闭可通过 FIN 表达。操作系统仍在运行时，监控脚本可以报告应用进程退出；能访问交换机管理接口时，可以查看链路状态；路由器也可能返回 ICMP 不可达。这些信号各自说明特定层面的问题，不能统一理解为“那台机器及其全部在途操作已经消失”。原书和旧稿把 RST、FIN 并列在端口无监听例子里，读时应保留二者的区别。

而且不能依赖每次故障都附带通知。机器断电可能来不及报告；管理接口也可能不可达；路由器无法凭空知道远端应用状态。没有明确响应时，常见做法仍是等待、重试，再根据超时将节点标记为疑似失效。这是推动恢复的策略，不是取得了远端死亡证明。

原书保留了一批真实研究和事故：某中型数据中心的研究记录约每月12次网络故障；GitHub 的交换机升级问题曾使数据包出现超过一分钟的延迟；有网卡只在一个方向丢包；A能联系B、B能联系C，却不代表A能联系C。这里按原书转述这些历史案例，不把特定部署的故障频率当成当今所有云的概率模型。

网络分区（network partition）是部分节点之间无法通信，与第7章的数据分片不同；它也未必把网络整齐地切成两个各自完全连通的区域。非对称故障、部分路径失效更加难察觉。能收到对方心跳，不保证对方能收到自己的写入；一个节点的“在线”状态也可能因观察者不同而不同。

处理故障不一定要求维持全部可用性。对于容许短暂停机的系统，明确返回错误、保护已有状态、网络恢复后重新工作，可能已经满足目标。真正危险的是没有定义故障路径：短暂中断引发永久死锁，或者节点各自接管后产生不能恢复的数据冲突。测试的对象应包含故障期间和恢复之后，而不仅是正常时的健康检查。

04超时为什么没有万能值：排队与误判会互相放大

假设一个理想系统保证每个数据包要么在 d 时间内到达，要么丢失；健康节点处理请求最多需要 r。那么一次成功往返应在 2d + r 内完成。笔记算例：若单程上界为20毫秒、处理上界为10毫秒，50毫秒就是该模型中的往返上界。超过它说明网络或节点没有满足成功路径条件，但仍不能据此断言请求从未执行。

普通数据中心通常没有这两个硬上界。网络尽力快速交付，服务器尽力及时处理，却没有承诺任何消息、任何调度都必在某个时间内完成。这里的无界延迟指没有算法可以依赖的已知有限上限，并非断言现实中一个包真的要飞行无限久。平均延迟很低、99.9%请求都很快，都不能充当所有执行的硬上界。

原书图9-2显示多个输入端口同时向一个输出端口发送数据：输出只能按链路速率逐个发送，其余包进入队列。队列满了即使设备没有坏也会丢包，TCP 重传又增加了等待。请求还可能在另外几处排队：本机 TCP 发送缓冲区；目标操作系统或应用线程池；虚拟机被暂停时的宿主机缓冲区；CPU 调度队列。把所有慢请求都归咎于“网络线路慢”，就容易错过真正瓶颈。

笔记假设：一个服务每秒最多处理1000个请求，短时持续到达1200个，每秒就净增加200个积压。两秒后约有400个请求等待；即便新到达率随后降到1000，系统也没有多余能力消除旧积压。这个简化计算忽略处理时间差异，却说明利用率接近极限时，几乎没有余量吸收突发。公有云里的吵闹邻居会进一步改变共享 CPU、网卡和链路上的等待。

短超时可以更早触发接管，却可能把过载造成的慢响应误判为死亡。原节点仍在发邮件，新节点又接手同一任务，就可能重复发送；原节点的工作被转移后，其他节点更忙，更多健康节点超时，形成级联失效。长超时减少误判，但真正失效时用户等待更久。这个取舍同时影响正确性责任和恢复速度，不能只按期望响应时间乘一个常数来决定。

原书建议长期、跨机器测量延迟分布，再结合业务后果选阈值。Phi Accrual 故障检测器进一步依据历史心跳间隔形成连续的怀疑程度，让应用按容忍程度决定何时行动；TCP 重传超时也会根据测量调整。自适应能改善经验决策，但过去的分布不会成为未来延迟的证明，系统仍需容忍误判。

UDP 不自动重传和提供 TCP 式流量控制，适合一些“迟到等于无用”的场景。原书以语音通话说明：错过播放时间的数据，不如留短暂静音后继续，用户可以请求对方重说。但交换机排队和 CPU 调度仍在；基于 UDP 的上层协议也可以自行重传、拥塞控制。不能从“使用 UDP”直接推出低延迟保证。

05网络延迟是资源分配的取舍，不是不可改变的天性

原书拿传统固定电话网作对照。建立电路时，沿途为通话预留固定带宽，每一跳按约定时间槽转发。在其介绍的 ISDN 示例中，每秒4000帧、每帧给通话16 bit，于是每250微秒有16 bit可用，合计每方向64 kbit/s。关键不是这个历史数字，而是下一跳的容量已被事先留出，不必临时与任意突发流量争抢。

这种时间模型中的同步，表示存在已知时间上界，不是应用采用同步函数调用。TCP 连接也不是预留电路：它维护传输状态，却通常没有向每个路由节点购买独占时隙。连接空闲时几乎不占传输带宽，发送时则竞争当前可用容量。

分组交换适合网页、邮件、文件等突发负载。若为一次文件传输预留很低带宽，有空闲资源也用不上；预留过高则可能因为无法承诺容量而拒绝建立电路。动态共享允许当前活跃的传输利用更多剩余容量，以提高利用率，代价是等待时长随竞争变化。

原书用一条能承载一万路通话的线路解释这个权衡：固定分配下，只有一个通话也只拿一个槽位；动态分配下，一个发送者可以暂时利用空闲容量，但大家同时活跃时就会排队。CPU 共享也一样，线程轮流使用核心提高了利用率，却使调度时间不再固定。云平台多租户并不是把同一份硬件凭空变大，而是在不同使用峰值之间共享资源。

如果确有需要，可以结合专用硬件、资源预留、准入控制、优先级和调度，提供更强的时延约束。原书还提到 ATM、InfiniBand、QoS 和 L4S 等不同路线。它们各自改善某些环节，不能仅凭协议名称推出端到端时延已经有界；带统计概率的延迟目标，也不同于无条件的硬上限。

旧稿沿原书将某些 QoS 机制概括为“多租户数据中心和公网未启用”，范围过宽。这里采用可验证的工程边界：除非部署和服务契约明确给出适用条件及端到端上界，否则应用不能因基础设施使用了 QoS 就据此证明超时判定准确。 延迟可预测性能够购买，但要付出资源余量、准入限制和管理成本；多数业务选择另一种成本组合。

06墙上时钟回答几点，单调时钟回答经过多久

应用用“时间”回答的是两类问题。文章什么时候发布、每天几点提醒，是时间点；请求等了多久、执行用了多少毫秒，是时间间隔。两者需要不同的时钟语义。

墙上时钟（time-of-day clock）返回日历意义的时间，例如 Linux 的 CLOCK_REALTIME 和 Java 的 System.currentTimeMillis()。它通常被校准到 UTC；这使不同机器的读数具有共同参照，但不意味着它们没有误差。管理员校时、NTP 调整或闰秒处理可能造成不连续跳变。

单调时钟（monotonic clock）适合测量间隔，例如 Java 的 System.nanoTime()。使用方法是同一时钟先读一次、工作后再读一次，取差值；绝对起点通常没有业务意义，更不能把A机器的单调读数直接减去B机器的读数。共同的单位不是共同的原点。

long started = System.nanoTime();
doWork();
long elapsedNanos = System.nanoTime() - started;
double elapsedMillis = elapsedNanos / 1_000_000.0;

这段笔记示例测的是调用间的经过时间，不是线程消耗的 CPU 时间，也不是其他节点的时间。它能避开墙上时钟突跳导致的负耗时，却不会让操作本身更快，也不承诺计时器毫无频率误差。操作系统可能通过渐调走时速率来校准；Linux 的单调钟保证连续调用不后退，但相邻读数可以相同，并非每次调用都严格增长。

还有一个容易遗漏的 API 差别。按 Linux man-pages 6.19，CLOCK_MONOTONIC不计系统挂起期间的时间，CLOCK_BOOTTIME则计入。线程因普通调度或 GC 没有运行，不等同整台系统进入挂起；选择超时钟时应明确要不要包含休眠。不能因为两者都叫单调钟，就假定所有平台和所有暂停都按同一种方式计时。

原书／旧稿限定修正：印刷359页将夏令时列为墙上时钟跳变原因；对当地民用时间显示而言成立，但 CLOCK_REALTIME这类 Unix 时间戳不因切换显示时区或夏令时而自动增减一小时。UTC 时间戳与本地时间转换应分层理解。旧稿“跨机比较用墙上时钟”也不应被读成排序铁律：跨机记录日历时刻可以用它，跨机证明因果先后还需要误差边界或专门协议。

07时钟同步：小数位很多，不代表误差很小

每台机器通常以石英振荡器计时。振荡频率随温度和设备而变化，因此本地时钟会漂移；同步服务只能周期性纠正。时钟偏差是某时刻两只钟读数的差，漂移率是走时快慢的差，分辨率则是读数最小步进。能输出纳秒数字，只说明表示得细，不说明接近真实 UTC 的程度。

原书援引早期 Spanner 论文中的200 ppm漂移假设。ppm是百万分之一：200 / 1,000,000 × 30秒 = 0.006秒，即30秒可积累6毫秒；一天则是17.28秒。这只是该速率上界下的漂移项，不是整个同步系统误差，更不是每台机器每天必然偏17秒。网络测量误差、时间源误差还要另计。

NTP 通过与时间服务器交换消息估计本地偏移。消息往返本身会排队，两个方向也未必耗时相同；客户端无法准确知道所有未知等待发生在哪一边。时间服务器还可能错误、失联或被防火墙阻断。即便本机 NTP 进程活着，也不证明它仍在跟踪可信时间源。多时间源和异常值剔除可降低单个错误来源的影响，但仍要检查同步状态与估计误差。

原书中的公网35毫秒实验、分钟级同步误差以及约7毫秒的历史 Spanner 数值，都有特定年代和环境。它们说明误差有数量级，不是今天产品的固定 SLA。高精度同步可以采用 PTP、硬件时间戳、GPS 或原子钟，并配合监控；GPS 也可能受干扰。若算法依赖最大偏差，监控阈值必须来自该算法的假设，不能照旧稿随意采用“超过50毫秒五分钟就告警”的通用数值。

闰秒是另一种边界：UTC 调整和软件对一天长度的假设可能冲突。平滑调整（smearing）把变化摊到较长时间，减少突跳，但混用不同平滑策略也会造成时钟不一致。原书印刷361页说“2035起不再使用闰秒” → BIPM 2022年第4号决议的精确表述是，在2035年或之前提高 UT1−UTC 的允许上限，并制定实施方案 → 不宜进一步宣称“到2035所有旧时间问题自动消失”。历史数据、不同时间尺度和校时故障依然存在。

错误时钟尤其隐蔽：服务可能仍正常响应，只有依赖时间戳比较的写入悄悄消失。对于确实依赖同步的系统，应把偏移和不确定度作为运行条件；超出假设时停止相关职责，比继续产出看似正常但没有依据的结果更重要。

08LWW 反例：发生得更晚，时间戳却更小

第6章介绍最后写入者胜出（LWW）：按时间戳选取最大值，将其他版本舍弃。问题是，“最大时间戳”只有在其生成规则满足所需顺序时，才能代表“业务上的后一次写入”。原书图9-3用一个只有数毫秒偏差的例子说明，这个前提很容易失效。

客户端A在节点1写 x=1，该节点给写入标记 42.004秒；更新先复制到节点3。客户端B随后在节点3读取这个值并执行加一，写成 x=2，但节点3的本地时钟只读到 42.003秒。B依赖A的结果，因此明确在因果上后于A；两个时间戳却反着排。

当两次写最终都到达节点2，它按 LWW 比较：42.004 > 42.003，于是保留 x=1，丢弃 x=2。无论节点2先收到哪一个，按同一规则归并的最终结果都相同。系统甚至可以成功收敛到所有副本都是1，同时丢掉业务期望保留的加一。收敛与保存因果上更新的结果，是两个不同目标。

这个例子不是两个用户互不知情地同时修改。它更严重的地方在于，B已经知道A，却仍被墙上时钟排序抹掉。若某客户端的钟突然走到未来，留下很大的时间戳，后续正常时间戳还可能很长时间都不能覆盖它。若两次写时间戳相同，增加随机决胜字段能给出确定结果，却不能恢复尚未记录的因果信息。

一种改善是读取已有版本，使新版本号一定大于所依赖的旧版本号，即使它超过当前物理时间。这会改变协调、读开销及版本生成规则；多个真正并发的修改仍需要解决。逻辑时钟通过计数器和消息依赖表达顺序，版本向量则进一步帮助识别并发，下一章将细讲这些机制。

不能把结论扩大为“所有物理时钟方法都不可能正确”。本节反对的是不带可靠误差边界和等待规则，直接用本机时钟读数证明先后。下一节的 TrueTime 正是通过显式暴露不确定度、承担等待成本来改变前提。同步本身改善读数，协议才负责把读数转化成保证。

09用时间区间推理：TrueTime 为什么需要提交等待

如果只知道时钟与真实时间最多相差100毫秒，那么一个读数10.4秒应被理解为 [10.3,10.5]，而不是精确的点。原书先用统计置信区间帮助建立直觉，再介绍 TrueTime、ClockBound 这种显式返回不确定范围的 API。两者不能混为一谈：只有“95%概率在内”的统计区间，不足以支持要求始终成立的安全性；TrueTime 的推理依赖其运行假设下的区间包含保证。

设事件A的区间为 [A最早,A最晚]，B为 [B最早,B最晚]。如果 A最晚 < B最早，就能断定B晚于A。若区间重叠，只能说这两次测量不足以区分；真实事件仍有先后，不能把“无法判断”写成“必然同时”。区间越窄，越容易分清，代价通常是更精心的授时基础设施。

这个能力与第8章的MVCC有关。快照读取需要一个跨分片一致的观察时点；若B依赖A，却给B更小的版本时间戳，一个时间戳截面就可能包含B而排除A，形成因果上不可能的快照。单机可以用统一计数器处理版本顺序，跨数据中心则要考虑计数器协调的开销。

Spanner 不是把系统时间直接塞进事务 ID 就结束。按原论文和官方文档，它组合复制、事务协议、版本存储与 TrueTime；协调者收到提交请求后，选择不小于当时 TT.now().latest 的提交时间戳 s，再通过提交等待确保真实时间已经越过 s，可用 TT.now().earliest > s 表达。此后才让客户端观察到该事务已完成。这两条规则共同支撑后续事务的实时先后约束。

笔记算例：若先前已选择 s=10.500秒，当前 TrueTime 区间是 [10.480,10.520]，则还不能宣布等待条件满足，因为真实时间可能仍在10.480。后来区间变成 [10.501,10.541]，下界已超过10.500，才满足该条件。它不是“总睡7毫秒”，也不是任意等待一个以前测得的固定区间长度；应以协议条件和当前误差范围判断。复制等其他工作还可以与部分等待重叠。

原书用“不重叠区间”解释提交等待的直觉，但旧稿把它进一步缩成固定等待和“原子钟主要为性能服务”，容易省略契约。可靠的误差界是正确性条件，精确时钟帮助缩短该界、降低等待。若时钟不再能给出可信区间，不能仅为保持吞吐而继续按旧范围工作。

本节也不是完整的 Spanner 实现说明。带时间戳的全局快照仍需确保相应版本已经可读、事务提交状态明确，并处理分片和副本进度。时间 API 提供必要的顺序依据，不单独代替事务或共识。

10租约检查通过后，线程仍可能暂停

租约（lease）可以理解为带期限的授权。节点取得租约后，在约定时间内承担某种独占职责，并在到期前续约；如果它崩溃而无法主动释放，期限结束后其他节点可以接管。这解决了“死进程永远占锁”的活性问题，却引出了“旧进程是否知道自己已失权”的问题。

原书的单主分片例子先检查租约剩余时间，不足十秒则续约，再确认租约有效并处理请求。第一处风险是，过期时间由另一台机器按其墙上时钟计算，客户端却拿本地时钟比较；两只钟有偏差，判断就可能错。但即便把协议改为以本地单调时钟计量期限，仍有第二处风险：检查和实际执行之间不是不可分割的一步。

客户端A：检查租约有效，剩余约10秒
客户端A：在检查之后暂停15秒
租约服务：原期限届满，允许B取得新租约
客户端B：以新持有者身份开始工作
客户端A：恢复，从刚才下一条指令继续写入

这是按原书15秒暂停展开的示意时序。A恢复时并没有从函数头重来；它保存的“检查通过”结果仍在寄存器或内存中。把检查再往后挪一行，没有关闭间隙，因为暂停可以发生在最后一次检查之后。即使本机能完全避免暂停，写请求也可能在网络中停留到租约过期后才到达。

暂停有许多来源。GC 可能暂停应用线程；共享锁和队列争用让线程等待；操作系统或虚拟机调度可能长时间不给它 CPU；虚拟机迁移、挂起和终端设备休眠可以中断整个执行；同步磁盘 I/O、首次类加载和缺页换入也会暂停看似普通的代码。网络块设备又把磁盘等待接到了网络不确定性上。人为发送停止信号也可以制造同样情境。

这些来源中，有些会使本机时钟继续走，有些涉及平台的休眠计时语义，但共同点是：外部世界可以继续推进，而本地执行停留在旧认识上。 原书过去数分钟 GC 的案例说明机制确实出现过；不能把旧时长当成所有现代运行时的常态，也不能因为现代GC明显缩短停顿，就删掉协议中的暂停处理。

单机互斥锁不会因持有线程短暂停调度，就自动把同一把锁授给别人；租约则刻意允许期限结束后接管。因而不能把本地互斥锁的使用经验直接搬成“先拿分布式锁，再放心执行任意外部操作”。后续隔离令牌会把最后一道权限判断放到真正修改资源的位置。

11硬实时与低暂停优化：保证和改善要分开

暂停并非绝对不能约束。原书以安全气囊举例：检测到碰撞后，不能因为恰好发生 GC 而延迟展开。在硬实时系统中，超过截止时间本身就是失效，即便最终算出的结果正确。这不同于网页即时推送、实时大屏或第12章所说的持续流处理；后者常表示低延迟愿望，不必包含最坏响应时间保证。

要提供硬保证，整条软件栈都要合作。调度器提供受约束的 CPU 分配，库函数给出最坏执行时间，内存分配和回收工作量受控，I/O与外设也必须符合时间假设。只把应用线程优先级调高，而磁盘、虚拟化平台和远端服务仍无界等待，无法完成端到端证明。

这样的系统可能牺牲吞吐量和资源利用率，还会限制可用语言与工具。它追求的是按时完成，而不是平均每秒做最多工作。对普通服务端数据系统，全面购买这些条件通常不合算；于是协议需要在暂停出现时守住正确性，性能优化则降低暂停的频率和影响。

原书讨论几种 GC 缓解思路：减少不必要分配、复用对象、在适当场景使用堆外存储；若运行时能够配合，可以在回收前移走新流量、排空正在处理的请求，再把回收视为计划内短暂下线。另一条路线是在长期对象积累前轮流重启进程。这些方法各有内存和复杂性代价，尤其“GC前预告并排空”需要专门支持，不能假定所有运行时都有这个接口。

原书与旧稿的版本纠正：印刷370页把 CMS、G1、ZGC、Epsilon、Shenandoah并列为 Java 运行时提供的回收器 → OpenJDK 的 JEP 363明确 CMS 已从 JDK14移除，JEP 318则明确 Epsilon只分配、不回收，堆用尽会失败 → 这份名单不能作为2026年任意JDK的推荐配置。现代低暂停收集器能改善尾延迟，但不能据此宣称整个进程永不暂停。

换成没有追踪式 GC 的语言也只是移除一个来源。线程竞争、页错误、I/O、操作系统调度仍会存在。把问题只归结为“Java不好”，就遗漏了原书最重要的结论：容错协议需要承受暂停，优化工作负责让暂停更少、更短。

12多数派决定协议权力，不会让旧节点自动消失

假设节点A收得到所有消息，却发不出响应。它的进程可能健康，甚至能看到其他节点正在讨论将它移出；但它的抗议无法传出。再假设A暂停一分钟，其他节点已经完成接管；A恢复后，本地内存仍记录着“我是主节点”。活着是物理事实，有权写入是协议事实，两者不能混用。

很多协议用法定人数（quorum）减少对单个参与者的依赖：决定必须获得足够多节点支持。最常见的配置是过半数，三个节点需要两个、五个需要三个；少数节点失效时，其余节点仍可能构成可工作的多数派。此时，某节点不能仅凭“我还能执行代码”继续行使已经转移的权力。

多数派有一个重要数学性质：任意两个过半集合必相交。五个节点中，{A,B,C}与{C,D,E}至少共享C。但这不等于“系统只能存在一个多数集合”，更不自动保证两个决定不冲突。若C对互相冲突的候选者都投票，两个集合仍可能各自收齐票数。

原书／旧稿推理补足：印刷373页把“只有一个多数”作为安全直觉，旧稿进一步写成“过半自然避免脑裂” → 真正能推出的是多数集合不能互不相交 → 还必须有协议规则，要求交点节点不能作出冲突承诺，并在崩溃后记得自己已承诺的内容。跨轮选举还需代次及日志规则。下一章的共识协议将补齐这些条件。

失权节点什么时候得知结果，也不是多数投票可以解决的。它可能仍暂停，或处在收不到决定的分区里。因此“它必须让位”不能只实现成一条通知消息。我们需要让其后续操作即使到达资源，也没有破坏新状态的权限。多数派用于形成授权决定，隔离用于落实决定；中间少一层，可靠锁服务也可能被不可靠的使用方式绕过。

原书区分了两种独占目的：只是不想重复计算同一个输入文件，偶尔双执行的后果可能是多花资源；如果要防止两个客户端同时覆盖一个文件，后果就是数据损坏。选择锁机制前先弄清哪种后果需要避免，比先选一个产品名更有效。

13锁服务没有犯错，文件为什么仍会被写坏

原书图9-4沿用 HBase 曾遇到的真实问题：客户端A取得文件租约，然后长时间暂停；租约到期后B合法取得新租约并写入；A恢复，仍按旧控制流写同一文件。锁服务每次授予时都遵守规则，但存储服务不知道哪些请求属于已过期的授权，于是两代客户端的写入冲突。

正常路径本来是：取租约、读取最新文件、计算修改、写回、释放。笔记假设：文件保存计数10，A读到10并准备写11；A暂停后B接管，读取10并写12；A醒来把旧计算11写回。此时丢掉的不是一次网络包，而是B已经完成的业务变化。只记录“谁最近成功获得锁”，并没有约束真正的数据入口。

图9-5更进一步：A不必恢复，甚至可以永久崩溃。它在崩溃前已经发出一个写请求，消息被网络长时间延迟；B接管并完成新写以后，旧请求才到达存储。同样的损坏仍会出现。因此，关闭旧进程、断开旧机器网络或给旧机器断电，不能撤回早已离开发送者的在途请求。

如果受保护动作是发送不可撤回的外部指令，问题会更加明显。客户端本地确认租约、甚至同时询问锁服务，只要最终操作没有共享同一个不可分割的权限检查点，网络延迟仍可能把检查和使用分开。一个服务无法替另一个完全不配合的资源强加原子边界。

解决思路因此要改变：不再试图保证所有旧持有者都及时意识到失权，而是保证旧持有者即便继续行动，其陈旧操作也会被资源识别。这个方法叫隔离（fencing）。它对“礼貌地停止工作”的客户端仍有好处，但正确性不依赖旧客户端先收到通知并主动配合退出。

14隔离令牌：把最后一道检查放到资源端

锁服务每次授予新的租约时返回一个严格递增的隔离令牌（fencing token）。原书图9-6用33和34表示相邻两代授权。每次访问受保护资源时，客户端都携带自己的令牌；资源记住已经接受的最大代次，拒绝比它更小的请求。这不是身份认证令牌，而是用来识别旧授权的顺序编号。

完整交接需要五步。A取得33并进行操作；A暂停或失联，租约到期；B取得34；B先在资源上完成携带34的写入或推进代次的操作；之后A带33的任何迟到写都被拒绝。关键转折发生在第四步，资源成功记录34之后，而非锁服务刚把34返回给B的瞬间。

笔记伪代码：假设资源支持一个持久、原子的状态更新操作，且客户端诚实地使用授予的令牌。advance只推进代次，replace还写业务值；这不是可直接复制运行的完整锁服务。

apply(resource, token, operation):
    atomic_durable_update(resource):
        if token < resource.max_token:
            reject STALE_OWNER
        resource.max_token = token
        if operation.kind == "replace":
            resource.value = operation.value

新持有者：取得token → 成功advance(token) → 读取最新状态 → 计算并写入

检查、更新最大令牌、业务修改必须处在同一个原子边界，不能先读 max_token，隔一段时间再无条件写。否则33检查通过后暂停，34写入完成，33又继续写，正好重复原来的漏洞。保存代次还须满足约定的崩溃恢复保证；资源重启后忘记34，就可能重新接受33。

旧稿伪代码用了 token <= last_token → 若同一租约允许多次写，第二次携带相同令牌就会被拒绝 → 应拒绝严格较小的代次，允许同代次操作按资源本身的并发规则执行。旧稿又把检查、写值、保存令牌分成三个无原子说明的调用 → 存在交错窗口 → 上面明确把三者放入持久原子更新。若设计成“每次操作都取新令牌”，则是另一份协议，不能与每次租约分配一个令牌混写。

还要避免先读取陈旧业务状态、再以新令牌覆盖别人。B可以先用不改业务内容的推进操作建立隔离，再读取最新数据。若在B的屏障之前33仍被接受，这不违反“屏障之后拒绝旧代次”的性质；B必须从屏障后的状态继续，不能假定获得34那刻起所有资源早已同步知道。若要求更强的即时撤权，需额外的资源端校验协议。

令牌也不自动解决同一代次内部的乱序与重试。两个34请求若写不同业务值，仍可能先后颠倒；同一请求重发仍可能重复副作用。操作序号、条件版本和请求ID处理的是这些不同问题。被拒绝的33不能仅重试原请求；重新竞争新租约后，还须重新读状态并计算。

原书列出 Chubby sequencer、Kafka epoch 以及共识协议的 ballot、term 等类似代次思想，也提到 ZooKeeper、etcd、Hazelcast 的相关机制。应核对具体作用域、重启和删除重建规则，不能随便拿一个叫“版本”的字段就当永不回退的全局令牌。对支持 CAS 式条件写的单个存储，协调也可能直接建立在该存储上；S3 等对象存储的条件写是可用机制，但不会自动解释任意自定义令牌字段。

15隔离多副本：少数旧写可以存在，却不能成为胜出版本

原书图9-7把隔离扩展到无主、LWW的复制存储。客户端直接给多个副本发送写入，每个副本按版本比较决定是否接受。为了让新持有者的写始终压过旧持有者，可以把隔离代次放在版本的最高优先级，代次内部再按操作顺序比较。

这里用一个明确的笔记表示法：版本是二元组 (代次, 代内序号)，按字典序比较。(34,1)大于(33,999)，因为先比较34与33，只有代次相等才比较第二项。原图把代次放在数字的高位；若实现为整数位段，必须给低位规定范围并防止溢出。旧稿用小数拼接物理时间的写法容易掩盖这一条件，元组更清楚。

假设三个固定副本R1、R2、R3，写法定人数为2、读法定人数为2，读者从响应中选最大版本。B以34写入R1和R2成功，R3此时不可达。A的33迟到后，R1和R2拒绝它，R3却可能接受，因为R3还没有见过34。局部接受旧写，不等于系统最终选择旧写。

为什么读取能挡住旧值？任意两个副本的读集合，必与已经保存34的两副本写集合相交。交点仍保有新版本，读者比较后选择34；读修复或反熵再把这个值传播给落后的副本。这个推理依赖固定成员、成功写入足够副本、版本不丢失且不回退、按最大版本读取等条件；读单个落后副本就没有同样保证。第6章已经说明，单独的 r+w>n 不能代替完整协议。

这一方案也不是把所有外部副作用回滚了。若R3接受33时就向别处发送邮件，后来被34覆盖无法收回邮件；原书讨论的是可按版本归并的存储状态。跨多个独立服务使用同一令牌时，各服务都要完成自己的隔离建立，不能以其中一个成功推断所有资源都已就绪，更不能把代次一致当成跨服务原子事务。

书外讨论与旧稿修正：旧稿将2016年的 Redlock 争论写成“只依赖时钟同步”及“其作者承认只追求性能” → 实际反驳强调的是相对时间速率的有界误差，并继续主张互斥安全，双方对系统模型和资源条件存在分歧 → 本笔记不把争论压成产品口号。可以保留确定的设计问题：租约依赖哪些时序假设，资源如何处理迟到操作，令牌是否真正有序。选用共识锁服务也不能省略资源端协议。

16拜占庭故障：任意错误行为，不只指恶意攻击

前面的33客户端是“诚实但过时”的：它仍按协议携带过去取得的令牌，没有伪造34或更大数字。若节点可以任意编造消息、对不同人给出矛盾回答，单靠递增编号就无法防住。这样的任意故障行为称为拜占庭故障（Byzantine fault）。

“任意”描述的是外部行为，不要求行为主体有恶意。软件错误、内存或寄存器损坏，都可能使节点发送完全不符合协议的结果；攻击者也可能故意制造相同表现。旧稿“软件bug≠拜占庭”的标题错误：软件bug可以表现为拜占庭故障，真正的问题是多个副本是否同时受到相同bug影响。

原书保留两个应用背景。航空航天系统可能受到辐射导致的硬件数据损坏，需要硬件与软件共同容错；多方互不信任的系统，如某些区块链协议，不能默认所有参与者都会遵守规则。拜占庭容错要求协议在一定数量任意故障参与者存在时仍满足规定性质，通常付出更多通信、验证和副本成本。

本书多数服务端系统采用更弱的故障假设：节点可能崩溃、停顿或携带过时状态，但没有任意伪造协议消息。原书提到常见BFT协议需要超过三分之二节点正确，例如四个节点容忍一个任意故障；这个数量关系应随协议、网络模型和认证假设一起理解，不是所有带BFT标签系统的统一公式。

把相同软件复制四份，并不能保证只有一份会触发同一缺陷。相同输入可能令四份同时给出错误结果，共同漏洞也可能使多个副本一起被攻陷。独立实现可以减少某些共同缺陷，却又有开发和一致性成本。多租户隔离、认证、访问控制、加密等机制仍有各自责任，BFT不是替它们兜底的万能层。

普通系统也能防范较弱形式的错误：应用级校验和可以检测遗漏的传输或存储损坏，TLS的完整性保护帮助发现篡改或损坏，解析器检查长度和字段范围，时间同步客户端排除异常来源。这些措施不构成完整BFT，却能减少现实故障进入协议核心。公网客户端可能恶意时，通常让可信服务端验证权限和业务规则，而不是让每次表单提交都走拜占庭共识。

17系统模型：先声明允许发生什么，再讨论算法正确

系统模型把复杂现实缩成可推理的假设集合。它不需要描述每一种交换机或GC实现，只需说明消息能否丢失、延迟有没有上界、节点可否恢复、恢复后还记得什么。只有这些条件明确，“算法始终正确”才有具体含义。

时序模型 可以依赖的条件 需要警惕的误读
同步模型 网络延迟、进程暂停、时钟误差有已知上界 不是零延迟、完美时钟，也不是阻塞式API
部分同步模型 存在最终可恢复的良好时序条件，之前可能严重超界 不能只说“平时很快”，省略活性所需的最终恢复
异步模型 不以时间上界作推理依据 纯异步算法不能用“等太久”证明对方故障

原书先将部分同步直观地说成“大多数时候表现良好”，随后在活性讨论中补充最终恢复同步条件。形式化讨论常见的是：上界存在但起初未知，或已知上界在某个未知稳定时刻后才适用。这里按这个意义阅读，不把偶尔快一下当成任何协议都能完成的充分条件。真实运行中使用超时，不必意味着安全性证明也依赖该超时准确。

节点故障则是另一条维度。崩溃—停止模型让节点停止后永不回来；崩溃—恢复模型允许未知时间后重启，内存丢失，但约定的稳定存储保留。拜占庭模型允许任意行为。还要注意现实中的性能退化和部分功能失效：原书举例，网卡从千兆速率降到约1 Kb/s，或后台线程已死锁、健康检查线程却仍能响应。

这类情况称为慢故障、跛行节点或灰色故障。它比完全崩溃更难处理：一个低成本 /health 请求及时返回，不证明实际查询、复制日志或磁盘写入还能推进。测试和监控要针对服务职责，而不只针对进程是否存在。时序模型必须允许这样的长等待，业务恢复还需识别哪些工作失去进展。

原书认为，部分同步加崩溃恢复通常最贴近常见数据系统。它仍有重要省略：稳定存储究竟能承受哪些故障？如果节点重启后忘了已经投过的票，或丢掉已经确认保存的版本，法定人数交点就失去“记住历史”的意义。证明不能自动跨过磁盘被擦除这一模型边界。

因此工程实现还需决定假设被破坏时怎么办：停止参与、重新加入并同步、从其他副本恢复，或要求人工介入。抽象不是否认这些可能性，而是帮助明确哪些故障已经被协议覆盖，哪些需要另一套恢复过程。

18安全性与活性：不做错，和最终做成

判断一个隔离令牌服务，不必先看它有多少服务器。可以先写三项性质：不同的成功授权得到不同令牌；如果请求X已经结束、请求Y才开始，那么 tokenX < tokenY；在所需健康条件成立时，请求最终得到响应。前两项是安全性（safety），第三项是活性（liveness）。这里安全性不是防攻击的信息安全。

安全性一旦被破坏，存在一段有限历史可以证明问题：已经发出了相同令牌，或后开始的请求得到更小令牌。以后再给出正确数字，也不能抹掉此前的违规事实。对资源隔离而言，“记录34后又接受33”就是这样的有限反例；即使后来把文件修回来，协议曾允许旧授权覆盖新状态仍然成立。

活性关心最终进展。一个请求现在尚未返回，不足以证明它永远不返回；后面总可能恢复并完成。因此无条件的“永远等待”虽然容易避免返回错误结果，却不能算有用的正确服务。完整契约需要同时说明不允许发生的事和应当最终发生的事。

旧稿条件纠正：它把令牌单调性写成“X先于Y完成，则X令牌较小” → 原书印刷382页明确是“X完成在Y开始之前” → 两个请求如果时间区间重叠，返回次序可能受网络延迟影响，不能强加完成先后的数字关系。比如X先分配33但响应慢，Y分配34先返回，这不自动违反非重叠调用的顺序要求。下一章的线性一致性会继续使用调用／返回区间。

区分两种性质的实用价值是允许有条件的进展。网络严重分区时，协议可以停止授予新令牌以守住安全；多数派恢复通信、请求者仍运行、调度有足够机会时，再要求最终给出结果。安全性必须在声明模型的所有允许执行中保持；活性则明确依赖网络恢复、足够多节点存活等条件。

“在模型内”这几个字不能删掉。一个假定稳定存储不会丢失的证明，并没有声称所有磁盘都被擦除后仍能恢复原结果；一个非拜占庭协议也未保证任意伪造消息下正确。协议应尽可能使时序失常影响进度而不破坏数据，但必须诚实写出它依赖的存储、成员和故障假设。

原书把最终一致性中的最终收敛归入活性，很有启发：此刻副本不同不必立即违反收敛要求，长期不再有新写且通信恢复后仍不收敛才是问题。不过实际的一致性契约也可能附带“不读到凭空产生的值”等安全性质，不能因出现“最终”二字就忽略其他要求。

19形式化方法与故障注入：分别检查哪一层

并发把普通操作组合成大量历史：一条消息可以先到、后到、丢失，节点可以在某个持久化点前后崩溃。手工写几个正常示例很难覆盖关键交错。本章第二版新增的重要主线，是将数学推理与实现测试组合起来，而不是凭“线上运行很久没坏”认定协议正确。

形式化证明把算法、假设和性质写成精确对象，证明所有允许执行都满足要求。它能发现靠自然语言难以看出的缺口，但证明对象与部署实现仍有距离。若模型假定原子持久化，实现却拆成两个可能中断的调用，算法证明不会自动替实现补上原子性。

模型检测（model checking）系统探索模型的状态和转移，找到违反性质的执行轨迹。以本章租约例子为笔记假设，模型可以只保留两名客户端、一个资源、两个代次和“暂停／恢复／写入”等动作。检查器不需要模拟完整数据库，也可能发现33检查通过、34写入、33覆盖的短反例；这正是抽象的价值。

状态空间通常不能无限穷举。限制节点数、消息数或执行长度后全部通过，只证明这个有限模型和边界内没有找到反例；要外推到任意规模或长度，需要额外证明或正确的抽象论证。原书列出 TLA+、Gallina、FizzBee 等规范或形式化语言，但它们所在工具链的能力不同；TLA+配合TLC进行模型检测，与在证明助理中构造证明，不宜统称为同一种按钮操作。

原书提到 CockroachDB、TiDB、Kafka 使用模型规范，以及研究者借 TLA+ 揭示 Viewstamped Replication 文字描述歧义可能导致数据丢失。这里按原书保留案例，不声称本笔记已复现这些分析。模型和代码还可能随维护逐渐脱节，需要对应的评审、跟踪或实现插桩，确认真正运行的行为仍符合规范。

故障注入则直接运行实现，注入断网、进程停止、节点重启、磁盘异常等，观察服务与恢复行为。Jepsen提供故障编排和历史检查框架；Netflix推广了生产环境故障实验。真实环境可以暴露模型没有包含的依赖，却较难控制每条线程和每个包的精确时序，发现一次异常后也可能很难重现。

有故障动作还不够，必须有正确性判断标准。针对隔离，可以记录资源接受的代次历史，检查其是否回退；针对转账，可以检查已提交结果是否满足余额规则；针对活性，可以在停止注入故障、恢复足够条件后观察是否重新推进。只看“进程没崩”和“最后还能读数据”，可能漏掉中途丢失的已确认写入。

三类证据因此互补：证明帮助理解所有允许路径；模型检测让小模型中的奇怪路径更容易暴露；故障注入让真实实现接受环境考验。它们的结论各有范围，不能相互冒充，也不要求每个低风险个人工具都采用完整工业工具链。

20确定性模拟：把难以重现的故障变成可重放历史

确定性模拟测试（deterministic simulation testing，DST）在受控环境中运行实际系统代码，把网络、磁盘、时钟和调度等非确定性来源交给模拟器。模拟器随机选择大量交错来找问题，但给定同一初始状态、种子和执行环境，选择过程可以重放。因此“随机化探索”与“确定性重现”并不矛盾。

以本章隔离问题作笔记假设：模拟器安排A取得33、在发送前暂停，推进虚拟时间使租约到期，让B获得34并完成资源写，最后恢复A。检查器发现资源竟接受33，就保存这个操作序列；修复原子检查以后，再跑同一序列应变成拒绝33。模拟器还可改为延迟A已发出的包，而不暂停A，验证同一保护是否覆盖两条失败路径。

原书介绍三种实现位置。应用层从设计时就隔离环境依赖：FoundationDB的Flow让生产执行和确定性模拟共享代码，TigerBeetle将状态变化集中到事件循环，并替换时钟等原语。运行时层替换调度器和常见异步库，例如原书介绍的FrostDB方案和Rust的MadSim。机器层则通过定制虚拟化环境接管时钟、存储、网络等，Antithesis是其例子。它们不是必须叠加的三层，而是不同控制边界。

这里的“真实代码”也有范围：应用层模拟运行的是接入环境抽象的实际协议代码，操作系统、真实磁盘驱动和网络硬件可能由模型代替。它不能证明替身准确覆盖全部硬件行为。机器层覆盖更广，也更难把全部非确定性收束起来。方法选择取决于最需要暴露哪类错误。

FoundationDB官方说明提供一个有用的补充案例：随机挑一组节点，逐个阻塞其网络连接，再以随机顺序解除，称为 swizzle-clogging。这不是只有“全网断开／全部恢复”的整齐场景，而是在恢复过程中制造不对称和交错，特别有助于发现深层状态问题。其测试还使用环状键值关系作为事务不变量，说明故障模式和检查标准必须共同设计。

受控时间还允许加速测试。下一事件在虚拟时间30秒后发生时，模拟器可以直接推进，而不真的睡30秒；从某个状态分叉不同故障计划，可以探索更多路径。但“探索很多”仍不是“穷举全部”，没有失败也只形成对已测试范围的证据。

要可重放，必须控制所有影响结果的输入。真实随机数、墙上时钟、线程交错、哈希表遍历次序、资源耗尽等任何遗漏，都可能让相同种子得到不同执行。测试日志最好记录种子、构建版本、配置和失败轨迹；代码或环境已经变化时，只保留一个种子未必足以重放历史。原书在章末特别提醒哈希顺序和内存、栈限制，避免把“单线程运行”误当成完整确定性。

21从不确定性中提炼可以兑现的承诺

本章可以收成三道区分：没有收到响应，不等于没有执行；本地判断仍有效，不等于资源必须接受；在许多测试中通过，不等于已证明所有环境下正确。 网络、时钟和进程暂停分别让观察、排序和授权产生缺口，协议需要在明确假设内把这些缺口补上。

确定性是一条反复出现的帮助理解的线索。第3章的事件溯源从事件重建视图，第5章的持久化执行重放工作流决定，第6章的某些复制方式和第8章的串行过程，都要求相同记录导向相同状态。把不可预测的输入显式记录或交给协议排序，才能使重放和检查有意义；这仍不自动使外部邮件、支付等副作用恰好一次。

设计一个具体系统时，可以沿三个问题前进。第一，允许网络、进程、存储怎样失败？第二，即使这样失败，哪些性质必须始终保持，哪些进展可以暂缓？第三，有什么原子边界、协议规则和测试证据支持这些性质？如果答案只是“超时设得够大”“一般不会暂停”，说明核心依赖还没有被讲清。

原书最后提醒，能用单机或嵌入式存储完成的需求，通常值得先保留这个简单边界。分布式的收益不只在规模，还包括跨节点容错和地理就近服务；但坏配置和共同缺陷仍可能击穿所有副本。明确动机，再选择已经充分验证的系统，比重新发明一份隐含假设众多的锁协议更稳妥。

下一章《一致性与共识》将从这里继续：怎样精确定义读写观察，怎样生成有序标识，怎样让法定人数真正构成不冲突的决定。本章给出的不是“什么都不可信”的结论，而是把信任变成有范围、可检查的契约。
