READING NOTES / CHAPTER 01

第 1 章｜数据系统架构的权衡取舍

Trade-Offs in Data Systems Architecture · 先说明数据为谁服务，再选择怎样保存与处理

同一笔销售，收银系统关心能否马上入账，分析师关心它怎样进入月度营收，推荐系统关心它能否帮助预测下一次购买，顾客则可能关心自己的购买记录保留多久。它们使用的是相关数据，却提出了不同的正确性、速度、成本与权利要求。只问“哪个数据库最好”，还没有把真正的问题说出来。

第二版以这些选择开始全书：运营型与分析型系统怎样分工，云服务怎样改变责任和底层架构，什么时候值得引入分布式，以及数据使用为什么必须考虑人。这里建立的术语会反复出现；重点是顺着数据的用途和流向理解取舍，而不是提前选出一套通用产品组合。

01数据密集型，难在数据的整个生命周期

数据密集型应用（data-intensive application）是指数据管理成为开发中的主要挑战：要保存大量数据，处理持续变化，协调并发操作，在故障时保持正确，并让服务持续可用。计算密集型则更突出如何把巨大计算分解并高效执行。两者可以重叠；训练模型既需要计算能力，也依赖可靠的数据准备，不能只凭“是否使用机器学习”分类。

本书关注的基本组件包括数据库、缓存、搜索索引、流处理与批处理。数据库让记录以后还能被找到；缓存保留昂贵操作的结果；搜索索引按关键词或条件定位信息；流处理持续响应新事件；批处理对一批积累的数据集中计算。它们不是每个应用都必须集齐的五件套。数据很少时，一个普通数据库甚至电子表格可能已足够；引入新组件，应有当前组件难以承担的具体任务。

以网页应用为例，浏览器中的前端负责用户交互，服务器上的后端处理请求并访问数据基础设施。后端业务进程常被设计为无状态（stateless）：处理完请求后，不把下一次请求必须依赖的信息只留在该进程中。订单仍然有状态，只是交给数据库保存；某些信息也可以保存在客户端。这样更换一个业务进程不必搬走全部订单，但数据库的持久化与并发责任并没有消失。

原书的中心问题因此是组合：各组件擅长什么，组合后数据怎样保持联系，出现分歧时以谁为准。一个搜索引擎单独工作很好，并不证明“先写订单库、再更新搜索”这个组合已经可靠。越多能力被拆到不同系统，越需要说明连接处的责任。

02OLTP 与 OLAP：一次查询究竟想知道什么

运营型系统（operational system）支持下单、支付、修改资料等日常业务，不是指运维监控系统。后端工程师让它根据用户行为读取并改变数据。分析型系统（analytical system）则从这些活动中寻找规律：业务分析师通过商业智能（BI）支持经营决策，数据科学家构建推荐、风险评分等模型。数据工程师连接两侧并维护基础设施，分析工程师进一步整理模型与转换，使数据适合消费。

两类工作的差别先体现在访问模式上。运营型请求常按键定位少量记录，这叫点查询（point query），例如按订单号查订单，再按用户操作增删改。用户正在等待，因此这种模式称为在线事务处理（OLTP）。这里的“事务”沿用早期商业交易的名称，本章宽泛地指低延迟读写；原子性、隔离性等精确定义要到第 8 章展开。

原书的连锁超市例子把分析需求说得很具体：一月份各店营收多少，促销时香蕉多卖了多少，哪种婴儿食品最常与某品牌尿布一起购买？这些问题关心许多记录之间的关系和汇总，不是某一笔交易。它们对应在线分析处理（OLAP）。其中 online 的确切历史含义原书也保留了不确定性，倾向于解释为分析师可以交互探索，而非只能领取预定报表；它不保证所有查询都立即完成。

下面是笔记假设的一份销售数据，金额以分计，避免小例子混入浮点金额问题：

sale_id store_id sale_date amount_cents
101 A 2026-01-03 1200
102 A 2026-01-04 800
103 B 2026-01-04 1500
104 A 2026-02-01 999 
-- 假设 sale_id 是主键：定位一笔销售。
SELECT store_id, amount_cents FROM sales WHERE sale_id = 101;

-- 汇总一月份各店销售额；不是取某一笔订单。
SELECT store_id, SUM(amount_cents) AS revenue_cents
FROM sales
WHERE sale_date >= '2026-01-01' AND sale_date < '2026-02-01'
GROUP BY store_id
ORDER BY store_id;

第一条返回 A 店的 1200 分；第二条得到 A 店 2000 分、B 店 1500 分。日期使用左闭右开区间，明确排除二月数据。真实数据增长后，前者通常仍只需定位少量记录，后者要处理许多相关销售；索引、分区或预聚合可能减少实际读取量，所以“分析”不等于每次必须扫完整张表。

比较维度 典型 OLTP 典型 OLAP
读取目标 按键取得少量具体记录 对大量相关记录连接、分组、聚合
写入方式 持续增删改业务记录 批量导入或接收事件流
查询来源 应用预先定义，频繁执行 分析师即席探索，单次可能复杂
数据视角 常关注当前状态 常保留历史变化以作比较
优化重点 大量小请求的响应与并发 大范围处理的效率与吞吐量

这张表描述常见特征，不是资格门槛。业务库可以保存历史，分析库也要接收写入；原书所谓分析侧“只读副本”，强调分析者通常不通过它修改上游业务事实，并不表示这个数据库永远不执行写操作。原表所列 GB—TB 与 TB—PB 也只是典型规模，不能用容量划出 OLTP/OLAP 的定义边界。

运营型应用通常把查询封装在接口里，以控制权限和资源消耗；分析师则需要组合不同字段、调整条件，不能每想到一个问题都等待后端发布版本。两侧对“自由查询”的态度不同，来自目标不同。另有产品分析／实时分析把大范围聚合嵌入用户产品，例如商家实时经营面板：它既是分析负载，又要求较低响应时间。因此“面向用户就必然 OLTP”同样不成立。

03数据仓库：把跨业务的分析接起来

SQL 能表达点查和汇总，所以小规模系统可以用同一个数据库承担两种工作。把两者拆开，需要理由。原书列出四项：数据散在收银、库存、物流等业务系统中，形成数据孤岛；适合频繁修改的结构未必适合批量分析；大查询争抢 CPU、内存和 I/O，会干扰业务响应；安全边界也可能不允许分析师直接连接生产库。

数据仓库（data warehouse）把多个来源的数据集中到独立的分析数据库中。这里的“集中”重要的不只是搬到一个地方，还包括把来源整理为可以相互比较的语义。假设销售系统按门店编号记录收入，采购系统按供应商货号记录成本，只复制两张表并不能直接算出各店利润，还需要商品映射、时间口径和退款处理规则。这是笔记对原书数据孤岛问题的展开。

数据进入仓库的典型过程是 ETL：提取（extract）—转换（transform）—加载（load）。提取可以定期导出，也可以连续取得更新；转换清理格式、统一含义并组织成分析友好的模式；加载将结果写入分析侧。ELT 则先加载，再利用目标系统的计算能力转换。二者区别在转换发生的位置与顺序，不是“旧方案”和“必然更好的新方案”。

继续用销售例子：提取当天销售与退款，将来源金额统一为分，把各系统门店编号映射到同一维度，再写入报表表。若退款一天后才到，月度汇总就需要修订；若数据源只保留最新状态，提取频率也会影响能否保留完整历史。数据搬到了仓库，不等于报表口径、新鲜度和历史完整性已经解决。 数据管道必须说明处理到什么位置、哪些来源仍未齐备，以及失败后如何继续。

外部 SaaS 又多一层边界：企业可能只能通过客户关系管理或支付供应商的 API 取得数据，不能读取其内部数据库。连接器能降低接入工作量，却无法替企业决定数据含义，也不能凭空获得 API 没有暴露的信息。

混合事务／分析处理（HTAP）尝试在一个系统中同时承接两类负载，减少外部搬运。原书指出，许多实现仍在内部安排不同的运营型与分析型机制，只是共同暴露一个接口。同一反欺诈应用既查当前记录又分析许多历史交易时，它可能有价值；但它不会自动汇合企业里其他几十套系统。因此 HTAP 不会使数据仓库的跨来源整合需求消失。

旧稿使用“为什么两类系统必须分开”的标题，容易把常见取舍变成硬性规定。原书同时承认通用数据库与 HTAP 的适用性。更准确的结论是：当干扰、数据整合和专用优化的收益超过维护两套路径的成本时，再选择分离。 具体的数据模型与物理布局，分别在第 3 章和第 4 章展开。

04数据湖与数据管道：保留不同的加工可能

数据仓库擅长通过关系模型和 SQL 提供统一分析，但数据科学还可能需要处理评论文本、图片或特征矩阵。特征工程（feature engineering）是把原始记录转换成模型可使用的输入表示，例如从购买历史产生一组数值。复杂文本处理或自定义变换常用 Python、R 等工具更自然；这不意味着 SQL 永远不能做机器学习相关工作，而是需求不总能方便地装入同一个查询模型。

数据湖（data lake）提供集中存放分析资料的文件仓库，可以容纳表记录、文本、图像等不同形式，常利用对象存储。它不要求所有数据先进入同一关系模式。相比提前加工成唯一报表表，保留较原始的表示，让多个消费者可以按各自目标转换：分析师整理销售汇总，数据科学家生成训练样本，两者不必共享全部加工步骤。

原书把偏好原始数据称为“寿司原则”。其工程收益是保留未来重新解释、重新加工的空间，而不是保证原始数据天然更真实。字段缺失、单位错误、采集偏差仍然存在；脱离数据字典的文件也可能根本无法正确使用。数据湖可以位于业务系统与数据仓库之间，二者共同工作，并非所有组织都应依次从仓库“升级”为湖。

保留原始表示还把一部分责任后移。每位消费者要知道字段含义、来源时间和可用范围，否则同一个“收入”可能被算出不同答案。原书随后引出 DataOps，强调数据管道的管理与运维，并联系治理、隐私与法规。自由的格式不意味着没有质量、访问和生命周期约束。

管道也不只按天传文件。批处理可以每天重算，流处理则持续响应事件，把分析反馈缩短到秒级附近，适合时间敏感的欺诈检测；这里是处理方式的能力方向，不是任意实现都承诺几秒完成。分析结果还会回到运营型系统：训练出的推荐模型部署上线，用户画像进入业务服务，这类回流常被称为反向 ETL（reverse ETL）。它不等于把原业务数据库全部倒写一遍，也不意味着派生结果变成所有原始事实的权威。

于是，架构不再只是“业务产生数据，报表消费数据”的单向终点，而是持续循环。选择批次、事件流或模型发布，取决于结果多久需要更新、失败怎样恢复，以及消费者能容忍多旧的数据；第 11—13 章会接着拆解这些机制，持续传播见第12章CDC。

05权威记录与派生数据：分歧时谁说了算

OLTP/OLAP 描述工作负载，权威记录系统（system of record）／派生数据（derived data）则描述数据关系。权威记录系统保存某类事实的正式版本，新输入先由这里接受；派生数据从已有信息计算或转换而来，例如缓存、搜索索引、物化视图和训练模型。物化视图就是把某个查询的结果提前计算并保存，以后可以直接读取。

原书用“每个事实表示一次”说明权威数据通常采用规范化表示，这不禁止数据库为容错保留多个物理副本。“权威”也不保证输入符合现实，而是约定当系统间发生分歧时，在哪里核对和纠正。商品标价录错了，权威库也可能有错；应通过正式修改路径修正，再向外传播，不能在搜索索引里悄悄改一个价格就认为问题已解决。

下面的笔记假设中，商品价格的正式版本从 100 元改为 90 元。业务修改先进入权威库，搜索索引稍后更新；分析汇总则按自身管道推进。沿实线读业务写入，沿虚线读派生传播：图上没有把这些系统圈成一个共同事务。

假设数据库成功提交后，索引更新失败，搜索仍显示 100 元。现在至少有三个不同问题：用户看到的旧值是否可接受，结算应到哪里取正式价格，索引如何重新追上来源。第一个是业务新鲜度要求，第二个是权威边界，第三个是数据集成机制。缓存过期、定期重算和持续捕获变更都可能参与设计；本章并未规定某一种同步工具是唯一答案。

派生数据在信息上是冗余的，但在服务能力上可能不可替代。搜索索引丢失后，原始商品仍在，复杂搜索却可能暂时不可用；大型模型重训也可能花费很久。因此旧稿的“丢了没关系”应改为：有条件可重建，不等于恢复立即完成或没有业务损失。 所需源数据、转换代码、配置和外部输入必须仍可取得；若历史已删除，就不能承诺重现依赖该历史的旧结果。模型可重新训练，也不当然意味着得到逐字节相同的模型。

角色取决于使用方式，不取决于产品名称。一个数据库既可以保管正式订单，也可以只存报表结果；运营型系统内部同时存在权威库和派生缓存十分常见。备份可恢复权威库，也不因此把权威库降格为派生系统。判断应从“事实在哪里接受、由什么信息生成、出现冲突怎样处理”开始，而不是只问文件是否能复制回来。

06云与自建：成本之外，还有谁能改变系统

原书把云与自建放回 build or buy：哪些能力值得自己承担，哪些适合采购。对软件应拆开两个问题：谁开发软件，谁部署和运维软件。自己写业务并自己运行、运行现成数据库、通过 API 使用厂商托管服务，是控制权与投入不同的安排。

“自己运行”也可以发生在云上：在云虚拟机安装 PostgreSQL，仍由自己承担数据库配置和维护；IaaS 提供的是计算等基础资源。使用托管数据库则把更多运行责任交给供应商。本地部署也不必字面上位于办公室，它可以是在租用机房中管理自己的服务器。只用“是否在云上”二分，会混淆这些责任差异。

经济性先看负载与技能。已有成熟运维能力、需求平稳且机器利用率高时，自有设备可能便宜；团队不熟悉系统、需要快速投入使用时，学习和招人的成本可能超过托管溢价。供应商从大量客户积累运维经验，用户则失去部分针对特定负载深度定制的自由。

分析负载尤其能体现弹性的价值。笔记假设每天有一段查询工作，需 40 个等效计算单元运行 30 分钟，其余时间不用这批算力。全天保留峰值容量对应 960 单元小时，理想按需执行是 20 单元小时。这只说明闲置容量的差别，不是 48 倍价格结论：云单价、最小计费、启动等待、数据存储与传输费用都没有代入。若报表可以慢一点、排队运行，较少的固定资源也可能更经济。

控制权的代价在异常时最明显。缺功能往往只能等待供应商支持；内部故障未必能自行修补；看不到底层指标与日志，会增加诊断难度。停服、涨价或产品变化可能迫使迁移，专有接口与数据导出成本构成供应商锁定（vendor lock-in）。政治制裁、跨境条件和供应商的数据保护能力，也可能影响服务能否持续使用。

这并不意味着客户只能被动等待任何事故；客户仍可设计降级或迁移路径，但无法直接控制供应商内部修复。对于需要精细硬件控制的低延迟关键路径，自建仍有理由。应按具体组件决定控制与外包的范围，而不是把全企业一次性押在“全部上云”或“全部自建”的口号上。

07云原生的技术变化：把计算与长期存储分开

云原生在本章指利用云服务能力重新设计的架构。把旧数据库装进 VM，只改变运行地点；让高层数据库构建于对象存储、专用存储服务和弹性计算之上，才可能改变故障恢复和伸缩方式。高层服务替用户隐藏更多细节，适合其目标负载时可以节省工作，需求不匹配时则会受到接口和行为限制。

对象存储（object storage）通过服务接口保存对象，常用于较大文件或数据块。它把数据分布、容量和部分硬件故障处理隐藏在服务后面，而不是让每个应用直接管理一台机器的磁盘。它不是拥有全部文件系统语义的远程硬盘，也不能因“由厂商管理”就推成任意故障下绝不丢失数据的承诺。

传统设计常让一台机器同时拥有 CPU、内存与数据磁盘。RAID 可以在同机多个盘之间提供一定磁盘故障冗余，但不能让整台机器故障时的服务自动转移到另一台。云 VM 的本地盘也可能随实例失效或替换而不可达；若把唯一持久状态放在这里，计算实例就不能随意销毁与更换。

远端块存储提供另一种选择：把虚拟磁盘从一个实例卸下，再挂给另一个实例，让原本面向磁盘的软件继续工作。其背后是经网络访问的存储服务，具有相应延迟与故障依赖。原书提到常见的 4 KiB 块大小，是概念示例，不意味着每个产品、每次 I/O 都固定为 4 KiB。直接按云环境设计的系统则可能采用专用存储协议，减少块设备仿真所带来的某些开销。

存算分离（separation of storage and compute）让长期数据保存在独立存储层，执行查询的 CPU 与内存位于计算层。对象存储适合较大块，频繁变化的小记录可以先由适合该负载的服务管理，再组织成更大的持久数据块；具体路径依系统而异，不是所有云数据库都把每次行更新直接写成一个对象。

按图看一次变化：查询增加，系统启动新的计算节点；节点从存储层取数据并逐渐建立缓存；查询减少时可释放算力，长期数据仍留在存储层。计算节点故障后，新节点也不必从坏机器上取回唯一的数据副本。于是存储容量和查询算力不必以相同比例增长。

交换条件是网络：读取远端数据有传输成本，冷缓存影响启动后的性能，多个计算节点也可能竞争共享存储吞吐。缓存可以降低重复读取，执行引擎可以减少不必要的数据移动，但这些能力需要实现。“分离”不是“完全无状态”，更不是持久性和恢复已经无条件成立。

原书还指出云服务常采用多租户（multitenancy）：多个客户共用硬件和服务，以提高利用率、方便管理。共享越充分，就越需要隔离资源与权限，避免一个客户的大查询挤压另一个客户的响应，或越过数据访问边界。它是供应商内部需要承担的工程工作，不应被产品外观上的“一个独立实例”掩盖。

08运维仍然存在，只是关注点改变了

传统运维往往直接面对机器：加磁盘、打系统补丁、迁移进程、规划下一批服务器。云服务把一部分机器细节放到 API 后面，客户更关注服务选择、连接与运行结果。DevOps 强调开发和运维共同负责服务；SRE 是原书引用的 Google 实践。它们推动可重复的自动化、临时实例、频繁发布、事故学习，以及不随个人离职而消失的系统知识。

按用量计费把一部分容量问题转成财务问题：不再先买完所有磁盘，不代表不用理解数据增长。持续保留的对象、没有结束的计算和重复执行的管道都会进入账单；服务也有并发、速率或其他配额。旧稿“容量规划本身消失了”过于绝对，应读为机器级预购减少，资源、配额和成本规划仍需承担。

假设一条分析任务由于输入格式错误反复失败重跑，云平台可以正常分配计算资源，业务却既得不到报表又持续花钱。客户仍要识别错误数据、控制重试、定位责任并修复流程。供应商对基础设施的维护不能代替应用正确性，也不能代替用户权限、依赖库安全和跨服务交互管理。

服务越多，接口、身份、限额与故障语义越可能不同。原书强调集成仍缺少统一标准，因此“用了托管服务”往往减少低层维护，却增加组合服务时需要理解的契约。衡量运维投入，应看整条服务路径能否可靠交付，而不是只数还剩几台需要登录的机器。

09分布式的理由，必须覆盖它新增的代价

分布式系统由多台机器通过网络协作，参与的进程称为节点。手机与后端已经构成分布式系统；所谓“先用单机”，通常指某个处理或存储子系统先不拆成集群，而不是要求所有用户都挤在同一设备上。

原书给出九种动机，可以归为三组。第一组是结构本来如此：多个用户的设备必须通信，存储与处理分别位于不同云服务也必须通信。第二组是运行目标：通过冗余容错，提高容量和吞吐，把节点放近全球用户以降低网络等待，按负载弹性增减资源，或让不同部分使用适合的磁盘、CPU、内存与 GPU。第三组是外部条件：适用的数据驻留要求，以及把可调度工作放到可再生电力更充足的时间和地点。

所以，容量不是唯一理由。即使数据能放进一台机器，也可能需要另一台承接故障；反过来，数据看起来很多，却不代表单机一定无法有效处理。地理部署、硬件选择与可用性要求应分别说明，不能用一个“数据规模”数字替所有目标作决定。

新增代价首先是部分失败与结果不确定。笔记假设订单服务请求付款：请求可能没到付款服务，也可能已经扣款而回复丢失，两个情形在调用方都表现为超时。如果把超时直接等同于“没有执行”，再次发起就可能重复扣款。增加一个网络边界，同时增加了调用身份、重复处理和恢复的责任；第 9 章将专门展开。

其次是通信与协调成本。数据要序列化、传输、排队，还可能在节点之间重新分组。如果数据本来就在本地，让计算靠近数据，可能比把整批数据搬到远端更快；这也解释了存算分离为何需要认真设计缓存与访问路径。让一百台机器执行，不意味着每台只花原来百分之一的时间。原书引用的 COST 研究比较系统超过一个有效单线程实现需要多少资源，发现某些被测系统要到数百核甚至仍未超过单线程。它是在提醒比较绝对完成时间与额外开销，不是证明所有集群都慢。 数据量、算法、单机内存和容错要求变化后，结论也会变化。

诊断同样变难。一次慢请求可能是最下游资源不足，也可能是上游排队，或多个小等待累积。可观测性（observability）关注能否用执行数据理解这些行为；分布式追踪记录调用关系和耗时，使团队可以沿请求路径追查。把每个服务的平均耗时各看一眼，未必能解释某一次失败。

最后是数据边界。如果订单与库存分属不同数据库，两个本地提交不会自动成为一项原子业务操作。分布式事务是可能的协调方法，却需要参与者支持，也可能削弱服务独立性。原书在这里保留问题，到第 8 章讨论保证和代价。选择分布式应说明它解决了哪项真实要求，并接受这些跨边界责任；若单机已满足要求，保留简单结构就是有依据的选择。

10微服务和 Serverless，分别重新安排哪种责任

微服务把应用分成职责明确、经网络 API 协作、由相应团队维护的服务。一个进程既可以接收上游请求，也可以作为客户端调用下游。拆分带来的核心收益是团队能够独立修改、发布和分配资源，而 API 隐藏内部实现，使变化不必传播到所有调用者。

原书因此说微服务主要用技术手段解决人的协作问题。以笔记假设的订单和商品团队为例，如果订单代码直接查询商品库内部表，商品团队改表结构仍须协调订单团队。独立部署虽然存在，独立演化却不完整。让商品服务拥有数据并公开稳定的业务接口，可以缩小这类共享契约。

这解释了“每个服务拥有自己的数据库”的常见建议，但旧稿将其称为“一条铁律”不准确。目标是维护责任与结构封装，不是要求每个服务都购买一台专属物理数据库机器；是否接受共享，仍要结合耦合、资源干扰和事务需求。硬拆一个必须共同完成的业务流程，也可能使协调成本超过收益。

服务拆开后，开发测试需要处理依赖，部署、日志、告警和扩缩容要覆盖更多运行单元。API 字段改变可能直到集成时才暴露兼容问题；接口描述和版本管理可以帮助，却不能取消这项责任。团队少、业务边界尚在快速变化时，一个模块清晰的简单应用常更合适。

Serverless／函数即服务（FaaS）改变的主要是部署和资源管理：平台按到来的请求分配与回收执行资源，用户无需逐台启停 VM。它仍在服务器上执行，相邻两次调用也可能落在不同机器，因此不能把进程内状态当成下一次必然可见的持久状态。

收益是更细的按需使用，代价可能是冷启动、执行时限、运行环境和并发约束。它与微服务并不是互相替代的分类：前者关注执行资源怎么管理，后者关注职责与团队怎么划分。数据库等服务也会用 Serverless 表示自动伸缩和按用量计费，具体含义须看服务契约。

计费补充与旧稿修正：“只按代码运行时间付费，闲时不花一分钱”不能作为一般承诺。核查 AWS Lambda 官方价格页，其按需事件函数同时考虑请求数与执行时长，预置并发则按配置的容量和启用时间计费；日志、存储等依赖还有各自账单。这里不比较具体价格，只说明“无须自己管理服务器”与“整个系统闲时零成本”是两件事。

11高性能计算：相似规模，不同失败目标

高性能计算（HPC）常用于天气模拟、分子动力学等大计算任务。它与在线数据系统都可能有许多节点，但优化目标不同。一次模拟首先关心大作业多久完成；在线业务首先关心节点故障时能否继续响应用户。原书据此比较两类环境，而非按“机器更多”排出技术等级。

HPC 作业常定期保存检查点（checkpoint），即某时刻的计算状态。节点故障后，一种常见做法是停止受影响作业，再从最近检查点恢复；损失的是检查点之后的一段计算。在线订单服务通常不能为等一个节点修好而整体停机，因此更需要部分故障下的持续服务。这不等于 HPC 所有故障都必须停掉整座超算。

通信方式也服务于目标。原书描述 HPC 常利用共享内存与远程直接内存访问（RDMA）等低开销机制，并针对已知通信模式使用网格、环面等拓扑；云数据中心常以 IP／以太网和 Clos 等多级交换结构提供广泛互连。HPC 节点往往靠得近，云服务则可能跨地区，且需要在互不信任的租户之间做隔离、认证与加密。

这些是典型差异，不是技术禁区：云也能承载 HPC，也会使用 RDMA；大规模分析与科学计算还可能共享批处理技巧。理解本节的目的，是在借用一种技术时先检查其假设：它是否允许中断作业，依赖什么通信模式和信任条件，能否满足我们真正需要的可用性。

12数据责任：能保存，不等于值得永久保存

系统不只服务于建设它的组织。贷款、招聘或推荐决定可能影响数据所涉及的人；位置和行为记录被泄露、关联或强制取得，也可能造成真实伤害。原书要求工程师把这些影响放入设计判断，而不是只在技术完成后询问“是否合法”。GDPR、CCPA 及 AI 相关监管是作者给出的背景；具体适用范围不能仅从某个技术或产品名称推定。

先看一个与本章直接相连的困难：删除如何沿数据流传播。原书指出不可变追加日志与删除要求之间存在张力。若只是再追加一条“用户已删除”的记录，旧内容可能仍在文件中；若从业务库删掉一行，搜索、分析文件和训练数据中也可能已有其表示。权威记录与派生数据的关系图，此时同时成为寻找清理范围的起点。

下面是笔记假设。某推荐服务保留个人浏览历史，并每天导出训练文件。适用的删除要求被确认后，只删在线资料表还不够：需要识别相关历史和派生文件，安排清理，并防止下一次从旧快照重建时把数据带回来。日志重写、保留期与备份恢复策略也必须相互配合。若数据已参与训练，从训练集移除样本并不自动证明已消除其对已部署模型的影响；本章提出这个问题，没有交付通用的机器遗忘算法。

法律限定与原书修正：印刷 25 页把 GDPR 概括为数据“不能再用于任何其他目的”。原页确有此句，但表述过于绝对。GDPR 第 5(1)(b) 条约束的是与原目的不相容的进一步处理，并规定特定公共利益归档、研究及统计用途的安排；第 6(4) 条还列出判断目的相容性的因素。因此应理解为受目的限制与合法处理条件约束，不能把“一切后续用途都禁止”当作法律原意。

删除权也有条件。第 17 条列出适用事由，并保留法律义务、表达与信息自由、特定公共利益或法律请求等例外。它不能被简化成“任何请求都立即删除全部副本”。同样，旧稿案例把“欧洲用户数据必须留在欧盟”当成一般要求，混淆了数据驻留与跨境传输：GDPR 第五章规定满足条件的传输机制，不是全面禁止出境。这些是依据官方文本的边界澄清，核查日期为 2026-11-07。

数据最小化（data minimization）把讨论进一步提前：只处理与明确目的相关且必要的数据，并控制可识别数据的保留时间。其收益不只是节省存储费用，而是减少未来需要保护、解释、纠正和清理的数据范围。原书强调泄露、法律责任、声誉以及用户人身安全都应计入成本；“先存下来，以后也许有用”的潜在收益，不能单独决定架构。

例如，一个只需统计每日活跃人数的功能，是否必须永久保存可关联个人的每次精确位置？这是需要用真实目的回答的问题，不能靠对象存储便宜决定。减少采集不是宣称所有风险归零，而是减少某些风险与维护责任的来源。PCI 相关要求、SOC 2 等客户审查也会影响组织的运行安排；它们与法律的来源和作用不同，不能因为通过某项审查，就推论所有数据用途都合理。

这一节把前面的“原始数据保留更多加工可能”放回完整取舍：保留有价值，但需要明确用途、期限和控制；派生有价值，但增加了追踪与更新责任。第 14 章还会从偏见、权力与隐私继续展开。这里已经足以看到，不收集某些数据、缩短某类历史，都是实在的架构决定。

13把选择写成有前提的判断

本章不是要求设计者永远回答“看情况”，而是让情况能够说清。选择分析库，要解释当前查询与业务路径怎样冲突；选择云服务，要比较利用率、团队技能和控制权；选择分布式，要说明单机之外的容量、可用性或地域要求；选择保留数据，要说明用途、期限和人的权益。

把这些决定连起来，一份小而有用的架构说明应能回答：事实从哪里进入，以谁为准，形成哪些派生表示；每类访问需要什么性能与新鲜度；谁维护底层服务，失败后谁继续工作；数据最终何时退出系统。任何产品名都不能替这些问题作答。

第 2 章将把“快、可靠、能增长、易维护”变成可讨论的非功能性要求；第 3 章转向模型和查询表达；第 4 章继续追踪一次读写怎样进入存储引擎。本章的取舍由此获得越来越具体的判断依据。
